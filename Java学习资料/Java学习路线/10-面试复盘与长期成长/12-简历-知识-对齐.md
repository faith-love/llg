# 12-简历知识点对齐

## 为什么要对齐简历

简历上写的每个技术点都可能被追问。写了但讲不清，比不写更危险。

## 简历技术点检查

每写一个技术点，都要能回答：

- 为什么用它。
- 用在项目哪里。
- 解决了什么问题。
- 有哪些替代方案。
- 踩过什么坑。
- 怎么测试或验证。

## 示例：Redis

简历写：

```text
使用 Redis 缓存热门文章，降低数据库查询压力。
```

必须能回答：

- 热门文章怎么定义。
- key 怎么设计。
- 过期时间多久。
- 文章更新后缓存怎么处理。
- 缓存穿透和击穿怎么防。
- 怎么判断缓存有效果。

## 不建议写的内容

不要写：

- 只看过没用过的技术。
- 配了一次但不理解的技术。
- 不能解释原理和问题的高级词。
- 项目里不存在的能力。

## 容易出错的示例

### 错误示例：简历写“熟悉高并发”

但项目没有压测、限流、缓存、异步、并发控制或排查经验。

### 为什么错

“熟悉高并发”会引来很深的追问，很容易暴露空泛。

### 正确写法

写具体能力：

```text
在订单简化项目中使用条件更新控制库存扣减，避免并发下超卖。
```

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| 简历对齐 | 保证写的能讲 | 避免被追问穿 | 每个词准备追问 | 重点是真实 |
| 技术描述 | 展示解决问题 | 不只是堆名词 | 场景 + 动作 + 结果 | 难点是量化 |
| 项目经历 | 证明能力 | 面试核心材料 | 写负责模块和难点 | 重点是具体 |
| 边界表达 | 避免过度承诺 | 不懂就别写熟悉 | 用了解、使用、负责区分 | 重点是诚实 |

## 本节练习

- 列出简历上所有技术词。
- 每个技术词写 5 个追问。
- 删除讲不清的技术点。
- 把“熟悉”改成具体项目动作。

## 本节通过标准

- 简历上的技术都能讲。
- 项目描述包含场景和结果。
- 不写无法被验证的空泛词。
- 能应对简历技术点追问。
