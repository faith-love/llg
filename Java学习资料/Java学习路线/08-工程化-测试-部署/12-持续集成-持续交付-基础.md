# 12-CI/CD 入门和质量门禁

## CI/CD 解决什么问题

CI 是持续集成，核心是每次提交后自动检查代码。

CD 是持续交付或持续部署，核心是把构建产物按流程发布出去。

小白阶段先重点理解 CI：

- 自动拉代码。
- 自动安装依赖。
- 自动运行测试。
- 自动打包。
- 失败时阻止合并或发布。

## 最小质量门禁

建议先做这些：

- `mvn clean 测试` 必须通过。
- 代码能成功打包。
- 不允许提交敏感配置。
- 说明 中启动命令保持可用。

## 简化流程

```text
push code
  -> checkout
  -> setup JDK
  -> mvn clean 测试
  -> mvn clean package
  -> build 未译10367
```

## 为什么要自动化

手动检查的问题：

- 容易忘。
- 每个人执行步骤不同。
- 出错后没有统一记录。
- 代码合并后才发现构建失败。

CI 的好处：

- 每次提交统一检查。
- 失败能及时发现。
- 质量标准更稳定。

## 容易出错的示例

### 错误示例：本地不跑测试，直接合并

```text
我只改了一点点，不会影响别的功能。
```

### 为什么错

很多 bug 正是“小改动”引入的，例如改字段名、改事务边界、改异常类型。

### 正确做法

至少在提交前执行：

```text
mvn clean 测试
```

有 CI 后也要关注 CI 结果。

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| CI | 自动检查提交 | 防止坏代码进入主线 | 先跑测试和打包 | 重点是失败要修 |
| CD | 自动或半自动发布 | 减少手动部署步骤 | 小项目先了解 | 难点是环境和回滚 |
| 质量门禁 | 定义最低标准 | 避免靠自觉 | 测试、打包、敏感信息检查 | 重点是标准要可执行 |
| 构建产物 | 可部署结果 | 保证部署来源一致 | jar 或镜像 | 重点是版本号 |
