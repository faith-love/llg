# 02-Git 工作流和提交习惯

## Git 解决什么问题

Git 负责记录代码变化，让你能回看历史、多人协作、开分支开发、合并代码和处理冲突。

没有 Git 的痛点：

- 改坏了不知道怎么回退。
- 不知道某段代码是谁什么时候改的。
- 多个人改同一个文件容易互相覆盖。
- 项目没有可追踪的开发记录。

## 必会命令

| 命令 | 作用 |
| --- | --- |
| `git status` | 查看当前改动 |
| `git add` | 暂存改动 |
| `git 通用mit` | 保存一次版本 |
| `git branch` | 查看和创建分支 |
| `git switch` | 切换分支 |
| `git merge` | 合并分支 |
| `git 日志 --oneline` | 查看简洁历史 |

## 提交信息

推荐格式：

```text
feat: add book borrowing API
fix: validate duplicate ISBN before insert
测试: cover borrow rollback
文档: update local startup guide
```

好提交的标准：

- 一次提交只做一类事情。
- 标题能说明改了什么。
- 不把格式化、重构、功能、测试全混在一个提交里。

## 分支习惯

小项目可以先用简单分支：

```text
主
feature/book-borrow
fix/未译38446-error
```

开发新功能时：

1. 从主分支拉出功能分支。
2. 在功能分支提交小步改动。
3. 本地测试通过。
4. 合并回主分支。

## 容易出错的示例

### 错误示例：一个提交塞太多内容

```text
feat: update project
```

里面同时包含登录、借书、格式化、依赖升级和 说明 修改。

### 为什么错

以后排查问题时，很难判断是哪部分改动引入了 bug。

### 正确做法

拆成多次提交：

```text
feat: add borrow 服务
测试: cover borrow stock rollback
文档: add borrow API example
```

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| 提交 | 保存一个可追踪版本 | 改坏后可以定位 | 小步提交 | 重点是一提交一件事 |
| 分支 | 隔离不同任务 | 避免功能没写完影响主线 | 功能和修复分开分支 | 难点是合并前保持清晰 |
| 冲突 | 多人改同一区域时出现 | 暴露真实改动碰撞 | 先理解双方意图再改 | 重点是不要盲目覆盖 |
| `忽略规则` | 忽略无需提交的文件 | 避免提交构建产物和本地配置 | 忽略 `target/`、`.idea/` 等 | 重点是不要提交密钥 |

## 本节练习

- 创建一个功能分支。
- 修改一个 说明 并提交。
- 写 3 条规范提交信息。
- 故意制造一次简单冲突并解决。

## 本节通过标准

- 能解释工作区、暂存区、提交的关系。
- 能独立完成一次分支开发和合并。
- 能写清楚提交信息。
- 能处理简单文本冲突。
