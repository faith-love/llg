# 12-测试、日志、部署和文档验收

## 为什么项目必须验收

项目不是“功能写完”就结束。真正可展示的项目需要能测试、能启动、能部署、能排查、能让别人看懂。

## 测试验收

至少覆盖：

- Service 核心成功路径。
- Service 核心失败路径。
- Controller 参数错误。
- 未登录和无权限。
- 事务回滚。
- 数据库唯一约束冲突。

## 日志验收

关键日志应该包含：

- 用户 ID。
- 业务 ID。
- 操作类型。
- 成功或失败。
- 异常堆栈。
- 耗时。

不要包含密码、Token、验证码等敏感信息。

## 部署验收

必须能说明：

- 如何启动数据库。
- 如何初始化表结构。
- 如何启动应用。
- 如何访问健康检查。
- 如何访问核心接口。
- 如何查看日志。

## 文档验收

说明 至少包含：

- 项目介绍。
- 技术栈。
- 环境要求。
- 本地启动。
- Docker 启动。
- 配置说明。
- 数据库脚本。
- 接口示例。
- 测试命令。
- 常见问题。

## 容易出错的示例

### 错误示例：项目只能自己电脑跑

```text
数据库我本地已经建好了，配置也在我电脑上。
```

### 为什么错

别人无法复现项目，面试或协作时可信度很低。

### 正确做法

提供初始化脚本、配置说明和 Docker Compose。

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| 测试 | 证明功能可靠 | 防止改坏 | 成功失败都测 | 重点是事务和权限 |
| 日志 | 支撑排查 | 出错有证据 | 关键业务打日志 | 重点是不泄密 |
| 部署 | 证明能运行 | 不只本地 IDE 能跑 | Docker Compose | 难点是配置 |
| 说明 | 降低理解成本 | 别人能复现 | 按模板写 | 重点是可执行 |

## 本节练习

- 给项目列出 10 个测试用例。
- 写一个部署验证清单。
- 给 说明 增加接口示例。
- 故意制造一次错误并通过日志定位。

## 本节通过标准

- 测试能覆盖核心成功和失败路径。
- 部署后能访问健康检查。
- 说明 能让新人启动项目。
- 日志能定位一次真实错误。
