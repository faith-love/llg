# 02-项目推进节奏和版本规划

## 为什么要分版本推进

项目烂尾通常不是因为不会写代码，而是因为一开始范围太大，没有版本节奏。

推荐把项目拆成：

- V0：能跑起来。
- V1：核心业务闭环。
- V2：补齐异常、校验、权限、测试。
- V3：工程化、部署、复盘。

## 每个版本的目标

| 版本 | 目标 | 产出 |
| --- | --- | --- |
| V0 | 项目能启动 | 基础结构、健康检查 |
| V1 | 核心功能能用 | 关键接口、表结构、业务流程 |
| V2 | 失败场景可控 | 参数校验、异常、权限、事务 |
| V3 | 能交付和展示 | 测试、说明、Docker、复盘 |

## 推荐节奏

每周固定输出：

- 一组可运行功能。
- 一次提交记录整理。
- 一份问题记录。
- 一次测试和验收。
- 一段项目复盘。

## 任务拆分方式

不要写这种任务：

```text
完成图书馆系统。
```

要拆成：

```text
设计 books 表。
实现新增图书接口。
实现 ISBN 重复校验。
补充新增图书测试。
更新 说明 接口示例。
```

## 容易出错的示例

### 错误示例：先做所有页面和所有表

一开始就画 20 张表、写 50 个接口，结果核心借阅流程还没跑通。

### 为什么错

项目没有闭环，任何一个环节都无法验收。

### 正确做法

先跑通最短链路：

```text
登录 -> 查询图书 -> 借阅 -> 扣库存 -> 返回结果
```

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| MVP | 最小可用版本 | 防止项目过大 | 先做核心闭环 | 重点是能演示 |
| 迭代 | 分批交付能力 | 每周有成果 | V0 到 V3 | 难点是控制新增需求 |
| 任务拆分 | 把大目标变小 | 降低拖延和混乱 | 每个任务可验收 | 重点是具体到接口或表 |
| 验收 | 判断是否完成 | 避免“差不多” | 每个版本有清单 | 重点是可运行 |

## 本节练习

- 给图书馆 未译25173EST API 写 V0-V3 计划。
- 把“借阅功能”拆成 8 个小任务。
- 为每个版本写验收标准。

## 本节通过标准

- 能把项目拆成多个版本。
- 每个版本都有明确产出。
- 能把大功能拆成可执行任务。
- 能避免长期没有可运行结果。
