# 08-接口设计和错误响应

## 接口设计解决什么问题

接口是前端、客户端和后端之间的契约。接口设计不清楚，会导致联调成本高、错误处理混乱、后续难维护。

## REST 设计原则

- URL 表资源。
- HTTP Method 表动作。
- 状态码表达结果类别。
- 响应体表达业务细节。

示例：

```text
GET    /接口/books
POST   /接口/books
GET    /接口/books/{id}
PUT    /接口/books/{id}
DELETE /接口/books/{id}
```

## 错误响应格式

推荐统一格式：

```json
{
  "code": "BOOK_NOT_FOUND",
  "name": "图书不存在",
  "details": {
    "bookId": 1001
  }
}
```

## 常见状态码

| 状态码 | 场景 |
| --- | --- |
| 200 | 查询或修改成功 |
| 201 | 创建成功 |
| 400 | 参数错误 |
| 401 | 未登录 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 409 | 状态冲突或重复 |
| 500 | 服务端未知错误 |

## 容易出错的示例

### 错误示例：所有错误都返回 200

```json
{
  "success": false,
  "name": "未登录"
}
```

HTTP 状态仍然是 200。

### 为什么错

客户端、网关、监控无法通过状态码判断错误类型。

### 正确做法

```text
401 Unauthorized
```

响应体再写业务错误码和说明。

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| URL | 表达资源 | 避免接口名混乱 | 用名词复数 | 重点是不要动词化 |
| Method | 表达动作 | 语义清楚 | GET 查，POST 建，PUT 改，DELETE 删 | 难点是复杂动作 |
| 状态码 | 表达结果类别 | 便于客户端和监控识别 | 不要全部 200 | 重点是 401/403 区分 |
| 错误码 | 表达业务原因 | 前端可精确处理 | code 稳定，name 可读 | 难点是一致性 |

## 本节练习

- 为图书馆项目设计 12 个接口。
- 给每个接口写 Method、URL、请求、响应。
- 给库存不足、重复 ISBN、未登录写错误响应。
- 检查是否存在所有接口都 POST 的问题。

## 本节通过标准

- URL 和 Method 语义清楚。
- 错误响应格式统一。
- 状态码使用合理。
- Swagger包含成功和失败示例。
