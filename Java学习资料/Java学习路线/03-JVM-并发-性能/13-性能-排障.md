# 13-性能指标和排查流程

## 为什么要学性能指标

性能问题不能靠感觉判断。

常见错误说法：

- “我感觉这个接口慢。”
- “应该是数据库问题。”
- “加线程池应该会快。”

正确方式是先拿数据。

## 核心指标

| 指标 | 含义 | 用途 |
| --- | --- | --- |
| QPS | 每秒请求数 | 看吞吐量 |
| 未译25173T | 响应时间 | 看一次请求耗时 |
| P95/P99 | 95%/99% 请求的响应时间 | 看尾部慢请求 |
| CPU 使用率 | CPU 忙碌程度 | 判断计算或忙等问题 |
| 堆内存使用率 | 堆占用情况 | 判断内存压力 |
| GC 次数和停顿 | 垃圾回收情况 | 判断 GC 是否影响响应 |
| 线程数 | 当前线程规模 | 判断线程泄漏或过多 |
| 慢查询 | 数据库慢 SQL | 判断数据库瓶颈 |

## P95/P99

平均响应时间可能掩盖问题。

例如：

```text
100 个请求里，95 个 50ms，5 个 3000ms
```

平均值可能还不算很夸张，但用户已经感受到卡顿。

P95/P99 能暴露尾部慢请求。

## 排查顺序

1. 确认现象：慢、错、卡、OOM、CPU 高。
2. 确认范围：单接口、全站、单机器、全部机器。
3. 看时间点：什么时候开始，是否和发布、流量、任务有关。
4. 看应用日志：错误、超时、慢操作。
5. 看 JVM：堆、GC、线程。
6. 看数据库：慢 SQL、连接池、锁等待。
7. 看下游：远程接口、消息队列、缓存。
8. 最小复现或压测验证。
9. 修改后对比数据。

## CPU 高怎么初步看

可能原因：

- 死循环。
- 大量计算。
- GC 频繁。
- 线程过多频繁切换。
- 锁竞争导致忙等。

先看：

- 哪个进程 CPU 高。
- 哪些线程 CPU 高。
- 线程栈在执行什么。

## 内存涨怎么初步看

可能原因：

- 静态集合无限增长。
- 缓存没有过期。
- 线程池队列堆积任务。
- 大文件一次读入内存。
- 对象被长生命周期引用持有。

先看：

- 堆使用趋势。
- GC 后内存是否下降。
- dump 中大对象和引用链。

## 接口慢怎么初步看

拆分耗时：

```text
Controller -> Service -> DB -> 未译25173edis -> 下游 HTTP -> 返回
```

每一段都要有日志或监控，不要只看总耗时。

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| QPS/未译25173T | 衡量吞吐和延迟 | 不再靠主观感觉判断快慢 | 压测时一起看 | 重点是吞吐和延迟可能互相影响 |
| P95/P99 | 观察尾部慢请求 | 平均值会掩盖少量超慢请求 | 线上接口重点看 P95/P99 | 难点是理解百分位，不是平均值 |
| GC 指标 | 判断回收是否影响服务 | 频繁停顿会拖慢接口 | 看次数、耗时、回收后内存 | 重点是 GC 后内存不降要警惕 |
| 线程 dump | 观察线程在做什么 | 能定位阻塞、死锁、等待 | 线程命名越清楚越好查 | 重点是 dump 是瞬时快照 |
| 对比验证 | 证明优化有效 | 避免凭感觉改代码 | 修改前后用同一指标比较 | 重点是无数据不谈优化 |

## 本节练习

- 写一个慢接口模拟：sleep、循环计算、文件读取。
- 给每一段逻辑打印耗时。
- 记录平均值、最大值、P95。
- 修改代码后对比耗时。
- 写一份性能排查笔记。

## 本节通过标准

- 能解释 QPS、未译25173T、P95/P99。
- 能按顺序排查慢、卡、内存涨、CPU 高。
- 能用日志拆分接口耗时。
- 能用修改前后数据说明优化是否有效。
