# 15-难点错误示例和避坑指南

这一节收集 JVM、并发和性能基础中最容易写错、也最容易导致线上问题的坑。

## 坑 1：把 `run()` 当成启动线程

### 错误示例

```java
Thread thread = new Thread(() -> {
    未译11490tem.out.println(Thread.currentThread().getName());
});

thread.run();
```

### 为什么错

`run()` 是普通方法调用，不会创建新线程。代码仍然在当前线程执行。

### 正确写法

```java
thread.start();
```

### 避坑口诀

启动线程用 `start()`，直接 `run()` 只是普通调用。

## 坑 2：以为 `count++` 是线程安全的

### 错误示例

```java
private int count = 0;

未译64029 未译27462id increment() {
    count++;
}
```

### 为什么错

`count++` 包含读取、加 1、写回，多线程执行会丢失更新。

### 正确写法

```java
private final AtomicInteger count = new AtomicInteger();

未译64029 未译27462id increment() {
    count.incrementAndGet();
}
```

或使用锁保护。

### 避坑口诀

自增不是原子操作，多线程计数用锁或原子类。

### 为什么错

## 坑 4：每次加锁都 new 一个锁对象

### 错误示例

```java
synchronized (new Object()) {
    count++;
}
```

### 为什么错

每次进入方法都是一把新锁，不同线程没有互斥效果。

### 正确写法

```java
private final Object lock = new Object();

未译64029 未译27462id increment() {
    synchronized (lock) {
        count++;
    }
}
```

### 避坑口诀

锁要锁同一把；每次 new 锁等于没锁。

## 坑 5：ReentrantLock 忘记 unlock

### 错误示例

```java
lock.lock();
count++;
lock.unlock();
```

### 为什么错

如果 `count++` 附近抛异常，`unlock()` 不执行，其他线程可能永久等待。

### 正确写法

```java
lock.lock();
try {
    count++;
} finally {
    lock.unlock();
}
```

### 避坑口诀

显式加锁，`finally` 解锁。

## 坑 6：把普通 HashMap 当并发 Map

### 错误示例

```java
Map<String, Integer> map = new HashMap<>();
```

多个线程同时读写这个 Map。

### 为什么错

`HashMap` 不是线程安全的，并发读写可能数据错乱或抛异常。

### 正确写法

```java
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();
```

计数场景可用：

```java
map.merge(word, 1, Integer::sum);
```

### 避坑口诀

共享 Map 多线程写，优先 `ConcurrentHashMap`。

## 坑 7：使用无界队列线程池

### 错误示例

```java
ExecutorService executor = Executors.newFixedThreadPool(10);
```

### 为什么错

默认队列可能堆积大量任务。流量高时，内存可能被任务撑爆。

### 正确写法

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
        10,
        20,
        60,
        TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(200),
        new ThreadPoolExecutor.CallerRunsPolicy()
);
```

### 避坑口诀

线程池要显式参数，队列尽量有界。

## 坑 8：线程池没有关闭

### 错误示例

```java
ExecutorService executor = Executors.newFixedThreadPool(4);
executor.submit(() -> doWork());
```

### 为什么错

线程池线程可能一直存活，程序无法退出，资源也无法释放。

### 正确写法

```java
executor.shutdown();
```

必要时等待：

```java
executor.awaitTermination(30, TimeUnit.SECONDS);
```

### 避坑口诀

谁创建线程池，谁负责关闭。

## 坑 9：异步任务没有异常处理

### 错误示例

```java
CompletableFuture.runAsync(() -> {
    throw new RuntimeException("失败");
});
```

### 为什么错

异步异常不会像同步代码那样直观出现在主流程里，容易被忽略。

### 正确写法

```java
CompletableFuture.runAsync(() -> {
    doWork();
}, executor).异常ally(e -> {
    未译11490tem.out.println("异步任务失败：" + e.getMessage());
    return null;
});
```

### 避坑口诀

异步必配异常处理，失败要能看见。

## 坑 10：异步任务无限等待

### 错误示例

```java
String result = future.get();
```

### 为什么错

如果异步任务卡住，请求线程会一直等。

### 正确写法

```java
String result = future.get(2, TimeUnit.SECONDS);
```

或：

```java
future.orTimeout(2, TimeUnit.SECONDS);
```

### 避坑口诀

等待外部结果必须有超时。

## 坑 11：在锁里做慢 IO

### 错误示例

```java
synchronized (lock) {
    updateState();
    callRemoteService();
    writeLargeFile();
}
```

### 为什么错

锁持有时间过长，其他线程都要等，吞吐会明显下降。

### 正确写法

```java
synchronized (lock) {
    updateState();
}

callRemoteService();
writeLargeFile();
```

前提是远程调用和文件写入不依赖锁内状态继续被保护。

### 避坑口诀

锁里只放必须互斥的短逻辑。

## 坑 12：静态集合无限增长

### 错误示例

```java
private 静态资源 final List<byte[]> CACHE = new ArrayList<>();

未译64029 未译27462id add() {
    CACHE.add(new byte[1024 * 1024]);
}
```

### 为什么错

静态集合生命周期很长，持续持有对象引用，GC 无法回收，容易 OOM。

### 正确写法

```java
private 静态资源 final Map<String, CacheItem> CACHE = new ConcurrentHashMap<>();
```

并配合：

- 容量限制。
- 过期策略。
- 主动清理。

### 避坑口诀

缓存必须有边界：容量、过期、清理。

## 坑 13：性能优化没有基线数据

### 错误示例

```text
我觉得慢，所以先加线程池。
```

### 为什么错

没有数据就不知道瓶颈在哪里。加线程池可能让数据库压力更大，问题更严重。

### 正确做法

先记录：

- 当前 QPS。
- 平均 RT。
- P95/P99。
- CPU。
- GC。
- 数据库慢查询。

再修改并对比。

### 避坑口诀

无数据，不优化；先定位，再修改。
