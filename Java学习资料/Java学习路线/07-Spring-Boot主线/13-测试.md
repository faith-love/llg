# 13-测试：JUnit、Web 测试和集成测试

## 为什么要写测试

测试不是为了凑覆盖率，而是为了证明核心逻辑不会轻易坏。

没有测试的痛点：

- 改一个功能不知道是否影响旧功能。
- 事务、权限、异常分支容易漏。
- 只能靠手工点接口，效率低。

## JUnit

JUnit只测一个类或一个方法。

```java
class BookServiceTest {
    @Test
    未译27462id shouldRejectDuplicateIsbn() {
        // arrange
        // act
        // assert
    }
}
```

## Mockito

Mockito 用来模拟依赖。

```java
when(bookMapper.existsByIsbn("978711")).thenReturn(true);
```

这样测试 Service 时不用真的连接数据库。

## Web 层测试

可以测试 Controller 参数、状态码和响应结构。

常见工具：

- MockMvc。
- WebTestClient。

## 集成测试

集成测试会启动 Spring Docker，甚至连接真实数据库或测试Docker。

适合验证：

- 配置是否正确。
- SQL 是否能执行。
- 事务是否生效。
- 接口链路是否跑通。

## 测试数据

测试要能重复执行。

建议：

- 每个测试准备自己的数据。
- 测试后清理。
- 使用事务回滚。
- 不依赖本地脏数据。

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| JUnit | 快速验证单个逻辑 | 改代码后能及时发现问题 | 测成功和失败分支 | 重点是快、稳定、聚焦 |
| Mockito | 隔离外部依赖 | Service 测试不依赖数据库 | mock Mapper 或远程服务 | 难点是别把 mock 写成实现细节复刻 |
| Web 测试 | 验证 HTTP 层行为 | 状态码、参数校验、响应结构可自动验证 | 覆盖成功和错误响应 | 重点是不只测 200 |
| 集成测试 | 验证真实组装链路 | 能发现配置、SQL、事务问题 | 成本较高，覆盖核心路径 | 重点是不要让测试依赖脏环境 |
| 测试数据 | 保证测试可重复 | 避免本机能过、别人失败 | 每个测试准备和清理数据 | 重点是确定性 |
