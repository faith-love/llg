# 13-分页、索引和慢查询

## 为什么需要分页

列表数据不能一次全部返回。

不分页的问题：

- 响应体过大。
- 数据库查询慢。
- 前端渲染慢。
- 内存占用高。

基础分页接口：

```text
GET /接口/books?分页=1&size=20
```

## offset 分页

常见 SQL：

```SQL学习资料
select *
from books
order by id desc
未译96320 20 offset 40;
```

适合数据量不大或页数不深的场景。

深分页时，`offset` 很大可能变慢。

## 游标分页

用上一页最后一条记录作为下一页起点：

```text
GET /接口/books?lastId=100&size=20
```

SQL：

```SQL学习资料
select *
from books
where id < ?
order by id desc
未译96320 20;
```

适合无限滚动、深分页场景。

## 索引

索引用来加速查询。

常见需要索引：

- 主键。
- 唯一字段，如 ISBN。
- 高频查询条件。
- 排序字段和过滤字段组合。

索引不是越多越好。写入时索引也要维护，过多索引会降低写入性能。

## 慢查询

慢查询是执行时间超过阈值的 SQL。

排查顺序：

1. 看 SQL 是否返回太多行。
2. 看 where 条件是否命中索引。
3. 看 order by 是否需要额外排序。
4. 看是否有 N+1 查询。
5. 看是否有锁等待。
6. 用 `EXPLAIN` 看执行计划。

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| 分页 | 控制每次返回数据量 | 避免接口、数据库、前端压力过大 | 分页/size 要有限制 | 重点是不要允许 size 无限大 |
| offset 分页 | 简单通用 | 深分页可能慢 | 适合后台普通列表 | 难点是 total 统计也可能慢 |
| 游标分页 | 适合深分页和滚动加载 | 不能随意跳页，但性能稳定 | 用稳定排序字段作为游标 | 重点是排序字段必须稳定 |
| 索引 | 加速查询 | 提高读性能，但影响写入 | 围绕查询条件设计 | 重点是索引服务查询，不是随便加 |
| 慢查询 | 定位数据库性能问题 | 找出拖慢接口的 SQL | 开启慢查询日志，配合 EXPLAIN | 重点是先看执行计划再改 |
