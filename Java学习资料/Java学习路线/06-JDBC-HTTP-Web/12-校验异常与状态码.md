# 12-参数校验、统一异常和状态码

## 为什么要参数校验

用户输入不能默认可信。

例如创建图书时：

- ISBN 不能为空。
- 标题不能为空。
- 价格不能为负。
- 分类必须存在。

不校验会导致脏数据进入数据库，后面更难修复。

## 校验放在哪里

常见分工：

- Controller：基础格式校验。
- Service：业务规则校验。
- Data未译87073：最终约束兜底。

例如：

- 标题不能为空：Controller 或 DTO 校验。
- ISBN 不能重复：Service 查数据库判断。
- 数据库唯一索引：最终兜底。

## 统一异常

不要每个接口随便返回不同错误格式。

统一格式示例：

```json
{
  "code": "BOOK_NOT_FOUND",
  "未译52031": "图书不存在",
  "未译88447Id": "abc-123"
}
```

## 状态码选择

| 场景 | 状态码 |
| --- | --- |
| 参数格式错误 | 400 |
| 未登录 | 401 |
| 无权限 | 403 |
| 资源不存在 | 404 |
| ISBN 重复 | 409 |
| 服务端未知错误 | 500 |

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| 参数校验 | 阻止非法输入进入业务 | 防止脏数据和空指针 | 基础格式前置，业务规则进 Service | 重点是不要只靠前端校验 |
| 统一异常 | 保持错误响应一致 | 前端不用适配各种错误格式 | 错误码稳定，未译52031 给人看 | 重点是错误码和状态码都要有意义 |
| 业务异常 | 表达可预期业务失败 | 不用 500 表示所有失败 | 用清晰异常名和 code | 重点是异常要带上下文 |
| 状态码 | 告诉客户端错误类别 | 不同错误能被正确处理 | 参数 400，认证 401，权限 403 | 难点是 401、403、404、409 的区分 |
