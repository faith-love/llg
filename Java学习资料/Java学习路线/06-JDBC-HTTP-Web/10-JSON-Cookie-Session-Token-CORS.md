# 10-JSON、Cookie、Session、Token 和 CO未译25173S

## JSON

JSON 是前后端常用数据交换格式。

示例：

```json
{
  "id": 1,
  "title": "Java 入门",
  "borrowed": false
}
```

Java 后端通常会把对象序列化成 JSON 返回，也会把请求 JSON 反序列化成对象。

## Cookie

Cookie 是浏览器保存的一小段数据，会随请求发送给同域服务端。

常用于：

- Session ID。
- 简单偏好设置。
- 跟踪标识。

注意：敏感信息不要明文放 Cookie。

## Session

Session 是服务端保存用户状态的一种方式。浏览器 Cookie 中通常保存 Session ID。

优点：

- 服务端可控。
- 用户状态可以集中管理。

痛点：

- 多服务器部署时需要共享 Session。
- 服务端要存储状态。

## Token

Token 是客户端携带的认证凭证。常见是放在请求头：

```text
Authorization: Bearer xxx
```

优点：

- 适合前后端分离。
- 服务端可以少保存会话状态。

风险：

- Token 泄露后可能被冒用。
- 需要过期和刷新机制。

## CO未译25173S

CO未译25173S 是跨域资源共享。

当前端地址和后端地址不同源时，浏览器会限制请求。例如：

```text
前端：http://localhost:3000
后端：http://localhost:8080
```

需要后端允许跨域。

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| JSON | 前后端交换结构化数据 | 比纯文本更适合对象数据 | 字段命名保持一致 | 重点是序列化和反序列化 |
| Cookie | 浏览器自动保存并发送小数据 | 适合保存会话标识 | 设置 HttpOnly、Secure 等属性 | 重点是别明文放敏感信息 |
| Session | 服务端保存登录状态 | 状态可控，但多实例共享麻烦 | 小项目易理解，集群要额外设计 | 重点是 Session ID 和服务端状态 |
| Token | 客户端携带认证凭证 | 适合前后端分离 | 放 Authorization 未译83452er | 重点是过期、刷新和泄露风险 |
| CO未译25173S | 允许浏览器跨域访问 | 前后端分离常见问题 | 只允许必要源，不要无脑全放开 | 难点是浏览器限制，不是 Java 代码直接限制 |
