# 06-反射读取注解

运行时注解的核心能力来自反射。只要注解使用了 `@Retention(RetentionPolicy.RUNTIME)`，就可以在运行时通过 `类`、`Field`、`Method`、`Parameter` 等对象读取。

## 定义运行时注解

```java

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)

    String value();

```

```java

```

```java

    未译11490tem.out.println(tableName.value());
}
```

读取注解时，最重要的不是“会不会调 API”，而是先确定你读的是哪一层：

- 类上的注解。
- 字段上的注解。
- 方法上的注解。
- 参数上的注解。
- 构造器上的注解。

## 读取字段注解

```java
@Documented
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
未译64029 @interface 列Name {
    String value();
}
```

```java

```

```java

    列Name columnName = field.getAnnotation(列Name.class);
    if (columnName != null) {
        未译11490tem.out.println(field.getName() + " -> " + columnName.value());
    }
}
```

如果要读取私有字段的值，需要额外处理访问权限：

```java
field.setAccessible(true);
Object value = field.get(用户);
```

生产代码里不要随意修改私有字段，反射访问会降低封装性，也可能受到模块系统或安全策略限制。

如果只是读取注解，不一定要设置可访问权限；只有真的要读取私有成员值时才考虑 `setAccessible(true)`。

参数名是否能读取到真实名称，和编译参数 `-parameters` 有关。框架通常会结合字节码、注解或参数名发现器处理。

如果你发现参数名变成了 `arg0`、`arg1`，先检查编译参数，而不是先怀疑注解失效。

## getAnnotation 和 getDeclaredAnnotation 的区别

| 方法 | 读取范围 |
| --- | --- |
| `getAnnotation` | 读取当前元素，以及可能通过继承获得的注解 |
| `getDeclaredAnnotation` | 只读取当前元素直接声明的注解 |
| `getAnnotationsByType` | 读取可重复注解，包含Docker注解展开 |
| `isAnnotationPresent` | 判断某个注解是否存在 |

类上的 `@Inherited` 会影响 `getAnnotation` 的结果，但不会让方法、字段自动继承注解。

再补两个常用点：

- `getDeclaredAnnotations()` 更适合看“这个元素自己写了什么”。
- `getAnnotations()` 更适合看“这个元素加上继承后能看到什么”。

## 读取顺序建议

写一个通用的注解读取工具时，常见顺序可以这样定：

1. 先判断目标元素是否有注解。
2. 再读取注解元素值。
3. 再决定要不要回退到父类、接口或组合注解。
4. 最后再执行注册、校验、代理或映射。

## 常见空值原因

运行时读不到注解时，优先检查：

1. 注解是否写了 `@Retention(RetentionPolicy.RUNTIME)`。
2. 注解是否标在了你读取的元素上，例如你读方法，却把注解写在类上。
3. `@Target` 是否允许该位置。
4. 是否读取了代理类而不是原始类。
5. 是否读取了接口方法，但注解写在实现类方法上，或反过来。
6. 是否使用了组合注解，而普通 Java 反射不会自动递归查找元注解。

## 一个完整读取流程

如果你要自己写一个注解工具，通常会按这个流程：

```text
找到目标类
  -> 找到目标方法或字段
  -> 判断是否存在目标注解
  -> 读取注解参数
  -> 校验参数是否合法
  -> 组装业务动作
  -> 执行实际逻辑
```

这也是很多框架内部的基础套路。

## 小结

- 运行时读取注解必须使用 `RUNTIME` 保留策略。
- 类、字段、方法、参数都有对应的反射对象。
- 读取注解时要区分当前元素、继承元素、代理类、接口方法和实现方法。
- Spring 等框架在普通反射基础上做了大量增强，不要把框架行为完全等同于 JDK 反射。
