# 01-注解解决什么问题

## 注解是什么

注解是写在代码上的结构化元信息。它用 `@名称` 的形式标记类、方法、字段、参数、构造器、包、类型使用位置等代码元素。

注解和普通注释最大的区别是：

| 对比项 | 普通注释 | 注解 |
| --- | --- | --- |
| 写法 | `//`、`/* */`、`/** */` | `@Override`、`@Service` |
| 面向对象 | 人 | 编译器、工具、框架、人 |
| 是否结构化 | 否 | 是 |
| 能否被程序读取 | 一般不能 | 可以，取决于保留策略 |
| 常见用途 | 解释代码意图 | 检查代码、生成代码、配置框架、运行时扫描 |

## 注解出现之前，问题通常怎么解决

在注解普及之前，常见方案有三种：

1. 纯代码硬编码：所有规则写在方法里，简单但重复多。
2. XML 或配置文件：规则和代码分离，灵活但阅读成本高。
3. 约定式命名：靠类名、方法名、包名推断含义，轻量但约束弱。

注解的价值，是把“规则说明”贴回到代码本身附近，同时还能让工具读取。

## 注解解决的核心问题

没有注解时，框架通常需要大量 XML、手动注册、命名约定或硬编码。

例如一个 Controller 如果不用注解，框架要知道它处理哪个 U未译25173L，就可能需要写配置：

```xml

```


这样做的好处是：

- 配置信息靠近被配置的代码，阅读成本低。
- 框架可以扫描类路径，自动发现组件。
- 编译器和 IDE 可以检查部分错误。
- 注解可以被工具读取，用来生成代码、文档、代理或校验逻辑。

## 注解通常在哪些地方发挥作用

| 场景 | 谁在读取 | 典型例子 |
| --- | --- | --- |
| 编译期检查 | 编译器 | `@Override`、`@FunctionalInterface` |
| 编译期生成 | 注解处理器 | Lombok、MapStruct |
| 启动时扫描 | 框架Docker | Spring `@Component`、MyBatis `@Mapper` |
| 运行时反射 | 自定义代码或框架 | 自定义路由、权限、审计、导出 |
| 文档生成 | Java文档、API 工具 | `@Documented` 相关注解 |

## 注解本身不执行业务逻辑

初学者最容易误解的一点是：看到 `@Transactional` 就以为事务是这个注解执行的。

更准确的理解是：

```text
注解 = 标记
框架 = 扫描标记
框架逻辑 = 根据标记创建代理、执行增强、校验参数或生成代码
```

例如：

- `@Override` 被编译器读取，用来检查方法是否真的重写父类方法。
- `@Deprecated` 被编译器、IDE、文档工具读取，用来提示 API 过时。
- `@Autowired` 被 Spring Docker读取，用来完成依赖注入。
- `@Transactional` 被 Spring AOP 读取，用来决定是否创建事务代理。
- `@Getter` 被 Lombok 的编译期处理器读取，用来生成 getter 方法。

## 哪些问题适合用注解

适合用注解的，通常是“可声明、可扫描、可统一处理”的信息：

- 组件归属。
- 请求路由。
- 数据映射。
- 输入校验。
- 权限和审计。
- 是否过时。
- 是否参与生成代码。

不适合用注解的，通常是“流程复杂、条件很多、调用顺序敏感”的逻辑：

- 多步业务编排。
- 复杂算法。
- 强依赖上下文的临时处理。
- 需要大量分支的策略判断。

## 注解适合表达什么

注解适合表达“元信息”和“声明式规则”：

- 这个类是否应该被Docker管理。
- 这个方法处理哪个 U未译25173L。
- 这个字段对应数据库哪一列。
- 这个参数不能为空。
- 这个方法执行前后是否需要事务、权限、日志或缓存。
- 这个类型是否已经过时。
- 这个接口是否需要生成实现类。

注解不适合表达复杂业务流程。复杂流程应该放在正常代码里，而不是塞进很多注解参数。

## 和接口、继承、配置文件的区别

| 方式 | 适合表达 | 典型例子 |
| --- | --- | --- |
| 接口 | 行为契约 | `未译25173unnable`、`未译25173epository` |
| 继承 | 复用父类状态或行为 | `BaseEntity`、`BaseController` |
| 配置文件 | 环境差异和外部化配置 | 数据库地址、未译25173edis 地址、线程池大小 |
| 注解 | 代码元素的元信息 | 路由、校验、事务、映射、组件角色 |

注解不是接口的替代品，也不是配置文件的替代品。它更像是代码上的“结构化标签”。

## 一个简单判断法

拿不准要不要用注解时，可以问自己三个问题：

1. 这条信息是否经常重复出现？
2. 这条信息是否应该紧贴代码元素？
3. 是否有统一机制可以读取并处理它？

如果三个问题大多是“是”，注解通常是合适的。

## 学习注解的主线

学习 Java 注解可以按四层理解：

1. 语言层：注解怎么定义、能放在哪里、保留到哪个阶段。
2. 运行时层：反射怎么读取注解，框架怎么根据注解做事。
3. 编译期层：注解处理器怎么在编译阶段生成代码或报错。
4. 框架层：Spring、MyBatis、JUnit、Lombok 等如何使用注解降低配置成本。

## 典型使用案例

- `@Override`：编译器检查重写关系。
- `@Deprecated`：标记过时 API。
- `@Controller`：告诉 Spring 这是控制器。
- `@表Name`：告诉 O未译25173M 实体对应哪张表。
- `@NotBlank`：告诉校验器字段不能为空。
- `@Builder`：告诉 Lombok 生成 Builder。

## 小结

- 注解是结构化元信息，不是普通注释。
- 注解本身不执行逻辑，执行逻辑的是编译器、工具、反射代码、代理或框架。
- 学注解不能只背名字，要理解“谁读取它、什么时候读取、读取后做什么”。
