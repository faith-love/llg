# 05-自定义注解设计

自定义注解不是为了“看起来高级”，而是为了把重复的元信息沉淀为统一约定，让框架、工具或公共代码可以读取并处理。

## 什么时候值得自定义注解

适合自定义注解的场景：

- 多个方法需要统一审计日志。
- 多个接口需要统一权限、限流、幂等、缓存、脱敏。
- 多个字段需要统一导入导出映射。
- 多个类需要标记模块、插件、策略、消息处理器。
- 编译期需要生成代码或做规则检查。

不适合自定义注解的场景：

- 只有一个地方使用。
- 只是为了替代一个普通方法调用。
- 注解参数越来越像一门配置语言。
- 使用者看不出注解会带来什么副作用。

一个简单判断标准是：如果这段信息需要被多个地方重复读取，而且又希望贴近代码元素本身，就可以考虑注解。否则优先用普通方法、配置类或枚举。

## 设计一个审计日志注解

目标：在业务方法上标记操作名称、模块和风险级别。

```java
@Documented
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface AuditLog {
    String value();
    String module() default "";
    RiskLevel risk() default RiskLevel.NORMAL;
}
```

```java
public enum RiskLevel {
    LOW, NORMAL, HIGH
}
```

使用：

```java
@AuditLog(value = "删除用户", module = "用户", risk = RiskLevel.HIGH)
public void delete用户(Long 用户Id) {
}
```

这类注解只负责描述“这是一个需要审计的操作”。真正记录日志的逻辑应该由 AOP、拦截器或代理代码完成。

如果把日志记录代码直接塞进注解，就会把“声明”和“执行”混在一起，后期很难维护。

## 设计一个字段导出注解

```java
@Documented
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface Excel列 {
    String value();
    int order() default 0;
}
```

```java
public class 用户ExportRow {
    @Excel列(value = "用户ID", order = 1)
    private Long id;

    @Excel列(value = "用户名", order = 2)
    private String 用户name;
}
```

导出工具可以通过反射读取字段上的 `@Excel列`，决定表头名称和列顺序。

这类注解通常只需要很少的元素：

- 一个主名称。
- 一个排序号。
- 少量开关位。

如果导出规则开始变复杂，优先把复杂逻辑放回导出策略类，不要把注解参数无限膨胀。

## 命名原则

好的注解名应该表达业务语义，而不是表达实现细节。

| 不推荐 | 推荐 | 原因 |
| --- | --- | --- |
| `@DoLog` | `@AuditLog` | 说明日志类型 |
| `@Check` | `@PermissionRequired` | 说明检查对象 |
| `@Handle` | `@Component` | 说明被框架如何识别 |
| `@Open` | `@PublicApi` | 说明访问语义 |

## 元素设计原则

注解元素越少越好。常见元素可以这样设计：

| 元素 | 适用场景 |
| --- | --- |
| `value` | 最核心、最常用的配置 |
| `name` | 命名型配置 |
| `type` | 传入一个类 |
| `groups` | 分组规则 |
| `order` | 排序 |
| `enabled` | 是否启用 |

避免：

- 元素过多，导致调用处像配置文件。
- 使用晦涩缩写。
- 使用布尔值组合出复杂状态。
- 没有默认值却不是必填语义。

设计时要尽量保证：

- 使用方一眼能读懂。
- 默认值能代表最常见场景。
- 处理器拿到注解后不需要再猜语义。

## 注解的演进边界

注解一旦开始广泛使用，修改成本会比较高，所以定义时要提前考虑版本演进：

- 元素名尽量稳定，不要轻易改名。
- 新需求优先加新元素，不要改变旧元素语义。
- 删除元素前先给出弃用过渡期。
- 行为变化尽量放到处理器或服务逻辑里，不要只改注解名字。

## 注解和枚举配合

当一个元素只有有限取值时，优先用枚举，而不是字符串。

```java
public enum CachePolicy {
    READ_ONLY,
    READ_WRITE,
    WRITE_THROUGH
}

public @interface CacheableQuery {
    String value();
    CachePolicy policy() default CachePolicy.READ_ONLY;
}
```

枚举的好处：

- 编译期能检查拼写。
- IDE 能自动提示。
- 重构更安全。
- 语义比字符串更稳定。

常见搭配思路：

- 注解表达“是否启用”。
- 枚举表达“模式或策略”。
- 反射或处理器表达“具体执行细节”。

## 小结

- 自定义注解应该表达稳定的元信息，而不是替代普通代码。
- 注解名要体现业务语义。
- 注解元素要少，默认值要清晰。
- 真正逻辑必须有明确处理方：AOP、反射工具、编译器插件或框架Docker。

## 小练习

1. 设计一个 `@RateLimit` 注解，想清楚哪些信息该放注解里，哪些该放配置里。
2. 设计一个 `@PermissionRequired` 注解，考虑是否需要角色、权限码和是否向上兼容。
3. 把一个已有的“配置项 + if 分支”案例改写成“注解 + 处理器”的思路。
