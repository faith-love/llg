# 15-注解设计规范和避坑清单

注解越靠近框架底层，越需要规范。一个设计不清晰的注解，会让调用者不知道它是否生效、什么时候生效、失败后怎么排查。

## 设计规范

定义注解前先回答这些问题：

| 问题 | 说明 |
| --- | --- |
| 谁读取它？ | 编译器、APT、Spring、AOP、反射工具、测试框架？ |
| 什么时候读取？ | 编译期、启动时、请求时、方法调用时？ |
| 标在哪里？ | 类、方法、字段、参数、类型使用位置？ |
| 不生效时有什么提示？ | 启动报错、编译报错、日志告警、静默跳过？ |
| 是否允许组合注解？ | 是否支持元注解递归查找？ |
| 是否需要继承？ | 是否处理父类、接口、重写方法？ |
| 是否有默认值？ | 默认值是否表达清晰？ |

如果这几个问题答不清楚，不要急着定义注解。先用普通代码把流程跑通，再抽象成注解。

## 推荐模板

运行时方法注解：

```java
@Documented
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface OperationLog {
    String value();
    String module() default "";
}
```

字段映射注解：

```java
@Documented
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface Export列 {
    String value();
    int order() default 0;
}
```

编译期代码生成注解：

```java
@Retention(RetentionPolicy.SOURCE)
@Target(ElementType.TYPE)
public @interface GenerateClient {
}
```

## 命名规范

| 类型 | 推荐命名 |
| --- | --- |
| 动作审计 | `@AuditLog`、`@OperationLog` |
| 权限控制 | `@PermissionRequired`、`@Require作用` |
| 字段映射 | `@Export列`、`@列Name` |
| 组件标记 | `@Component`、`@StrategyComponent` |
| 生成代码 | `@GenerateClient`、`@GenerateMapper` |

不要使用 `@Flag`、`@Mark`、`@DoSomething` 这类语义模糊的名字。

## 避坑清单

### 1. 忘记 RUNTIME

现象：反射读取结果为 `null`。

原因：注解没有写 `@Retention(RetentionPolicy.RUNTIME)`。

处理：需要运行时读取的注解必须明确写 `RUNTIME`。

### 2. Target 写错

现象：注解不能标在想标的位置，或误标到不该标的位置。

处理：业务注解必须明确 `@Target`，不要依赖默认“哪里都能写”的宽松行为。

### 3. 注解写了但没人处理

现象：代码上有注解，但没有任何效果。

原因：没有编译器、处理器、框架、AOP 或反射代码读取它。

处理：每个注解都要有明确处理方。

### 4. Spring 注解不在扫描路径

现象：`@Component`、`@Service`、`@Mapper` 等不生效。

处理：

- 检查启动类包路径。
- 检查 `@ComponentScan`、`@MapperScan`。
- 检查模块是否被主应用依赖。

### 5. 事务注解自调用失效

现象：同类内部方法调用 `@Transactional` 方法，事务不生效。

原因：调用没有经过 Spring 代理。

处理：把事务方法放到另一个 Bean，或调整调用路径。

### 6. 注解参数过多

现象：一个注解有十几个参数，调用处很难读。

处理：拆分注解、改用配置类、改用普通代码，或把复杂策略交给 Bean。

### 7. 组合注解读取不到

现象：自定义组合注解上标了某个元注解，但自己的反射代码读不到。

原因：JDK 普通反射不会自动递归查找所有元注解。

处理：自己实现递归查找，或使用 Spring 的注解工具。

### 8. 接口和实现类注解位置不一致

现象：框架读取接口方法，但注解写在实现类；或框架读取实现类，但注解写在接口。

处理：明确框架读取策略，团队统一注解书写位置。

### 9. 注解默认值语义不清

现象：空字符串、`0`、`false` 到底表示未配置还是业务值不清楚。

处理：在注释或文档里写清默认值语义，必要时使用枚举。

### 10. 注解隐藏副作用

现象：写一个注解后，方法突然多了事务、锁、缓存、权限、异步等行为，但调用者不容易发现。

处理：注解名必须表达副作用，关键注解要有统一文档和代码评审标准。

## 排查顺序

注解不生效时按这个顺序查：

1. 这个注解应该由谁处理？
2. 保留策略是否正确？
3. 作用目标是否正确？
4. 注解是否写在框架实际读取的位置？
5. 当前类是否被框架扫描或注册？
6. 是否通过代理对象调用？
7. 是否被继承、接口、重写、桥接方法影响？
8. 是否缺少依赖、配置开关或编译参数？
9. 是否有日志能证明处理器扫描到了它？

## 代码评审清单

评审注解相关代码时，可以看：

- 注解名是否表达真实语义。
- `@Retention` 是否符合处理时机。
- `@Target` 是否足够精确。
- 默认值是否安全。
- 是否有明确处理器。
- 是否有不生效时的日志或异常。
- 是否有最小测试覆盖。
- 是否和已有框架注解重复造轮子。

## 小结

注解规范的关键是可预期。使用者要知道写在哪里、何时生效、失败怎么排查；维护者要知道谁负责读取和处理。

## 小练习

1. 审查一个自定义注解，补齐处理方、保留策略、作用目标说明。
2. 找一个注解参数过多的例子，尝试拆分或改成配置类。
3. 为一个 `@AuditLog` 注解写一份不生效排查清单。
