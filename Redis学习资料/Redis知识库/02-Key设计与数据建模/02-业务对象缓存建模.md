# 业务对象缓存建模

## 常见建模方式

对象缓存有三种常见方式：

| 方式 | 示例 | 优点 | 风险 |
| --- | --- | --- | --- |
| String 保存 JSON | `缓存:用户:1` | 读写简单 | 局部字段更新困难 |
| Hash 保存字段 | `用户:1` | 字段级更新方便 | 单个 Hash 可能过大 |
| 多 Key 拆分 | `用户:1:base`、`用户:1:perm` | 边界清晰 | Key 数量增加 |

## 选择原则

- 只读多、整体读写：String JSON。
- 字段更新频繁：Hash。
- 子对象生命周期不同：拆分多 Key。
- 查询条件复杂：不要强行用 Redis 承担，回到数据库或Elasticsearch。

## 缓存 Aside 模式

典型读流程：

1. 先查 Redis。
2. 命中则返回。
3. 未命中查数据库。
4. 写入 Redis，并设置 TTL。
5. 返回结果。

典型写流程：

1. 先更新数据库。
2. 再删除缓存。
3. 必要时通过消息或延迟双删降低并发不一致窗口。

## 建模示例

商品详情页可以拆成：

```text
缓存:product:{id}:base
缓存:product:{id}:price
缓存:product:{id}:stock-view
缓存:product:{id}:re通用mend
```

基础信息 TTL 长一些，价格和库存展示 TTL 短一些，推荐结果可异步刷新。

## 粒度选择

缓存粒度越粗，读取越简单，但更新成本越高。缓存粒度越细，更新灵活，但 Key 数量和读取次数会上升。

商品详情可以按变化频率拆分：

- 基础信息：标题、图片、分类，变化少。
- 价格信息：促销、会员价，变化中等。
- 库存展示：变化频繁，但通常不要求完全实时。
- 推荐内容：可异步计算，可降级为空。

这样某个字段变化时，不必删除整个详情缓存。

## 防止缓存污染

缓存对象时要避免把用户私有信息写进公共 Key。例如商品详情公共缓存不应包含“当前用户是否收藏”“当前用户专属价格”，这些内容应该单独按用户维度缓存或实时查询。

## 练习

- 为商品详情页画出缓存拆分表。
- 标出公共缓存和用户私有缓存。
- 说明更新价格时需要删除哪些 Key。
