# Key 命名规范与生命周期

## 命名目标

好的 Key 命名应当能让人直接看懂：属于哪个业务、是什么对象、哪个维度、是否有版本或时间。命名不是审美问题，而是排障、统计、删除和迁移的基础。

## 推荐格式

```text
业务域:对象类型:对象ID:属性
业务域:场景:日期:维度
```

示例：

```text
mall:用户:1001:profile
mall:product:sku:9001
mall:rank:daily:2026-05-14
mall:rate:order-create:用户:1001:202605141530
```

## 生命周期

每类 Key 都要明确：

- 是否必须设置 TTL。
- TTL 多长，是否要加随机抖动。
- 数据是否允许提前删除。
- 删除后能否从数据库或上游重新构建。
- 是否需要预热或异步刷新。

## 命名禁忌

- 没有业务前缀，例如 `用户:1`。
- 同一业务多套命名风格混用。
- Key 里包含不可控长文本。
- 用 `*` 扫描在线核心路径。
- 版本升级时直接复用旧 Key，导致新旧结构混读。

## 检查清单

- 前缀是否能归属到系统和模块？
- 是否能用 `SCAN MATCH prefix:*` 精准定位？
- 是否能按时间或版本做灰度迁移？
- 是否设置了 TTL 或归档清理策略？

## 命名分层

推荐把 Key 拆成稳定层级：

```text
公司或系统:业务域:对象类型:对象ID:属性或场景
```

例如：

```text
shop:mall:product:1001:detail
shop:mall:用户:1001:profile
shop:支付:idem:req-20260514-001
```

层级越稳定，后续迁移、统计、清理越简单。不要把会变化的展示文案、用户名、长 JSON 片段放进 Key。

## 生命周期分类

| 类型 | TTL 建议 |
| --- | --- |
| 查询缓存 | 必须有 TTL |
| 验证码和令牌 | 短 TTL |
| 分布式锁 | 极短 TTL，并支持续期或兜底 |
| 排行榜 | 按日、周、月拆 Key，历史归档或过期 |
| 配置缓存 | 可较长 TTL，但要有主动失效机制 |

## 练习

- 为商品详情、用户登录态、订单幂等、接口限流各设计一个 Key。
- 写出每个 Key 的 TTL、删除方式和重建方式。
