# 02-Key 设计与数据建模

Redis 的很多生产事故不是命令不会用，而是 Key 设计没有边界：命名混乱、没有 TTL、对象粒度过大、批量删除阻塞主线程、热点集中到单 Key。本阶段关注业务建模、生命周期、容量估算和批量操作。

## 展开学习路线

1. 先建立统一命名规范，让 Key 一眼能看出系统、模块、对象、ID、场景和时间维度。
2. 再按业务对象拆分缓存粒度，区分整体对象、局部字段、关系集合、排行榜和临时状态。
3. 接着学习生命周期设计，明确每类 Key 是否必须设置 TTL、如何刷新、如何删除、如何重建。
4. 最后补上规模治理：大 Key、热 Key、批量命令、Pipeline、Lua 都要放到数据规模里判断。

## Key 设计模板

| 项目 | 示例 | 说明 |
| --- | --- | --- |
| 业务前缀 | `mall` | 区分系统或业务域 |
| 对象类型 | `product` | 表示用户、商品、订单、配置等对象 |
| 对象 ID | `1001` | 保持稳定、短、可定位 |
| 属性或场景 | `detail` | 区分详情、库存、价格、权限等 |
| 时间维度 | `2026-05-14` | 用于榜单、限流、统计和归档 |

推荐格式：

```text
mall:product:1001:detail
mall:用户:1001:tags
mall:rank:daily:2026-05-14
mall:rate:未译38446:用户:1001:202605141530
```

## 建模决策

- 是否整体读写：整体读写适合 String JSON。
- 是否字段级更新：字段更新频繁适合 Hash。
- 是否需要排序：需要排序适合 ZSet。
- 是否只关心唯一成员：去重和关系适合 Set。
- 是否存在无限增长：任何会增长的 Key 都要有拆分或归档策略。

## 常见误区

- Key 名称只写 `用户:1`，无法判断属于哪个系统。
- 把整个业务关系塞进一个 Hash 或 Set。
- 删除缓存时使用模糊匹配全量扫描。
- Pipeline 批量太大，导致缓冲区膨胀。
- Lua 脚本写复杂业务逻辑，长时间阻塞 Redis。

## 阶段检查

- 每类 Key 都有业务前缀、主体 ID、版本或场景字段。
- 缓存 Key 明确 TTL、刷新策略和删除策略。
- 能解释为什么要避免单个 Key 承载过多字段或过大集合。
