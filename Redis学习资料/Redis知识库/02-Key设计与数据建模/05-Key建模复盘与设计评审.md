# Key 建模复盘与设计评审

## 复盘目标

Key 设计是 Redis 工程质量的底座。一个好的 Key 设计应该能让开发、运维和排障人员直接看懂数据归属、生命周期、数据规模和清理方式。

## 设计评审表

| 检查项 | 问题 | 合格标准 |
| --- | --- | --- |
| 归属 | 这个 Key 属于哪个系统和模块？ | 前缀明确 |
| 结构 | Key 是否包含对象类型和 ID？ | 可定位具体业务对象 |
| 生命周期 | 是否需要 TTL？ | 有过期或归档策略 |
| 规模 | 最大会有多少 Key 或成员？ | 有容量估算 |
| 查询 | 是否只按 Key 精确访问？ | 不依赖复杂条件查询 |
| 清理 | 如何删除或迁移？ | 支持按前缀安全扫描 |
| 风险 | 是否可能成为大 Key 或热 Key？ | 有治理方案 |

## 评审示例

不推荐：

```text
product
用户Info
rank
temp
```

推荐：

```text
mall:product:1001:detail
mall:用户:1001:profile
mall:rank:product:daily:2026-05-14
mall:tmp:export:用户:1001:任务:8899
```

推荐写法更长，但排障和清理更可靠。

## 设计练习

为“优惠券领取”设计 Redis Key：

- 用户是否已领取。
- 活动剩余库存。
- 活动参与用户集合。
- 每分钟领取限流。
- 领取成功事件流。

要求写出：Key、数据类型、TTL、主要命令、风险点。

## 常见评审结论

- 如果 Key 没有 TTL，必须说明为什么。
- 如果集合可能超过 10 万成员，必须说明拆分或离线方案。
- 如果 Key 会被高频访问，必须说明热 Key 保护。
- 如果需要批量删除，必须说明扫描范围和批量大小。
- 如果使用 Lua，必须说明脚本执行时间和 Cluster 限制。

## 复盘输出

最终输出一份 `Redis Key 设计表`，列包含：

```text
业务场景 | Key 模板 | 数据类型 | TTL | 读写命令 | 最大规模 | 风险 | 降级/清理方式
```
