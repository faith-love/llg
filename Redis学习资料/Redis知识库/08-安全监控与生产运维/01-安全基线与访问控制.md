# 安全基线与访问控制

## 基线原则

Redis 不应直接暴露公网。生产访问应通过内网、安全组、防火墙和账号权限控制。安全不是只设置一个密码，而是限制可访问范围、可执行命令和可见数据。

## 必做项

- 绑定内网地址或本机地址。
- 配置密码或 ACL 用户。
- 禁止公网安全组访问 6379。
- 限制危险命令或改名。
- 配置 TLS 时确认客户端支持。
- 日志和配置中避免泄露密码。

## ACL 示例

```bash
ACL SETUSER app-用户 on >strong-password ~app:* +@read +@write -@dangerous
ACL LIST
```

不同应用应使用不同账号和 Key 前缀，减少误操作影响范围。

## 危险命令

需要谨慎控制：

- `FLUSHALL`
- `FLUSHDB`
- `CONFIG`
- `SHUTDOWN`
- `KEYS`
- `EVAL`
- `MIGRATE`

不是所有命令都必须禁用，但必须有权限边界和审计策略。

## 检查清单

- 是否能从公网直接连上 Redis？
- 应用账号是否只访问自己的前缀？
- 运维账号是否有审批和审计？
- 密码是否进入代码仓库或 shell 历史？

## 最小权限思路

不同应用不要共用同一个 Redis 超级账号。可以按系统、环境和用途拆分账号：

- 应用读写账号：只能访问本业务前缀。
- 只读账号：只允许排查和监控读取。
- 运维账号：需要审批和审计。
- 临时账号：用后关闭或删除。

权限边界越清楚，误删和越权访问的影响越小。

## 网络隔离

安全组、防火墙、VPC、子网和绑定地址要一起配置。即使设置了密码，也不应该让 Redis 直接暴露公网。公网扫描 Redis 是常见攻击面。

## 练习

- 写一份 Redis 上线安全检查表。
- 为一个应用设计只允许访问 `app:*` 的 ACL。
- 说明为什么不能把 Redis 密码写进代码仓库。
