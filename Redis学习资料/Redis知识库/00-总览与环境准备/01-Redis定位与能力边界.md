# Redis 定位与能力边界

## Redis 适合做什么

Redis 的核心优势是低延迟读写、丰富的数据结构、原子命令和成熟的复制高可用能力。它适合放在需要快速访问、允许用内存换响应时间、并且可以接受一定工程取舍的位置。

常见场景：

- 缓存热点查询结果，减少数据库压力。
- 计数器、点赞数、阅读数、库存预扣等高频状态。
- 登录态、验证码、短期令牌和会话数据。
- 排行榜、关注关系、标签集合、去重集合。
- 分布式锁、限流、幂等记录、延迟任务和消息流。

## Redis 不适合做什么

Redis 不是 MySQL 的完整替代品。只要业务要求复杂事务、强一致查询、多表关联、长期低成本存储，主存储仍应使用关系型数据库或专门的数据系统。

不建议的场景：

- 把 Redis 当唯一账务系统。
- 把所有业务表无脑镜像到 Redis。
- 保存大文件、长文本、图片或不可控的大对象。
- 用 `KEYS *` 这类全量扫描能力支撑在线业务。
- 在没有备份、告警、限流和降级的情况下承载核心链路。

## 和其他组件的边界

| 组件 | 主要职责 | 与 Redis 的关系 |
| --- | --- | --- |
| MySQL | 可靠持久化、事务、查询 | Redis 通常作为缓存或短期状态层 |
| MQ | 异步解耦、削峰、可靠投递 | Redis Stream 可处理轻量消息，但不是所有 MQ 的替代 |
| 本地缓存 | 进程内快速访问 | Redis 适合跨实例共享和集中失效 |
| Elasticsearch | 搜索、复杂检索 | Redis 不适合复杂全文检索作为主方案 |

## 设计原则

- Redis 中的数据要有明确责任：缓存、状态、计数、队列或锁。
- 每类数据要有容量预估、过期策略和降级方案。
- 重要数据必须能从主库或备份恢复，不依赖 Redis 中唯一副本。
- 所有在线命令都要考虑时间复杂度和数据规模。

## 判断一个场景能不能放 Redis

先回答四个问题：

1. 这份数据是否必须长期可靠保存？
2. Redis 中的数据丢失后，能否从数据库、日志或上游系统重建？
3. 数据是否有明确访问模式，例如按 Key 精确读取、计数、排序或集合计算？
4. 数据规模是否能被内存成本和增长速度覆盖？

如果答案偏向“必须强一致、必须复杂查询、无法重建、规模不可控”，就不应该把 Redis 作为主承载。比较稳妥的做法是让数据库保存事实数据，Redis 只保存可重建的派生数据或短期状态。

## 业务落地示例

商品详情页适合用 Redis 缓存，因为商品基础信息可以从数据库重建，并且查询方式通常是按商品 ID 精确读取。订单支付流水不适合只放 Redis，因为它涉及资金、审计和强一致状态，Redis 最多保存支付状态的短期查询缓存或幂等标记。

## 练习

- 找一个你熟悉的接口，写出它的数据是否适合进入 Redis。
- 标出它的主存储、缓存 Key、TTL、失效方式和降级方式。
- 说明 Redis 不可用时接口应该返回什么。
