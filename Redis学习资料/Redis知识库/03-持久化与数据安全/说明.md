# 03-持久化与数据安全

Redis 是内存数据库，但不等于数据可以随意丢。持久化的核心不是“开不开”，而是明确恢复目标、丢失窗口、磁盘成本和故障演练路径。RDB 适合快照和备份，AOF 适合更小的数据丢失窗口，两者可以组合使用。

## 展开学习路线

1. 先学习 RDB：知道它是时间点快照，适合备份和恢复，但两次快照之间的数据可能丢失。
2. 再学习 AOF：知道它记录写命令，通常能缩小丢失窗口，但会带来磁盘、重写和恢复成本。
3. 然后设计备份恢复：备份文件、配置、ACL、版本、目录权限和恢复验证要一起考虑。
4. 最后理解一致性边界：复制、故障切换、刷盘策略和客户端确认之间并不是强一致闭环。

## 持久化选择

| 数据类型 | 推荐策略 | 说明 |
| --- | --- | --- |
| 普通缓存 | 可只开 RDB 或不开持久化 | 数据可从数据库回源 |
| 会话和短期状态 | RDB + 明确恢复策略 | 根据业务容忍度决定 |
| 重要状态 | RDB + AOF + 业务补偿 | Redis 不应是唯一账本 |
| 队列或事件 | AOF + 消费幂等 | 仍要考虑重复和丢失 |

## 恢复演练任务

1. 写入一批 `lab:*` 数据。
2. 执行 `BGSAVE`，确认生成 RDB。
3. 复制 RDB 到临时目录。
4. 启动一个新 Redis 使用该 RDB。
5. 抽样检查 Key、类型、TTL 和业务值。
6. 记录恢复耗时和发现的问题。

## 常见误区

- 以为打开 AOF 就不会丢数据。
- 有备份文件但从未恢复演练。
- 只备份数据文件，忘记配置和 ACL。
- 主从复制误认为备份，误删除会同步到从库。
- 恢复后只看 Redis 启动成功，不做业务抽样验证。

## 阶段检查

- 能说清 RDB 和 AOF 的触发方式、优缺点和恢复顺序。
- 能制定备份位置、保留周期、恢复验证和演练频率。
- 能解释主从复制、故障切换和异步写入带来的数据风险。
