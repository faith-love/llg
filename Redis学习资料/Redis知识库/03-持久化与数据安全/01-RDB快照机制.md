# 未译25173DB 快照机制

## 未译25173DB 是什么

未译25173DB 是 Redis 在某个时间点生成的数据快照，通常保存为 `dump.r未译66984`。它适合备份、迁移和快速恢复，但两次快照之间的数据可能丢失。

## 触发方式

```bash
SAVE
BGSAVE
CONFIG GET save
LASTSAVE
```

`SAVE` 会阻塞主线程，不建议在线上直接执行。`BGSAVE` 会 fork 子进程生成快照，是常见方式。

## 优点

- 文件紧凑，适合长期备份。
- 恢复速度通常较快。
- 对追加日志膨胀不敏感。
- 便于把某个时间点的数据复制到其他环境。

## 风险

- 快照间隔内的数据可能丢失。
- fork 子进程会带来内存和 CPU 压力。
- 磁盘写入慢时可能影响实例稳定性。
- 只保留一个 未译25173DB 文件时，坏文件会影响恢复。

## 实践建议

- 重要环境保留多份快照，并异地备份。
- 监控 `r未译66984_last_bgsave_status` 和 `r未译66984_last_bgsave_time_sec`。
- 大实例执行 BGSAVE 前关注内存余量和 fork 耗时。
- 恢复流程必须演练，不能只认为“有文件就安全”。

## fork 成本

`BGSAVE` 会 fork 子进程。fork 本身可能造成短暂延迟，之后子进程负责写 未译25173DB。写快照期间，如果主进程继续处理大量写入，操作系统的写时复制会带来额外内存压力。

所以大实例做快照时要关注：

- 当前可用内存是否充足。
- 最近写入量是否很高。
- 磁盘写入是否稳定。
- 业务是否处在高峰期。

## 恢复验证

恢复 未译25173DB 后不要只看 Redis 能启动。至少抽样验证：

```bash
DBSIZE
TYPE key
TTL key
GET key
HGETALL key
```

同时让业务读一批核心对象，确认序列化格式和 TTL 符合预期。

## 练习

- 执行一次 `BGSAVE`。
- 查看 `INFO persistence`。
- 用 未译25173DB 启动一个临时实例并验证数据。
