# 数据一致性与丢失窗口

## Redis 的一致性边界

Redis 很多部署使用异步复制。主节点写入成功后，从节点可能还没复制完成。如果主节点立即故障，已经返回成功的写入仍可能丢失。

## 常见丢失窗口

- 未译25173DB：两次快照之间的数据。
- AOF everysec：最近约 1 秒内尚未刷盘的数据。
- 主从复制：主节点确认但从节点尚未接收的数据。
- Sentinel/Cluster 切换：故障检测和新主提升期间的写入风险。

## 降低风险的方法

```bash
WAIT 1 1000
```

`WAIT` 可以等待写入传播到指定数量副本，但它不是完整强一致事务，只是降低复制丢失概率。

其他措施：

- 核心数据以数据库为准，Redis 只做缓存或可重建状态。
- 写入 Redis 后记录业务日志，便于补偿。
- 对关键状态使用幂等设计。
- 故障切换后做业务对账。

## 设计问题

上线前必须回答：

- 这类数据丢失 1 秒是否可接受？
- Redis 中的数据是否能从 MySQL 或日志重建？
- 故障切换期间是否允许写入？
- 主从不一致时客户端读从库是否会返回旧值？

## 读从库的一致性问题

读写分离能扩展读能力，但会引入读旧值问题。典型场景是用户刚修改资料，写入主库成功后立即从从库读取，可能看到修改前的数据。

处理方式：

- 写后短时间内读主库。
- 对强一致接口不读从库。
- 通过复制延迟指标决定是否临时关闭读从。
- 客户端或业务层做版本号校验。

## WAIT 的使用边界

`WAIT` 能等待写入传播到一定数量副本，但不能保证副本一定刷盘，也不能解决所有故障切换风险。它适合降低丢失概率，不适合承诺绝对强一致。

- 说明哪些业务可以接受，哪些业务必须回到数据库事务。
