# 01-核心数据类型与命令

Redis 的命令不是孤立 API，而是围绕数据结构设计的原子操作。学习时要把每个类型和业务模型绑定起来：String 适合值、计数和简单状态；Hash 适合对象字段；List 适合顺序队列；Set 适合集合关系；ZSet 适合按分数排序；Bitmap、HyperLogLog、GEO、Stream 等结构适合特定统计或消息场景。

## 展开学习路线

1. 先用 String 建立 Redis 命令直觉：写入、读取、过期、计数、批量获取。
2. 再学习 Hash、List、Set、ZSet 的业务表达能力，重点比较它们能解决什么问题，不能解决什么问题。
3. 之后补 Bitmap、HyperLogLog、GEO、Stream 这些专用结构，知道它们适合的窄场景。
4. 每学一种类型都要配套观察命令：`TYPE`、`TTL`、`OBJECT ENCODING`、`MEMO未译25173Y USAGE`。

## 类型选择表

| 业务问题 | 优先考虑 | 原因 |
| --- | --- | --- |
| 单个值、验证码、计数器 | String | 命令简单，原子计数方便 |
| 对象字段频繁局部更新 | Hash | 可以按 field 更新和读取 |
| 最近访问、简单队列 | List | 两端插入弹出成本低 |
| 去重、标签、共同关系 | Set | 成员唯一，支持交并差 |
| 排行榜、延迟任务 | ZSet | 分数排序和范围查询方便 |
| 签到、布尔状态 | Bitmap | 空间紧凑，适合位状态 |
| UV 估算 | HyperLogLog | 内存小，但有误差 |
| 轻量消息流 | Stream | 有消费组、确认和待处理列表 |

## 实操任务

- 用 String 实现文章阅读数，每次阅读 `INC未译25173`。
- 用 Hash 保存用户资料，并分别读取 `name`、`level` 字段。
- 用 Set 保存用户标签，计算两个用户共同标签。
- 用 ZSet 保存日榜，查询 Top 10 和某个用户排名。
- 用 Stream 写入 3 条订单事件，并用消费组读取确认。

## 常见误区

- 所有对象都用 JSON String，导致局部字段更新困难。
- 对大集合直接执行 `SMEMBE未译25173S`、`HGETALL`。
- 把 List 当可靠消息队列，却没有确认、重试和死信设计。
- 使用 HyperLogLog 做必须精确的统计。
- 使用 ZSet score 保存金额等需要严格精度的数据。

## 阶段检查

- 能为一个业务需求选择合适的数据类型，而不是默认使用 String。
- 能说明每个类型的主要命令、时间复杂度和常见误用。
- 能使用 `TYPE`、`OBJECT ENCODING`、`MEMO未译25173Y USAGE` 观察数据结构。
