# 06-性能优化与排障

Redis 快不代表使用方式一定快。慢查询、大 Key、阻塞命令、网络抖动、连接池耗尽、持久化重写、复制延迟都会让业务感知到超时。本阶段建立一套排障顺序：先看症状，再看指标，再定位命令和数据结构。

## 展开学习路线

1. 先理解 Redis 的事件模型和阻塞点，知道快的前提是命令短、数据小、网络稳定。
2. 再掌握慢查询和延迟诊断，区分服务端执行慢、排队慢、网络慢和客户端等待连接慢。
3. 然后把客户端纳入排障范围，检查连接池、超时、重试、序列化和批量调用方式。
4. 最后建立压测方法，用接近真实的数据规模和命令组合验证容量，而不是只看空命令 QPS。

## 排障路径

```text
用户表现 -> 应用日志 -> 客户端连接池 -> Redis 慢查询 -> Redis 延迟事件 -> 内存/CPU/网络 -> 具体 Key 和命令
```

不要一开始就重启 Redis。先保留证据，再判断是否需要止血。

## 指标解释

| 指标 | 说明 | 可能原因 |
| --- | --- | --- |
| 慢查询增加 | 命令执行耗时高 | 大 Key、复杂命令、Lua 时间长 |
| P99 抖动 | 少量请求非常慢 | fork、AOF、网络、连接池排队 |
| 连接数过高 | 客户端连接膨胀 | 连接池配置错误、短连接 |
| blocked_客户端s | 阻塞客户端 | 阻塞命令、Stream/List 阻塞读取 |
| 命中率下降 | 缓存未命中增加 | TTL、批量失效、Key 规则变化 |

## 实操任务

- 故意创建大 Hash，对比 `HGET` 和 `HGETALL` 的差异。
- 打开慢查询日志，执行一批高成本命令并观察 `SLOWLOG`。
- 用小连接池压测应用侧等待连接的表现。
- 使用 `Redis学习资料-benchmark` 和真实业务脚本分别压测，对比结论差异。

## 常见误区

- 只看 Redis 平均耗时，不看 P95/P99。
- 业务超时就断定 Redis 服务端慢。
- 忽略客户端连接池和序列化成本。
- 用 `KEYS *` 排查线上问题。
- 压测数据太小，无法暴露真实大 Key 和网络传输成本。

## 阶段检查

- 能使用 `SLOWLOG`、`LATENCY`、`INFO` 初步定位问题。
- 能说明为什么 `KEYS`、大范围 `HGETALL`、大集合删除会阻塞。
- 能设计接近真实业务的压测，而不是只看空命令 QPS。
