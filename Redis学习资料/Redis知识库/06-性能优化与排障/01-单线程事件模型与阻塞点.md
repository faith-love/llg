# 单线程事件模型与阻塞点

## Redis 为什么快

Redis 的核心命令执行路径主要在内存中完成，并通过事件循环处理网络读写和命令执行。单线程模型减少了锁竞争，但也意味着一个慢命令会阻塞后续命令。

## 常见阻塞点

- 大 Key 的读写、删除和序列化。
- `KEYS`、大范围 `HGETALL`、`SMEMBERS`。
- Lua 脚本执行时间过长。
- RDB/AOF 相关 fork 和磁盘写入压力。
- 客户端输出缓冲区堆积。
- 网络抖动导致客户端重试放大流量。

## 观察命令

```bash
INFO commandstats
SLOWLOG GET 10
LATENCY DOCTOR
CLIENT LIST
```

`commandstats` 可以看命令调用次数和耗时分布，`CLIENT LIST` 可以观察客户端缓冲区、连接状态和空闲时间。

## 设计原则

- 在线请求只执行复杂度可控的命令。
- 大集合分页扫描用 `SCAN` 系列命令。
- 删除大 Key 用 `UNLINK`。
- Lua 只处理短小的原子逻辑。
- 批量操作控制单批大小。

## 排查顺序

1. 先确认业务超时发生时间。
2. 对齐 Redis 慢查询、延迟事件和监控指标。
3. 找到具体命令和 Key。
4. 判断是数据规模、网络、客户端还是持久化引起。

## 单线程不是唯一线程

Redis 的命令执行主路径可以理解为单线程，但 Redis 还会使用后台线程处理一些任务，例如异步释放、持久化相关后台工作等。学习时重点把握：命令执行如果长时间占用主线程，其他请求就要排队。

所以“Redis 快”的前提是每条命令都短小，Key 规模受控，网络传输不夸张。

## 高风险命令替代

| 高风险写法 | 替代思路 |
| --- | --- |
| `KEYS prefix:*` | `SCAN MATCH prefix:* COUNT n` |
| 大 Key `DEL` | `UNLINK` |
| 大 Hash `HGETALL` | `HSCAN` 或按 field 读取 |
| 大 Set `SMEMBERS` | `SSCAN` 或拆分集合 |

## 练习

- 创建一个大 List，观察 `LRANGE 0 -1` 的耗时。
- 用 `SCAN` 替代 `KEYS` 做前缀查找。
- 说明为什么 Redis CPU 不高时业务仍可能超时。
