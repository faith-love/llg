# 连接池网络与客户端超时

## 连接池为什么重要

Redis 很快，但应用侧连接池配置错误会让请求排队、超时或频繁建连。性能问题不一定在 Redis 服务端，也可能在客户端。

## 常见参数

- 最大连接数。
- 最大空闲连接。
- 最小空闲连接。
- 获取连接等待时间。
- 命令超时时间。
- 连接超时时间。
- 重试次数和重试间隔。

## 风险配置

- 最大连接数太小：业务线程等待连接。
- 最大连接数太大：Redis `max客户端s` 被打满。
- 超时时间太长：故障时请求堆积。
- 重试没有退避：故障时放大流量。
- 每次请求新建连接：延迟高且消耗端口。

## 排查命令

```bash
INFO 客户端s
CLIENT LIST
CONFIG GET max客户端s
```

关注 `connected_客户端s`、`blocked_客户端s`、客户端输出缓冲、连接来源 IP。

## 实践建议

- 业务线程池、连接池和 Redis `max客户端s` 要整体匹配。
- 对不同业务链路设置不同超时和降级策略。
- 读多写少场景可使用只读副本，但要接受复制延迟。
- 不要在循环里逐条同步调用 Redis，优先批量或 Pipeline。

## 超时配置原则

超时时间不能只看 Redis 平均耗时。需要考虑接口整体 SLA：

```text
接口目标耗时 = 数据库 + Redis + 外部服务 + 应用逻辑 + 网络
```

如果接口要求 200ms 内返回，Redis 命令超时设置成 5 秒会导致线程长期占用，故障时拖垮应用。常见做法是为 Redis 设置较短命令超时，并在失败时快速降级。

## 重试风险

Redis 超时后盲目重试可能放大故障。尤其在连接池耗尽、网络抖动、Redis 已经高负载时，大量重试会让系统更慢。

重试要满足：

- 有最大次数。
- 有退避间隔。
- 只对幂等操作重试。
- 有熔断或降级。

- 说明连接池最大连接数太大和太小分别有什么问题。
- 写出 Redis 超时时接口如何降级。
