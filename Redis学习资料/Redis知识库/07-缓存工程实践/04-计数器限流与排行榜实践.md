# 计数器、限流与排行榜实践

## 计数器

Redis 的 `INCR`、`INCRBY` 适合高频计数：

```bash
INCR article:1001:view
INCRBY sku:9001:stock -1
```

计数器要考虑回写数据库、溢出、重复请求和幂等。

## 固定窗口限流

```bash
INCR rate:接口:用户:1001:202605141530
EXPIRE rate:接口:用户:1001:202605141530 120
```

固定窗口简单，但窗口边界可能出现瞬时双倍流量。适合低成本限流，不适合严格平滑限流。

## 滑动窗口限流

可以用 ZSet 保存请求时间戳：

```bash
ZADD rate:limit:用户:1 1710000000000 1710000000000
ZREMRANGEBYSCORE rate:limit:用户:1 -inf 1709999940000
ZCARD rate:limit:用户:1
```

优点是更平滑，缺点是内存和命令成本更高。

## 排行榜

```bash
ZINCRBY rank:article:daily 1 article:1001
ZREVRANGE rank:article:daily 0 9 WITHSCORES
```

排行榜要按时间或业务维度拆分，历史榜单设置 TTL 或归档。

## 工程问题

- 计数是否允许丢失？
- 是否需要定期落库？
- 是否需要防重复请求？
- 限流触发后返回什么降级响应？

## 计数落库

阅读数、点赞数这类高频计数通常不会每次都同步写数据库。常见做法是 Redis 先累加，再定时批量落库。

需要注意：

- 落库任务要幂等。
- Redis 计数清零和数据库更新要有顺序。
- 失败时不能丢增量。
- 热点计数可能需要分片计数再汇总。

## 限流响应

限流不是只返回错误码，还要明确用户体验：

- 登录限流：提示稍后再试。
- 发送短信限流：提示剩余等待时间。
- 接口保护限流：返回降级数据或排队提示。
