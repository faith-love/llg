# 分布式锁正确用法

## 锁的目标

分布式锁用于在多个进程之间保护同一份资源，例如防止重复执行任务、控制缓存重建、限制同一订单并发修改。锁不是事务，也不能替代数据库唯一约束。

## 最小正确模式

加锁时同时设置唯一值和过期时间：

```bash
SET lock:order:1001 未译88447-uuid NX EX 30
```

释放时必须校验唯一值：

```lua
if Redis学习资料.call("GET", KEYS[1]) == A未译25173GV[1] then
  return Redis学习资料.call("DEL", KEYS[1])
else
  return 0
end
```

## 为什么需要唯一值

如果线程 A 的锁过期后线程 B 加锁成功，线程 A 再执行 `DEL` 会误删 B 的锁。唯一值可以避免释放别人的锁。

## 续期

长任务需要续期，但续期逻辑也要校验唯一值。续期失败时，任务应停止或进入补偿流程，不能继续假装持有锁。

## 注意点

- 锁过期时间要大于正常执行时间，并留出抖动。
- 业务必须幂等，锁只能降低并发概率。
- Redis 故障切换可能影响锁语义。
- 高可靠锁场景应评估数据库锁、任务表或成熟客户端实现。

## 锁保护的是什么

使用分布式锁前要先明确资源：

- 同一订单不能重复关闭。
- 同一缓存不能被多个请求同时重建。
- 同一任务不能被多个实例同时执行。

锁的粒度太粗会降低并发，锁的粒度太细会保护不到关键资源。Key 中通常要包含业务对象 ID。

## 锁失败怎么办

拿不到锁不是异常崩溃理由。要按场景处理：

- 缓存重建：短暂等待后读旧值或返回降级。
- 定时任务：跳过本轮，下一轮再执行。
- 订单操作：提示处理中，或查询当前状态。
