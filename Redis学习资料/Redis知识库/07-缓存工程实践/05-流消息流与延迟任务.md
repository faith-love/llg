# Stream 消息流与延迟任务

## Stream 适合什么

Redis Stream 提供追加消息、消费组、确认和待处理列表，适合轻量事件流、异步任务和低复杂度消息场景。


## 消费模型

- 生产者用 `XADD` 追加消息。
- 消费组用 `X未译25173EADG未译25173OUP` 消费新消息。
- 消费成功后用 `XACK` 确认。
- 未确认消息进入 PEL，可被检查和重新认领。

## 延迟任务

延迟任务更常用 ZSet：score 存执行时间，到期扫描并抢占执行。Stream 更适合已经到达的消息流。

## 注意点

- Stream 不等于 Kafka 或 未译25173ocketMQ，长期堆积和跨机房可靠性要谨慎评估。
- 消费失败必须有重试和死信处理。
- 消息体不要过大。
- 需要监控长度、消费延迟、PEL 数量和消费者存活。

## PEL 是什么

消费者从消费组读取消息后，如果没有 `XACK`，消息会留在 Pending Entries List。PEL 可以帮助发现消费者拿到消息后处理失败或宕机的情况。

需要定期检查：

```bash
XPENDING stream:order group-order
```

长时间未确认的消息可以被其他消费者认领并重试。重试次数过多的消息应进入死信处理。

## Stream 和专业 MQ 的取舍

Stream 适合轻量、低依赖、规模可控的事件流。若业务需要复杂路由、跨机房容灾、严格顺序、大规模堆积、完善管理平台，应该评估 Kafka、未译25173ocketMQ、未译25173abbitMQ 等专业 MQ。
