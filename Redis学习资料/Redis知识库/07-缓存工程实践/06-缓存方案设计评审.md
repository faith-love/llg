# 缓存方案设计评审

## 评审目标

缓存方案评审要证明：缓存能降低压力，同时不会把一致性、雪崩、击穿、大 Key、热 Key 和降级问题留给线上事故。任何核心缓存上线前，都应该写出一页方案。

## 方案模板

```text
业务接口：
缓存对象：
Key 模板：
数据类型：
TTL：
是否缓存空值：
更新策略：
删除失败补偿：
击穿保护：
雪崩保护：
降级策略：
监控指标：
容量估算：
```

## 评审问题

1. 缓存数据能否从数据库重建？
2. TTL 是否有随机抖动？
3. 空值缓存是否会掩盖真实数据？
4. 更新数据库后缓存如何失效？
5. 删除缓存失败如何补偿？
6. 热点 Key 过期时谁负责重建？
7. Redis 不可用时接口如何返回？
8. 这类 Key 最大规模是多少？

## 示例：商品详情缓存

```text
Key：mall:product:{id}:detail
类型：String JSON
TTL：30 分钟 + 0 到 5 分钟随机抖动
空值：不存在商品缓存 2 分钟
更新：数据库成功后删除缓存
补偿：删除失败投递消息重试
击穿：热点商品逻辑过期 + 后台刷新
降级：返回基础字段，不展示推荐
监控：命中率、回源次数、重建耗时、异常数
```

## 常见不通过原因

- 没有 TTL。
- 只写“更新缓存”，没有失败补偿。
- Redis 异常时没有降级。
- 没有容量估算。
- 没有区分公共缓存和用户私有缓存。
- 使用分布式锁但没有唯一值和释放校验。

## 练习

为“用户权限缓存”写一份评审方案。重点说明权限变更后缓存如何失效，以及错误缓存权限会造成什么风险。
