# 项目面试综合复盘

## 复盘目标

面试里的 Redis 不是背命令，而是证明你能在项目中把 Redis 用稳。一个好的回答要包含场景、设计、风险、监控和结果。

## 项目表达结构

```text
业务背景：
为什么需要 Redis：
使用的数据类型：
Key 如何设计：
TTL 和容量如何控制：
缓存一致性如何处理：
高并发风险如何处理：
Redis 异常如何降级：
上线后监控什么：
最终效果：
```

## 示例回答：商品详情缓存

```text
我们在商品详情接口使用 Redis 缓存热点商品数据。
Key 按 mall:product:{id}:detail 设计，value 使用 JSON，TTL 30 分钟并加随机抖动。
读接口先查缓存，未命中回源数据库并写缓存；更新商品时先更新数据库，再删除缓存，删除失败通过消息重试。
热点商品使用逻辑过期和后台刷新，避免缓存击穿。
监控命中率、回源次数、慢查询和大 Key，Redis 异常时返回基础字段并关闭推荐模块。
上线后数据库查询压力明显下降，接口 P95 稳定在目标范围内。
```

## 常见追问准备

| 追问 | 回答重点 |
| --- | --- |
| 缓存不一致怎么办 | 更新数据库后删缓存，失败补偿，允许短暂最终一致 |
| Redis 挂了怎么办 | 快速失败、降级、本地兜底、限流 |
| 大 Key 怎么处理 | 识别、拆分、限制成员、`UNLINK` 删除 |
| 热 Key 怎么处理 | 本地缓存、多副本读、逻辑过期、限流 |
| 为什么不用本地缓存 | 跨实例共享、集中失效、容量和一致性考虑 |
| 分布式锁安全吗 | 唯一值、过期、Lua 释放、业务幂等 |

## 自我检查

如果你的回答里没有以下内容，就还不完整：

- 具体 Key。
- 具体数据类型。
- TTL。
- 一致性策略。
- 异常降级。
- 监控指标。
- 方案缺点。
