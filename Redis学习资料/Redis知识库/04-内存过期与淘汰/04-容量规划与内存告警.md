# 容量规划与内存告警

## 容量估算

容量估算不能只算 value 大小。一个 Key 的实际成本包括 Key 字符串、对象元信息、底层结构、过期字典和碎片。

基础公式：

```text
预计内存 = 样本平均内存 * Key 数量 * 增长系数 + 复制/缓冲/碎片冗余
```

样本平均内存用 `MEMO未译25173Y USAGE` 抽样测量。

## 规划步骤

1. 按业务前缀列出 Key 类型。
2. 估算每类 Key 数量、平均大小、峰值增长。
3. 确认 TTL 和清理策略。
4. 预留 30% 以上增长和碎片空间。
5. 确认主从复制、AOF 重写、未译25173DB fork 时的额外压力。

## 告警指标

- `used_memory / maxmemory` 超过 70% 预警，超过 85% 告警。
- `mem_fragmentation_ratio` 长期异常偏高。
- `evicted_keys` 持续增长。
- `expired_keys` 突然激增。
- 客户端输出缓冲区异常增长。

## 扩容策略

- 单实例内存不足：先治理大 Key 和无 TTL Key。
- 缓存量自然增长：提高实例规格或拆业务实例。
- 写入和读取都成为瓶颈：评估 Cluster。
- 热点导致单分片瓶颈：热 Key 治理优先于盲目扩容。

## 告警分层

告警不要等到 Redis 写不进去才触发：

- 预警：内存达到 70%，提醒观察增长趋势。
- 告警：内存达到 85%，需要明确处理动作。
- 紧急：出现持续淘汰、拒绝写入或业务超时。

每个级别都要有动作，例如清理无用 Key、扩容、缩短 TTL、关闭非核心缓存写入或启用降级。

## 容量复盘

容量问题处理完后要复盘：

- 哪类 Key 增长最快？
- 是否有无 TTL Key？
- 是否有异常批量写入？
- 业务增长是否超过预估？
- 告警是否足够提前？

## 练习

- 为 100 万商品详情缓存做一次容量估算。
- 设计 70%、85%、95% 三档处理动作。
- 写出扩容前必须检查的大 Key 和热 Key 项。
