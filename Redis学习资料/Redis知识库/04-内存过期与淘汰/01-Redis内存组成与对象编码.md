# Redis 内存组成与对象编码

## 内存由什么组成

Redis 内存不只包含业务值，还包括 Key、对象头、字典、跳表、过期字典、客户端缓冲区、复制缓冲区、AOF/RDB 相关缓冲区和内存碎片。

常用观察：

```bash
INFO memory
MEMORY STATS
MEMORY USAGE key
OBJECT ENCODING key
```

## 对象编码

Redis 会根据数据规模选择底层编码。例如小 Hash、小 ZSet 可能使用紧凑编码，变大后会转换为更适合查询和更新的结构。编码变化会影响内存占用和性能。

观察示例：

```bash
HSET 用户:1 name Ada age 20
OBJECT ENCODING 用户:1
```

## 内存碎片

`mem_fragmentation_ratio` 表示 Redis 使用内存和分配器实际占用内存的比例。值过高可能说明碎片严重，也可能和系统内存、后台任务有关。

处理方式：

- 评估是否开启主动碎片整理。
- 减少大 Key 频繁创建和删除。
- 控制对象大小和生命周期。
- 在低峰期执行迁移或重启恢复碎片，但必须有高可用保障。

## 实践建议

- 估算容量时至少包含业务数据、Key 开销、复制缓冲和增长冗余。
- 不要用少量样本直接线性推断全部容量，先抽样不同类型 Key。
- 内存告警要早于 `maxmemory`，否则业务只会看到超时或写入失败。

## 为什么小对象也有成本

一个很短的值并不只占几个字节。Redis 还要保存 Key 字符串、对象头、字典项、过期信息和分配器开销。大量短 Key 可能比少量大 Value 更浪费元数据内存。

设计 Key 时要平衡可读性和长度。Key 名称要能排障，但不要把长文本、完整 JSON 或重复描述写进 Key。

## 编码变化的影响

小 Hash 或小 ZSet 可能使用紧凑编码，成员变多后会转换为普通哈希表或跳表。转换后内存会上升，但查询和更新更适合大规模数据。

这也是为什么容量估算不能只测少量小样本。要用接近生产规模的数据测试。

## 练习

- 创建一个小 Hash，查看 `OBJECT ENCODING`。
- 逐步增加字段数量，再观察编码变化。
- 对比短 Key 和长 Key 的 `MEMORY USAGE`。
