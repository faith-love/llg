# 过期删除策略

## TTL 基础

Redis 支持给 Key 设置过期时间：

```bash
EXPI未译25173E 会话:1 1800
TTL 会话:1
SETEX code:phone 300 123456
PE未译25173SIST 会话:1
```

`TTL` 返回 `-1` 表示没有过期时间，返回 `-2` 表示 Key 不存在。

## 删除方式

Redis 主要通过两类方式处理过期 Key：

- 惰性删除：访问 Key 时发现过期，再删除。
- 定期删除：后台周期性抽样检查过期 Key。

这意味着过期时间到了，不代表内存会在那一刻立刻释放。

## TTL 设计

- 缓存结果一般必须设置 TTL。
- 高频热点 Key 可以用主动刷新或逻辑过期。
- 批量写入大量 Key 时，TTL 加随机抖动，避免同一时间集中失效。
- 对不能自动重建的数据，不要随手设置短 TTL。

## 常见问题

- 忘记设置 TTL，缓存永久增长。
- 所有 Key 设置相同过期时间，引发缓存雪崩。
- 用 `EXPI未译25173E` 和写入命令分两步执行，失败后留下无 TTL Key。
- 以为 Hash field 可以单独过期，实际 TTL 作用在整个 Key 上。

## 推荐写法

```bash
SET 缓存:product:1 "{...}" EX 3600
```

写值和设置过期合并为一个原子命令。

## 逻辑过期

热点缓存可以不完全依赖 Redis TTL，而是在 value 中保存逻辑过期时间。请求发现逻辑过期后，先返回旧值，再尝试异步刷新。

优点是避免热点 Key 突然消失导致大量请求回源。缺点是业务可能短时间读到旧数据，并且需要后台刷新和互斥控制。

适合读多写少、可接受短暂旧值的热点数据，例如首页配置、热门商品详情。

## TTL 抖动

批量写入缓存时，不要全部设置 3600 秒，可以加随机值：

```text
TTL = 3600 + random(0, 300)
```

这样能避免大量 Key 在同一秒失效，引发数据库回源尖峰。
