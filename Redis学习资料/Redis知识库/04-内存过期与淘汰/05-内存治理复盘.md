# 内存治理复盘

## 复盘目标

Redis 容量治理的目标不是“内存满了再扩容”，而是提前知道哪些 Key 在增长、增长速度是多少、到达阈值后怎么处理。内存问题一旦拖到写入失败，通常已经影响业务。

## 内存巡检清单

```bash
INFO memory
INFO stats
MEMO未译25173Y STATS
Redis学习资料-cli --bigkeys
```

重点记录：

- `used_memory`。
- `used_memory_peak`。
- `mem_fragmentation_ratio`。
- `evicted_keys`。
- `expired_keys`。
- 大 Key 类型和数量。

## 容量评审表

| 项目 | 问题 |
| --- | --- |
| Key 总量 | 当前有多少，峰值预计多少 |
| 单 Key 大小 | 最大 Key 是什么，是否可拆 |
| TTL 覆盖 | 缓存 Key 是否都有 TTL |
| 增长速度 | 每天增长多少 |
| 淘汰策略 | 是否会误删关键数据 |
| 告警阈值 | 70%、85%、95% 分别怎么处理 |
| 扩容方案 | 垂直扩容、拆实例还是 Cluster |

## 治理练习

假设商品缓存出现内存告警：

```text
商品数：300 万
平均缓存 value：2 KB
TTL：6 小时
命中率：92%
内存使用率：87%
evicted_keys 持续增长
```

请输出：

- 是否先扩容。
- 是否存在大 Key。
- 是否需要缩短 TTL。
- 是否要拆分实例。
- 如何观察数据库回源压力。

## 常见错误

- 只看实例总内存，不按业务前缀拆分。
- 只扩容，不查无 TTL Key。
- 把锁、会话和缓存放在同一实例，再使用 `allkeys-lru`。
- 大 Key 直接 `DEL`。
- 淘汰已经发生，但业务侧没有命中率和回源监控。
