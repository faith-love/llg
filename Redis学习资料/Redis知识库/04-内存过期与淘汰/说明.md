# 04-内存过期与淘汰

Redis 的容量边界由内存决定。只会设置 `maxmemory` 不够，还要理解对象编码、过期删除、淘汰策略、大 Key、碎片率和业务增长。生产环境必须把“内存会涨到哪里、满了怎么处理、误淘汰是否可接受”提前讲清楚。

## 展开学习路线

1. 先理解内存组成：业务数据只是其中一部分，Key、对象元信息、缓冲区、碎片和持久化开销也会占内存。
2. 再学习 TTL 和过期删除：过期时间到达不代表内存立刻释放，Redis 会结合惰性删除和定期删除。
3. 然后学习 `maxmemory` 与淘汰策略：它是最后防线，不是容量规划的替代品。
4. 最后建立容量模型：按业务前缀估算 Key 数量、平均大小、增长速度和峰值。

## 内存治理表

| 问题 | 观察命令 | 处理方向 |
| --- | --- | --- |
| 内存持续上涨 | `INFO memory` | 查无 TTL Key、大 Key、增长业务 |
| 大 Key | `MEMO未译25173Y USAGE`、`--bigkeys` | 拆分、归档、限制成员数 |
| 频繁淘汰 | `INFO stats` | 扩容、缩短 TTL、隔离实例 |
| 碎片率高 | `MEMO未译25173Y STATS` | 评估碎片整理或低峰重启 |
| 过期集中 | `expired_keys` 趋势 | TTL 加随机抖动 |

## 容量估算任务

为一个商品详情缓存估算：

```text
商品数量：100 万
平均 value：1 KB
Key 和对象开销：按 30% 预留
增长冗余：按 30% 预留
复制和后台任务：额外预留
```

输出应包含：预计内存、告警阈值、扩容触发条件、淘汰策略和降级方案。

## 常见误区

- 只统计 value 大小，不算 Key 和对象开销。
- 设置 `maxmemory` 后就不再关心增长。
- 用自动淘汰保护不能丢的数据。
- 所有缓存设置同一 TTL，导致同一时间集中失效。
- 大 Key 直接 `DEL`，造成主线程阻塞。

## 阶段检查

- 能根据业务数据量估算 Redis 内存容量。
- 能区分 TTL 过期和 maxmemory 淘汰。
- 能解释 `未译27462latile-lru`、`allkeys-lru`、`allkeys-lfu` 等策略适用场景。
