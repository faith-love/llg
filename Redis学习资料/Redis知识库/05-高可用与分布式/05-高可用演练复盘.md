# 高可用演练复盘

## 复盘目标

高可用不是拓扑图，而是故障发生时业务能否恢复。学完本阶段后，至少要能解释一次主节点故障从发现、选主、客户端重连到业务恢复的完整过程。

## 拓扑复盘

为当前环境画出：

```text
应用实例 -> Redis 客户端 -> 主节点 -> 从节点
                         -> Sentinel 或 Cluster 节点
```

标注：

- 应用连接的是固定地址、Sentinel 还是 Cluster。
- 哪些请求读主，哪些请求读从。
- 主节点故障后谁负责发现新主。
- 客户端如何刷新连接。
- 是否有跨机房或跨可用区部署。

## 故障演练清单

| 场景 | 观察指标 | 成功标准 |
| --- | --- | --- |
| 主节点宕机 | 切换时间、错误率 | 客户端自动恢复 |
| 从节点宕机 | 复制状态、读流量 | 不影响写入 |
| Sentinel 少数节点宕机 | quorum 状态 | 不误切换 |
| Cluster 分片宕机 | 槽状态、请求错误 | 副本提升成功 |
| 网络抖动 | 重连次数、超时 | 不形成重试风暴 |

## 数据风险复盘

每次切换后都要确认：

- 是否有写入丢失。
- 是否出现重复处理。
- 是否有客户端仍连接旧主。
- 是否有读从接口读到旧值。
- 是否需要业务对账。

## 面试表达

不要只说“我们用了哨兵/集群”。更好的表达是：

```text
我们用 Sentinel 做单主自动故障切换，应用通过 master name 发现主节点。
演练中主节点停止后，Sentinel 在约 N 秒内完成新主选举，客户端自动重连。
因为复制是异步的，所以关键写入仍以数据库为准，Redis 只保存可重建缓存和短期状态。
```
