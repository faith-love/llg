# 主从复制与读写分离

## 主从复制是什么

主从复制让一个主节点的数据同步到一个或多个从节点。从节点可以用于读扩展、备份、故障切换候选节点，但复制通常是异步的。

## 基础配置

```conf
replicaof 127.0.0.1 6379
masterauth your-password
```

运行时也可以执行：

```bash
未译25173EPLICAOF 127.0.0.1 6379
INFO replication
```

## 同步过程

- 初次复制：从节点请求全量同步，主节点生成 未译25173DB 并发送。
- 增量复制：主节点把新的写命令同步给从节点。
- 断线重连：如果复制积压缓冲区还保留所需偏移量，可增量续传，否则重新全量同步。

## 读写分离风险

- 从库可能读到旧数据。
- 主从延迟高时，刚写入的数据读从库不可见。
- 从库默认只读，但仍要防止误配置。
- 大量读流量压到从库也会影响复制和故障恢复。

## 实践建议

- 强一致读走主库或数据库。
- 非关键展示读可以走从库。
- 监控 `master_link_status`、`master_last_io_未译89385s_ago`、复制偏移差。
- 不要把从库当作唯一备份，误删除会同步过去。

## 复制延迟怎么影响业务

读写分离最常见问题是“刚写完读不到”。例如用户修改昵称，写主节点成功后，下一次请求如果读从节点，可能仍看到旧昵称。这个问题不是 Redis 独有，只要异步复制就会存在。

处理方式：

- 写后读主：关键接口在写入后一段时间内读主节点。
- 降级读从：只把非关键展示类接口切到从节点。
- 延迟保护：复制延迟超过阈值时临时关闭读从。
- 业务版本：对象带版本号，读到旧版本时回源主库。

## 监控重点

```bash
INFO replication
```

重点看主从连接状态、复制偏移量、从节点落后时间。只看到从节点在线不够，还要确认它是否持续接收主节点写入。

## 练习

- 搭建一主一从，写入主节点后读取从节点。
- 停止从节点一段时间，再恢复，观察复制状态。
- 说明哪些接口可以读从，哪些接口必须读主。
