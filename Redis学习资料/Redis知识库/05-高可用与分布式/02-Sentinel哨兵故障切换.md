# Sentinel 哨兵故障切换

## Sentinel 解决什么

Sentinel 用于监控主从实例，在主节点故障时自动选举新的主节点，并通知客户端新的主节点地址。它适合不需要分片、但需要自动故障切换的场景。

## 基本职责

- 监控 Redis 主从节点是否存活。
- 多个 Sentinel 协商主节点是否客观下线。
- 选择一个从节点提升为新主。
- 让其他从节点复制新主。
- 向客户端暴露当前主节点信息。

## 关键概念

| 概念 | 含义 |
| --- | --- |
| 主观下线 | 单个 Sentinel 判断节点不可达 |
| 客观下线 | 多个 Sentinel 达成故障判断 |
| quorum | 判断客观下线需要的票数 |
| failover | 主从切换过程 |

## 注意点

- Sentinel 自身也要至少 3 个节点，避免单点判断。
- 客户端必须支持 Sentinel 发现主节点，否则切换后仍连旧地址。
- 切换期间可能短暂不可写。
- 异步复制下，故障主节点未同步的数据可能丢失。

## 演练清单

1. 关闭主节点。
2. 观察 Sentinel 日志和新主产生。
3. 检查客户端是否重新连接。
4. 恢复旧主，确认它成为新主的从节点。
5. 对比业务读写是否正常。

## 客户端接入方式

使用 Sentinel 时，应用不应该写死 Redis 主节点地址。客户端应配置 Sentinel 地址和 master name，由 Sentinel 返回当前主节点。

如果客户端不支持 Sentinel，故障切换后它可能仍然连接旧主节点，表现为持续写入失败或写到错误节点。

## 选主关注点

Sentinel 会根据从节点状态选择新主。优先考虑复制偏移更接近原主、优先级合适、连接状态正常的从节点。如果所有从节点都落后很多，切换后仍可能丢数据。

因此 Sentinel 不是强一致方案，它解决的是自动发现和切换，不解决异步复制的全部数据风险。

## 练习

- 配置 3 个 Sentinel 监控一个主从组。
- 停止主节点并记录切换耗时。
- 恢复旧主，观察它是否被重新配置为从节点。
- 写一段故障复盘：业务不可用多久，是否丢数据，客户端是否自动恢复。
