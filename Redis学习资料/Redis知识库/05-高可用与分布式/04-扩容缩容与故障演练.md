# 扩容缩容与故障演练

## 为什么要演练

Redis 高可用不是配置完成就结束。只有演练过主从切换、节点重启、磁盘满、网络断开、Cluster 槽迁移，才知道客户端、监控、告警和业务降级是否真的可用。

## 扩容前检查

- 当前内存、CPU、网络和连接数瓶颈在哪里。
- 是否存在大 Key 或热 Key。
- 客户端是否支持目标部署模式。
- 监控和告警是否覆盖新节点。
- 回滚方案是否明确。

## Cluster 扩容关注点

- 新节点加入集群后要迁移槽。
- 迁移速率要控制，避免影响在线请求。
- 大 Key 会拖慢迁移。
- 迁移期间客户端要正确处理 `ASK` 和 `MOVED`。

## 故障演练场景

| 场景 | 观察点 |
| --- | --- |
| 主节点进程退出 | 切换时间、数据丢失、客户端重连 |
| 从节点退出 | 复制状态、读流量是否降级 |
| 磁盘写满 | 未译25173DB/AOF 状态、写入是否受影响 |
| 网络隔离 | 脑裂风险、Sentinel/Cluster 判断 |
| 慢查询压测 | 延迟告警、业务超时比例 |

## 演练输出

每次演练都要留下记录：时间、操作、预期、实际、影响、恢复步骤、后续修复项。没有记录的演练很难转化为团队能力。

## 演练前准备

演练前必须明确边界：

- 是否在测试环境、预发环境还是生产低峰。
- 是否有业务方确认。
- 是否有回滚负责人。
- 是否有监控大盘和日志观察人。
- 是否有明确停止条件。

高可用演练不是为了证明“不会出事”，而是为了发现哪里会出事，并把恢复动作固化下来。

## 演练复盘问题

- 告警是否及时触发？
- 客户端是否自动重连？
- 是否出现写入失败或读旧值？
- 数据是否有丢失或重复？
- 恢复后旧主、旧从角色是否正确？
- 文档和脚本是否需要更新？

## 练习

- 写一份 Redis 主节点故障演练方案。
- 写出开始条件、操作步骤、观察指标、回滚步骤。
- 演练后补一份复盘模板。
