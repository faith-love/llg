# 05-高可用与分布式

Redis 从单机走向生产，需要解决复制、故障切换、读写分离、分片和扩容问题。主从复制提供副本，Sentinel 提供自动故障转移，Cluster 提供分片和横向扩展。每种方案都要同时考虑客户端支持、数据一致性和运维复杂度。

## 展开学习路线

1. 先从主从复制开始，理解全量同步、增量同步、复制偏移量和复制延迟。
2. 再学习 Sentinel，重点是主观下线、客观下线、选主、故障切换和客户端重新发现主节点。
3. 然后学习 Cluster，掌握 16384 槽、hash tag、跨槽限制、`MOVED` 和 `ASK`。
4. 最后做故障演练，把“理论上高可用”变成“客户端真的能恢复、业务真的能降级”。

## 架构选择表

| 模式 | 适合场景 | 主要风险 |
| --- | --- | --- |
| 单机 | 本地学习、小型非核心缓存 | 单点故障、容量有限 |
| 主从 | 读扩展、备份副本 | 主节点故障需要人工或外部切换 |
| Sentinel | 单主自动故障切换 | 切换期间短暂不可用，客户端要支持 |
| Cluster | 大容量、大吞吐、分片 | 运维复杂，跨槽命令受限 |
| 云托管 Redis | 降低运维成本 | 参数、版本、费用和故障行为受平台约束 |

## 演练任务

- 搭建一主两从，观察 `INFO replication`。
- 手动停止主节点，记录业务不可写时间。
- 使用 Sentinel 完成自动切换，确认客户端是否重连。
- 在 Cluster 中写入带 hash tag 的多 Key，验证是否落同槽。
- 迁移槽前先查大 Key，评估迁移风险。

## 常见误区

- 以为主从复制等于强一致。
- Sentinel 搭好了，但客户端仍写死主节点地址。
- Cluster 上直接使用跨槽多 Key 命令。
- 没有压测和演练就上线自动切换。
- 热 Key 问题用扩容解决，结果仍然压在单分片。

## 阶段检查

- 能画出单机、主从、哨兵、Cluster 的部署结构。
- 能说明故障切换时可能发生的短暂不可用和数据丢失。
- 能根据业务规模判断是否需要 Cluster，而不是过早分布式化。
