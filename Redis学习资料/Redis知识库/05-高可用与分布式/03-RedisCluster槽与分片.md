# Redis Cluster 槽与分片

## Cluster 解决什么

Redis Cluster 通过 16384 个 hash slot 把数据分布到多个主节点，每个主节点负责一部分槽。它解决单实例内存和吞吐上限问题，同时提供分片级高可用。

## 槽和 Key 的关系

Redis 根据 Key 计算 hash slot。同一个命令涉及多个 Key 时，这些 Key 通常必须在同一槽。可以使用 hash tag 控制槽位：

```text
cart:{用户:1001}:items
cart:{用户:1001}:coupon
```

花括号中的内容相同，两个 Key 会落到同一槽。

## 常见客户端行为

- 收到 `MOVED` 后刷新槽位映射。
- 收到 `ASK` 后临时访问迁移中的目标节点。
- 连接池通常按节点维护。
- 多 Key 命令在不同槽会失败。

## 适用场景

- 数据量超过单机可控内存。
- 读写吞吐超过单主节点能力。
- 业务能接受分布式运维复杂度。
- 客户端和监控系统都支持 Cluster。

## 风险

- 扩容、缩容、迁移比单机复杂。
- 大 Key 迁移会慢。
- 热 Key 仍会压垮单个分片。
- 跨槽事务和 Lua 脚本受限制。

## hash tag 使用边界

hash tag 能让多个 Key 落到同一个槽，解决部分多 Key 命令限制：

```text
order:{1001}:base
order:{1001}:items
order:{1001}:日志s
```

但不要滥用 hash tag。如果大量 Key 都使用同一个 tag，会把数据压到一个槽和一个分片，破坏分片均衡。

## Cluster 下的命令习惯

- 多 Key 命令要确认是否同槽。
- Lua 脚本涉及的 Key 也要在同一槽。
- 客户端要能自动处理 `MOVED` 和 `ASK`。
- 大 Key 会影响槽迁移速度。
