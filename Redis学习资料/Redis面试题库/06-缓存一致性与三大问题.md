# 缓存一致性与三大问题

## 高频问题

### 缓存和数据库如何保证一致性？

大多数业务使用最终一致。常见方案是先更新数据库，再删除缓存。删除失败要重试或通过消息补偿。缓存设置 TTL，避免长期不一致。

答题重点：

- 不轻易双写数据库和缓存。
- 删除缓存比更新缓存更常见。
- 失败补偿和 TTL 是兜底。
- 强一致场景不应只依赖缓存。

### 缓存穿透、击穿、雪崩分别是什么？

- 穿透：查询不存在的数据，缓存和数据库都没有。
- 击穿：热点 Key 过期，大量请求同时回源。
- 雪崩：大量 Key 同时失效或 Redis 故障，数据库压力暴涨。

治理：

- 穿透：空值缓存、参数校验、Bloom Filter。
- 击穿：互斥锁、逻辑过期、后台刷新。
- 雪崩：TTL 随机抖动、分批预热、限流降级。

## 常见追问

- 先删缓存还是先更新数据库？
- 延迟双删解决什么问题？
- 删除缓存失败怎么办？
- 热点 Key 如何逻辑过期？

## 项目表达

```text
商品更新时我们先更新数据库，提交成功后删除 Redis 缓存。删除失败会投递消息重试。缓存 TTL 加随机抖动，热点商品使用逻辑过期和后台刷新，避免击穿。
```

## 回答误区

- 说通过双写保证强一致，但不提失败处理。
- 只说三大问题定义，不说项目治理。
- 空值缓存 TTL 过长，导致真实数据创建后仍返回空。
