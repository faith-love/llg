## 使用方式

1. 先读场景，不急着看命令。
2. 再写出自己的 Key 设计和流程图。
3. 对照文档里的风险和监控项补全方案。
4. 最后用“练习任务”把案例改成自己的项目版本。

## 案例评审标准

- Key 命名清晰，能看出业务归属和对象 ID。
- 数据类型选择能解释理由。
- TTL、容量、过期和清理策略明确。
- 异常路径包含 Redis 不可用、数据库异常、并发冲突和重复请求。
- 监控指标能反映业务影响，而不只是 Redis 存活。
