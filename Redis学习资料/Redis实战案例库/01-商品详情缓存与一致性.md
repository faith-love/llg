# 商品详情缓存与一致性

## 场景

商品详情接口读多写少，用户访问频繁，数据库直接承载全部流量会增加压力。Redis 适合作为商品详情缓存，但必须处理缓存穿透、热点击穿、数据库和缓存不一致等问题。

## Key 设计

| 数据 | Key | 类型 | TTL |
| --- | --- | --- | --- |
| 商品详情 | `mall:product:{id}:detail` | String JSON | 30 分钟 + 随机抖动 |
| 空值缓存 | `mall:product:{id}:empty` | String | 2 分钟 |
| 热点重建锁 | `lock:mall:product:{id}:rebuild` | String | 10 秒 |

如果商品详情包含价格、库存、推荐等变化频率不同的数据，应拆成多个 Key，避免一个字段变化就删除整个缓存。

## 读流程

1. 根据商品 ID 查询 `mall:product:{id}:detail`。
2. 命中则返回。
3. 未命中先检查空值缓存。
4. 仍未命中则查数据库。
5. 数据库存在时写入详情缓存。
6. 数据库不存在时写入短 TTL 空值缓存。

## 写流程

商品更新时推荐：

1. 先更新数据库。
2. 数据库提交成功后删除缓存。
3. 删除失败时记录重试消息。
4. 必要时做延迟二次删除。

不要先更新缓存再更新数据库，否则数据库事务回滚后容易留下错误缓存。

## 风险与处理

- 缓存穿透：缓存空值，参数校验，必要时使用 Bloom Filter。
- 缓存击穿：热点商品使用逻辑过期或互斥锁重建。
- 缓存雪崩：TTL 加随机抖动，避免批量同秒过期。
- 一致性问题：删除缓存失败必须重试或异步补偿。
- 大 Value：详情字段过多时拆 Key。

## 监控指标

- 商品详情缓存命中率。
- 回源数据库次数。
- 空值缓存命中次数。
- 缓存重建耗时。
- 删除缓存失败次数。
- 热点商品访问 Top。

## 练习任务

为“商品详情 + 价格 + 库存展示 + 推荐商品”设计一套拆分缓存方案，写出每个 Key 的 TTL、更新策略和降级返回。
