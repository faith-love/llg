# 秒杀库存预扣与防超卖

## 场景

秒杀活动中，数据库很难直接承载瞬时高并发扣库存。Redis 可以保存活动库存并做原子预扣，但最终订单和库存事实仍应以数据库为准。

## Key 设计

| 数据 | Key | 类型 | TTL |
| --- | --- | --- | --- |
| 活动库存 | `seckill:stock:{activityId}:{skuId}` | String 计数器 | 活动结束后过期 |
| 用户购买标记 | `seckill:用户:{activityId}:{用户Id}` | String | 活动结束后过期 |
| 成功队列 | `stream:seckill:order` | Stream | 按消费能力保留 |

## 预扣流程

1. 校验活动时间和用户资格。
2. 使用 Lua 原子判断是否买过、库存是否大于 0。
3. 库存充足则扣减库存，写用户购买标记。
4. 写入下单事件流。
5. 后台消费者创建数据库订单。

## Lua 逻辑

脚本最小逻辑：

```text
如果用户已购买，返回重复购买
如果库存小于等于 0，返回售罄
库存减 1
写入用户购买标记
返回成功
```

不要把创建订单、调用支付、复杂风控都写进 Lua。

## 风险与处理

- Redis 预扣成功但订单创建失败：需要回补库存或进入失败补偿。
- 用户重复请求：购买标记必须先判断。
- 库存不一致：活动结束后和数据库对账。
- 热 Key：库存 Key 会成为热点，必要时分片库存。
- 恶意流量：入口限流和验证码不能省。

## 监控指标

- 预扣成功数。
- 售罄返回数。
- 重复购买拦截数。
- 下单事件积压。
- 订单创建失败数。
- Redis 脚本耗时。

## 练习任务

为 1000 件库存、每人限购 1 件的秒杀活动设计 Redis 预扣方案，写出 Key、Lua 逻辑、失败补偿和对账流程。
