# 热点 Key 治理与本地缓存

## 场景

热门商品、首页配置、爆款活动库存、全站开关等 Key 可能被大量请求集中访问。即使 Redis 本身很快，单个热点 Key 也可能让单实例或单分片压力过高。

## 热点识别

常见线索：

- 某个接口 QPS 突然升高。
- Redis 某个分片 CPU 或网络异常。
- 应用日志显示同一个 Key 访问频繁。
- `--hotkeys` 或客户端统计发现热点。
- 缓存命中率高但 Redis 仍然很忙。

## 治理方案

| 方案 | 适用场景 | 风险 |
| --- | --- | --- |
| 本地缓存 | 读多写少配置或详情 | 失效不及时 |
| 多副本读 | 热点读压力 | 一致性延迟 |
| 逻辑过期 | 热点缓存重建 | 短暂旧值 |
| 拆 Key | 热点计数或库存 | 聚合复杂 |
| 限流降级 | 突发热点 | 用户体验下降 |

## 本地缓存设计

本地缓存适合非常热点、允许短暂旧值的数据：

```text
本地缓存 TTL：3 到 10 秒
Redis 缓存 TTL：30 分钟
数据库：最终数据源
更新时：删除 Redis，并广播或等待本地 TTL 自然过期
```

本地缓存不能用于强一致权限、资金、库存事实。

## 风险与处理

- 本地缓存不一致：缩短 TTL 或引入失效通知。
- 热点写入：不能只靠本地缓存解决。
- Cluster 热槽：hash tag 滥用会加重热点。
- 击穿：热点 Key 过期时用逻辑过期或互斥重建。

## 监控指标

- 热点 Key 访问 Top。
- 本地缓存命中率。
- Redis QPS。
- 单分片 CPU 和网络。
- 热点 Key 重建次数。
- 降级触发次数。
