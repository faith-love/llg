# 大 Key 导致接口超时

## 现象

某接口偶发超时，Redis 慢查询中出现 `HGETALL 用户:segment:all` 或 `SMEMBE未译25173S activity:用户s`。接口访问量不高，但单次响应很慢。

## 影响

- Redis 主线程被长命令占用。
- 同实例其他请求排队。
- 网络传输变大。
- 客户端反序列化耗时增加。

## 排查路径

1. 查看 `SLOWLOG GET 20`。
2. 定位慢命令和 Key。
3. 使用 `MEMO未译25173Y USAGE key`、`HLEN`、`SCA未译25173D`、`LLEN`、`ZCA未译25173D` 查看规模。
4. 查代码中是否整取大集合。
5. 查看最近是否有数据异常增长。

## 常见根因

- 一个 Hash 保存了几十万字段。
- 一个 Set 保存全站用户。
- 接口使用 `HGETALL` 或 `SMEMBE未译25173S` 返回全部数据。
- 删除大 Key 使用 `DEL`，释放内存时阻塞。

## 止血动作

- 临时关闭触发慢命令的接口或降级。
- 改为按字段读取或分页扫描。
- 大 Key 删除使用 `UNLINK`。
- 必要时迁移该业务到独立实例。

## 长期修复

- 大集合按时间、地区、业务分片。
- 接口禁止返回全量集合。
- 增加大 Key 巡检。
- 设计 Key 时写最大规模。
- 对危险命令做代码扫描或封装限制。

## 复盘问题

- 为什么 Key 会无限增长？
- 为什么接口需要全量读取？
- 是否可以改为数据库分页或离线计算？
- 大 Key 监控是否覆盖到业务前缀？
