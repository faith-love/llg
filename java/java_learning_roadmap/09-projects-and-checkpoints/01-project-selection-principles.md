# 01-项目选择原则

## 项目选择解决什么问题

很多小白选项目时容易犯两个错：

- 项目太小，只能展示 CRUD。
- 项目太大，做一半烂尾。

合适的项目应该刚好能覆盖你当前阶段的核心能力，并且能完整交付。

## 好项目的标准

| 标准 | 说明 |
| --- | --- |
| 业务清楚 | 能一句话说清项目解决什么问题 |
| 范围可控 | 2-6 周能做出可演示版本 |
| 后端能力完整 | 有接口、数据库、事务、校验、异常、测试 |
| 有难点 | 至少 2-3 个能讲清楚的技术点 |
| 可复盘 | 能说明问题、方案、取舍和结果 |

## 不推荐的项目

- 只有静态页面，没有后端能力。
- 只做增删改查，没有业务规则。
- 一上来做商城、社交、网约车全量系统。
- 完全照抄视频，没有自己的设计和复盘。
- 只堆技术名词，例如 Redis、MQ、微服务都加一点但说不清为什么。

## 项目难度分层

| 阶段 | 推荐项目 | 主要训练 |
| --- | --- | --- |
| 基础阶段 | 命令行图书管理 | 类设计、集合、IO、异常 |
| Web 入门 | 图书馆 REST API | 接口、数据库、事务、鉴权 |
| 综合阶段 | 博客系统 | 内容模型、搜索、缓存、文件上传 |
| 进阶阶段 | 订单系统简化版 | 并发、幂等、状态机、异步 |

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| 范围控制 | 防止项目烂尾 | 小白容易贪大 | 先做 MVP | 重点是完整交付 |
| 技术匹配 | 用项目训练对应能力 | 技术乱加会失焦 | 每个技术回答“为什么” | 难点是克制 |
| 业务规则 | 让项目不只是 CRUD | 面试能讲真实问题 | 加库存、状态、权限等规则 | 重点是规则可验证 |
| 复盘价值 | 把项目变成能力证明 | 只写代码不等于会做项目 | 记录问题和取舍 | 重点是讲清思考 |

## 本节练习

- 给自己选 2 个候选项目。
- 写出每个项目训练哪些能力。
- 删掉暂时不需要的高级功能。
- 写出项目 MVP 范围。

## 本节通过标准

- 能解释为什么选这个项目。
- 能说明项目覆盖哪些 Java 后端能力。
- 能控制项目范围。
- 能避免只堆技术名词。
