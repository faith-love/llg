# 07-表设计和范式/反范式

## 表设计先看业务

不要一上来就建很多表。先问：

- 业务对象有哪些？
- 对象之间是什么关系？
- 哪些字段必填？
- 哪些字段唯一？
- 最常见查询是什么？
- 数据会不会增长很快？

## 范式

范式的目标是减少重复数据和更新异常。

简单理解：

- 一张表只描述一个主题。
- 字段只保存原子值。
- 重复信息尽量拆出去。

例如分类名不应该在每本书里重复存很多遍，可以拆成 `categories` 表。

## 反范式

有时为了查询性能，会冗余一些字段。

例如借阅记录里冗余图书标题：

```text
borrow_records.book_title
```

好处：历史记录显示不受图书改名影响。

代价：数据可能重复，需要明确更新策略。

## 一对多

一个分类有多本书：

```text
categories 1 -> N books
```

在多的一方保存外键：

```text
books.category_id
```

## 多对多

一本书可以有多个标签，一个标签可以属于多本书：

```text
books N -> N tags
```

通常用中间表：

```text
book_tags(book_id, tag_id)
```

## 知识点深挖

| 知识点 | 作用 | 痛点或优点 | 技巧 | 难点和重点 |
| --- | --- | --- | --- | --- |
| 范式 | 减少重复和更新异常 | 数据更一致 | 先按主题拆表 | 重点是别把所有字段堆一张表 |
| 反范式 | 提升查询或保留历史快照 | 读更方便，但有冗余 | 明确冗余字段更新策略 | 难点是性能和一致性取舍 |
| 一对多 | 表达主从关系 | 常见业务关系 | 外键放在多的一方 | 重点是关系方向 |
| 多对多 | 表达互相关联 | 不能简单互塞字段 | 用中间表 | 重点是中间表也可以有业务字段 |
| 查询驱动设计 | 表结构服务查询 | 纯理论设计可能难用 | 结合高频查询验证设计 | 重点是业务和查询一起看 |
