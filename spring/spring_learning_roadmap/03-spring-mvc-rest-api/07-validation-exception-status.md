# 07-校验、异常和状态码分工

## 三件事不要混

接口失败时，最常见的三类问题是：

- 参数格式不对。
- 业务规则不满足。
- 系统内部异常。

如果这三类问题都返回一样的结构、一样的状态码，调用方就很难处理。

## 参数校验

适合放在 DTO 和请求入口：

- 必填。
- 长度。
- 格式。
- 数值范围。

典型状态码通常是 `400`。

## 业务异常

适合放在 Service：

- 图书不存在。
- 图书状态不允许借出。
- 用户已超出借阅上限。

常见状态码：

- `404`
- `409`
- 部分场景下 `403`

## 系统异常

系统异常不是业务分支。

例如：

- 空指针。
- 数据库连接失败。
- 第三方接口超时。

这类错误通常要返回统一的兜底错误结构，状态码常见为 `500`。

## 设计原则

- 参数校验失败，不要伪装成业务失败。
- 业务失败，不要全都打成 `500`。
- 系统异常，不要吞掉再返回假成功。

## 本节通过标准

- 能区分参数校验、业务异常、系统异常。
- 能给不同失败路径设计合理状态码。
- 能保持错误结构一致而语义不混乱。
