# 01-请求处理主线

## 请求是怎么进来的

Spring MVC 请求处理可以先按一条主线理解：

```text
HTTP 请求 -> Web 容器 -> DispatcherServlet -> HandlerMapping -> Controller 方法
-> Service -> 返回值处理器 -> HTTP 响应
```

真实实现更复杂，但先掌握这条主线，排查问题时才知道往哪里看。

## DispatcherServlet 的位置

DispatcherServlet 是 Spring MVC 的前端控制器。

它负责：

- 接收请求。
- 查找哪个 Controller 方法处理这个请求。
- 调用参数解析器完成参数绑定。
- 调用返回值处理器构造响应。
- 把异常交给异常解析器。

可以把它理解为 MVC 请求的总调度中心。

## 找到目标方法

请求进入后，Spring 会通过 HandlerMapping 找到匹配的处理器方法。

常见映射：

- `@GetMapping`
- `@PostMapping`
- `@PutMapping`
- `@PatchMapping`
- `@DeleteMapping`

如果请求返回 404，先不要猜业务问题，先确认路由是否匹配到了方法。

## 参数绑定

找到方法后，Spring 会根据参数类型和注解完成绑定。

例如：

- `@PathVariable`：路径参数。
- `@RequestParam`：查询参数。
- `@RequestBody`：请求体。
- `@RequestHeader`：请求头。

绑定失败时，问题通常出在参数名、类型、格式或 JSON 结构上。

## 返回值处理

Controller 返回值不会直接原样发回浏览器。Spring 会通过返回值处理器和消息转换器，把对象转换成 JSON、文本、文件流等响应。

最常见的是：

- Java 对象 -> JSON。
- 字符串 -> 文本响应。
- `ResponseEntity` -> 带状态码和响应头的响应。

## 异常处理

请求过程中任意一步出错，都可能进入异常处理器。

常见失败点：

- 路由不匹配。
- 参数绑定失败。
- 参数校验失败。
- 业务异常。
- 系统异常。

统一异常处理的价值在于：前端不用猜每个接口失败时会返回什么形状。

## 本节练习

1. 给一个最小接口打断点。
2. 观察请求进入 Controller 前后的调用过程。
3. 故意传错路径、参数类型和请求体格式。
4. 记录 404、400、500 分别在什么环节产生。

## 本节通过标准

- 能用自己的话画出请求处理主线。
- 能说出 DispatcherServlet 的职责。
- 能判断一个问题更像是路由、绑定、业务还是返回值处理问题。
