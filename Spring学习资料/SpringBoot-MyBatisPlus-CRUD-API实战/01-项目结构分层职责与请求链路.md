# 项目结构、分层职责与请求链路

这一节先不急着写代码，先理解一个后端 CRUD API 项目为什么要拆这么多文件。小白最容易把所有代码都写在 Controller 里，短期能跑，后期会非常难维护。

## 标准请求链路

一次“新增用户”请求大概这样走：

```text
浏览器或前端页面
  -> POST /api/users
  -> UserController.create()
  -> UserService.createUser()
  -> UserServiceImpl.createUser()
  -> UserMapper.insert()
  -> MyBatis-Plus
  -> MySQL users 表
```

返回时反过来：

```text
MySQL users 表
  -> UserDO
  -> UserResponse
  -> ApiResponse<UserResponse>
  -> JSON
  -> 前端
```

这里最重要的点：数据库对象 `UserDO` 不直接返回给前端，前端响应对象用 `UserResponse`。

## 每层职责

| 层 | 典型文件 | 主要职责 |
| --- | --- | --- |
| 启动层 | `CrudDemoApplication.java` | 启动 Spring Boot，扫描 Mapper |
| 配置层 | `MybatisPlusConfig.java` | 配置 MyBatis-Plus 插件，比如分页 |
| 通用层 | `ApiResponse.java`、`GlobalExceptionHandler.java` | 统一响应和异常格式 |
| Controller | `UserController.java` | 暴露 HTTP API，接收参数，返回结果 |
| DTO | `UserCreateRequest.java`、`UserResponse.java` | 请求入参和响应出参 |
| Converter | `UserConverter.java` | DTO 和 Entity 互相转换 |
| Entity | `UserDO.java` | Java 对象和数据库表字段映射 |
| Mapper | `UserMapper.java` | 调用数据库，继承 MyBatis-Plus `BaseMapper` |
| Service | `UserService.java` | 定义业务能力 |
| ServiceImpl | `UserServiceImpl.java` | 实现业务规则、事务和数据库调用 |

## 为什么不要 Controller 直接调 Mapper

看起来最短的写法是：

```java
// 不推荐：Controller 直接调用 Mapper
@PostMapping
public UserDO create(@RequestBody UserDO user) {
    userMapper.insert(user);
    return user;
}
```

问题：

- HTTP 入参和数据库对象混在一起，前端可以传数据库内部字段。
- 没有业务层，后续加事务、校验、权限会很乱。
- Controller 会越来越胖，测试也困难。
- 数据库字段变更会直接影响接口响应。

推荐链路：

```text
Controller
  -> 接收 UserCreateRequest
  -> 调用 UserService
  -> 返回 UserResponse
```

## 推荐包结构

```text
com.example.crud
  common
  config
  user
    controller
    converter
    dto
    entity
    mapper
    service
      impl
```

说明：

- `common` 放全局通用能力。
- `config` 放框架配置。
- `user` 是一个业务模块，用户相关代码都放里面。
- 每个业务模块内部再分 controller、dto、entity、mapper、service。

## 请求对象和数据库对象的区别

新增用户请求只需要：

```json
{
  "username": "ada",
  "nickname": "Ada Lovelace",
  "email": "ada@example.com"
}
```

但数据库表里可能还有：

```text
id
status
deleted
created_at
updated_at
```

这些字段不应该都让前端传。比如：

- `id` 由数据库生成。
- `status` 可以由后端默认设置。
- `deleted` 是逻辑删除字段，不能让前端控制。
- `created_at`、`updated_at` 由后端自动填充。

所以要拆：

- `UserCreateRequest`：前端能传什么。
- `UserDO`：数据库实际存什么。
- `UserResponse`：接口返回什么。

## 本专题采用的命名

| 后缀 | 含义 |
| --- | --- |
| `DO` | Data Object，数据库表对象 |
| `Request` | 接口请求参数 |
| `Response` | 接口返回数据 |
| `Mapper` | 数据库访问接口 |
| `Service` | 业务接口 |
| `ServiceImpl` | 业务实现 |
