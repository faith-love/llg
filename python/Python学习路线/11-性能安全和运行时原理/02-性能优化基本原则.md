# 性能优化基本原则

性能优化的第一原则是：不要猜。先测量，再定位，再修改，最后验证。没有基准数据的优化很容易把代码改复杂，却没有解决真正瓶颈。

## 性能优化流程

推荐流程：

1. 描述现象。
2. 建立可复现输入。
3. 记录基准数据。
4. 使用工具定位瓶颈。
5. 提出最小修改方案。
6. 修改并验证。
7. 对比优化前后。
8. 记录副作用和取舍。

## 先定义目标

不要只说“太慢”。要具体：

- 处理 10 万行 CSV 从 60 秒降到 10 秒以内。
- API P95 从 800ms 降到 300ms。
- 内存峰值从 2GB 降到 500MB。
- 批处理任务在 30 分钟内完成。

目标必须可测量。

## 控制变量

基准测试时保持：

- 同一台机器。
- 同一 Python 版本。
- 同一输入数据。
- 同一依赖版本。
- 同一环境变量。
- 尽量减少后台干扰。

否则数据不可比较。

## 找最大瓶颈

优先优化：

- 占总耗时最多的函数。
- 调用次数极高的函数。
- 内存增长最快的路径。
- 外部 IO 等待最多的环节。

不要先优化只占 1% 的代码。

## 性能维度

常见维度：

- 响应时间。
- 吞吐量。
- CPU 使用率。
- 内存峰值。
- IO 等待。
- 数据库查询次数。
- 网络请求次数。
- 启动时间。

不同场景关注不同指标。

## 读写权衡

常见取舍：

- 用缓存换速度，但增加一致性风险。
- 用内存换 IO，但增加内存占用。
- 用并发换吞吐，但增加复杂度。
- 用预计算换查询速度，但增加更新成本。

必须记录取舍。

## 可读性边界

如果优化让代码难懂，要问：

- 性能收益是否显著？
- 是否有测试保护？
- 是否有注释解释原因？
- 是否可以局部封装？
- 是否有更简单方案？

微小收益不值得大幅牺牲可读性。

## 常见错误

### 凭感觉改代码

没有 profile，可能优化错地方。

### 只跑一次测试

性能数据有波动，要多次运行。

### 用小数据推断大数据

小数据下看不出算法复杂度问题。

### 忽略外部系统

慢可能在数据库、网络、磁盘，不一定在 Python 代码。

## 练习

1. 给一个慢脚本写现象描述。
2. 准备固定输入数据。
3. 记录优化前耗时。
4. 多次运行取平均或中位数。
5. 写一份优化目标。
6. 用 profile 找热点。
7. 修改一个热点并对比。
8. 记录优化副作用。

## 验收标准

- 能说清性能优化流程。
- 能建立可复现基准。
- 能用数据证明优化有效。
- 能记录性能和可读性取舍。
