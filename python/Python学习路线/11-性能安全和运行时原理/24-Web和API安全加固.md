# Web和API安全加固

Web/API 安全需要覆盖认证、授权、输入、CORS、CSRF、XSS、限流、错误响应、审计日志和部署配置。任何一个环节放松都可能造成风险。

## 认证和授权

认证：

- 你是谁。

授权：

- 你能做什么。

必须检查：

- token 是否有效。
- token 是否过期。
- 用户是否有权限。
- 资源是否属于该用户。

## 越权

常见：

```text
GET /orders/100
```

用户把 100 改成 101，访问别人订单。

防护：

- 查询时带上当前用户条件。
- service 层检查资源归属。
- 管理员权限单独判断。

## CORS

生产环境：

- 明确允许来源。
- 不随意 `*`。
- 带凭证时更要收紧。

CORS 不是认证授权。

## CSRF

如果使用 Cookie 认证，浏览器可能自动携带 Cookie，需关注 CSRF。

防护：

- SameSite Cookie。
- CSRF token。
- 避免 GET 修改状态。
- 检查 Origin/Referer。

如果使用 Authorization Bearer 且不自动携带，CSRF 风险模型不同。

## XSS

API 返回的数据如果被前端直接渲染为 HTML，可能造成 XSS。

后端要：

- 不存储危险 HTML，或明确转义策略。
- 设置合理 Content-Type。
- 不返回未清理的用户输入作为 HTML。

前端也要做输出编码。

## 限流

需要限制：

- 登录尝试。
- 短信验证码。
- 文件上传。
- 搜索接口。
- 高成本导出接口。

限流不是为了性能，也是为了安全。

## 错误响应

不要泄露：

- 堆栈。
- SQL。
- 文件路径。
- token。
- 内部服务地址。

返回统一错误码和 request_id。

## 审计日志

记录：

- 登录成功/失败。
- 权限拒绝。
- 关键数据修改。
- 删除操作。
- 管理员操作。
- 文件下载。

日志要脱敏。

## 常见错误

### 只在前端做权限

后端必须校验。

### GET 接口修改状态

可能被预取或 CSRF 利用。

### CORS 全放开

生产风险高。

### 错误响应泄露内部细节

攻击者可利用这些信息。

## 练习

1. 为资源详情接口增加归属检查。
2. 区分 401 和 403。
3. 设计登录限流规则。
4. 检查 CORS 配置。
5. 设计 Cookie SameSite 策略。
6. 统一错误响应。
7. 给关键操作增加审计日志。
8. 写 Web API 安全加固清单。

## 验收标准

- 能识别越权、CSRF、XSS、CORS 风险。
- 能设计认证授权和资源归属检查。
- 能为高风险接口加限流和审计。
- 能避免错误响应泄露内部信息。
