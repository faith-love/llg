# 依赖和供应链安全

Python 项目通常依赖大量第三方包。依赖能提高效率，也带来供应链风险：漏洞、恶意包、拼写相似包、维护停止、许可证冲突和版本漂移。

## 依赖固定

应用项目应固定可复现依赖：

- lock 文件。
- 精确版本。
- CI 使用同一安装方式。

不固定依赖会导致不同时间安装得到不同代码。

## 漏洞扫描

常见方向：

- 检查已知 CVE。
- 检查过期包。
- 检查依赖树。

工具会变化，原则是把依赖安全检查纳入流程，而不是上线前手动看一眼。

## typosquatting

拼写相似恶意包：

```text
requests
reqeusts
```

安装前检查包名、下载来源、维护者和文档。

## 依赖来源

风险来源：

- 未知镜像源。
- 直接从 URL 安装。
- Git 分支安装。
- 私有包权限不清。

生产依赖来源要可追踪。

## 许可证

商业项目要关注许可证：

- MIT。
- Apache-2.0。
- BSD。
- GPL。
- LGPL。

许可证不合规也是交付风险。

## 维护状态

检查：

- 是否长期无更新。
- issue 是否无人处理。
- 是否支持当前 Python 版本。
- 是否有替代品。

## 最小依赖原则

不要为一个很小功能引入大型依赖。

问：

- 标准库是否足够？
- 依赖是否活跃？
- 是否增加安全面？
- 是否影响镜像大小？

## 常见错误

### 随手 pip install

不记录依赖来源和版本。

### 不提交 lock

应用项目可复现性差。

### 忽略传递依赖

漏洞可能来自间接依赖。

### 使用拼错包名

可能安装恶意包。

## 练习

1. 列出项目直接依赖。
2. 列出间接依赖。
3. 检查依赖是否固定。
4. 检查包名是否来自可信来源。
5. 检查许可证。
6. 检查维护状态。
7. 删除一个不必要依赖。
8. 写依赖安全检查清单。

## 验收标准

- 能解释供应链风险。
- 能固定和审查依赖。
- 能识别拼写相似包风险。
- 能把依赖安全纳入 CI 或发布流程。
