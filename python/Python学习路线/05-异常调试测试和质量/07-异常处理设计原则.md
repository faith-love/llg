# 异常处理设计原则

异常处理的目标不是消灭报错，而是让错误被合适的位置发现、表达、记录和处理。好的异常处理应该保留上下文，不隐藏问题。

## 原则一：只捕获能处理的异常

如果当前层不知道怎么处理，就不要捕获。

不推荐：

```python
try:
    save_order(order)
except Exception:
    pass
```

推荐：

```python
save_order(order)
```

让上层处理。

## 原则二：捕获要具体

不推荐：

```python
except Exception:
    print("失败")
```

推荐：

```python
except FileNotFoundError:
    print("文件不存在")
except PermissionError:
    print("没有权限")
```

## 原则三：保留原始异常

包装异常时使用 `raise from`。

```python
except ValueError as error:
    raise ConfigError("配置格式错误") from error
```

## 原则四：不要吞异常

危险写法：

```python
except Exception:
    pass
```

如果必须忽略，写明原因，并尽量捕获具体异常：

```python
try:
    path.unlink()
except FileNotFoundError:
    pass  # 文件已经不存在，目标状态已满足
```

## 原则五：入口层统一友好提示

命令行入口可以统一捕获业务异常：

```python
def main():
    try:
        run()
    except AppError as error:
        print(f"错误：{error}")
        return 1
    return 0
```

底层保持异常，上层负责展示。

## 原则六：日志记录要有上下文

```python
logger.exception("保存订单失败，order_id=%s", order_id)
```

不要只写：

```python
logger.error("失败")
```

## 原则七：不要在库函数里直接 print

库函数应该抛异常或返回结果，由调用方决定如何展示。

## 原则八：异常信息不要泄露敏感数据

不要把密码、token、身份证号、完整密钥写进异常或日志。

## 常见错误

### 捕获后返回 None

```python
try:
    return parse(data)
except ValueError:
    return None
```

如果调用方无法区分“本来就是 None”和“解析失败”，会制造新问题。

### 过度包装异常

每一层都包装一次，traceback 会很长。只在边界变化时包装。

### 用异常做正常分支

高频正常逻辑优先用条件判断。

## 练习

1. 把 `except Exception: pass` 改成具体处理。
2. 给包装异常加 `raise from`。
3. 设计一个入口层统一处理 `AppError`。
4. 删除库函数里的 `print`。
5. 给日志补充上下文。
6. 检查异常信息是否包含敏感数据。

## 验收标准

- 能说明在哪里捕获异常。
- 能避免吞异常。
- 能保留异常链。
- 能区分底层抛出和入口展示。
- 能写有上下文且不泄露敏感信息的错误信息。
