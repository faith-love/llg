# 数据库设计和范式反范式

数据库设计决定了后续查询、维护、扩展和数据质量的难度。好的表设计不是字段堆砌，而是清晰表达实体、关系、约束和变化边界。

## 设计步骤

推荐顺序：

1. 找实体。
2. 找关系。
3. 定字段。
4. 定主键。
5. 定外键。
6. 定约束。
7. 定索引。
8. 定审计字段。
9. 写数据字典。

## 实体

实体是业务中需要长期保存的信息对象。

例如电商系统：

- 用户。
- 商品。
- 订单。
- 订单明细。
- 支付记录。
- 退款记录。

每个实体通常对应一张表。

## 字段设计

字段要回答：

- 字段含义是什么？
- 数据类型是什么？
- 是否必填？
- 默认值是什么？
- 是否唯一？
- 是否可变？
- 是否需要索引？
- 是否来自外部系统？

## 审计字段

常见审计字段：

- `created_at`
- `updated_at`
- `deleted_at`
- `created_by`
- `updated_by`

学习阶段至少保留 `created_at` 和 `updated_at`。

## 状态字段

状态字段要有枚举范围。

示例：

```text
pending
paid
cancelled
refunded
```

不要让状态值自由输入。

## 范式

范式关注减少重复和更新异常。

简单理解：

- 一个字段只表达一个含义。
- 重复数据拆出去。
- 非主键字段依赖主键。
- 多对多用中间表。

## 反范式

为了性能或报表，可以冗余字段。

例如订单表保存：

- 用户下单时昵称快照。
- 订单总金额。
- 商品数量。

但必须说明：

- 冗余字段来源。
- 何时更新。
- 如何校验一致性。

## 数据字典

示例：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | INTEGER | 是 | 主键 |
| email | TEXT | 是 | 用户邮箱，唯一 |
| status | TEXT | 是 | 用户状态 |

数据字典能让代码、SQL 和业务理解一致。

## 常见错误

### 字段名含义模糊

例如 `type`、`flag`、`data`，后续难维护。

### 状态值没有约束

同一个状态可能出现 `paid`、`PAID`、`已支付`。

### 金额使用浮点类型

金额应使用数据库 decimal/numeric 类型或整数分。

### 没有唯一约束

代码层去重不可靠，数据库也要守住唯一性。

## 练习

1. 设计用户表。
2. 设计商品表。
3. 设计订单表。
4. 设计订单明细表。
5. 给每张表写数据字典。
6. 标出主键和外键。
7. 设计订单状态枚举。
8. 说明哪些字段需要索引。
9. 说明一个反范式字段的同步规则。

## 验收标准

- 能按实体和关系设计表。
- 能写数据字典。
- 能说明范式和反范式取舍。
- 能设计约束和索引。
