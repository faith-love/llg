# 代码格式化和导入整理

代码格式化的目标不是争论风格，而是让团队不用在缩进、换行、引号、导入顺序上浪费时间。格式统一后，代码评审可以更聚焦业务逻辑。

## 格式化工具

常见：

- black。
- ruff format。

二者都可以自动格式化代码。项目中选择一种主格式化工具即可。

## black

运行：

```powershell
black src tests
```

检查但不修改：

```powershell
black --check src tests
```

## ruff format

运行：

```powershell
ruff format src tests
```

检查：

```powershell
ruff format --check src tests
```

## 行宽

常见行宽：

- 88。
- 100。
- 120。

项目统一即可，不要每个工具配置不同。

示例：

```toml
[tool.ruff]
line-length = 100
```

## 导入整理

导入通常按顺序：

1. 标准库。
2. 第三方库。
3. 本项目模块。

示例：

```python
from pathlib import Path

import requests

from my_project.config import Settings
```

## isort 和 ruff

可以使用 isort，也可以用 ruff 的导入整理规则。

重点不是工具名字，而是：

- 规则统一。
- 本地和 CI 一致。
- 自动修复优先。

## 格式化和 lint 的边界

格式化：

- 代码排版。
- 换行。
- 空格。
- 引号风格。

lint：

- 未使用变量。
- 未使用导入。
- 可疑代码。
- 复杂度。
- 规则违规。

## 常见错误

### 手动争论格式

把格式交给工具。

### 本地格式化和 CI 配置不同

会出现本地过、CI 失败。

### 多个格式化工具互相打架

比如 black 和另一个工具对同一段代码反复改格式。要固定主工具。

### 只检查不自动修复

本地开发时优先自动修复，CI 再 check。

## 练习

1. 给项目配置 ruff format 或 black。
2. 格式化 `src` 和 `tests`。
3. 在 CI 中使用 `--check`。
4. 配置统一 line-length。
5. 整理导入顺序。
6. 删除未使用导入。
7. 记录格式化前后的 diff。

## 验收标准

- 能配置并运行格式化工具。
- 能统一行宽和导入顺序。
- 能区分 format 和 lint。
- 能保证本地和 CI 使用同一规则。
