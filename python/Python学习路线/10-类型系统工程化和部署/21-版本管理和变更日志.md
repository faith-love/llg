# 版本管理和变更日志

版本号和变更日志用于告诉使用者“这次发布了什么，是否兼容，是否需要调整”。没有版本管理，项目交付会变成猜谜。

## SemVer

语义化版本：

```text
MAJOR.MINOR.PATCH
```

例如：

```text
1.4.2
```

含义：

- MAJOR：不兼容变更。
- MINOR：向后兼容的新功能。
- PATCH：向后兼容的 bug 修复。

## 0.x 版本

`0.x` 通常表示 API 还不稳定。即便如此，也要记录破坏性变更。

## 版本号位置

可能在：

- `pyproject.toml`。
- 包内 `__version__`。
- Git tag。

要避免多个位置不一致。学习阶段可以先以 `pyproject.toml` 为准。

## CHANGELOG

示例：

```markdown
# Changelog

## 0.2.0

### Added

- 增加 CSV 导出。

### Fixed

- 修复空文件处理错误。
```

常见分类：

- Added。
- Changed。
- Deprecated。
- Removed。
- Fixed。
- Security。

## 破坏性变更

例如：

- 删除公共函数。
- 改函数参数。
- 改返回值结构。
- 改错误码。
- 提高最低 Python 版本。

必须明确记录。

## Git tag

发布版本常用 tag：

```powershell
git tag v0.1.0
```

当前任务没有要求提交或打 tag，学习阶段只需理解流程。

## 常见错误

### 版本号不变但内容变了

调用方无法区分版本。

### changelog 只写“更新”

没有实际信息。

### 不记录破坏性变更

调用方升级会踩坑。

### 多处版本号不一致

自动化发布容易出错。

## 练习

1. 给项目设置 `0.1.0`。
2. 写第一个 CHANGELOG。
3. 为 bug 修复设计 PATCH 版本。
4. 为新功能设计 MINOR 版本。
5. 为破坏性变更设计 MAJOR 版本。
6. 列出 5 个破坏性变更。
7. 检查项目中版本号是否重复定义。
8. 写发布说明模板。

## 验收标准

- 能解释 SemVer。
- 能维护 CHANGELOG。
- 能识别破坏性变更。
- 能保持版本来源清晰。
