# CI基础

CI 是持续集成。它的作用是在统一、干净、可复现的环境中运行质量检查，防止只在个人电脑上通过的代码进入主分支。

## CI 应该检查什么

基础流水线：

```text
checkout -> setup python -> install deps -> format check -> lint -> type check -> tests -> build
```

至少包含：

- 格式检查。
- lint。
- 类型检查。
- 测试。
- 构建。

## GitHub Actions 概念

核心概念：

- workflow。
- job。
- step。
- runner。
- action。
- matrix。

示例结构：

```yaml
name: CI

on:
  push:
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
```

## Python 版本

使用明确版本：

```yaml
- uses: actions/setup-python@v5
  with:
    python-version: "3.14"
```

如果项目支持多个版本，使用 matrix。

## 缓存

依赖安装可能较慢，可以缓存 pip 或工具缓存。

注意：

- 缓存是优化，不是正确性的依赖。
- lock 文件变化时缓存应失效。

## 失败策略

CI 失败时：

- 不能忽略。
- 先看第一个失败步骤。
- 本地复现同一命令。
- 修复后再推送。

## secrets

CI 中的密钥必须使用平台 secrets。

不要：

- 写进 yaml。
- 打印到日志。
- 在 PR 来自不可信分支时暴露。

## 常见错误

### CI 命令和本地命令不同

README 应写清本地复现命令。

### 只跑测试不跑 lint/type

很多问题进主分支后才发现。

### CI 不构建包

打包错误发布时才暴露。

### 在日志中输出密钥

严重安全风险。

## 练习

1. 写一个 CI workflow 草稿。
2. 增加 Python setup。
3. 安装依赖。
4. 运行 ruff format check。
5. 运行 ruff check。
6. 运行 mypy 或 pyright。
7. 运行 pytest。
8. 运行 build。
9. 说明如何本地复现 CI 失败。

## 验收标准

- 能解释 CI 的价值。
- 能设计 Python 项目基础 CI 流水线。
- 能保护 secrets。
- 能让本地命令和 CI 命令保持一致。
