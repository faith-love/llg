# IO密集和CPU密集任务

并发模型选择的第一步是判断任务类型。不要一上来就决定用线程、进程或 asyncio，先弄清楚程序的时间花在哪里。

## IO 密集任务

IO 密集任务的大部分时间花在等待外部资源：

- 网络请求。
- 文件读写。
- 数据库查询。
- 等待外部命令。
- 等待用户输入。
- 等待远程服务响应。

这类任务 CPU 往往没有忙满，程序慢是因为在等。

适合模型：

- 线程池。
- asyncio。
- 少量进程也可以，但通常不是首选。

## CPU 密集任务

CPU 密集任务的大部分时间花在计算：

- 图片处理。
- 视频转码。
- 压缩解压。
- 加密哈希。
- 大量数学运算。
- 复杂文本解析。
- 机器学习预处理。

这类任务 CPU 忙，程序慢是因为计算量大。

适合模型：

- 进程池。
- 原生扩展库。
- 向量化计算。
- 分布式计算。

线程通常不是纯 Python CPU 密集任务的首选。

## 混合型任务

很多真实任务是混合的：

```text
下载文件 -> 解压 -> 解析 -> 写入数据库
```

处理方式：

- 下载阶段用线程或 asyncio。
- 解析计算阶段用进程池。
- 写数据库阶段控制连接数量。

不要强行用一种模型解决所有阶段。

## 如何判断瓶颈

### 看 CPU 使用率

如果单进程 CPU 使用率很高，可能是 CPU 密集。

如果 CPU 很低但程序耗时长，可能是 IO 密集。

### 加时间日志

```python
from time import perf_counter

start = perf_counter()
result = do_work()
elapsed = perf_counter() - start
print(f"耗时: {elapsed:.3f}s")
```

分别记录：

- 读取耗时。
- 网络请求耗时。
- 解析耗时。
- 写入耗时。

### 做最小对比

写三个版本：

- 串行版本。
- 线程池版本。
- 进程池版本。

用同一批输入比较耗时和资源。

## 模型选择表

| 任务 | 推荐模型 | 理由 |
| --- | --- | --- |
| 下载多个网页 | 线程池或 asyncio | 大部分时间等待网络 |
| 批量读取小文件 | 线程池 | 文件 IO 等待较多 |
| 计算大量 Fibonacci | 进程池 | 纯 Python CPU 计算 |
| 计算文件哈希 | 视情况 | 读取 IO 和哈希计算都有成本 |
| 调用多个外部命令 | 线程池或 subprocess 管理 | 等待外部进程 |
| 处理 10 万个很小任务 | 先考虑批处理 | 调度成本可能超过收益 |
| 长连接聊天服务 | asyncio | 大量连接和等待 |

## 并发数量不是越大越好

并发数量过大会导致：

- 网络请求被对方限流。
- 本机文件句柄耗尽。
- 数据库连接耗尽。
- 内存占用上升。
- 日志爆炸。
- 错误重试形成任务风暴。

建议：

- 先从小并发开始，例如 5、10、20。
- 观察耗时、失败率、CPU、内存。
- 给每个外部资源设置上限。

## 任务粒度

粒度太小：

- 调度成本高。
- 日志数量大。
- 线程池或进程池开销明显。

粒度太大：

- 单个任务失败影响范围大。
- 负载不均。
- 进度不易观察。

合理粒度：

- 一个 URL。
- 一个文件。
- 一批记录。
- 一个独立计算单元。

## 常见错误

### 不测量就优化

没有基准耗时，不知道并发是否真的改进。

### 用线程加速 CPU 计算

常规 CPython 下，纯 Python CPU 计算通常不会因为线程明显变快。

### 并发数量直接设置 1000

这通常会先压垮自己或外部服务。

### 忽略外部系统限制

数据库、API、文件系统都有容量边界。你的程序并发越高，越要尊重这些边界。

## 练习

1. 写一个串行下载模拟任务，用 `time.sleep()` 模拟 IO。
2. 写一个串行 CPU 计算任务。
3. 分别记录两个任务的耗时。
4. 用线程池优化 IO 模拟任务。
5. 用线程池尝试优化 CPU 任务，观察效果。
6. 用进程池优化 CPU 任务。
7. 对同一任务测试并发数 1、2、5、10 的耗时。
8. 写一份模型选择说明。

## 验收标准

- 能判断任务是 IO 密集、CPU 密集还是混合型。
- 能用数据而不是感觉判断瓶颈。
- 能解释为什么并发数量不能无限增大。
- 能为一个任务选择合适模型并说明理由。
