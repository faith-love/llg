# 超时取消和异常处理

并发程序必须主动处理超时、取消和异常。没有超时的任务可能永久卡住；没有取消机制的后台任务可能无法退出；没有异常收集的并发程序可能悄悄失败。

## 为什么需要超时

超时用于定义等待边界。

没有超时时：

- 网络请求可能一直卡住。
- 外部服务不可用时线程被占满。
- 调度任务堆积。
- 程序无法按时退出。

## asyncio 超时

常用：

```python
import asyncio


result = await asyncio.wait_for(work(), timeout=5)
```

如果超时，会抛出 `asyncio.TimeoutError`。

示例：

```python
try:
    result = await asyncio.wait_for(work(), timeout=5)
except asyncio.TimeoutError:
    print("任务超时")
```

## 取消任务

```python
task = asyncio.create_task(work())
task.cancel()
```

取消不是粗暴杀死。它会在协程的等待点注入 `CancelledError`。

协程应该允许取消传播：

```python
async def work():
    try:
        await asyncio.sleep(10)
    finally:
        print("清理资源")
```

不要随便吞掉 `CancelledError`。

## 取消后的清理

适合放在 `finally`：

- 关闭文件。
- 释放连接。
- 写入中间状态。
- 撤销临时资源。
- 记录日志。

## gather 和取消

当一组任务中某个失败时，要明确策略：

- 失败即终止全部。
- 失败记录后继续。
- 超时任务取消，其他任务继续。
- 超时后整体取消。

不同策略代码不同，不要依赖默认行为。

## 线程池超时

```python
future.result(timeout=5)
```

注意：

- 这只是主线程等待结果的超时。
- 已经运行的线程任务不一定被停止。
- 任务内部也要设置网络请求或 IO 超时。

## 进程池超时

进程任务超时后，可以考虑取消未开始任务，或终止进程池。但终止进程可能带来资源清理问题。

设计原则：

- 单个任务内部可控制。
- 输入分片不要过大。
- 中间结果可恢复。
- 超时后记录任务输入。

## 异常收集

线程池和进程池：

```python
try:
    result = future.result()
except Exception as exc:
    ...
```

asyncio：

```python
try:
    result = await task
except Exception as exc:
    ...
```

## 错误分类

建议把错误分成：

| 类型 | 处理 |
| --- | --- |
| 参数错误 | 直接失败 |
| 配置错误 | 直接失败 |
| 网络超时 | 可有限重试 |
| 外部服务 5xx | 可有限重试 |
| 权限错误 | 记录并停止相关任务 |
| 数据格式错误 | 记录坏数据并继续 |
| 编程错误 | 暴露并修复 |

## 常见错误

### 超时只设置在外层

外层等待超时不一定能停止内部阻塞调用。内部库也要设置 timeout。

### 吞掉所有异常

`except Exception: pass` 会让故障不可见。

### 吞掉 CancelledError

可能导致任务无法取消。

### 失败任务没有输入上下文

日志里只有错误，没有任务 ID、URL、文件路径，就难以复现。

## 练习

1. 给 asyncio 任务设置 `wait_for` 超时。
2. 取消一个正在 sleep 的任务。
3. 在 `finally` 中记录清理日志。
4. 让 `gather` 中一个任务失败，观察结果。
5. 用 `return_exceptions=True` 收集错误。
6. 给线程池任务的 HTTP 请求设置 timeout。
7. 给每个失败结果保留输入参数。
8. 写一个错误分类函数。

## 验收标准

- 能给任务设置超时。
- 能取消 asyncio Task。
- 能正确处理异常并保留上下文。
- 能区分可重试错误和不可重试错误。
