# 项目需求文档写法

需求文档用于说明项目为什么做、做什么、不做什么、如何验收。没有需求文档的项目容易范围漂移，最后变成半成品。

## 基本结构

```markdown
# 项目需求文档

## 背景

## 目标

## 用户角色

## 功能范围

## 非功能需求

## 不做什么

## 验收标准

## 风险
```

## 背景

说明问题来源：

- 当前痛点。
- 手工流程。
- 数据问题。
- 系统缺口。
- 学习目标。

## 目标

目标要可验证：

- 支持批量整理 1000 个文件。
- API P95 小于 300ms。
- 报表生成时间小于 1 分钟。
- 测试覆盖核心流程。

## 用户角色

例子：

- 管理员。
- 普通用户。
- 数据分析者。
- 运维人员。
- 脚本使用者。

不同角色有不同权限和工作流。

## 功能范围

按优先级：

- P0：必须。
- P1：重要。
- P2：可选。

## 非功能需求

包括：

- 性能。
- 安全。
- 可维护性。
- 可观测性。
- 可部署性。
- 兼容性。

## 不做什么

明确排除范围：

- 不做前端 UI。
- 不支持分布式。
- 不接入真实支付。
- 不支持多租户。

这能防止范围失控。

## 验收标准

每个功能都要能验收：

- 给定输入。
- 执行动作。
- 预期输出。
- 错误场景。

## 常见错误

### 目标不可测量

“体验更好”太抽象。

### 功能范围无限扩张

没有 P0/P1/P2。

### 不写非功能需求

性能、安全、日志、测试被遗漏。

### 不写不做什么

项目边界模糊。

## 练习

1. 为一个项目写背景。
2. 写 3 个可测量目标。
3. 定义用户角色。
4. 列出 P0/P1/P2。
5. 写非功能需求。
6. 写不做什么。
7. 写 10 条验收标准。

## 验收标准

- 需求文档能说明项目价值。
- 功能范围清晰。
- 验收标准可执行。
- 风险和排除范围明确。
