# 代码评审能力

代码评审不是挑格式，也不是表达个人偏好。好的评审关注正确性、边界、可维护性、安全、性能和测试证据。

## 评审优先级

优先看：

1. 功能是否正确。
2. 是否有数据丢失或安全风险。
3. 错误路径是否处理。
4. 测试是否覆盖关键行为。
5. 接口是否破坏兼容。
6. 代码结构是否可维护。
7. 性能是否有明显问题。

格式问题交给工具。

## 评审清单

检查：

- 输入校验。
- None 和异常处理。
- 资源释放。
- 并发安全。
- 路径安全。
- SQL/命令注入。
- 密钥日志。
- 测试覆盖。
- 配置默认值。
- 文档更新。

## 提问方式

好的反馈：

```text
这里如果 file_path 是绝对路径，会不会绕过 upload_dir？建议 resolve 后检查父目录。
```

不好的反馈：

```text
这写得不行。
```

评审要具体、可执行。

## 分级反馈

可以分：

- 必须修改：bug、安全、破坏兼容。
- 建议修改：可维护性、清晰度。
- 可选讨论：风格和替代方案。

## 自评

提交前先自评：

- 我改了什么？
- 为什么这样改？
- 风险是什么？
- 如何验证？
- 哪些地方需要 reviewer 重点看？

## 常见错误

### 只看代码风格

工具能解决的不要占用评审精力。

### 不看测试

没有测试证据的改动风险高。

### 不看错误路径

生产问题经常来自错误路径。

### 反馈不可执行

无法帮助作者修改。

## 练习

1. 评审一个自己的旧项目。
2. 找 3 个错误处理问题。
3. 找 3 个测试缺口。
4. 找 2 个安全边界问题。
5. 写 5 条具体 review comment。
6. 给自己的 PR 写自评说明。
7. 建立个人 review checklist。

## 验收标准

- 能按风险优先评审代码。
- 能写具体、可执行的反馈。
- 能区分必须修改和建议修改。
- 能自评自己的改动。
