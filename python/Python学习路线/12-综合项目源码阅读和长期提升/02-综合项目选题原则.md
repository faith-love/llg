# 综合项目选题原则

综合项目的价值不在于名字大，而在于能真实运行、能说明问题、能体现能力、能持续维护。选题过大容易烂尾，选题过小又无法证明综合能力。

## 好项目的标准

好项目通常满足：

- 解决一个明确问题。
- 输入输出清楚。
- 有真实使用场景。
- 可以分阶段交付。
- 可以测试。
- 可以演示。
- 可以扩展。
- 可以讲清技术取舍。

## 避免的选题

不建议：

- 只有 CRUD 没有业务规则。
- 只跟教程复制。
- 依赖大量外部服务但没有替代方案。
- 目标过大，例如完整电商平台。
- 无法测试和验收。
- 没有用户或使用场景。

## 选题维度

| 维度 | 问题 |
| --- | --- |
| 业务价值 | 它解决什么问题？ |
| 技术覆盖 | 覆盖哪些阶段能力？ |
| 可演示性 | 5 分钟内能展示什么？ |
| 可测试性 | 如何证明它正确？ |
| 可部署性 | 能否本地或容器运行？ |
| 可扩展性 | 后续能加什么？ |
| 风险 | 最大不确定性是什么？ |

## 推荐项目类型

### 自动化工具

适合展示：

- CLI。
- 文件处理。
- 标准库。
- 日志。
- 报告。
- 打包发布。

### Web API

适合展示：

- FastAPI。
- 参数校验。
- 数据库。
- 认证。
- 测试。
- 部署。

### 数据处理系统

适合展示：

- pandas。
- ETL。
- 数据质量。
- 增量处理。
- 报表。

### 异步任务系统

适合展示：

- asyncio。
- 队列。
- 重试。
- 调度。
- 监控。

### 性能安全加固

适合展示：

- profile。
- 内存分析。
- 安全检查。
- 修复报告。

## 选题评分表

每项 1-5 分：

- 真实价值。
- 可完成度。
- 技术覆盖。
- 演示效果。
- 测试可行。
- 文档可写。
- 后续扩展。

总分高不一定最好，还要看你当前时间和能力。

## 最小可行版本

每个项目先定义 MVP：

- 最少功能。
- 最少输入输出。
- 最小部署方式。
- 最小测试集。

MVP 完成后再扩展。

## 常见错误

### 项目范围过大

导致长期没有可运行版本。

### 只选自己熟悉的简单题

无法体现成长。

### 只关注技术不关注使用场景

项目讲不清价值。

### 没有验收标准

不知道什么时候算完成。

## 练习

1. 写 5 个项目候选题。
2. 用评分表打分。
3. 给最高分项目写 MVP。
4. 写项目使用场景。
5. 写项目不做什么。
6. 写项目风险清单。
7. 选择 3 个最终项目。

## 验收标准

- 能为项目定义真实问题。
- 能控制项目范围。
- 能写出 MVP 和验收标准。
- 能选择能展示综合能力的项目。
