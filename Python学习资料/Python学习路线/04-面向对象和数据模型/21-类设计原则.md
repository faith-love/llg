# 类设计原则

学会写类不等于所有地方都应该用类。好的类应该表达稳定的领域概念，维护清晰的不变量，并通过方法提供有意义的行为。

## 什么时候用类

适合用类：

- 数据和行为天然绑定。
- 对象有状态，并且状态会变化。
- 需要维护不变量。
- 多个函数总是围绕同一组数据工作。
- 需要多态或协议。
- 需要表达领域概念。

示例：

- `Book`
- `用户`
- `订单`
- `Cart`
- `BankAccount`
- `ReportGenerator`

## 什么时候不用类

不适合强行用类：

- 只是一个简单数据转换。
- 函数没有共享状态。
- 只有一个方法，且类名很空泛。
- 为了“看起来高级”而包装函数。

示例：

```python
def clean_text(text):
    return text.lower().strip()
```

这种简单函数不需要类。

## 类名表达领域概念

推荐：

```python
class ShoppingCart:
    pass


class 订单Item:
    pass
```

不推荐：

```python
class Manager:
    pass


class Processor:
    pass
```

除非上下文非常明确，否则 `Manager`、`Processor`、`Handler` 容易变成大杂烩。

## 方法表达行为

对象方法应该表达业务行为，而不是简单暴露内部字段。

推荐：

```python
cart.add_item(item)
cart.total_price()
order.cancel()
book.borrow()
```

不推荐把对象当字典外壳：

```python
用户.set_name(name)
用户.get_name()
```

Python 中简单属性通常可以直接访问。

## 不变量

不变量是对象始终应该保持成立的规则。

例如：

- 价格不能小于 0。
- 账户余额不能低于冻结额度。
- 已取消订单不能发货。
- 已借出的图书不能再次借出。

对象方法应该维护这些规则。

## 组合优先

如果关系是 has-a 或 uses，优先组合。

继承只用于明确 is-a 关系。

## 小而清晰

一个类不要承担太多职责。

如果类里出现：

- 数据校验。
- 文件读写。
- 网络请求。
- 报表格式化。
- 数据库保存。
- 命令行交互。

全部混在一起，就应该拆分。

## 避免过度抽象

不要提前设计复杂父类、接口、工厂、策略，除非已经出现明确变化点。

学习阶段优先：

1. 先写简单类。
2. 发现重复和变化。
3. 再抽象。

## 常见错误

### 贫血对象

类只有数据，没有行为，所有逻辑都在外部函数里。

这不一定错，但如果逻辑总围绕这个对象，就应该考虑把行为放回类。

### 上帝类

一个类什么都管，方法很多，状态很多，难测试。

### 继承滥用

为了复用几行代码建立父类，后续会变得僵硬。

## 练习

1. 判断 10 个场景是否需要类。
2. 把一个简单函数从类中移出去。
3. 给 `Book` 添加借出和归还行为。
4. 给 `订单` 添加取消规则。
5. 找一个上帝类示例并拆分职责。
6. 把一个错误继承改成组合。

## 验收标准

- 能判断何时用类。
- 能设计表达领域概念的类名。
- 能用方法维护对象不变量。
- 能避免过度抽象和上帝类。
