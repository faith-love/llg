# 任务拆分和迭代计划

综合项目能否完成，关键在任务拆分。任务太大容易拖延，任务太碎又难看出进展。好的迭代计划应该每一步都有可验证产出。

## 里程碑

示例：

- M1：项目骨架和运行入口。
- M2：核心功能 MVP。
- M3：错误处理和日志。
- M4：测试和质量门禁。
- M5：文档和演示。
- M6：部署和复盘。

## Issue 写法

一个任务应包含：

- 背景。
- 目标。
- 范围。
- 验收标准。
- 依赖。
- 风险。

## 任务粒度

合适任务：

- 1-4 小时可以完成。
- 有明确文件或模块。
- 有测试或验证方式。
- 完成后项目状态更好。

过大任务：

- “完成整个 API”。
- “优化所有性能”。
- “重构项目”。

## 垂直切片

优先做端到端小闭环：

```text
一个接口 -> 服务 -> 存储 -> 测试 -> 文档
```

比先搭所有层但没有功能更好。

## 风险优先

先验证最大不确定性：

- 外部 API 是否可用。
- 数据格式是否稳定。
- 性能是否达标。
- 部署是否可行。
- 权限模型是否清楚。

## 每周节奏

每周固定：

- 计划本周任务。
- 完成一个可运行增量。
- 写测试。
- 更新 说明。
- 写复盘。

## 常见错误

### 先做大量基础设施

没有可用功能，容易失去反馈。

### 任务没有验收标准

不知道是否完成。

### 忽略风险任务

最后才发现核心方案不可行。

### 文档最后再写

容易和代码脱节。

## 练习

1. 为项目拆 5 个里程碑。
2. 写 10 个 Issue。
3. 给每个 Issue 写验收标准。
4. 标出任务依赖。
5. 找出最大风险任务。
6. 设计第一个垂直切片。
7. 写一周迭代计划。

## 验收标准

- 任务能逐步交付。
- 每个任务有验收标准。
- 先处理高风险任务。
- 每周都有可运行增量。
