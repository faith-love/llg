# 技术方案和架构设计

技术方案用于说明项目如何实现，以及为什么这样实现。它不需要一开始就写成复杂架构文档，但必须讲清模块边界、数据流、接口、依赖和取舍。

## 基本结构

```markdown
# 技术方案

## 目标

## 总体架构

## 模块划分

## 数据模型

## API 或命令设计

## 数据流

## 错误处理

## 测试策略

## 部署方案

## 风险和取舍
```

## 总体架构

用简单图表达：

```text
CLI/API -> 服务 -> repository -> 数据base/file
```

不要过度复杂，先表达清楚边界。

## 模块划分

每个模块说明：

- 职责。
- 输入。
- 输出。
- 不负责什么。
- 依赖谁。

## 数据流

数据处理项目尤其需要：

```text
原始数据 -> 校验 -> 清洗 -> 转换 -> 汇总 -> 报告
```

Web 项目需要：

```text
request -> router -> 服务 -> repository -> response
```

## 接口设计

包括：

- CLI 命令。
- HTTP API。
- 配置文件。
- 内部函数接口。
- 输出报告格式。

## 错误处理

说明：

- 哪些错误直接失败。
- 哪些错误记录后继续。
- 错误响应格式。
- 日志字段。
- 重试策略。

## 取舍说明

示例：

- 先用 SQLite，不上 PostgreSQL，因为学习阶段部署成本更低。
- 先用本地文件队列，不引入 Redis，因为任务规模可控。
- 先用同步 API，不上异步，因为瓶颈不在并发。

## 常见错误

### 只有技术名词没有取舍

方案要解释为什么。

### 模块职责重叠

后续容易循环依赖。

### 不考虑错误路径

真实项目大部分复杂度在错误处理。

### 不写数据流

数据从哪里来、到哪里去不清楚。

## 练习

1. 为项目画总体架构。
2. 写模块职责表。
3. 写数据流。
4. 写 API 或 CLI 设计。
5. 写错误处理策略。
6. 写测试策略。
7. 写 5 个技术取舍。

## 验收标准

- 能讲清模块边界。
- 能讲清数据流。
- 能讲清错误处理和测试策略。
- 能说明关键技术取舍。
