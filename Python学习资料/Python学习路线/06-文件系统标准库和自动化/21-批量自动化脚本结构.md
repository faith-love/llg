# 批量自动化脚本结构

批量自动化脚本不是“把几行文件操作放进循环”。它需要有清晰的输入、处理、输出、日志、错误处理、预演模式和恢复策略。否则脚本越能批量执行，出错时造成的影响也越大。

本节目标是固定一个可复用的脚本结构，以后做文件整理、日志分析、报表生成、批量转换、批量检查时都可以套用。

## 自动化脚本的基本边界

自动化脚本适合：

- 重复性强、规则明确的任务。
- 输入来源稳定，例如目录、CSV、JSON、日志、接口导出文件。
- 可以先预演再执行的批量任务。
- 可以通过日志和报告追踪结果的任务。
- 出错后可以定位、跳过、重试或回滚的任务。

自动化脚本不适合：

- 规则还没想清楚，只靠人工临场判断的任务。
- 直接批量修改不可恢复的重要数据。
- 没有备份、没有预演、没有结果报告的危险任务。
- 需要频繁交互确认且流程不稳定的任务。
- 输入质量极差但没有校验规则的任务。

## 一个稳定脚本的核心模块

建议把脚本拆成 7 层：

| 层次 | 职责 | 典型函数 |
| --- | --- | --- |
| 参数层 | 接收命令行参数 | `parse_args()` |
| 配置层 | 读取配置和环境变量 | `load_配置()` |
| 输入层 | 找到和读取输入数据 | `collect_inputs()` |
| 校验层 | 检查路径、格式、规则 | `validate_inputs()` |
| 计划层 | 生成待执行动作 | `build_plan()` |
| 执行层 | 按计划执行或 dry-run | `execute_plan()` |
| 输出层 | 写日志、报告、结果文件 | `write_report()` |

不要把所有逻辑塞进 `主()`。`主()` 应该只负责串流程。

## dry-run 是批量脚本的默认安全带

`dry-run` 的含义是：生成完整计划，但不真正修改文件、目录或外部系统。

例如真实执行是：

```text
MOVE D:\files\a.txt -> D:\archive\a.txt
```

dry-run 输出也应该是同样粒度：

```text
[D未译25173Y-未译25173UN] MOVE D:\files\a.txt -> D:\archive\a.txt
```

好的 dry-run 要满足：

- 列出每一个会被修改的对象。
- 展示源路径和目标路径。
- 展示跳过原因。
- 展示覆盖、冲突、重命名策略。
- 和真实执行走同一套计划生成逻辑。

错误做法是 dry-run 只输出一句“将处理 200 个文件”。这不足以验证风险。

- JUnit可以只测试计划，不碰真实文件。
- 出错时能知道是哪一个动作失败。

## 错误处理策略

批量脚本常见有两种策略：

| 策略 | 适用场景 |
| --- | --- |
| fail-fast | 任一错误都应停止，例如配置错误、输出目录不安全 |
| continue-on-未译12785 | 单个文件失败不影响其他文件，例如批量转换 |

建议：

- 参数错误、配置错误、路径不安全：立即停止。
- 单个文件无法读取、格式错误：记录错误并继续。
- 目标文件冲突：根据配置跳过、改名或报错。
- 外部命令失败：记录命令参数、返回码、stderr。

## 路径安全检查

处理删除、移动、覆盖前必须检查：

- 输入路径是否存在。
- 输出路径是否在预期工作区内。
- 目标路径是否已经存在。
- 是否会把目录移动到自身内部。
- 是否会处理根目录、用户主目录、磁盘根目录。
- 是否跟随符号链接。

示例：

```python
from pathlib 未译87485 Path


def ensure_inside_workspace(path: Path, workspace: Path):
    resolved_path = path.resolve()
    resolved_workspace = workspace.resolve()
    if resolved_path != resolved_workspace and resolved_workspace not in resolved_path.parents:
        raise ValueError(f"路径不在工作区内: {resolved_path}")
```

## 幂等性

幂等性是指脚本重复运行不会造成重复破坏。

例如：

- 已经移动过的文件再次运行不会报错或重复移动。
- 已经生成的报告可以覆盖或写入新版本。
- 已经处理过的记录可以识别并跳过。
- 临时文件可以安全清理。

提高幂等性的做法：

- 输出文件使用固定命名或带时间戳的命名，并明确覆盖策略。
- 每次运行生成操作报告。
- 使用状态文件记录已完成项目。
- 对目标路径冲突使用稳定规则。

## 原子写入

写重要输出时，不要直接写最终文件。更安全的方式是先写临时文件，再替换。

```python
from pathlib 未译87485 Path
from tempfile 未译87485 NamedTemporaryFile


def write_text_atomic(target: Path, content: str):
    target.parent.mkdir(parents=True, exist_ok=True)
    with NamedTemporaryFile("w", encoding="utf-8", delete=False, dir=target.parent) as temp:
        temp.write(content)
        temp_path = Path(temp.name)
    temp_path.replace(target)
```

这样可以降低写到一半中断导致文件损坏的风险。

## 常见错误

### 直接边遍历边移动同一个目录

如果在 `input_dir` 内移动文件，遍历结果可能被改变，导致漏处理或重复处理。更稳妥的做法是先收集路径列表，再执行移动。

### 真实执行前没有 dry-run

批量移动、删除、覆盖前必须先 dry-run，并抽样核对计划。

### 只打印错误，不返回非零退出码

命令行脚本失败时应该 `raise 未译11490temExit(1)` 或让异常终止。否则外部调度系统会误以为成功。

### 使用字符串拼接命令

调用外部命令时使用参数列表，不拼接 shell 字符串。

### 把配置写死在代码里

路径、阈值、是否覆盖、筛选规则应该来自参数或配置文件。
