# 增量同步和幂等性

数据任务很少只运行一次。每天、每小时、失败后重跑，都会遇到重复数据和部分成功问题。增量同步和幂等性是 ETL 能否长期稳定运行的核心。

## 全量和增量

全量同步：

```text
每次处理所有数据
```

优点：

- 简单。
- 结果完整。

缺点：

- 数据量大时慢。
- 容易影响数据库。
- 重复处理成本高。

增量同步：

```text
只处理上次之后变化的数据
```

优点：

- 快。
- 成本低。

缺点：

- 需要水位线。
- 需要处理迟到数据。
- 需要保证不漏不重。

## watermark

watermark 是同步水位线。

常见水位：

- 自增 ID。
- 更新时间 `updated_at`。
- 创建时间 `created_at`。
- 文件批次号。
- 消息 offset。

示例：

```text
last_updated_at=2026-05-11 10:00:00
```

下次只处理更新晚于该时间的数据。

## 幂等性

幂等性是指同一个任务重复执行，结果仍然正确。

例如：

- 同一订单重复导入不会产生两条。
- 同一批数据重跑只更新已有记录。
- 失败后重跑不会重复累计金额。

## upsert

upsert 是存在则更新，不存在则插入。

不同数据库语法不同：

- SQLite：`INSERT ... ON CONFLICT DO UPDATE`
- PostgreSQL：`ON CONFLICT`
- MySQL：`ON DUPLICATE KEY UPDATE`

前提：

- 有主键或唯一键。

## 去重表

可以建立导入记录表：

```text
import_batches
processed_files
processed_events
```

记录：

- batch_id。
- source_file。
- checksum。
- started_at。
- finished_at。
- status。

## 迟到数据

如果按更新时间增量，可能有迟到数据。

策略：

- 水位线回看一段时间。
- 按主键 upsert。
- 记录处理窗口。

例如每次处理最近 2 小时变化数据，即使上次已经处理过，也通过 upsert 保证不重复。

## 常见错误

### 只按 created_at 增量

更新过的旧数据可能漏掉。

### 没有唯一键

无法可靠去重和 upsert。

### 先更新水位再写数据

写入失败后可能丢数据。应在成功提交后更新水位。

### 重复运行累计指标

例如每天重跑时把销售额重复加到汇总表。

## 练习

1. 设计一个 watermark 表。
2. 用 updated_at 做增量查询。
3. 成功写入后更新水位。
4. 失败时不更新水位。
5. 给目标表增加唯一键。
6. 实现 SQLite upsert。
7. 记录 processed_files。
8. 用文件 checksum 防止重复导入。
9. 设计迟到数据回看策略。
10. 重跑同一批数据验证不重复。

## 验收标准

- 能区分全量和增量。
- 能设计 watermark。
- 能解释幂等性。
- 能用唯一键和 upsert 防止重复写入。
- 能处理失败重跑。
