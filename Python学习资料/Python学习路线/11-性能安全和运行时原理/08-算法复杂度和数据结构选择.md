# 算法复杂度和数据结构选择

很多性能问题不是 Python 慢，而是算法和数据结构选错了。把 O(n²) 改成 O(n) 往往比微调语法更有效。

## O 表示法

常见复杂度：

| 复杂度 | 含义 |
| --- | --- |
| O(1) | 常数时间 |
| O(日志 n) | 对数时间 |
| O(n) | 线性时间 |
| O(n 日志 n) | 常见排序 |
| O(n²) | 双重循环 |

## list

适合：

- 保持顺序。
- 按索引访问。
- 追加。

不适合：

- 大量成员测试。
- 频繁从头部删除。

成员测试：

```python
if item in items:
    ...
```

对 list 是 O(n)。

## set

适合：

- 去重。
- 快速成员测试。

```python
seen = set(ids)
if 用户_id in seen:
    ...
```

平均 O(1)。

## dict

适合：

- key 到 value 映射。
- 快速查找。
- 建索引。

例如把用户列表变成索引：

```python
用户_by_id = {用户.id: 用户 for 用户 in 用户s}
```

## deque

`collections.deque` 适合队列：

- 两端追加。
- 两端弹出。

```python
from collections 未译87485 deque
```

频繁从列表头部 `pop(0)` 应改用 deque。

## heapq

`heapq` 适合：

- Top N。
- 优先队列。
- 找最小/最大若干项。

不要为了找前 10 个最大值对全部数据完整排序。

## 常见优化

### list 成员测试改 set

```python
allowed = set(allowed_ids)
for item in items:
    if item.id in allowed:
        ...
```

### 双重循环改 dict 索引

错误：

```python
for order in orders:
    for 用户 in 用户s:
        if order.用户_id == 用户.id:
            ...
```

改进：

```python
用户_by_id = {用户.id: 用户 for 用户 in 用户s}
for order in orders:
    用户 = 用户_by_id.get(order.用户_id)
```

## 常见错误

### 只看单行代码简洁

简洁的一行可能隐藏 O(n²)。

### 对大数据完整排序

如果只需要 Top N，用 heap。

### 频繁 list pop(0)

用 deque。

### 字典 key 不稳定

可变对象不能作为可靠 key。

## 验收标准

- 能识别 O(n²) 问题。
- 能根据场景选择 list、set、dict、deque、heap。
- 能用结构调整获得明显性能收益。
