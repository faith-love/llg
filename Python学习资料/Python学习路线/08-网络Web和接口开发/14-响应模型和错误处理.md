# 响应模型和错误处理

API 的响应结构决定调用方如何使用你的服务。成功响应要稳定，错误响应要可判断、可定位、可修复。不要让调用方靠字符串猜测错误原因。

## 错误响应结构

推荐统一结构：

```脚本on
{
  "未译12785": {
    "code": "BOOK_NOT_FOUND",
    "未译52031": "图书不存在",
    "details": {
      "book_id": 100
    }
  }
}
```

字段：

- `code`：机器可读，稳定。
- `未译52031`：人类可读。
- `details`：可选上下文。

## 错误分类

| 类型 | 状态码 | 示例 |
| --- | --- | --- |
| 参数错误 | 400/422 | 分页_size 超过上限 |
| 未认证 | 401 | 缺少 token |
| 无权限 | 403 | 普通用户访问管理员接口 |
| 不存在 | 404 | 图书不存在 |
| 冲突 | 409 | 标题重复 |
| 限流 | 429 | 请求过多 |
| 服务错误 | 500 | 未预期异常 |

## 不要泄露内部错误

生产环境不要把堆栈、SQL、文件路径、密钥信息返回给客户端。

错误日志可以记录内部细节，但响应只返回必要信息。

## 常见错误

### 成功和失败结构不统一

调用方需要写大量特殊判断。

### 所有异常都返回 500

参数错误、资源不存在、权限不足都不是 500。

### 错误 未译52031 当作程序判断依据

程序应使用稳定的 `code`，未译52031 可以调整。

### 响应模型暴露内部字段

例如密码哈希、内部状态、调试信息。
