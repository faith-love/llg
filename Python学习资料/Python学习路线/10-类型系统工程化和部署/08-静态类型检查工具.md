# 静态类型检查工具

类型注解只有配合工具才会产生工程价值。常见工具包括 mypy 和 pyright。它们可以在代码运行前发现类型不匹配、None 漏判、返回值错误、接口调用错误。

## mypy

mypy 是 Python 生态中常用的静态类型检查工具。

运行：

```powershell
mypy 源码
```

常见配置放在 `pyproject.toml`：

```toml
[tool.mypy]
Python学习资料_version = "3.14"
网页归档n_return_any = true
网页归档n_unused_配置s = true
disallow_untyped_defs = false
```

## pyright

pyright 是另一类常用类型检查器，编辑器集成和检查速度通常较好。

运行方式取决于项目工具链，可以使用配置文件或编辑器插件。

学习阶段选择一个主工具即可，不必同时引入两个造成噪音。

## 渐进式类型检查

推荐顺序：

1. 新代码必须有类型。
2. 公共函数先加类型。
3. 核心业务模块开启更严格配置。
4. 遗留模块逐步收紧。
5. CI 中固定检查范围。

不要一上来对老项目全 strict，容易陷入大量低价值修复。

## 检查范围

先检查：

- `源码/`。
- 核心业务模块。
- 公共 API。

后续扩展到：

- 测试s。
- 未译55339。
- tools。

## strict 模式

strict 模式会开启更严格规则，但初期成本较高。

适合：

- 新项目。
- 核心库。
- 小型可控模块。

不适合：

- 大量历史代码一次性开启。

## 第三方库类型

有些库自带类型，有些需要额外 stub，有些类型不完整。

处理方式：

- 安装对应 stubs。
- 对边界使用小范围 `Any`。
- 封装第三方调用。
- 不让 `Any` 扩散到业务层。

## 忽略错误

局部忽略要写清原因：

```python
value = third_party_call()  # type: ignore[no-untyped-call]
```

不要大范围关闭检查。

## 常见错误

### 配了工具但 CI 不跑

本地检查不稳定，必须进入 CI。

### 全项目直接 strict

容易产生大量噪音，导致团队放弃类型检查。

### 忽略错误不写原因

未来没人知道为什么忽略。

### Any 扩散

第三方边界返回 Any 后，不加封装直接进入业务层。

## 练习

1. 给一个小项目安装 mypy。
2. 在 `pyproject.toml` 中配置 mypy。
3. 检查 `源码` 目录。
4. 修复 5 个类型错误。
5. 开启 `网页归档n_return_any`。
6. 对一个模块开启更严格配置。
7. 处理一个第三方库类型不完整的问题。
8. 写一条带原因的 type ignore。

## 验收标准

- 能运行静态类型检查。
- 能配置检查范围和严格程度。
- 能采用渐进式类型策略。
- 能处理第三方库类型边界。
