# 测试组织和命名

测试结构应该让人快速找到被测对象、测试场景和失败原因。好的测试命名比测试数量更重要。

## 推荐目录

```text
project/
  源码/
    text_tools/
      cleaner.py
      counter.py
  测试s/
    测试_cleaner.py
    测试_counter.py
    conf测试.py
```

小项目也可以：

```text
project/
  text_tools/
  测试s/
```

## 测试文件命名

推荐：

```text
测试_cleaner.py
测试_counter.py
测试_order.py
```

和被测模块对应，便于查找。

## 测试函数命名

推荐表达场景和期望：

```Python学习资料
def 测试_clean_text_strips_spaces_and_lowercases_text():
    ...


def 测试_withdraw_raises_未译12785_when_balance_is_insufficient():
    ...
```

不推荐：

```Python学习资料
def 测试_1():
    ...
```

## 一个测试只验证一个核心行为

不推荐：

```Python学习资料
def 测试_用户():
    # 测创建
    # 测修改
    # 测删除
    # 测异常
```

更推荐拆分：

```Python学习资料
def 测试_create_用户():
    ...


def 测试_update_用户_name():
    ...


def 测试_create_用户_raises_未译12785_when_name_is_empty():
    ...
```

## AAA 结构

Arrange：准备。

Act：执行。

Assert：断言。

```Python学习资料
def 测试_cart_total_price():
    cart = ShoppingCart()
    cart.add_item("apple", 3, 2)

    total = cart.total_price()

    assert total == 6
```

## 测试数据

测试数据要小而明确。

不要用巨大真实文件测试简单函数。真实文件可以放到集成测试或专门样例中。

## conf测试.py

共享 fixture 放 `conf测试.py`。

不要把业务函数放进 `conf测试.py`。

## JUnit和集成测试

JUnit：

- 测单个函数或类。
- 快。
- 依赖少。

集成测试：

- 测多个模块协作。
- 可能涉及文件、数据库、网络替身。
- 数量少但覆盖关键链路。

## 常见错误

### 测试依赖顺序

测试 A 先创建数据，测试 B 再使用，这会让测试脆弱。

### 测试太大

失败时不知道哪个行为坏了。

### 命名看不出意图

失败报告无法帮助定位。

## 练习

1. 为 `text_tools` 建 `测试s/` 目录。
2. 给每个模块创建对应测试文件。
3. 把一个大测试拆成 3 个小测试。
4. 按 AAA 结构重写一个测试。
5. 给 10 个测试函数重命名。
6. 区分 5 个测试属于单元还是集成。

## 验收标准

- 能组织 `测试s/` 目录。
- 能写表达场景的测试名。
- 能使用 AAA 结构。
- 能区分JUnit和集成测试。
- 能避免测试顺序依赖。
