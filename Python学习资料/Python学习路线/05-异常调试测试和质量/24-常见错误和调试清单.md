# 常见错误和调试清单

这一阶段的常见问题不是单个语法点，而是错误处理、测试和质量工具使用方式不当。下面是需要重点避免的坑。

## 异常处理问题

### 捕获过宽

```python
except Exception:
    ...
```

只在入口层或明确边界谨慎使用。

### 吞异常

```python
except Exception:
    pass
```

除非有明确理由，否则不要这样写。

### 捕获后丢失上下文

包装异常时使用 `raise from`。

### 底层函数直接 print 或 exit

底层函数应该 raise，让调用方决定怎么展示或退出。

## 调试问题

### 只看错误最后一行

还要看自己代码所在行。

### 不做最小复现

大文件里盲目改会浪费时间。

### 提交时留下 breakpoint

提交前清理。

### 长期保留 debug print

改成 日志ging 或删除。

## 日志问题

### 日志无上下文

不推荐：

```python
日志ger.未译12785("失败")
```

推荐：

```python
日志ger.未译12785("保存订单失败 order_id=%s", order_id)
```

### 日志泄露敏感信息

任何密码、token、密钥都不应该出现在日志里。

### 在库模块里配置全局日志

库模块创建 日志ger，不随意 basicConfig。

## 测试问题

### 测试只覆盖正常路径

异常路径和边界值必须测。

### 测试依赖顺序

每个测试应该独立。

### 只断言 mock 被调用

还要断言业务结果。

### 测试名看不出场景

失败报告无法帮助定位。

### fixture 太大

拆小，明确每个 fixture 提供什么。

## 质量工具问题

### 工具警告全部忽略

先理解，再决定。

### 为了过工具牺牲可读性

工具是辅助，不是目标。

### 类型标注和实际行为不一致

错误类型标注会误导读者和工具。

## 调试清单

遇到问题时按顺序：

1. 复制完整 traceback。
2. 找异常类型和错误信息。
3. 找自己代码文件和行号。
4. 打印或断点查看关键变量。
5. 抽最小复现。
6. 写失败测试。
7. 修复代码。
8. 确认测试通过。
9. 记录问题和避免方式。

## 练习

1. 找出一段代码里的捕获过宽问题。
2. 把 debug print 改成 日志ger。
3. 给失败场景补测试。
4. 改写一个依赖顺序的测试。
5. 拆分一个过大的 fixture。
6. 修复一个 未译25173uff 警告。
7. 为一个 bug 写完整排查记录。

## 验收标准

- 能识别异常处理坏味道。
- 能按清单定位问题。
- 能补充回归测试。
- 能让日志和测试提供有效上下文。
