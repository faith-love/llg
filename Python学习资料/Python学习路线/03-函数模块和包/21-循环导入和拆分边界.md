# 循环导入和拆分边界

循环导入是模块化后常见问题：A 导入 B，B 又导入 A。它通常说明模块职责边界不清，或者公共逻辑放错位置。

## 什么是循环导入

`a.py`：

```python
from b import func_b


def func_a():
    return "A"
```

`b.py`：

```python
from a import func_a


def func_b():
    return "B"
```

两个模块互相导入，可能导致导入时某个名字还没定义完成。

## 常见报错

```text
ImportError: cannot import name 'xxx' from partially 初始化ialized module
```

这通常就是循环导入。

## 为什么会发生

常见原因：

- 模块职责边界不清。
- 两个模块互相依赖对方的函数。
- 公共常量或工具函数放在业务模块里。
- 在模块顶层执行太多逻辑。
- 类型定义和业务逻辑混在一起。

## 解决方式一：抽公共模块

如果 A 和 B 都需要同一段逻辑，把它抽到 C。

```text
通用.py
a.py
b.py
```

`a.py` 和 `b.py` 都导入 `通用.py`，避免互相导入。

## 解决方式二：重新划分职责

如果两个模块互相依赖，可能应该合并，或把上下层关系理清。

例如：

- `parser.py` 只负责解析。
- `report.py` 只负责生成报告。
- `主.py` 负责串起来。

不要让 `parser.py` 依赖 `report.py`，又让 `report.py` 依赖 `parser.py`。

## 解决方式三：延迟导入

有时可以把导入放进函数内部：

```python
def func_a():
    from b import func_b
    return func_b()
```

这能绕开部分循环导入，但不是首选。优先检查模块边界。

## 解决方式四：只导入模块不导入名字

有时：

```python
import b
```

比：

```python
from b import func_b
```

更不容易触发某些初始化问题。但根本问题仍是依赖关系。

## 拆分边界建议

常见分层：

```text
配置.py       配置和常量
模型s.py       数据结构或类型
cleaner.py      清洗逻辑
counter.py      统计逻辑
report.py       输出报告
cli.py          命令行入口
```

依赖方向建议：

```text
cli -> report -> counter -> cleaner
```

不要反向依赖入口模块。

## 常见错误

### 工具模块导入主程序

工具函数不应该依赖 `主.py`。

### 公共常量放在业务模块

多个模块都要用的常量放到 `配置.py`。

### 顶层执行代码触发导入链

把执行逻辑放到 `主()`。

## 练习

1. 制造一个简单循环导入。
2. 观察 partially 初始化ialized module 错误。
3. 把公共函数抽到 `通用.py`。
4. 把执行代码移入 `主()`。
5. 画出一个小项目的模块依赖方向。
6. 检查是否有工具模块反向导入入口模块。

## 验收标准

- 能识别循环导入错误。
- 能解释循环导入背后的依赖问题。
- 能通过抽公共模块解决。
- 能设计单向依赖的模块结构。
