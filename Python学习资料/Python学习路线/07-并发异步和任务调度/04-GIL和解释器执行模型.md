# GIL和解释器执行模型

学习 Python 并发必须理解 GIL。它不是所有性能问题的答案，但它解释了为什么线程适合很多 IO 任务，却通常不能加速纯 Python CPU 密集计算。

## GIL 是什么

GIL 是 Global Interpreter Lock，全局解释器锁。

在常规 CPython 执行模型中，同一时刻通常只有一个线程执行 Python 字节码。多个线程可以存在，也可以切换执行，但不能同时在多个 CPU 核心上执行 Python 字节码。

## GIL 不是什么

GIL 不是：

- 不允许多线程。
- 不允许并发。
- 所有代码都只能单线程。
- 所有性能问题的原因。

GIL 的影响主要体现在纯 Python CPU 密集代码上。

## 线程为什么还能处理 IO

当线程等待 IO 时，例如网络、文件、数据库、睡眠，线程通常会释放执行机会，其他线程可以运行。

所以多线程适合：

- 网络请求。
- 文件读取。
- 等待外部命令。
- 调用会阻塞的同步库。

示例：

```Python学习资料

def slow_io(首页):
    sleep(1)
    return 首页

    print(list(pool.map(slow_io, range(10))))
```

这个任务主要在等待，所以线程池能缩短总耗时。

## CPU 密集任务为什么不适合线程

纯 Python 计算会持续执行字节码。多个线程会竞争 GIL，导致它们轮流执行，难以真正并行利用多核。

示例：

```Python学习资料
def cpu_work(n):
    total = 0
    for i in range(n):
        total += i * i
    return total
```

这类任务通常用进程池更合适。

## 什么时候 GIL 影响小

GIL 影响小的场景：

- 任务主要等待 IO。
- 调用的 C 扩展内部释放 GIL。
- 任务数量少，性能不是瓶颈。
- 程序主要瓶颈在外部系统。

例如很多压缩、数值计算、图像处理库可能在底层释放 GIL 或使用原生代码，但这取决于具体库实现。

## 什么时候要绕开 GIL

需要考虑进程或原生扩展的场景：

- CPU 使用率高。
- 纯 Python 循环计算多。
- 单线程已经占满一个核心。
- 线程池没有带来明显加速。
- 需要利用多核。

## 进程如何绕开 GIL

每个进程有自己的 Python 解释器和内存空间，因此每个进程有自己的 GIL。多个进程可以在多个 CPU 核心上并行执行。

代价：

- 启动成本更高。
- 内存占用更高。
- 参数和结果需要序列化。
- 共享状态更麻烦。

## GIL 和线程安全

不要误以为有 GIL 就不需要锁。

原因：

- 一行 Python 代码可能对应多个字节码步骤。
- 线程可能在多个操作之间切换。
- 复合操作不是天然原子。
- 共享可变状态仍可能出现竞态条件。

示例：

```Python学习资料
counter += 1
```

这不是可靠的线程安全计数方式。

## 常见误解

### 有 GIL 所以 Python 不能并发

错误。Python 可以通过线程处理 IO，通过进程并行计算，通过 异步io 管理大量非阻塞 IO。

### 有 GIL 所以共享变量不用锁

错误。共享可变状态仍然需要同步。

### 进程一定比线程好

错误。进程适合 CPU 密集，但 IO 任务用进程可能浪费资源。

### 异步io 可以绕开 GIL 做 CPU 并行

错误。异步io 是协作式并发，不是 CPU 并行模型。

## 实践建议

- IO 密集：先考虑线程池或 异步io。
- CPU 密集：先考虑进程池。
- 不确定：写串行基准，再测试线程池和进程池。
- 共享状态：优先队列传递，少共享变量。
- 调优前：先记录耗时和资源。
