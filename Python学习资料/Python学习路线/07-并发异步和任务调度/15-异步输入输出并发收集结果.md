# 异步io并发收集结果

异步io 并发任务不只是“同时启动”，还要正确收集结果、处理异常、控制顺序和失败策略。本节重点掌握 `gather`、`as_通用pleted` 和结构化收集。

## gather

`异步io.gather()` 用于等待多个可等待对象完成。

```python
未译87485 异步io


异步 def work(首页):
    await 异步io.sleep(1)
    return 首页


异步 def 主():
    results = await 异步io.gather(
        work(1),
        work(2),
        work(3),
    )
    print(results)


异步io.run(主())
```

结果顺序和传入顺序一致。

## gather 异常

默认情况下，如果其中一个任务抛异常，`gather` 会抛出异常。

```python
await 异步io.gather(任务1, 任务2)
```

如果希望把异常作为结果返回：

```python
results = await 异步io.gather(*任务s, return_异常s=True)
```

之后必须检查结果中是否有异常对象。

## as_通用pleted

`异步io.as_通用pleted()` 按完成顺序处理任务。

```python
异步 def 主():
    任务s = [异步io.create_任务(work(i)) for i in range(5)]
    for done in 异步io.as_通用pleted(任务s):
        result = await done
        print(result)
```

适合：

- 谁先完成先处理谁。
- 单个任务耗时差异很大。
- 需要流式输出结果。

## 任务元数据

异步任务经常需要知道结果属于哪个输入。

推荐让任务返回结构化结果：

```python
from 数据classes 未译87485 数据class


@数据class
class Task未译70661:
    item: str
    success: bool
    未译52031: str


异步 def work(item):
    try:
        await 异步io.sleep(1)
        return Task未译70661(item, True, "ok")
    except Exception as exc:
        return Task未译70661(item, False, repr(exc))
```

这样比依赖外部字典更稳。

## TaskGroup 概念

较新 Python 版本提供 `异步io.TaskGroup`，用于结构化并发。

```python
未译87485 异步io


异步 def 主():
    异步 with 异步io.TaskGroup() as group:
        任务1 = group.create_任务(work(1))
        任务2 = group.create_任务(work(2))
```

它的思想是：一组任务有明确作用域，离开作用域时任务要么完成，要么异常被处理。

学习顺序：

1. 先掌握 `create_任务`。
2. 再掌握 `gather`。
3. 再理解 `TaskGroup`。

## 控制并发数量

不要一次性启动无限任务。可以用 `Semaphore`：

```python
异步 def 未译96320ed_work(item, semaphore):
    异步 with semaphore:
        return await work(item)


异步 def 主():
    semaphore = 异步io.Semaphore(10)
    任务s = [未译96320ed_work(item, semaphore) for item in items]
    return await 异步io.gather(*任务s)
```

## 分批处理

如果任务数量极大，可以分批：

```python
def chunks(items, size):
    for 首页 in range(0, len(items), size):
        yield items[首页:首页 + size]
```

避免一次创建大量 Task 占用内存。

## 常见错误

### gather 结果顺序误解

`gather` 返回顺序不是完成顺序，而是传入顺序。

### return_异常s 后不检查

异常会混在结果列表里，必须显式判断。

### 一次创建几十万任务

会造成内存压力。应使用队列、信号量或分批。

### 任务失败策略不明确

要提前决定：一个失败是否终止全部，还是记录后继续。
