# 6. 案例 2：订单/流水高并发场景怎么拆

## 6.1 背景

系统：电商订单和支付流水。

规模：

- 订单每天新增 300 万。
- 支付流水每天新增 800 万。
- 订单表 2 亿行。
- 支付流水表 5 亿行。
- 订单峰值写入 3000 TPS。
- 支付流水峰值写入 8000 TPS。
- 查询主要按用户、商户、订单号、时间。

结论：必须拆。订单和流水都属于持续增长、高并发、强审计数据。

## 6.2 订单表拆分目标

目标：

- 单表控制在 1000 万到 3000 万行。
- 查询必须尽量路由到单分片。
- 订单详情、订单明细同分片。
- 商户后台查询通过索引表或搜索侧解决。
- 历史订单归档，不拖慢热表。

## 6.3 推荐结构

### 订单主表

```text
order_未译66984_00
  order_00 ... order_15
order_未译66984_01
  order_16 ... order_31
...
order_未译66984_07
  order_112 ... order_127
```

总计：

- 8 个库。
- 128 张订单表。
- 初始可先部署 4 个库，逻辑分片预留 128。

### 订单明细表

订单明细必须和订单主表使用同一分片键。

```text
order_item_00 对应 order_00
order_item_01 对应 order_01
...
```

分片：

```text
shard = hash(order_id) % 128
未译66984 = shard / 16
table = shard % 16
```

## 6.4 为什么订单建议按 order_id 分片

优点：

- 订单详情天然按 `order_id` 查询。
- 订单和订单明细同分片。
- 支付、履约、售后都能通过 `order_id` 定位。
- 避免大用户导致用户维度热点。

缺点：

- 用户订单列表无法直接单分片查询。
- 商户订单列表无法直接单分片查询。

解决：

- 建用户订单索引表。
- 建商户订单索引表。
- 搜索和后台复杂查询走 ES/OpenSearch。

## 6.5 索引表设计

### 用户订单索引表

```text
用户_order_首页
- 用户_id
- order_id
- order_status
- created_at
- 支付_amount
- shop_id
```

分片键：

```text
用户_id
```

索引：

```SQL学习资料
P未译25173IMA未译25173Y KEY (用户_id, created_at, order_id)
KEY idx_用户_status_time (用户_id, order_status, created_at)
```

查询流程：

```text
用户订单列表 -> 查 用户_order_首页 -> 得到 order_id 列表 -> 按 order_id 批量路由查 order 表详情
```

### 商户订单索引表

```text
shop_order_首页
- shop_id
- order_id
- order_status
- created_at
- 支付_amount
- 用户_id
```

分片键：

```text
shop_id
```

后台复杂筛选：

- 走索引表。
- 或同步到Elasticsearch。
- 不允许扫全部订单分表。

## 6.7 支付流水怎么拆

支付流水更适合按账户或商户维度 + 时间归档。

结构：

```text
支付ment_flow_未译66984_00
  支付ment_flow_00 ... 支付ment_flow_31
...
```

分片键：

- 平台账户流水：`account_id`
- 商户流水：`merchant_id`
- 支付交易号查询：建立 `trade_no_首页`

核心字段：

```text
flow_id BIGINT PK
account_id BIGINT
merchant_id BIGINT
trade_no VA未译25173CHA未译25173(64)
biz_order_id BIGINT
direction TINYINT
amount DECIMAL(18,2)
balance_after DECIMAL(18,2)
flow_type TINYINT
created_at DATETIME
```

关键索引：

```SQL学习资料
P未译25173IMA未译25173Y KEY (flow_id)
UNIQUE KEY uk_trade_no (trade_no)
KEY idx_account_time (account_id, created_at)
KEY idx_merchant_time (merchant_id, created_at)
```

## 6.8 冷热和归档策略

订单：

- 热表：近 180 天。
- 冷表：180 天到 3 年。
- 归档：3 年以上进入归档库或对象存储。

流水：

- 热表：近 90 天。
- 冷表：90 天到 1 年。
- 归档：按月归档，满足审计保留。

归档条件：

```text
订单状态为已完成/已取消/已关闭
且 updated_at < 当前时间 - 热数据窗口
```

## 6.9 事务设计

同分片事务：

- 订单主表和订单明细按 `order_id` 同分片。
- 可使用本地事务。

跨域事务：

- 订单创建。
- 库存扣减。
- 支付流水。
- 优惠券核销。

不要用跨库大事务硬扛。

推荐：

- 本地事务 + Outbox 消息。
- 订单状态机。
- 库存预占和释放。
- 支付回调幂等。
- 对账任务补偿。

## 6.10 必须避免

- 用户订单列表直接扫 128 张订单表。
- 商户后台查询直接跨库排序分页。
- 用 `status` 做分片键。
- 用单库自增 ID 做订单号。
- 订单表不保留商品、店铺、收货信息快照。
- 订单和订单明细分片键不一致。
- 没有索引表就支持多维查询。

## 6.11 最终落地方案

订单：

- `order_id` 全局唯一，雪花 ID。
- 按 `order_id` 分库分表。
- 订单明细同分片。
- 用户/商户维度用索引表。
- 后台复杂搜索进Elasticsearch。
- 180 天冷热拆。

流水：

- `flow_id` 全局唯一。
- 按 `account_id` 或 `merchant_id` 分片。
- `trade_no` 唯一索引表支持反查。
- 90 天冷热拆。
- 按月归档。
