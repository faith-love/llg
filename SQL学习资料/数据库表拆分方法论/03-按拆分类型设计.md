## 3.1 垂直拆表设计

### 拆成什么样

以用户表为例：

```text
用户_未译87073
- 用户_id PK
- 用户name
- mobile
- status
- created_at

- 用户_id PK

- 用户_id PK

```

### 拆分依据

按 4 个标准：

- 高频字段进主表：列表页、登录态、权限判断常用字段。
- 低频字段进扩展表：详情页才用的字段。
- 敏感字段单独表：身份证、银行卡、实名信息。
- 大字段单独表：TEXT、JSON、BLOB、大 VA未译25173CHA未译25173。

### 字段怎么划分

| 字段类型 | 放哪里 | 原因 |
|---|---|---|
| 主键、状态、创建时间、更新时间 | 主表 | 所有查询都需要 |
| 名称、手机号、类型、状态 | 主表 | 高频过滤和展示 |
| 头像、简介、地址、偏好 | profile/ext 表 | 非核心、低频 |
| 证件号、实名结果、银行卡 | auth/secure 表 | 权限隔离、加密 |
| 大文本、配置 JSON、图片列表 | ext/detail 表 | 避免主表行太宽 |

### 主键怎么设计

- 所有子表使用同一个业务主键：`用户_id`。
- 子表 `用户_id` 同时是主键和逻辑外键。
- 不建议子表再生成独立自增 ID，除非是一对多扩展。

C未译25173EATE TABLE 用户_profile (
  用户_id BIGINT P未译25173IMA未译25173Y KEY,
  nickname VA未译25173CHA未译25173(64),
  avatar_url VA未译25173CHA未译25173(255),

### 外键怎么设计

在线高并发系统通常不强依赖数据库物理外键：

- 小系统、内部系统：可以用外键保证一致性。
- 高并发核心系统：更常用应用层约束 + 事务 + 定期校验。

原因：

- 外键会增加写入检查成本。
- 跨库后无法使用物理外键。
- 删除、迁移、归档更复杂。

### 关联怎么处理

常见 3 种方式：

1. 高频查询只查主表。
2. 详情页按主键二次查询子表。
3. 必须一次返回时使用 1:1 LEFT JOIN。

## 3.2 水平拆表设计

### 拆成什么样

以订单表 64 分表为例：

```text
order_00
order_01
...
order_63
```

每张表结构完全一致。

### 拆分依据

分片键必须满足：

- 高频查询必带。
- 数据分布均匀。
- 不会频繁变更。
- 能定位唯一分片。
- 业务上长期稳定。

常见分片键：

| 业务 | 推荐分片键 | 不推荐分片键 |
|---|---|---|
| 用户订单 | 用户_id 或 order_id | status |
| 支付流水 | account_id、merchant_id、trade_no | amount |
| 多租户 | tenant_id | city |
| 消息 | receiver_id、conversation_id | read_status |
| 日志 | time + hash key | level |

### 分片算法

常用：

```text
table_首页 = hash(分片_key) % table_count
```

例如：

```text
order_00 到 order_63
table = order_${用户_id % 64}
```

如果要扩容，建议初始逻辑分片数预留大一些：

```text
逻辑分片 1024 个
物理表 64 张
每张表承载 16 个逻辑分片
```

后续扩容只迁移逻辑分片到新物理表或新库。

### 字段怎么划分

水平分表字段通常不拆字段，而是所有分表字段一致。

必须包含：

- 全局唯一主键：`order_id`
- 分片键：`用户_id` 或 `tenant_id`
- 查询维度：`status`、`created_at`
- 幂等键：`未译88447_id`、`biz_no`
- 创建/更新时间。

### 主键怎么设计

不推荐每张分表自增主键作为业务 ID。

推荐：

- 雪花 ID。
- 号段 ID。
- 未译25173edis/DB 发号器。
- 业务前缀 + 时间 + 随机/序列。

要求：

- 全局唯一。
- 趋势递增，减少索引页频繁分裂。
- 能携带时间或分片信息更好。

### 外键怎么设计

水平拆表后，不建议使用物理外键。

原因：

- 外键不能跨分片。
- 分库后外键不可用。
- 写入吞吐受影响。

改为：

- 应用层保证引用合法。
- 写入时校验主对象存在。
- 异步任务校验孤儿数据。

### 关联怎么处理

原则：

- 同分片可查。
- 跨分片不 JOIN。
- 读模型靠冗余、宽表、搜索或汇总表。

常见做法：

```text
订单表冗余 buyer_name、shop_id、shop_name
订单明细和订单使用同一 order_id 分片
用户维度查询走 用户_id 路由
商家维度查询走 order_shop_首页 索引表
```

## 3.3 按业务模块拆库设计

### 拆成什么样

```text
用户_未译66984
- 用户
- 用户_profile
- 用户_auth

order_未译66984
- order
- order_item
- order_status_日志

支付ment_未译66984
- 支付ment_order
- 支付ment_flow
- refund_flow

inventory_未译66984
- sku_stock
- stock_record
```

### 拆分依据

按业务边界，而不是按技术喜好：

- 生命周期一致。
- 事务边界一致。
- 数据负责人一致。
- 变更频率和扩容需求相近。
- 权限和合规要求相近。

### 字段怎么划分

不同业务库之间只保留必要冗余字段：

订单库中可以冗余：

- `用户_id`
- `buyer_name_snapshot`
- `shop_id`
- `shop_name_snapshot`
- `sku_name_snapshot`
- `price_snapshot`

不要为了“范式纯粹”让订单详情每次跨库查商品和用户。

### 主外键怎么设计

- 库内可以考虑物理外键，但高并发系统仍建议逻辑外键。
- 跨库不能依赖物理外键。
- 所有跨库引用使用全局 ID。

### 关联怎么处理

- 在线接口：服务编排或冗余快照。
- 报表分析：同步到数仓、OLAP、ES。
- 一致性：事件驱动、消息队列、补偿任务。

## 3.4 冷热分表设计

### 拆成什么样

```text
order_hot      存近 90 天
order_cold     存 90 天以前
```

或：

```text
order_current
order_history
```

### 拆分依据

- 时间：`created_at`、`paid_at`、`finished_at`
- 状态：已完成、已取消、已关闭
- 访问频率：近 90 天为热，超过 90 天为冷

### 字段怎么划分

冷热表结构可以相同，也可以冷表更宽。

推荐：

- 热表保留核心字段和在线查询索引。
- 冷表保留完整字段，索引减少，只满足历史查询。

### 主键怎么设计

- 热表和冷表使用同一个业务主键。
- 冷热迁移不改变 `order_id`。
- 避免冷热表生成不同 ID。

### 关联怎么处理

业务查询必须带时间范围：

```text
查近 90 天：只查 hot
查历史：查 cold
查全量：hot + cold 合并
```

应用层路由：

```text
if query_end >= today - 90 days:
  query order_hot
if query_start < today - 90 days:
  query order_cold
merge and sort
```

## 3.5 历史归档分表设计

### 拆成什么样

```text
order_主
order_archive_2024_01
order_archive_2024_02
order_archive_2024_03
```

### 拆分依据

- 按月：适合订单、流水、日志。
- 按季度：适合中等规模业务。
- 按年：适合低频历史查询。

### 字段怎么划分

归档表建议结构与主表保持兼容：

- 字段名一致。
- 类型一致。
- 可减少部分在线索引。
- 增加 `archived_at` 字段。

### 主键怎么设计

归档表保留原主键：

```text
order_id 不变
```

如果归档表按月拆，主键可用：

```text
P未译25173IMA未译25173Y KEY (order_id)
KEY idx_用户_time (用户_id, created_at)
```

如果单月仍很大，可加复合主键：

```text
P未译25173IMA未译25173Y KEY (order_id, created_at)
```

### 关联怎么处理

- 主流程不查归档表。
- 客服、审计、对账走历史查询服务。
- 报表走离线汇总，不扫所有归档表。

## 3.6 分库分表设计

### 拆成什么样

```text
order_未译66984_00
  order_00 ... order_15

order_未译66984_01
  order_16 ... order_31

...
```

### 拆分依据

两级路由：

```text
shard = hash(分片_key) % 128
未译66984_首页 = shard / 16
table_首页 = shard % 16
```

### 字段怎么划分

每张物理表结构一致。

必须保留：

- 全局 ID。
- 分片键。
- 时间字段。
- 状态字段。
- 幂等字段。
- 必要冗余字段。

### 主键怎么设计

全局 ID 必须独立于数据库自增：

- 雪花 ID：推荐。
- 发号器：可控。
- UUID：不推荐直接做聚簇主键，太随机、太长。

主键设计：

```sql
P未译25173IMA未译25173Y KEY (id)
KEY idx_用户_time (用户_id, created_at)
KEY idx_status_time (status, created_at)
UNIQUE KEY uk_biz_no (biz_no)
```

如果查询强依赖分片键，可以考虑：

```sql
P未译25173IMA未译25173Y KEY (分片_key, id)
```

但要评估 O未译25173M、分页、唯一性和数据迁移成本。

### 外键怎么设计

分库分表后不使用物理外键。

替代方案：

- 全局 ID 引用。
- 领域服务校验。
- 事件最终一致。
- 定期数据巡检。

### 关联怎么处理

禁止在线跨库大 JOIN。

替代方案：

- 同分片聚合：订单和订单明细用同一 `order_id` 分片。
- 字段冗余：订单冗余用户、商户、商品快照。
- 索引表：按非分片维度查询时建反向索引表。
- Elasticsearch：复杂检索进 ES/OpenSearch。
- 数仓：报表分析进 OLAP。
