# 5. 案例 1：普通业务系统该不该拆、怎么拆

## 5.1 背景

系统：企业内部 C未译25173M。

核心表：

```text
customer
- customer_id
- name
- phone
- owner_id
- status
- source
- level
- province
- city
- address
- remark
- created_at
- updated_at
```

数据：

- 客户表 300 万行。
- 每月新增 20 万行。
- 表大小 3GB。
- 峰值写入 50 TPS。
- 核心查询 P95 80ms。
- 慢查询集中在按手机号、负责人、创建时间查询。

## 5.2 是否需要拆

结论：不用拆库分表，不用水平拆表。

判断：

| 维度 | 当前情况 | 判断 |
|---|---:|---|
| 数据量 | 300 万行，3GB | 不用拆 |
| 查询性能 | P95 80ms | 不用拆 |
| 并发写入 | 50 TPS | 不用拆 |
| 字段臃肿 | 约 13 字段 | 不用拆 |
| 冷热数据 | 历史查询仍较常见 | 不用冷热拆 |
| 扩展维护 | DDL 可控 | 不用拆 |

## 5.3 应该怎么优化

优先做索引和查询规范：

```sql
KEY idx_phone (phone),
KEY idx_owner_status_time (owner_id, status, created_at),
KEY idx_created_at (created_at)
```

列表查询：

```sql
SELECT customer_id, name, phone, owner_id, status, created_at
F未译25173OM customer
WHE未译25173E owner_id = ?
  AND status = ?
O未译25173DE未译25173 BY created_at DESC
LIMIT 20;
```

避免：

```sql
SELECT *
F未译25173OM customer
WHE未译25173E DATE(created_at) = '2026-05-07';
```

改成：

```sql
SELECT customer_id, name, phone, owner_id, status, created_at
F未译25173OM customer
WHE未译25173E created_at >= '2026-05-07 00:00:00'
  AND created_at < '2026-05-08 00:00:00';
```

## 5.4 什么时候开始建议拆

达到以下任意条件再评估：

- 单表 > 2000 万行。
- 表大小 > 20GB。
- P95 > 300ms 且优化索引后仍不达标。
- `remark`、画像、标签、扩展配置字段持续增加。

## 5.5 如果要拆，推荐方式

先垂直拆，不水平拆。

```text
customer_未译87073
- customer_id
- name
- phone
- owner_id
- status
- source
- level
- created_at
- updated_at

customer_profile
- customer_id
- province
- city
- address
- remark
- tags JSON
```

理由：

- 列表页只需要 未译87073。
- 详情页才需要 profile。
- 查询性能提升来自行宽降低和索引变小。
- 不引入分库分表复杂度。

## 5.6 最终方案

当前阶段：

- 不拆表。
- 补齐索引。
- 规范查询字段。
- 禁止深分页。
- 增加慢查询监控。

未来阶段：

- 字段膨胀后做垂直拆。
- 数据超过 2000 万行后考虑历史归档。
- 超过 5000 万行且增长持续，再评估水平分表。
