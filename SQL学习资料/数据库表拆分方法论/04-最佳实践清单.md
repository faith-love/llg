# 4. 库表拆分最佳实践和避坑清单

## 4.1 拆分时机

### 正确时机

- 单表已接近 5000 万行，且未来 6 到 12 个月会继续高速增长。
- 核心查询 P95 > 500ms，SQL 和索引优化后仍无法达标。
- 历史数据 > 90%，核心查询只查近期。
- 字段 > 100 或平均行长 > 8KB。
- 写入峰值 > 1000 TPS，锁等待和主从延迟无法通过单机优化解决。
- DDL、备份、恢复、索引重建已经影响发布和运维。

### 错误时机

- 刚建系统就做复杂分库分表。
- 数据只有几十万到几百万行，只是查询没建索引。
- 业务边界还没稳定。
- 团队没有分布式事务、数据校验、扩容迁移能力。
- 只是因为“以后可能很大”。

## 4.2 拆分前必须先做的优化

拆表前先确认这些项：

- 慢查询是否有合适索引。
- 是否存在 `SELECT *`。
- 是否有深分页，例如 `LIMIT 1000000, 20`。
- 是否有函数包裹索引列，例如 `DATE(created_at) = ...`。
- 是否有低效模糊查询，例如 `LIKE '%keyword%'`。
- 是否有过多二级索引。
- 是否可以用缓存、读写分离、归档解决。
- 是否可以用垂直拆表解决，而不是直接分库分表。

## 4.3 主键设计原则

### 总原则

- 全局唯一。
- 趋势递增。
- 短字段优先。
- 不依赖单表自增作为全局业务 ID。
- 能支持幂等和排查。

### 推荐方案

| 方案 | 适用 | 优点 | 风险 |
|---|---|---|---|
| 雪花 ID | 大多数分库分表业务 | 全局唯一、趋势递增、性能高 | 机器号和时钟回拨治理 |
| 号段模式 | 高并发核心交易 | 可控、批量获取、性能好 | 发号中心可用性 |
| UUID/ULID | 跨系统生成 | 去中心化 | UUID 太长且随机，不适合聚簇主键 |
| 数据库自增 | 单库单表 | 简单 | 分库分表后冲突 |

### 不推荐

- 用手机号、身份证号、邮箱作为主键。
- 用随机 UUID 直接做 InnoDB 聚簇主键。
- 分表后仍依赖每张表自增 ID 当业务 ID。

## 4.4 分片键设计原则

好的分片键：

- 高频查询必带。
- 数据分布均匀。
- 不会变。
- 能定位到单个分片。
- 和业务边界一致。

差的分片键：

- `status`：低基数，热点严重。
- `created_at` 单独作为 hash 分片键：时间热点明显。
- `city`：分布不均。
- 可变字段：迁移成本高。

常见选择：

| 业务 | 推荐分片键 |
|---|---|
| 用户订单 | 用户_id 或 order_id |
| 商户订单 | merchant_id + order_id 设计索引表 |
| 支付流水 | account_id、merchant_id、trade_no |
| 多租户 | tenant_id |
| 消息 | conversation_id 或 receiver_id |
| IoT 数据 | device_id + time |

## 4.5 索引设计

### 垂直拆表

- 主表索引服务核心列表和状态查询。
- 子表以主键为核心，少建索引。
- 大字段表不要为低频字段建过多索引。

### 水平拆表

每张分表索引结构保持一致。

常见索引：

```sql
P未译25173IMA未译25173Y KEY (id)
KEY idx_分片_time (用户_id, created_at)
KEY idx_status_time (status, created_at)
UNIQUE KEY uk_biz_no (biz_no)
```

### 冷热/归档表

- 热表索引服务在线接口。
- 冷表索引服务客服、审计、对账。
- 归档表不要照搬热表所有索引。

### 索引避坑

- 单表索引不要无限增加，> 8 个就要评审。
- 联合索引遵循最左前缀。
- 区分度低的单列索引价值有限。
- 写多读少表要控制索引数量。

## 4.6 联表查询限制

### 拆分后仍可 JOIN

- 垂直拆表后，同库 1:1 表可以 JOIN。
- 冷热分表内单独查热表或冷表可以 JOIN。
- 同分片内小范围 JOIN 可以接受。

### 不建议 JOIN

- 跨库 JOIN。
- 跨多个分片 JOIN。
- 在线接口跨几十张分表聚合后排序分页。

### 替代方案

- 字段冗余。
- 快照字段。
- 索引表。
- 查询服务聚合。
- Elasticsearch。
- 数仓/OLAP。

## 4.7 跨表事务

### 单库内

垂直拆表后的 1:1 多表写入，可以使用本地事务：

```text
begin
  insert 用户_未译87073
  insert 用户_profile
通用mit
```

### 跨库后

不建议依赖 XA 作为常规方案。

推荐：

- 本地事务 + 可靠消息。
- Outbox 表。
- Saga 补偿。
- TCC 只用于强一致核心场景。

### 判断标准

- 钱、库存、额度：强一致，设计专门事务方案。
- 画像、统计、消息通知：最终一致。
- 报表、搜索索引：异步一致。

## 4.8 数据同步

常见同步场景：

- 旧表到新表双写。
- 热表到冷表迁移。
- 业务库到Elasticsearch。
- 业务库到数仓。

推荐流程：

1. 建新表。
2. 全量迁移历史数据。
3. 增量同步 bin日志 或双写。
4. 校验新旧数据。
5. 灰度读新表。
6. 全量切读。
7. 停旧写。
8. 保留回滚窗口。

校验指标：

- 行数一致。
- 主键集合一致。
- 核心字段 checksum 一致。
- 增量延迟可控。
- 异常数据可补偿。

## 4.9 扩容预留

### 初始分片数

不要只按当前量设置。

建议：

- 当前 1000 万级：16 或 32 逻辑分片。
- 当前 1 亿级：64 或 128 逻辑分片。
- 未来 10 亿级：256 到 1024 逻辑分片。

### 逻辑分片和物理分片分离

推荐：

```text
逻辑分片 1024
当前物理库 4 个
当前物理表 64 张
逻辑分片映射到物理位置
```

扩容时迁移部分逻辑分片，不改变业务分片算法。

## 4.10 归档策略

必须提前定义：

- 热数据窗口：例如 90 天。
- 归档周期：每天、每周、每月。
- 归档条件：状态已完结 + 超过 N 天。
- 校验方式：行数、checksum、抽样。
- 查询入口：历史查询服务。
- 保留周期：按合规要求。
- 删除策略：软删、硬删、冷存储。

归档任务要求：

- 幂等。
- 可重试。
- 限速。
- 可暂停。
- 有监控。
- 有回滚窗口。

## 4.11 避坑清单

### 设计坑

- 没有分片键就分库分表。
- 分片键选择低基数字段。
- 用可变字段做分片键。
- 不预留扩容空间。
- 拆完仍要求跨分片 JOIN。
- 忽略历史数据查询入口。

### 主键坑

- 分库分表后仍用单表自增 ID。
- 用随机 UUID 做聚簇主键。
- ID 无法按时间排查。
- 没有幂等唯一键。

### 查询坑

- 在线接口跨所有分表查。
- 跨分片排序分页。
- 统计报表直接扫 OLTP 分表。
- 非分片维度查询没有索引表。

### 事务坑

- 拆库后还假设本地事务可用。
- 依赖跨库强一致但无补偿。
- 没有处理消息重复、乱序、丢失。

### 运维坑

- 没有迁移校验。
- 没有灰度读写。
- 没有回滚方案。
- 没有分片级监控。
- 备份恢复粒度没重新设计。

## 4.12 推荐评审清单

拆表方案上线前必须回答：

- 当前数据量和 12 个月后数据量是多少？
- 当前 P95/P99、TPS、慢查询、锁等待是多少？
- 分片键是什么，为什么？
- 查询是否都能带分片键？
- 不带分片键的查询怎么处理？
- 主键如何全局唯一？
- 是否需要跨表/跨库事务？
- 历史数据如何归档？
- 如何全量迁移和增量同步？
- 如何校验数据一致？
- 如何灰度和回滚？
- 如何扩容？
