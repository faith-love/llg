# 7. 案例 3：大宽表字段臃肿如何垂直拆分

## 7.1 背景

系统：商品中心。

原表：

```text
product
- product_id
- shop_id
- category_id
- title
- subtitle
- status
- sale_price
- stock
- brand_id
- created_at
- updated_at
- detail_html TEXT
- image_urls JSON
- spec_脚本on JSON
- audit_status
- audit_reason
- audit_operator
- audit_time
- seo_title
- seo_keywords
- seo_description
- risk_score
- risk_tags JSON
- extra_配置 JSON
- 其他扩展字段...
```

问题：

- 字段 130 个。
- 平均行长 12KB。
- 商品列表只需要 12 个字段。
- `detail_html`、`image_urls`、`spec_脚本on` 很大。
- 商品列表 P95 700ms。
- buffer pool 命中率下降。
- 给表加字段和索引越来越慢。

结论：必须垂直拆表。

## 7.2 拆分目标

- 主表控制在 30 个字段以内。
- 商品列表只查主表。
- 大字段从主表移除。
- 审核、风控、SEO、扩展配置按业务边界拆。
- 详情页按需组装。

## 7.3 推荐拆分结构

### 商品基础表

```text
product_base
- product_id PK
- shop_id
- category_id
- brand_id
- title
- subtitle
- status
- sale_price
- stock
- created_at
- updated_at
```

用途：

- 列表页。
- 搜索同步。
- 上下架。
- 价格库存展示。

### 商品详情表

```text
product_detail
- product_id PK
- detail_html TEXT
- image_urls JSON
- spec_脚本on JSON
- after_sale_policy TEXT
- updated_at
```

用途：

- 商品详情页。
- 图文详情编辑。

### 商品审核表

```text
product_audit
- product_id PK
- audit_status
- audit_reason
- audit_operator
- audit_time
- last_submit_time
```

用途：

- 审核后台。
- 审核流转。

### 商品 SEO 表

```text
product_seo
- product_id PK
- seo_title
- seo_keywords
- seo_description
```

用途：

- SEO 页面。
- 低频运营配置。

### 商品风控表

```text
product_risk
- product_id PK
- risk_score
- risk_level
- risk_tags JSON
- risk_updated_at
```

用途：

- 风控系统。
- 违规识别。

### 商品扩展配置表

```text
product_ext
- product_id PK
- extra_配置 JSON
- feature_flags JSON
- updated_at
```

用途：

- 非核心扩展字段。
- 灰度能力。
- 临时业务配置。

## 7.4 字段划分规则

| 字段类别 | 表 | 判断标准 |
|---|---|---|
| 列表页字段 | product_base | 高频展示、过滤、排序 |
| 交易核心字段 | product_base | 价格、库存、状态 |
| 大文本/图片/规格 | product_detail | 大字段、详情页才用 |
| 审核状态和原因 | product_audit | 审核域独立 |
| SEO 字段 | product_seo | 低频运营配置 |
| 风控分数和标签 | product_risk | 权限和业务域独立 |
| 临时扩展 JSON | product_ext | 非核心、低频、变化快 |

## 7.5 主键设计

所有 1:1 子表使用：

```text
product_id PK
```

不为 `product_detail`、`product_audit` 生成单独 ID。

原因：

- 保持 1:1 关系简单。
- 查询时按 `product_id` 直接定位。
- 迁移和校验容易。

## 7.6 外键设计

推荐逻辑外键，不强制物理外键。

原因：

- 商品写入和更新频繁。
- 后续可能按商品 ID 水平拆分。
- 物理外键会增加批量导入、迁移、删除复杂度。

必须做的应用约束：

- 创建子表前必须存在 `product_base`。
- 删除商品时统一走服务，不允许直接删主表。
- 定期校验孤儿数据。

## 7.7 查询方式

### 商品列表

只查主表：

```sql
SELECT product_id, shop_id, title, status, sale_price, stock, updated_at
FROM product_base
WHERE shop_id = ?
  AND status = ?
ORDER BY updated_at DESC
LIMIT 20;
```

### 商品详情

按需 JOIN 或二次查询：

```sql
SELECT
  b.product_id,
  b.title,
  b.sale_price,
  b.stock,
  d.detail_html,
  d.image_urls,
  d.spec_脚本on
FROM product_base b
LEFT JOIN product_detail d ON b.product_id = d.product_id
WHERE b.product_id = ?;
```

### 审核后台

只查审核域字段：

```sql
SELECT b.product_id, b.title, a.audit_status, a.audit_reason, a.audit_time
FROM product_audit a
JOIN product_base b ON a.product_id = b.product_id
WHERE a.audit_status = ?
ORDER BY a.audit_time DESC
LIMIT 50;
```

## 7.8 索引设计

`product_base`：

```sql
PRIMARY KEY (product_id)
KEY idx_shop_status_time (shop_id, status, updated_at)
KEY idx_category_status (category_id, status)
KEY idx_brand_status (brand_id, status)
```

`product_detail`：

```sql
PRIMARY KEY (product_id)
```

`product_audit`：

```sql
PRIMARY KEY (product_id)
KEY idx_audit_status_time (audit_status, audit_time)
```

`product_risk`：

```sql
PRIMARY KEY (product_id)
KEY idx_risk_level_time (risk_level, risk_updated_at)
```

## 7.9 迁移步骤

1. 创建新表。
2. 双写新旧字段。
3. 全量回填子表。
4. 校验行数和核心字段 checksum。
5. 灰度详情页读新表。
6. 列表页改读 `product_base`。
7. 停止旧表大字段写入。
8. 观察一个完整业务周期。
9. 清理旧字段。

## 7.10 预期收益

拆前：

- 主表 130 字段。
- 平均行长 12KB。
- 列表 P95 700ms。

拆后：

- `product_base` 约 12 到 20 字段。
- 平均行长 < 1KB。
- 列表 P95 可降到 100ms 到 200ms 区间。
- 大字段只在详情页读取。
- 审核、风控、SEO 独立迭代。

## 7.11 必须避免

- 把所有字段拆成过多小表，导致详情页 JOIN 十几张表。
- 子表使用独立自增主键，增加关联复杂度。
- 列表页继续 JOIN 大字段表。
- 大字段表建立大量无效索引。
- 没有双写和校验就直接切读。
