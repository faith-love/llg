# 监控日志埋点与可观测性

前端可观测性的目标是回答四个问题：发生了什么、影响了谁、从哪个版本开始、应该怎么定位。只有错误日志而没有版本、用户、路由、source map 和性能上下文，线上排障仍然会很困难。

## 可观测性组成

| 类型 | 关注点 |
| --- | --- |
| Error | JS 异常、Promise rejection、资源加载失败 |
| RUM | 页面加载、性能指标、用户环境 |
| Log | 关键业务日志、状态变化、降级记录 |
| Trace | 前端请求和后端链路关联 |
| Event | 用户行为、转化、实验曝光 |
| Release | 版本、commit、构建、source map |

## 错误监控

至少采集：

- error message。
- stack trace。
- source map 后的源码位置。
- release version。
- route。
- browser、OS、device。
- 用户匿名标识。
- 发生次数和影响用户数。
- 最近部署版本。

要避免采集敏感信息，例如 token、手机号、身份证、完整地址。

## source map 策略

生产 source map 需要上传到监控平台，但不建议公开暴露。

流程：

```text
build -> generate sourcemap -> upload with release -> deploy assets -> monitor maps stack
```

关键是 release 要一致。构建产物、source map、监控事件必须使用同一个版本标识。

## 白屏监控

白屏不是一种单独错误，而是一类结果。可能原因：

- JS 资源加载失败。
- 初始化异常。
- 接口阻塞。
- 路由权限异常。
- CSS 或字体异常。
- 根节点未渲染。

可以监控：

- 根节点是否有内容。
- 首屏关键容器是否渲染。
- 资源加载错误。
- 初始化阶段耗时。
- 未捕获异常。

## 请求监控

前端请求要记录：

- URL 模板，不要记录完整敏感参数。
- method。
- status。
- duration。
- trace id。
- error code。
- 是否重试。
- 是否命中降级。

如果后端也有 trace，前端请求头可以携带 trace id，方便串联全链路。

## 埋点治理

埋点不是随便 `track('click')`。

需要治理：

- 事件命名规范。
- 属性字段规范。
- 曝光、点击、提交、成功、失败的语义。
- 埋点类型定义。
- 数据校验。
- Feature Flag 和实验维度。
- 隐私合规。

TypeScript 可以约束埋点：

```typescript
type AnalyticsEvent =
  | { name: 'user_search'; keyword: string; resultCount: number }
  | { name: 'order_submit'; orderId: string; amount: number }
```

## 告警

告警要基于用户影响，不只基于事件数量。

更合理的告警条件：

- 某版本错误率超过阈值。
- 白屏率超过阈值。
- 支付页接口失败率超过阈值。
- LCP 或 INP P75 明显劣化。
- 某 Feature Flag 用户错误集中上升。

## 落地清单

- 错误是否能还原到源码行？
- 监控事件是否包含 release、route、用户环境？
- 是否能区分发生次数和影响用户数？
- 是否有白屏、资源失败、接口失败监控？
- 埋点是否有类型和命名规范？
- 告警是否能关联版本、页面和负责人？

## 深入展开：可观测性要连接 release 和用户影响

前端监控的高级要求是能做关联分析：

```text
错误事件
  -> release
  -> source map
  -> 页面路径
  -> 用户环境
  -> Feature Flag
  -> 请求 trace
  -> 影响用户数
```

只看错误次数会误导决策。一个错误发生一万次但只影响一个用户，和一个错误发生一百次但影响一百个支付用户，优先级完全不同。

埋点也要区分业务事件和技术事件：

| 类型 | 示例 |
| --- | --- |
| 业务事件 | 搜索、提交订单、保存配置 |
| 技术事件 | chunk 加载失败、白屏、接口超时 |
| 实验事件 | flag 曝光、实验分组、目标转化 |

三类事件最好都带 release 和环境信息，方便发布后观察变化。
