# 构建体系选型与统一配置

构建体系的核心不是“哪个工具最快”，而是把源码稳定转成可部署、可调试、可缓存、可回滚的产物。高级工程化要能区分不同工具的职责，并把它们组合成适合团队的标准构建链路。

## 构建链路

```text
源代码
  -> 类型检查
  -> 语法转换
  -> 模块解析
  -> 依赖图构建
  -> 资源处理
  -> tree-shaking
  -> 分包
  -> 压缩
  -> source map
  -> manifest
  -> dist
```

不是每个工具都做所有步骤。混淆职责会导致排障困难。

## 工具职责

| 工具 | 主要职责 |
| --- | --- |
| TypeScript Compiler | 类型检查、声明文件生成、部分语法降级 |
| Babel | 语法转换、JSX 转换、插件化 AST 改写 |
| SWC / esbuild | 高性能语法转换、压缩、部分打包能力 |
| Vite | 开发服务器、预构建、生产构建集成 |
| Webpack | 依赖图、loader、plugin、复杂资源打包 |
| Rollup | ESM 优先的打包和库构建 |
| Rspack | 兼容 Webpack 生态的高性能打包器 |
| minifier | 压缩、dead code、mangle、注释剔除 |

更细的 Babel 和 bundler 流程可以回到 [Babel 工程化深入理解](../Babel工程化深入理解/说明.md)。

## 应用项目和库项目不同

| 项目类型 | 构建目标 |
| --- | --- |
| 应用 | 输出 HTML、JS、CSS、静态资源，部署到 CDN 或服务器 |
| 组件库 | 输出 ESM/CJS/types/style，供其他项目安装 |
| SDK | 输出浏览器、Node 或多运行时版本 |
| SSR 应用 | 同时输出 client bundle 和 server bundle |

应用关注页面加载和缓存，库关注模块格式、类型声明、sideEffects、peer dependencies 和兼容性。

## 统一配置策略

中大型团队不要让每个项目手写一套配置。

推荐拆成内部配置包：

```text
packages/
  config-eslint/
  config-ts/
  config-vite/
  config-vitest/
```

应用侧只保留少量业务差异：

```typescript
import { defineAppConfig } from '@repo/config-vite'

export default defineAppConfig({
  entry: 'src/main.tsx',
  product: 'admin',
  analyze: true
})
```

统一配置的关键是可扩展，不是强行覆盖所有项目。配置包要允许业务项目添加别名、代理、插件和特殊构建参数。

## 构建模式

| 模式 | 关注点 |
| --- | --- |
| development | 快速启动、HMR、错误定位 |
| test | 稳定、可 mock、和 CI 兼容 |
| staging | 接近生产、接入测试环境服务 |
| production | 压缩、缓存、source map 策略、监控关联 |

不要把环境配置写死在构建脚本里。构建模式、部署环境和运行时配置要分清楚。

## 构建产物检查

生产构建后应该检查：

- 是否生成 manifest。
- JS/CSS 是否带内容 hash。
- source map 是否按策略生成和上传。
- 静态资源是否进入正确目录。
- 包体是否超过预算。
- polyfill 是否符合目标浏览器。
- 动态 import 是否拆包合理。
- 第三方依赖是否被重复打包。

## 常见问题定位

| 问题 | 优先检查 |
| --- | --- |
| 语法不兼容 | Babel/SWC targets、Browserslist、polyfill |
| 类型通过但运行失败 | TS 只做类型检查，不保证运行时契约 |
| 依赖被打进库产物 | external、peerDependencies 配置 |
| tree-shaking 无效 | 模块格式、sideEffects、副作用代码 |
| sourcemap 对不上 | minifier、上传版本、release 标识 |
| 构建慢 | 缓存、并行、预构建、loader/plugin 瓶颈 |

## 落地清单

- 是否明确每个工具负责什么？
- 应用构建和库构建是否分开设计？
- 构建配置是否可复用但允许局部扩展？
- 生产构建是否有产物分析和预算？
- source map 是否能关联线上版本？
- 构建失败是否能快速定位到类型、转换、打包还是压缩阶段？

## 深入展开：把 Babel 放进构建治理

构建体系不能只选一个工具名，还要把每个阶段的责任边界写清楚。Babel 应该作为“语法和 AST 转换层”纳入构建治理，而不是被模糊地叫成“打包工具”。

| 阶段 | 关键问题 | 需要沉淀的配置 |
| --- | --- | --- |
| 语法解析 | 项目到底允许哪些语法 | parser plugin、TS/JSX/decorators 配置 |
| 语法转换 | 目标环境需要降级到什么程度 | preset-env、targets、Browserslist |
| 运行时兼容 | API 和 generator 怎么兼容 | core-js、regenerator、transform-runtime |
| 模块打包 | 依赖图和 chunk 如何生成 | Vite/Webpack/Rollup/Rspack 配置 |
| 产物优化 | 如何压缩、分包、缓存和分析 | minifier、manualChunks、analyzer、budget |
