# SSR SSG ISR 与全栈前端

渲染模式会影响首屏性能、SEO、缓存、部署、数据一致性和故障边界。高级前端工程化要能根据页面类型选择 CSR、SSR、SSG、ISR 或混合模式，而不是所有页面都用同一种方案。

## 常见渲染模式

| 模式 | 含义 | 适合场景 |
| --- | --- | --- |
| CSR | 浏览器下载 JS 后渲染 | 后台系统、强交互应用 |
| SSR | 请求时服务端渲染 HTML | SEO、首屏要求高、数据实时 |
| SSG | 构建时生成静态 HTML | 文档、博客、营销页 |
| ISR | 静态页面按策略增量再生成 | 内容站、商品详情、半实时页面 |
| Islands | 页面局部组件水合 | 内容为主、少量交互 |

## CSR 的特点

优点：

- 部署简单。
- 前后端边界清晰。
- 适合复杂交互。

缺点：

- 首屏依赖 JS。
- SEO 和弱网体验较差。
- 白屏风险更明显。

管理后台通常可以用 CSR，因为用户登录后使用，SEO 不是主要目标。

## SSR 的特点

优点：

- 首屏 HTML 更快可见。
- SEO 更友好。
- 可以在服务端完成部分数据预取。

成本：

- 需要 Node 或边缘运行时。
- 服务端和客户端代码都要构建。
- 水合不一致问题。
- 缓存和故障边界更复杂。

SSR 不等于性能一定好。如果服务端响应慢、数据接口慢、JS 仍然很大，用户体验仍然会差。

## SSG 和 ISR

SSG 适合内容稳定的页面：

- 文档。
- 博客。
- 帮助中心。
- 营销落地页。

ISR 适合大量页面但不要求每次实时：

- 商品详情。
- 内容详情。
- 分类页。

关键是制定缓存和再生成策略：

```text
页面缓存多久
数据变更如何触发刷新
生成失败是否保留旧页面
```

## 水合问题

SSR/SSG 页面通常需要 hydration，让静态 HTML 绑定客户端交互。

常见问题：

- 服务端和客户端时间、随机数不同。
- 依赖 `window` 的代码在服务端执行。
- 用户状态导致 HTML 不一致。
- 国际化或主题在两端不同。

治理方式：

- 区分 server-only 和 client-only 代码。
- 对不稳定值延迟到客户端渲染。
- 统一数据序列化。
- 在 CI 中跑 SSR 构建和 smoke。

## 缓存层

SSR 系统通常有多层缓存：

```text
浏览器缓存
  -> CDN
  -> 边缘缓存
  -> Node 服务缓存
  -> 数据接口缓存
```

性能问题要看整条链路，不要只看前端 bundle。

## 选型建议

| 页面类型 | 推荐 |
| --- | --- |
| 管理后台 | CSR |
| 文档站 | SSG |
| 营销页 | SSG 或 SSR |
| 商品详情 | ISR 或 SSR |
| 搜索结果 | SSR 或 CSR，取决于 SEO |
| 高交互编辑器 | CSR，局部 SSR 意义有限 |

## 落地清单

- 页面是否真的需要 SEO 或更快首屏？
- SSR 的服务端运行、监控和扩容是否准备好？
- 数据缓存和页面缓存策略是否明确？
- 是否有 hydration mismatch 检查？
- 服务端错误是否能独立监控和回滚？
- 是否能按页面选择不同渲染模式？

## 深入展开：渲染模式要和缓存策略一起设计

选择 SSR、SSG、ISR 不能只看首屏和 SEO，还要看缓存和失效策略。

| 模式 | 核心问题 |
| --- | --- |
| CSR | JS 下载和执行前用户看到什么 |
| SSR | 每次请求的服务端成本和失败降级 |
| SSG | 构建时间和内容更新延迟 |
| ISR | 页面重新生成失败时是否保留旧页面 |
| Islands | 哪些区域需要交互，哪些保持静态 |

SSR 项目要额外监控服务端：

```text
server render error
data fetch duration
cache hit rate
hydration mismatch
edge or node runtime memory
```

否则团队只会用前端监控看浏览器错误，却看不到服务端渲染链路的问题。
