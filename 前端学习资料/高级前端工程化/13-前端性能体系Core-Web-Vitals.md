# 前端性能体系 Core Web Vitals

前端性能不是只看打包体积。用户感受到的性能包括页面何时显示、何时可交互、交互是否卡顿、布局是否跳动、接口是否慢、长任务是否阻塞。Core Web Vitals 提供了一组适合长期治理的用户体验指标。

## 核心指标

| 指标 | 含义 | 常见影响因素 |
| --- | --- | --- |
| LCP | 最大内容绘制，衡量主要内容出现速度 | 服务器响应、图片、字体、阻塞资源 |
| INP | 交互到下一次绘制，衡量整体交互响应 | 长任务、JS 执行、主线程阻塞 |
| CLS | 累积布局偏移，衡量视觉稳定性 | 图片无尺寸、广告插入、字体切换 |

不要只在 Lighthouse 中看一次分数。真实用户设备、网络、地区、页面路径不同，表现会差很多。

## Lab 和 RUM

| 类型 | 含义 | 价值 |
| --- | --- | --- |
| Lab | 实验室环境测试 | 可重复、适合开发阶段定位问题 |
| RUM | 真实用户监控 | 反映真实设备、网络和用户路径 |

高级工程化需要两者结合：

```text
开发阶段用 Lab 定位
上线后用 RUM 评估真实影响
```

## LCP 优化

常见手段：

- 优化服务器响应时间。
- 首屏图片使用合适尺寸和格式。
- 对关键图片设置 preload 或优先级。
- 减少阻塞渲染的 CSS 和 JS。
- 使用 CDN 和缓存。
- SSR 或 SSG 提前输出首屏内容。

排查顺序：

```text
TTFB -> 资源加载 -> 渲染阻塞 -> LCP 元素渲染
```

## INP 优化

INP 关注整个页面生命周期里的交互响应。

常见问题：

- 大量 JS 首屏执行。
- 点击后同步计算太重。
- 列表渲染没有虚拟化。
- 输入框联动太多状态更新。
- 第三方脚本阻塞主线程。

优化手段：

- 拆分长任务。
- 延迟非关键 JS。
- 对列表做虚拟滚动。
- 对输入做 debounce 或 transition。
- Web Worker 处理重计算。
- 减少重复渲染。

## CLS 优化

布局偏移通常来自：

- 图片、视频、iframe 没有宽高。
- 字体加载后文字尺寸变化。
- 动态插入 banner、广告、提示条。
- 骨架屏和真实内容尺寸差异大。

治理方式：

- 给媒体资源预留尺寸。
- 对动态区域预留空间。
- 字体使用合理 fallback 和加载策略。
- 不在用户阅读区域上方突然插入内容。

## 性能预算和发布门禁

性能指标要进入工程流程：

```text
PR: 包体预算 + Lighthouse smoke
Staging: 关键页面 Lab 测试
Production: RUM P75 指标 + 告警
```

建议按页面类型设置预算：

- 首页。
- 登录页。
- 搜索页。
- 详情页。
- 结算页。
- 管理后台核心列表页。

## 数据分维度分析

RUM 数据要能按维度拆：

- 页面路径。
- 设备类型。
- 浏览器。
- 网络类型。
- 地区。
- 版本。
- 用户类型。
- 是否命中特定 Feature Flag。

否则只能看到平均值，无法定位真实瓶颈。

## 落地清单

- 是否采集 LCP、INP、CLS？
- 是否按 P75 而不是平均值评估？
- 是否能按页面、版本、设备、地区拆分？
- 性能预算是否进入 PR 或发布门禁？
- 是否能把性能问题关联到具体 release？
- 是否有性能回归告警和负责人？

## 深入展开：从指标倒推工程动作

Core Web Vitals 不能只做报表，要能倒推工程动作。

| 指标变差 | 常见工程动作 |
| --- | --- |
| LCP 变差 | 优化首屏接口、关键图片、SSR/SSG、预加载、CDN |
| INP 变差 | 拆长任务、减少重复渲染、虚拟列表、延迟第三方脚本 |
| CLS 变差 | 预留图片尺寸、稳定骨架屏、控制动态插入区域 |

建议把性能问题按页面和版本建立责任链：

```text
页面路径 -> 版本 -> 指标劣化 -> 具体资源或交互 -> 修复 PR -> 发布后回看
```

如果性能预算只在 PR 阶段看 Lighthouse，而没有线上 RUM 回看，就很容易漏掉真实用户的低端设备、弱网和地区差异。
