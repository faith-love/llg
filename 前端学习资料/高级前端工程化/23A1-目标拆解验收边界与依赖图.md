# 目标拆解、验收边界与依赖图

这一页把练习项目从“我要做一个 monorepo”拆成真正可交付的工程目标。工程化项目最容易失败的地方不是代码不会写，而是目标边界不清：最后到底验收什么、哪些能力必须沉淀成包、哪些能力只属于应用层。

## 步骤一：写项目任务书

先在根目录创建 `docs/project-brief.md`：

```markdown
# acme-frontend-platform 项目任务书

## 背景

ACME 有两个前端应用：

- admin：内部运营后台
- portal：客户门户

两个应用需要共享 UI、请求、权限、灰度、监控和工程配置。

## 目标

- 用 pnpm workspace 管理 apps 和 packages
- 用统一 TypeScript、ESLint、Vitest、Vite 配置降低复制成本
- 用 turbo 管理任务依赖、缓存和 affected build
- 用 CI 保证 lint、typecheck、test、build 必须通过
- 用 runtime config、feature flag、monitoring 支持上线后治理

## 非目标

- 不实现真实登录后端
- 不实现完整业务后台
- 不接入真实监控 SaaS
- 不追求复杂 UI 视觉，只关注组件 API 和工程结构
```

这一步的关键是写清“非目标”。工程化练习不是业务系统练习，如果一开始就陷入复杂业务，会掩盖真正要练的依赖治理、构建链路和质量门禁。

## 步骤二：定义完成标准

继续写 `docs/acceptance.md`：

```markdown
# 验收标准

## 本地开发

- pnpm install 可以安装所有 workspace 依赖
- pnpm dev 可以同时启动 admin 和 portal
- pnpm --filter admin dev 可以只启动 admin

## 质量门禁

- pnpm lint 失败时能定位到具体 package
- pnpm typecheck 不允许 any 逃逸到 public API
- pnpm test 覆盖 shared、api-client、ui 的核心行为
- pnpm build 先构建依赖包，再构建应用

## 工程治理

- packages 不能 import apps
- 应用只能从包入口 import，不能 deep import src
- runtime config 能在不重新构建的情况下切换环境值
- feature flag 对同一用户稳定分流
- production build 能移除 debug 调用
```

验收标准要写成可以运行、可以观察、可以失败的条件。比如“代码质量好”不是验收标准，`pnpm lint` 能阻断不合规 import 才是。

## 步骤三：画包依赖图

在 `docs/dependency-graph.md` 记录依赖方向：

```text
apps/admin
  -> @acme/ui
  -> @acme/api-client
  -> @acme/auth
  -> @acme/feature-flags
  -> @acme/shared

apps/portal
  -> @acme/ui
  -> @acme/api-client
  -> @acme/auth
  -> @acme/feature-flags
  -> @acme/shared

@acme/ui
  -> @acme/shared

@acme/auth
  -> @acme/shared

@acme/api-client
  -> @acme/shared

@acme/feature-flags
  -> @acme/shared
```

再写禁止方向：

```text
packages/* -X-> apps/*
@acme/shared -X-> react
@acme/api-client -X-> react
@acme/auth -X-> apps/*
apps/admin -X-> apps/portal
```

这里的 `-X->` 是工程规则，不是 TypeScript 自带能力。后续需要用 ESLint、边界检查脚本、review checklist 一起保证。

## 步骤四：把工程目标映射成代码模块

把“能力”映射到“包”：

| 能力 | 落点 | 原因 |
| --- | --- | --- |
| 组件复用 | `packages/ui` | UI 是跨应用复用能力，不应该放在某个 app 下 |
| 请求封装 | `packages/api-client` | 统一错误、baseURL、adapter、拦截逻辑 |
| 权限判断 | `packages/auth` | 页面只关心能不能显示，不关心权限规则细节 |
| 灰度分流 | `packages/feature-flags` | 分流算法和配置读取要统一 |
| 工具函数 | `packages/shared` | 只能放无框架、低耦合工具 |
| TS 配置 | `packages/config-ts` | 避免每个包复制 `tsconfig` |
| ESLint 配置 | `packages/config-eslint` | 统一 import 边界、代码风格和规则 |
| 测试配置 | `packages/config-vitest` | 保证 jsdom、coverage、setup 一致 |

这个映射决定了后续目录结构。不要先创建目录再想职责，否则很容易出现 `shared` 变成垃圾桶。

## 步骤五：写 owner 表

`docs/owners.md`：

```markdown
# Owners

| 范围 | Owner | 职责 |
| --- | --- | --- |
| apps/admin | admin-team | 运营后台业务 |
| apps/portal | portal-team | 客户门户业务 |
| packages/ui | design-system | 组件 API、设计 token、组件测试 |
| packages/api-client | platform | 请求协议、错误模型、adapter |
| packages/auth | platform | session、role、permission |
| packages/feature-flags | platform | flag 类型、灰度算法 |
| packages/config-* | platform | 工程配置和升级 |
```

owner 表不是形式主义。真实团队里，组件库、构建配置、业务应用必须有人负责，否则改动会变成“谁都能改，谁都不兜底”。

## 练习

1. 按上面的格式创建 `docs/project-brief.md`、`docs/acceptance.md`、`docs/dependency-graph.md`、`docs/owners.md`。
2. 给每个 package 写一句“为什么它应该是 package，而不是 app 内部目录”。
3. 给每个禁止依赖方向写一个反例，例如 `@acme/shared` import React 会导致什么问题。

## 验收

- 能从目标解释到目录，而不是只背目录。
- 能说清 apps 和 packages 的依赖方向。
- 能说清每个 package 的 owner 和 public API 边界。
- 后续新增包时，可以先补 owner 和依赖图，再写代码。
