# 安全工程化与供应链安全

前端安全不是上线前临时扫一下漏洞。高级工程化要把安全放进开发、依赖、构建、发布和运行时监控中。前端暴露在用户浏览器里，任何输入、依赖、脚本、配置和第三方资源都可能成为风险入口。

## 常见前端安全风险

| 风险 | 说明 |
| --- | --- |
| XSS | 用户输入或富文本被当成脚本执行 |
| CSRF | 利用用户登录态发起非预期请求 |
| 点击劫持 | 页面被嵌入 iframe 诱导点击 |
| 敏感信息泄露 | token、密钥、个人信息进入前端或日志 |
| 供应链攻击 | npm 包、构建脚本、CI 凭证被污染 |
| 依赖漏洞 | 间接依赖存在已知漏洞 |
| source map 泄露 | 生产源码公开暴露 |

## XSS 治理

XSS 防护原则：

- 默认转义用户输入。
- 不直接使用不可信 HTML。
- 富文本必须经过白名单 sanitizer。
- 避免拼接脚本和 URL。
- 配置 CSP 降低执行风险。

危险写法：

```typescript
element.innerHTML = userInput
```

框架能帮你处理大多数文本插值，但 `dangerouslySetInnerHTML`、富文本渲染、Markdown 渲染仍然需要额外治理。

## Token 和敏感信息

不要把秘密放到前端：

- API secret。
- 数据库密码。
- 私钥。
- 服务端 token。
- 内部系统凭证。

前端只能保存用户侧凭证，并且要结合后端安全策略，例如 HttpOnly Cookie、SameSite、CSRF token、短期 access token 等。

## CSP

Content Security Policy 可以限制脚本、样式、图片、连接来源。

示例方向：

```text
script-src 'self'
connect-src 'self' https://api.example.com
img-src 'self' data: https:
frame-ancestors 'none'
```

CSP 需要和第三方脚本、监控、埋点、CDN 共同设计。不要上线一个过宽的策略后就不再维护。

## 供应链安全

npm 供应链风险来自：

- 新包维护者不可信。
- 包被接管。
- install script 执行恶意代码。
- 依赖混淆。
- lockfile 被恶意修改。
- CI token 泄露。

治理方式：

- frozen lockfile。
- 依赖审计。
- 限制发布权限。
- 关键包升级人工 review。
- CI secret 最小权限。
- 生产构建环境隔离。
- 内部包发布启用身份和权限控制。

## 构建和发布安全

检查项：

- 生产 source map 不公开。
- 环境变量不含秘密。
- CDN 上传路径不被覆盖错版本。
- 构建日志不打印 token。
- 制品不可被任意人替换。
- 回滚版本仍然可用。
- 第三方脚本有来源审查。

## 安全进入 CI

可以在流水线中加入：

- 依赖漏洞扫描。
- secret scanning。
- license 检查。
- lockfile diff 检查。
- 禁止危险 API lint 规则。
- 生产构建安全配置检查。

## 落地清单

- 用户输入和富文本是否有统一 sanitizer？
- 是否避免前端保存服务端秘密？
- CSP、frame-ancestors、安全响应头是否配置？
- 依赖升级是否有审计和 review？
- CI secret 是否最小权限？
- 生产 source map 是否只上传到受控位置？
- 安全问题是否有负责人和修复 SLA？

## 深入展开：安全要进入默认工程路径

安全不能依赖上线前人工检查。要把安全放进默认路径：

| 阶段 | 安全动作 |
| --- | --- |
| 开发 | 禁止危险 API、统一 sanitizer、敏感字段类型约束 |
| 提交 | secret scanning、lint 危险模式 |
| 安装 | frozen lockfile、依赖审计、install script 风险控制 |
| 构建 | 不打印 secret、不公开 source map、制品签名或校验 |
| 发布 | CDN 权限控制、配置审计、回滚版本保留 |
| 运行 | CSP 报告、异常监控、攻击特征告警 |

供应链安全还要看权限。CI token、npm 发布 token、CDN 上传凭证都应该最小权限、定期轮换，并避免在日志中泄露。
