# 包管理器与依赖治理

依赖治理的核心目标是可复现、可升级、可审计。前端项目最大的外部变量通常不是业务代码，而是 npm 依赖树。一个小版本升级、一个间接依赖变动、一个重复安装的包，都可能导致构建失败、包体膨胀或线上异常。

## 包管理器关注点

| 工具 | 关注点 |
| --- | --- |
| npm | 官方默认，生态兼容强 |
| pnpm | 硬链接和内容寻址存储，依赖隔离更严格，适合 monorepo |
| yarn | workspace 能力成熟，版本策略要看团队选择 |

选择包管理器不是只看安装速度，还要看：

- lockfile 是否稳定。
- workspace 支持是否符合仓库规模。
- 幽灵依赖是否容易暴露。
- CI 缓存是否容易配置。
- 团队是否能统一版本和命令。

## 依赖类型

| 字段 | 适合放什么 | 常见错误 |
| --- | --- | --- |
| `dependencies` | 运行时需要的包 | 把构建工具放进来导致库消费者安装额外依赖 |
| `devDependencies` | 构建、测试、类型、脚本工具 | 应用运行时真正需要的包被误放这里 |
| `peerDependencies` | 插件、组件库要求宿主提供的包 | 组件库把 React 打进产物 |
| `optionalDependencies` | 可选能力或平台相关依赖 | 没有降级逻辑 |

组件库通常要把 `react`、`vue` 等框架放到 `peerDependencies`，避免多个框架副本进入用户项目。

## 版本范围

```text
1.2.3   固定版本
~1.2.3  允许 patch 升级
^1.2.3  允许 minor 和 patch 升级
*       几乎不可控
```

应用项目可以适度使用 `^`，但必须提交 lockfile。基础库、脚手架模板、工程配置包更适合收敛版本范围，避免消费者环境不可控。

## Lockfile 规则

lockfile 是构建可复现的基础。

推荐规则：

- 应用项目提交 lockfile。
- monorepo 只保留根目录一个 lockfile。
- CI 使用 frozen lockfile 安装，禁止自动改 lockfile。
- 依赖升级 PR 必须单独提交，不和业务代码混在一起。
- lockfile 大变更要检查是否引入重复依赖或可疑包。

pnpm 示例：

```bash
pnpm install --frozen-lockfile
pnpm why react
pnpm list vite --depth 10
```

## 幽灵依赖

幽灵依赖是指代码引用了 `package.json` 没声明的包。它可能因为间接依赖刚好存在而本地可用，但依赖树变化后就会失败。

```typescript
// package.json 没声明 lodash，却直接引用
import debounce from 'lodash/debounce'
```

治理方式：

- 使用更严格的包管理器策略。
- ESLint 检查 import 是否来自声明依赖。
- CI 中从干净环境安装并构建。
- 禁止依赖根目录未声明的偶然包。

## 依赖升级策略

依赖升级不要等到安全漏洞或框架大版本才处理。

推荐节奏：

- patch 升级：定期自动化，跑完整 CI。
- minor 升级：按月或双周集中处理。
- major 升级：先做兼容评估、迁移文档和回滚方案。
- 框架升级：先升级工具链，再升级业务代码，最后清理兼容层。

升级 PR 应该包含：

- 升级范围。
- breaking changes 摘要。
- 验证命令。
- 受影响应用。
- 回滚方式。

## 供应链风险

依赖治理还要关注安全：

- 不安装来源不明、维护停滞或下载异常的包。
- 检查 install scripts，避免安装阶段执行高风险脚本。
- 对生产镜像或部署包做依赖审计。
- 对核心依赖建立白名单和升级负责人。
- 对内部包启用发布权限控制和变更日志。

## 依赖治理清单

- 仓库是否强制统一包管理器？
- Node 版本和包管理器版本是否固定？
- CI 是否使用 frozen lockfile？
- 是否能解释每个核心依赖为什么存在？
- 是否能查出重复依赖和超大依赖？
- 组件库是否正确声明 peer 依赖？
- 依赖升级是否有自动化和人工评审结合？

## 深入展开：依赖治理要看依赖图

依赖治理不能只看 `package.json`，要看最终依赖图。

重点检查：

| 检查项 | 为什么重要 |
| --- | --- |
| 重复版本 | 多个 React、日期库、图表库会增加体积甚至导致运行异常 |
| 间接依赖 | 间接依赖升级也可能引入漏洞或破坏构建 |
| peer 依赖 | 组件库和插件必须和宿主项目共享关键运行时 |
| install scripts | 安装阶段能执行脚本，是供应链风险入口 |
| lockfile diff | 锁文件大变更可能隐藏大量依赖替换 |

建议建立依赖分级：

```text
S 级：React/Vue、构建工具、包管理器、TypeScript、核心组件库
A 级：路由、状态、请求、监控、图表、编辑器
B 级：普通工具库
```

S 级依赖升级必须独立 PR、完整 CI、写明回滚方式；B 级依赖可以更自动化。这样依赖治理不会被“一刀切”拖慢。
