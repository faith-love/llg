# 项目架构分层与目录治理

目录不是文件的摆放方式，而是架构边界的表达方式。一个好的目录结构应该让开发者一眼看出：业务模块在哪里、共享能力在哪里、哪些代码可以互相依赖、哪些代码不能跨层引用。

## 分层目标

项目分层要解决四个问题：

- 降低认知成本：新人能快速找到入口。
- 控制影响范围：改一个模块不应该影响无关模块。
- 避免循环依赖：依赖方向清晰。
- 支持复用和迁移：共享逻辑能抽包，业务逻辑能拆分。

## 推荐分层

一个中大型应用可以从这些层开始：

```text
src/
  app/              # 应用启动、路由、全局 Provider、全局样式
  pages/            # 页面级组合，负责路由入口
  features/         # 业务功能模块
  entities/         # 领域实体、模型、状态和接口适配
  shared/           # 与具体业务弱相关的通用能力
  widgets/          # 可复用业务组件组合
```

这不是固定模板，关键是明确依赖方向。例如：

```text
app -> pages -> features -> entities -> shared
```

上层可以依赖下层，下层不要反向依赖上层。`shared` 不应该引用 `features`，否则共享层会被业务污染。

## 模块内部结构

一个业务模块内部也要有边界：

```text
features/user-profile/
  api.ts            # 请求封装
  model.ts          # 状态、类型、领域逻辑
  ui.tsx            # UI 组合
  hooks.ts          # 对外暴露的 hook
  index.ts          # 稳定导出面
```

对外只暴露 `index.ts`，避免其他模块直接引用内部文件：

```typescript
// 推荐
import { UserProfileCard } from '@/features/user-profile'

// 不推荐
import { UserProfileCard } from '@/features/user-profile/ui/UserProfileCard'
```

稳定导出面可以降低重构成本。内部文件可以调整，只要 `index.ts` 的契约不变，外部就不受影响。

## 目录治理规则

| 规则 | 原因 |
| --- | --- |
| 禁止跨业务模块深层引用 | 避免业务耦合扩散 |
| 禁止 shared 依赖业务模块 | 保持共享层纯净 |
| 页面只做组合，不沉淀复杂领域逻辑 | 页面变化频繁，不适合承载核心逻辑 |
| API 请求层和 UI 层分离 | 方便测试、mock 和替换数据源 |
| 模块对外只暴露稳定入口 | 降低重构影响面 |
| 公共类型不要无脑放到 `types` | 类型也要按领域归属 |

## 如何用工具强制边界

只写文档不够，需要用工具约束。

可以用 ESLint 限制导入路径：

```json
{
  "rules": {
    "no-restricted-imports": [
      "error",
      {
        "patterns": [
          "@/features/*/internal/*",
          "@/pages/*/*"
        ]
      }
    ]
  }
}
```

monorepo 中可以用包边界控制：

```text
apps/admin -> packages/ui
apps/web   -> packages/ui
packages/ui 不允许依赖 apps/*
```

## 常见反模式

| 反模式 | 后果 |
| --- | --- |
| `components` 目录塞所有组件 | 组件没有业务归属，越来越难找 |
| `utils` 目录无限膨胀 | 工具函数没有边界，重复和副作用混杂 |
| 页面文件里写完整业务流程 | 页面无法复用，测试困难 |
| 共享层引用业务接口 | 共享代码无法迁移 |
| 类型集中放一个巨大 `types.ts` | 类型变成全局垃圾桶 |

## 架构评审清单

新增模块前问这些问题：

- 这个模块属于页面、业务功能、领域实体还是共享能力？
- 它的上游和下游是谁？
- 它对外暴露哪些 API？
- 它是否需要测试？
- 它会不会被多个应用复用？
- 它未来是否可能拆成 package？

如果这些问题答不清，先不要急着写代码。目录治理的本质，是在代码扩散之前先控制变化边界。

## 深入展开：把目录变成架构契约

目录治理要从“怎么放文件”升级为“怎么限制变化传播”。建议给每一层写清楚四件事：

| 维度 | 要回答的问题 |
| --- | --- |
| 职责 | 这一层负责业务编排、领域模型、UI 还是基础能力 |
| 允许依赖 | 这一层可以 import 哪些层 |
| 禁止依赖 | 哪些 import 属于架构违规 |
| 对外契约 | 外部只能从哪个入口引用 |

例如 `features/order` 可以依赖 `entities/user` 和 `shared/request`，但不应该直接依赖 `pages/admin`。如果确实需要跨业务通信，优先通过路由参数、事件契约、后端状态或共享领域服务，不要让两个 feature 互相深层引用。

成熟做法是把规则固化成自动检查：

```text
目录约定 -> import 边界规则 -> CI 阻断 -> 架构例外必须评审
```

这样架构不会随着人员流动和需求压力慢慢失效。
