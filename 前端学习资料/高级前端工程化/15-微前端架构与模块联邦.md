# 微前端架构与模块联邦

微前端的目标是让多个团队或多个子应用可以独立开发、独立发布、独立演进，同时在用户侧形成一个统一产品体验。它解决组织和发布问题，但会引入运行时、依赖、样式、路由、性能和治理复杂度。

## 什么时候值得用

适合：

- 多团队维护大型前端平台。
- 子应用发布节奏差异明显。
- 历史技术栈难以一次性统一。
- 需要逐步迁移旧系统。
- 业务边界天然拆分，例如控制台、营销、报表、设置。

不适合：

- 只是想拆组件。
- 只有一个小团队。
- 业务边界不清。
- 不能接受运行时复杂度和性能成本。

## 微前端拆分原则

按业务能力拆，不按技术层拆。

```text
推荐：订单子应用、用户子应用、报表子应用
不推荐：header 子应用、table 子应用、form 子应用
```

子应用应该能独立开发、独立测试、独立部署，并拥有自己的业务边界。

## 主应用和子应用职责

| 角色 | 职责 |
| --- | --- |
| 主应用 | 登录态、全局导航、权限、路由分发、布局、公共配置 |
| 子应用 | 业务页面、业务状态、子路由、局部资源 |
| 共享层 | 设计系统、请求客户端、埋点、权限 SDK |

不要让主应用承载过多业务逻辑，否则主应用会变成新的单体。

## 模块联邦

Module Federation 允许一个应用在运行时加载另一个应用暴露的模块。

概念：

| 概念 | 含义 |
| --- | --- |
| host | 消费远程模块的应用 |
| remote | 暴露模块的应用 |
| exposes | remote 对外暴露的模块 |
| remotes | host 声明可加载的 remote |
| shared | 共享依赖，例如 React |

适合场景：

- 运行时加载远程组件。
- 多应用共享模块但独立发布。
- 逐步迁移大型系统。

## 共享依赖风险

共享 React、Vue、状态库等核心依赖时要谨慎。

风险：

- 版本不一致导致运行异常。
- 多份框架副本导致上下文失效。
- 共享依赖升级影响多个子应用。
- remote 不可用导致 host 页面失败。

治理方式：

- 核心依赖制定版本矩阵。
- remote 加载失败有降级 UI。
- 共享模块有兼容性测试。
- 发布前验证 host 和 remote 组合。

## 样式隔离

微前端常见样式问题：

- 全局 CSS 污染。
- reset 冲突。
- 组件库样式重复注入。
- z-index 冲突。
- 主题变量不一致。

解决方式：

- CSS Modules、CSS-in-JS、命名空间。
- 设计 token 统一。
- 避免子应用写全局选择器。
- 对弹层、通知、遮罩制定层级规范。

## 路由和通信

路由要明确主从关系：

```text
/orders/* -> orders app
/users/*  -> users app
```

应用间通信要尽量少。优先通过 URL、后端状态或共享 SDK，而不是随意全局事件。

如果必须通信，定义事件契约：

```typescript
type MicroAppEvent =
  | { type: 'auth:expired' }
  | { type: 'theme:changed'; theme: 'light' | 'dark' }
```

## 落地清单

- 是否因为组织和发布边界需要微前端，而不是为了炫技？
- 子应用是否有清晰业务边界？
- remote 加载失败是否有降级方案？
- shared 依赖版本是否有治理策略？
- 样式、路由、权限和埋点是否统一？
- 主应用是否避免承载过多业务逻辑？

## 深入展开：微前端先治理运行时边界

微前端最难的不是把子应用加载出来，而是运行时边界治理。

| 边界 | 要治理的问题 |
| --- | --- |
| 依赖边界 | React/Vue、状态库、组件库是否单例或版本兼容 |
| 样式边界 | 全局样式、z-index、主题变量是否互相污染 |
| 路由边界 | 主应用和子应用谁拥有路由控制权 |
| 权限边界 | 登录态、租户、角色如何统一 |
| 发布边界 | 子应用独立发布后 host 是否兼容 |
| 监控边界 | 错误归属到 host 还是 remote |

模块联邦尤其要做“组合验证”：只测试 remote 自己通过还不够，还要测试 host 加载不同 remote 版本是否正常。否则独立发布会变成线上集成测试。
