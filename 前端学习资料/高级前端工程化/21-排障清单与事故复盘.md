# 排障清单与事故复盘

高级工程化必须覆盖事故处理。线上问题发生时，最重要的不是证明谁写错了，而是快速止血、明确影响、定位根因、恢复服务，并把教训转化为系统改进。

## 排障顺序

```text
确认现象
  -> 判断影响范围
  -> 找最近变更
  -> 查看监控和日志
  -> 复现或缩小范围
  -> 止血
  -> 根因分析
  -> 长期修复
  -> 复盘改进
```

不要一开始就深入代码。先判断是不是新版本、配置、接口、CDN、浏览器兼容或第三方服务问题。

## 常见前端事故

| 现象 | 优先检查 |
| --- | --- |
| 白屏 | JS 异常、资源 404、入口 HTML、runtime config |
| 某页面打不开 | 路由配置、权限、接口、懒加载 chunk |
| 样式错乱 | CSS hash、缓存、组件库版本、全局样式 |
| 登录异常 | Cookie、跨域、SameSite、网关、时间 |
| 接口大量失败 | API 域名、网关、鉴权、后端发布 |
| 部分用户异常 | 浏览器版本、灰度 flag、地区、租户 |
| sourcemap 对不上 | release 不一致、上传失败、产物覆盖 |
| 性能突降 | 包体变化、第三方脚本、接口慢、缓存失效 |

## 止血优先

止血方式：

- 回滚到上一版本。
- 关闭 Feature Flag。
- 切换 runtime config。
- CDN 回退入口 HTML。
- 降级非核心功能。
- 屏蔽问题路由。
- 后端临时兼容旧协议。

如果用户影响很大，先止血再深挖根因。

## 最近变更

排障时先收集：

- 最近发布版本。
- 最近合并 PR。
- 依赖升级。
- 构建配置改动。
- 环境变量或配置中心变更。
- CDN、网关、后端接口发布。
- Feature Flag 变更。

大多数事故和最近变更相关。

## 排障材料

一个好的排障系统应该能快速提供：

- release 和 commit。
- source map 后栈信息。
- 用户影响数。
- 页面路径。
- 浏览器和设备分布。
- 错误首次出现时间。
- 是否集中在某个 flag 或地区。
- 失败请求和 trace id。

## 复盘模板

```text
事故标题：
发生时间：
发现方式：
影响范围：
用户影响：
时间线：
根因：
止血动作：
长期修复：
为什么监控没有提前发现：
为什么测试没有覆盖：
后续行动项：
负责人：
截止时间：
```

复盘要关注系统改进，不要只停留在“开发自测不充分”。

## 行动项

好的行动项应该具体可验收：

```text
不好：加强测试
好：为支付提交流程增加 Playwright smoke，CI release 阶段必跑，失败阻断上线
```

行动项要进入工程 backlog，并在下次复盘确认完成。

## 落地清单

- 是否有一键回滚或关闭开关能力？
- 是否能快速查到最近发布和配置变更？
- 错误是否能定位到源码？
- 监控是否能给出影响用户数？
- 事故是否有固定复盘模板？
- 复盘行动项是否有负责人和截止时间？

## 深入展开：前端事故要先区分变更类型

排障时第一件事是判断最近变更属于哪一类：

| 变更类型 | 典型事故 |
| --- | --- |
| 代码变更 | JS 异常、路由错误、权限判断错误 |
| 构建变更 | chunk 路径错误、polyfill 缺失、sourcemap 错配 |
| 配置变更 | API 域名错误、Feature Flag 误开、CDN 路径错误 |
| 依赖变更 | 包行为变化、浏览器兼容问题、体积暴涨 |
| 后端变更 | 字段缺失、状态码变化、跨域或鉴权失败 |
| 基础设施变更 | CDN 缓存、网关、证书、DNS |

Babel 相关事故常出现在“构建变更”和“依赖变更”里。例如新依赖发布了现代语法但被 `exclude node_modules` 跳过，低版本浏览器就会生产报错。排障时要把浏览器版本维度拉出来看。
