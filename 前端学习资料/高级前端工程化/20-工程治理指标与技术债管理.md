# 工程治理指标与技术债管理

工程化是否有效，不能只靠感觉。高级前端工程化需要用指标观察交付效率、质量、稳定性、性能和维护成本，也需要用制度管理技术债。没有指标，工程优化很难获得持续投入。

## 指标分类

| 分类 | 指标示例 |
| --- | --- |
| 交付效率 | PR lead time、构建时间、部署频率 |
| 质量 | CI 失败率、测试覆盖关键路径、缺陷逃逸率 |
| 稳定性 | 发布失败率、回滚次数、MTTR |
| 性能 | LCP、INP、CLS、包体体积 |
| 维护性 | TypeScript strict 覆盖、any 数量、循环依赖 |
| 依赖 | 过期依赖数、漏洞数、重复依赖 |
| 平台使用 | 脚手架使用率、组件库覆盖率、配置统一率 |

指标要服务决策，不要为了好看而收集。

## DORA 思路

可借鉴四类交付指标：

- 部署频率。
- 变更前置时间。
- 变更失败率。
- 服务恢复时间。

前端可以落到：

```text
从 PR 创建到合并多久
从合并到上线多久
上线后多少版本需要回滚
线上事故平均多久恢复
```

## 技术债分类

| 类型 | 示例 |
| --- | --- |
| 架构债 | 模块边界混乱、循环依赖 |
| 类型债 | 大量 any、声明文件缺失 |
| 依赖债 | 老版本框架、漏洞依赖 |
| 测试债 | 核心流程无自动化测试 |
| 性能债 | 包体过大、首屏慢 |
| 监控债 | 错误无 source map、缺告警 |
| 体验债 | 组件不统一、可访问性差 |

债务不是所有都要立刻还，但必须可见、可排序、可追踪。

## 债务台账

建议记录：

```text
标题
影响范围
风险等级
业务影响
修复成本
负责人
计划窗口
验收标准
```

技术债如果没有验收标准，很容易变成长期讨论。

## RFC 和 ADR

重大工程决策需要文档化。

RFC 适合讨论新方案：

- 背景。
- 目标。
- 非目标。
- 方案。
- 替代方案。
- 风险。
- 迁移计划。

ADR 适合记录已经做出的架构决策：

- 决策是什么。
- 为什么这样选。
- 放弃了什么。
- 后续如何评估。

## 治理节奏

推荐固定节奏：

- 每周看 CI 和构建指标。
- 每双周清理 flaky 测试和高频告警。
- 每月做依赖升级窗口。
- 每季度评估架构债和性能预算。
- 大事故后必须复盘并产生改进项。

## 避免指标伤害

指标不能变成形式主义。

错误用法：

- 只追求覆盖率数字，忽略测试价值。
- 为降低 CI 失败率而关闭规则。
- 为提高部署频率而牺牲质量。
- 只统计平均值，忽略 P95 和核心路径。

## 落地清单

- 是否有工程指标看板？
- 是否能按团队、应用、版本查看指标？
- 技术债是否有台账和优先级？
- 是否有固定依赖升级和债务偿还节奏？
- 重大工程决策是否有 RFC 或 ADR？
- 指标是否真的影响工程决策？

## 深入展开：指标要能驱动取舍

工程指标的作用是帮助团队取舍，而不是制造排行榜。

建议每个指标都配三件事：

| 内容 | 示例 |
| --- | --- |
| 目标值 | PR 基础 CI P95 小于 10 分钟 |
| 行动阈值 | 连续两周超过 10 分钟就启动优化 |
| 责任人 | 工程平台 owner 或对应应用 owner |

技术债也要按影响排序：

```text
线上稳定性风险 > 发布阻塞风险 > 安全风险 > 性能风险 > 维护成本 > 代码洁癖
```

这样团队在需求压力下也能优先处理真正影响交付和稳定性的债务，而不是只改容易改的部分。
