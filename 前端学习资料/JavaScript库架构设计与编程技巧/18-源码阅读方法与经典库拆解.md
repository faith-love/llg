# 源码阅读方法与经典库拆解

读优秀库源码，不是逐行翻译，而是提炼设计问题和解决方案。你要看它如何定义核心概念、如何设计 public API、如何组织模块、如何处理扩展、错误、类型、构建和测试。

## 源码阅读顺序

推荐顺序：

1. 先看 README，理解用户视角 API。
2. 看 package.json，理解入口、构建产物、依赖。
3. 看 `src/index.ts`，找 public API。
4. 看核心类型，找领域模型。
5. 找 create/init 函数，看实例如何启动。
6. 找 plugin/middleware/adapter，理解扩展点。
7. 看 tests，确认作者认为哪些行为重要。
8. 看 changelog，理解 API 如何演进。

不要一开始扎进最深的实现细节。

## 阅读问题清单

| 问题 | 目的 |
| --- | --- |
| 这个库的核心模型是什么？ | 抓住主线 |
| public API 有几个入口？ | 判断使用者心智负担 |
| 哪些文件是 core？哪些是 adapter？ | 理解分层 |
| 扩展点在哪里？ | 学插件设计 |
| 错误如何表达？ | 学调试体验 |
| 类型如何推断？ | 学 TS API 设计 |
| 测试覆盖哪些行为？ | 学契约保护 |

## 经典库观察点

| 库 | 值得学习的点 |
| --- | --- |
| Lodash | 小函数 API、组合、兼容和边界处理 |
| Redux | 单向数据流、store、reducer、middleware |
| Axios | 请求配置、interceptor、adapter、错误归一化 |
| Zod | schema 模型、类型推断、safeParse |
| React Query | cache、异步状态、重试、失效和订阅 |
| Vite | 插件 hook、dev/build 分层、adapter 思维 |
| Rollup | 插件系统、模块图、输出阶段 |

## 做源码笔记

笔记不要只写“这个函数做了什么”，要写设计结论：

```text
问题：请求库如何支持浏览器和 Node？
方案：核心流程只依赖 adapter 接口，xhr/http/fetch 作为具体实现。
收益：core 可测试，运行时可替换。
代价：adapter 契约必须稳定。
```

## 从源码反推 API

尝试回答：

- 为什么这个 API 长这样？
- 作者放弃了哪些设计？
- 哪些能力放进 core，哪些放成插件？
- 哪些测试说明这是重要契约？
- 哪些历史 changelog 说明设计踩过坑？

## 自检清单

- 是否先从 public API 读起？
- 是否画出了核心模型？
- 是否区分 core、adapter、plugin？
- 是否总结了设计取舍，而不是只摘代码？
- 是否结合 tests 理解契约？
- 是否能把源码设计迁移到自己的库？

## 知识点展开与对应练习

| 知识点 | 小点展开 | 对应练习 | 验收标准 |
| --- | --- | --- | --- |
| README 入手 | 先从用户视角理解 API，不要直接跳实现 | 选一个库，先只读 README 写 API 图 | 能画出 5 个主要 API 和使用关系 |
| package.json | 从入口、exports、依赖、构建脚本判断库形态 | 分析一个库的 package.json | 说明 ESM/CJS/types/peerDependencies/sideEffects |
| index 入口 | public API 从入口文件开始识别 | 找出一个库的 public exports | 区分 public API 和 internal helper |
| 核心模型 | 类型和核心类通常暴露设计主线 | 为 Axios、Redux 或 Zod 画核心模型 | 至少包含 5 个核心概念和关系 |
| 扩展点 | plugin、middleware、adapter、hook 是源码重点 | 找一个库的扩展点实现 | 说明扩展点何时调用、能改什么、不能改什么 |
| tests | tests 是作者认为必须稳定的契约 | 阅读一个库 5 个测试用例 | 总结每个测试保护的 public 行为 |
| changelog | changelog 能看到 API 演进和踩坑历史 | 找一个 major 版本变更 | 写出 breaking change、迁移成本和设计教训 |
