# 库的定位边界与用户画像

库设计的第一步不是写代码，而是确定它服务谁、解决什么问题、不解决什么问题。定位越模糊，API 越容易膨胀，内部实现越容易被各种边缘需求拖乱。

## 先写一句话定位

一个库应该能用一句话说明：

```text
这个库帮助谁，在什么场景下，用什么方式，解决什么问题。
```

示例：

```text
一个面向浏览器和 Node 的轻量请求客户端，通过 adapter 和 middleware 机制统一请求、重试、取消、错误归一化和类型化响应。
```

这句话能帮助判断后续需求是否属于库的边界。

## 用户画像

用户画像不是市场文案，而是 API 设计依据。

| 用户 | 需求 | 设计影响 |
| --- | --- | --- |
| 业务开发者 | 简单、好上手、错误提示清楚 | 默认值友好、API 少而稳定 |
| 框架作者 | 可扩展、可组合、底层能力可接入 | plugin、hook、adapter |
| 库维护者 | 内部清晰、可测试、可兼容升级 | 分层、测试、版本策略 |
| TypeScript 用户 | 类型推断准确 | 泛型、重载、声明文件 |

同一个库不能无代价地满足所有人。核心 API 要服务主要用户，高级扩展点服务高级用户。

## 定义非目标

非目标比目标更重要。它能阻止库变成万能工具箱。

示例：

```text
目标：
- 提供请求配置标准化
- 支持拦截器和重试
- 支持浏览器 fetch 和 Node adapter

非目标：
- 不负责 UI loading 组件
- 不内置业务鉴权逻辑
- 不强制绑定某个状态管理库
```

非目标不是永久不能做，而是当前版本不承诺。

## 功能分层

把功能分成三层：

| 层级 | 含义 |
| --- | --- |
| core | 库没有它就不存在 |
| optional | 常用但可以关闭或替换 |
| ecosystem | 适合放到插件或周边包 |

例如请求库：

```text
core: request config、adapter、response、error
optional: retry、timeout、cache、interceptor
ecosystem: React hook、Vue plugin、mock adapter、devtools
```

核心越小，库越稳定；生态越开放，库越容易扩展。

## 边界判断问题

新增需求前问：

- 这是 80% 使用者需要的能力吗？
- 是否可以通过插件实现？
- 是否会增加核心包体？
- 是否会引入新运行时依赖？
- 是否会污染已有 API？
- 是否会把业务规则带进通用库？
- 是否有测试和文档维护成本？

如果答案不清楚，先作为插件或实验 API，不要直接并入 core。

## 输出定位文档

成熟库应该有一个 `design.md` 或 README 中的定位段落：

```text
Problem
Goals
Non-goals
Core concepts
Runtime support
Extension points
Compatibility policy
```

这份文档能降低维护者之间的争论，也能让使用者知道库的边界。

## 知识点展开与对应练习

| 知识点 | 小点展开 | 对应练习 | 验收标准 |
| --- | --- | --- | --- |
| 一句话定位 | 用一句话说明服务对象、场景、方式和问题，防止范围发散 | 给 `mini-request`、`mini-store`、`mini-schema` 各写一句定位 | 每句话都能看出“谁用、在哪用、解决什么” |
| 用户画像 | 业务用户要简单，库作者要扩展，TS 用户要推断，维护者要稳定 | 为一个库列 3 类用户画像 | 每类用户都写出最关心的 API 或文档点 |
| goals | goals 描述当前版本承诺解决的问题 | 为 `mini-request` 写 5 条 goals | 每条都能转成一个可测试功能 |
| non-goals | non-goals 用来拒绝不该进入核心的能力 | 为 `mini-request` 写 5 条 non-goals | 至少包含 UI、业务鉴权、框架绑定、服务端存储、全局状态其中 3 类 |
| core/optional/ecosystem | core 必须小而稳定，optional 可配置，ecosystem 适合插件或周边包 | 把请求库能力分成三层 | retry、cache、React hook、mock adapter 必须能放到合理层级 |
| 需求准入 | 新需求要评估包体、依赖、API 污染和维护成本 | 模拟一个“加内置登录弹窗”需求，写拒绝或接纳理由 | 结论必须说明是否进 core、plugin 还是不做 |
