# 测试体系契约兼容与回归

库测试重点不是覆盖内部每一行，而是保护 public API 契约。一个库被多个项目依赖后，任何行为变化都可能影响使用者，所以测试要覆盖边界、兼容、类型、构建产物和回归场景。

## 测试层级

| 测试 | 保护什么 |
| --- | --- |
| 单元测试 | 纯函数、核心模型、数据结构 |
| 契约测试 | public API 行为 |
| 类型测试 | TS 推断和错误提示 |
| 兼容测试 | 不同 Node、浏览器、模块格式 |
| 构建测试 | ESM/CJS/types/exports 可用 |
| 回归测试 | 已修复 bug 不再出现 |

## 契约测试

契约测试从使用者视角写：

```typescript
test('client.get returns normalized data', async () => {
  const client = createClient({ adapter: mockAdapter })
  const data = await client.get<User>('/users/1')

  expect(data.name).toBe('Ada')
})
```

不要只测内部函数。内部可以重构，契约不能随意变。

## 边界测试

库要测异常输入：

- 参数缺失。
- 配置非法。
- 重复注册。
- dispose 后调用。
- 异步取消。
- adapter 失败。
- 插件抛错。
- 空数据和大数据。

边界测试能保护错误提示和行为稳定。

## 类型测试

类型测试关注：

```typescript
const user = await client.get<User>('/user')
user.name
```

以及错误用法是否报类型错误。类型退化也是 breaking change。

## 构建产物测试

发布前要确认：

```text
import { createClient } from 'your-lib'
const { createClient } = require('your-lib')
import { retryPlugin } from 'your-lib/plugins/retry'
```

这些入口是否都能工作，类型是否能找到。

## 回归测试

每修一个 bug，都尽量补一个测试：

```text
bug: dispose 后 pending promise 仍然触发 listener
test: dispose 后 listener 不再被调用
```

这样库才会越来越稳。

## 自检清单

- 是否从使用者视角测试 public API？
- 是否覆盖错误和边界输入？
- 是否测试类型推断？
- 是否测试构建产物入口？
- 每个 bug fix 是否补回归测试？
- 是否在多个 Node 或浏览器版本验证？

## 知识点展开与对应练习

| 知识点 | 小点展开 | 对应练习 | 验收标准 |
| --- | --- | --- | --- |
| 单元测试 | 保护纯函数、核心模型和边界计算 | 给 `normalizeConfig` 写单测 | 覆盖默认值、非法 URL、headers 合并 |
| 契约测试 | 从使用者视角测试 public API | 写 `createClient().get()` 契约测试 | 不依赖内部函数名，只断言外部行为 |
| 类型测试 | 类型推断和报错也是兼容契约 | 写 `client.get<User>()` 类型测试 | 类型退化时测试失败 |
| 兼容测试 | 不同运行时和模块格式都要验证 | 分别测试 ESM import 和 CJS require | 两种入口都能加载，类型入口可用 |
| 构建测试 | package exports 和 dist 文件要真实可消费 | 在临时 example 项目安装本地包 | 能运行基础请求示例，不引用 src |
| 回归测试 | 每个 bug fix 都变成测试资产 | 为“dispose 后 listener 仍触发”写回归测试 | 修复前失败，修复后通过 |
| Flaky 治理 | 不稳定测试会降低团队信任 | 给异步测试去掉固定 sleep | 使用可控 promise、mock timer 或明确事件断言 |
