# 错误处理异常码与调试体验

库的错误提示是开发者体验的重要部分。业务代码出错可以靠调试上下文理解，库代码出错时，使用者往往只看到一段堆栈。好的库应该明确告诉使用者错在哪里、为什么错、怎么修。

## 错误设计目标

- 错误类型稳定。
- 错误码可搜索。
- message 能解释原因。
- 包含必要上下文。
- 不泄露敏感信息。
- 能区分使用错误和运行时错误。

## 错误类型

```typescript
class LibraryError extends Error {
  constructor(
    public code: string,
    message: string,
    public details?: Record<string, unknown>
  ) {
    super(message)
    this.name = 'LibraryError'
  }
}
```

使用：

```typescript
throw new LibraryError(
  'INVALID_OPTIONS',
  'createClient: options.baseURL must be a valid URL',
  { baseURL: options.baseURL }
)
```

## 错误分类

| 分类 | 示例 | 处理 |
| --- | --- | --- |
| 使用错误 | 参数缺失、配置非法 | 直接抛出，message 写清楚 |
| 环境错误 | fetch 不存在、DOM 不可用 | 提示运行环境和解决方案 |
| 运行错误 | 请求失败、解析失败 | 返回结构化错误 |
| 内部错误 | 不应该发生的状态 | 带错误码并建议提 issue |

## Result 或 throw

两种错误风格：

```typescript
// throw 风格
const data = parse(input)

// result 风格
const result = safeParse(input)
if (!result.ok) {
  console.log(result.error)
}
```

建议：

- 编程错误用 throw。
- 用户输入校验可提供 safe API。
- 异步请求返回 rejected promise 或结构化 error，保持一致。

## Debug 模式

可以提供调试能力：

```typescript
createClient({
  debug: true,
  logger: console
})
```

调试日志要有层级：

- info：关键生命周期。
- warn：可恢复问题。
- error：失败。
- trace：详细内部流程。

生产环境不要默认输出大量日志。

## 错误文档

错误码应该能查：

```text
INVALID_OPTIONS
原因：传入配置不符合要求
常见场景：baseURL 为空或不是 URL
解决：传入合法 baseURL
```

错误码稳定后，使用者可以在监控和日志中聚合。

## 自检清单

- 错误是否有 code？
- message 是否能指导修复？
- 是否区分使用错误和运行时错误？
- 是否提供 safe API？
- 是否支持 debug/logger？
- 错误 details 是否避免敏感信息？

## 知识点展开与对应练习

| 知识点 | 小点展开 | 对应练习 | 验收标准 |
| --- | --- | --- | --- |
| 错误类型 | 自定义错误要包含 name、code、message、details | 实现 `LibraryError` | `instanceof Error` 成立，code 可被监控聚合 |
| 错误分类 | 使用错误、环境错误、运行错误、内部错误处理方式不同 | 为请求库设计 8 个错误码 | 每个错误码都标注分类、触发场景和修复建议 |
| message 设计 | message 要指出哪个 API、哪个参数、为什么错 | 改写 5 个模糊错误信息 | 每个 message 都包含 API 名、问题字段和期望值 |
| Result 风格 | safe API 适合用户输入解析，不应让使用者大量 try/catch | 实现 `safeParseJSON` 和 `parseJSON` 两套 API | 一个返回 Result，一个抛 `LibraryError` |
| debug 模式 | debug 只在需要时输出，且可替换 logger | 实现 `createClient({ debug, logger })` | debug=false 不输出；debug=true 输出 requestId 和耗时 |
| details 脱敏 | 错误上下文不能泄露 token、cookie、password | 实现 `sanitizeDetails(details)` | 敏感 key 被替换成 `[redacted]` |
| 错误文档 | 错误码需要可搜索文档 | 写 `ERRORS.md` 的 5 个错误码条目 | 每个条目包含原因、常见场景、解决方式 |
