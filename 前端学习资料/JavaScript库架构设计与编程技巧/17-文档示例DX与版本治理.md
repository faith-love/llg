# 文档示例 DX 与版本治理

库的文档就是产品界面。使用者第一次接触库时，看到的不是内部架构，而是 README、示例、类型提示、错误信息和 changelog。开发者体验差的库，即使内部实现优秀，也很难被正确使用。

## README 应该包含

- 这个库解决什么问题。
- 安装方式。
- 最小可运行示例。
- 核心概念。
- 常用 API。
- TypeScript 用法。
- 运行环境支持。
- 版本兼容策略。
- 常见问题。

最小示例应该能复制运行：

```typescript
import { createClient } from 'your-lib'

const client = createClient({ baseURL: '/api' })
const users = await client.get<User[]>('/users')
```

## 示例设计

示例按层次组织：

| 层级 | 内容 |
| --- | --- |
| Quick Start | 1 分钟跑起来 |
| Basic | 常见能力 |
| Advanced | 插件、适配器、类型、性能 |
| Recipes | 业务组合方案 |
| Migration | 版本迁移 |

不要让使用者从复杂示例开始。

## API 文档

API 文档要说明：

- 参数。
- 默认值。
- 返回值。
- 错误。
- 副作用。
- 示例。
- 版本变化。

如果 API 会触发网络、DOM、缓存或全局状态，要明确写出来。

## DX 细节

好的开发者体验包括：

- 类型自动提示。
- 错误码可搜索。
- 默认值合理。
- 调试模式。
- 小包体。
- 清晰子路径导出。
- 迁移指南。

DX 不是“语法糖越多越好”，而是正确使用成本低。

## 版本治理

语义化版本：

| 版本 | 含义 |
| --- | --- |
| patch | 修 bug，不改变 API |
| minor | 新增兼容能力 |
| major | breaking change |

breaking change 要有：

- 变更说明。
- 影响范围。
- 迁移前后对比。
- codemod 或替代方案。
- 废弃周期。

## deprecate 策略

不要突然删除 API。可以先标记废弃：

```typescript
/**
 * @deprecated Use createClient instead.
 */
export function initClient() {}
```

并在运行时开发模式提示。

## 自检清单

- README 是否能让新用户 1 分钟跑起来？
- 文档是否说明默认值和错误？
- 示例是否覆盖基础和高级用法？
- changelog 是否清晰？
- breaking change 是否有迁移指南？
- 废弃 API 是否有替代方案和删除时间？

## 知识点展开与对应练习

| 知识点 | 小点展开 | 对应练习 | 验收标准 |
| --- | --- | --- | --- |
| README 第一屏 | 第一屏要说明价值、安装和最小示例 | 写 `mini-request` README 第一屏 | 60 秒内能理解用途并复制运行 |
| 示例分层 | Quick Start、Basic、Advanced、Recipes 服务不同用户 | 设计 8 个示例目录 | 至少包含 retry、cache、abort、custom adapter |
| API 文档 | 文档要写参数、默认值、返回、错误和副作用 | 为 `createClient` 写 API 文档 | 包含 options 表、返回类型、错误码和示例 |
| DX | 类型提示、错误码、debug、子路径导出都影响使用体验 | 设计一个 DX 检查清单 | 至少覆盖安装、导入、类型、错误、调试、升级 |
| changelog | changelog 不是 commit 列表，要面向使用者说明影响 | 为一次 minor 发布写 changelog | 分为 Added、Fixed、Deprecated、Migration |
| deprecated | 废弃 API 要有替代方案和删除时间 | 给 `initClient` 写 deprecated 迁移说明 | 包含旧写法、新写法、计划删除版本 |
| 迁移指南 | breaking change 要给具体前后对比 | 写 v1 到 v2 的迁移指南 | 至少包含 3 个 API 变化和对应改法 |
