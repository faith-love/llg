# 阅读路线与能力地图

学习 JS 库设计，要把注意力从“怎么实现一个功能”转向“怎么设计一个可长期使用的能力”。库代码要面对未知使用者、未知运行环境、未知组合方式和长期版本演进，所以它必须比业务代码更重视边界、契约、测试和兼容。

## 能力地图

```text
问题定义
  -> API 设计
  -> 核心模型
  -> 模块边界
  -> 扩展机制
  -> 状态与副作用
  -> 异步和错误
  -> 类型与构建
  -> 测试和文档
  -> 版本治理
```

每一层都要稳定。API 不稳定，使用者升级困难；核心模型混乱，内部复杂度会快速失控；测试不足，库越流行越不敢改。

## 学习阶段

| 阶段 | 目标 | 产出 |
| --- | --- | --- |
| 设计意识 | 知道库和业务代码的差异 | 能写清楚库解决的问题和非目标 |
| API 能力 | 设计稳定入口和参数 | 能给一个功能设计 2-3 套 API 并比较取舍 |
| 架构能力 | 拆分 core、adapter、plugin、utils | 能画出模块依赖图 |
| 编程技巧 | 掌握组合、策略、事件、中间件、缓存等模式 | 能实现可扩展核心流程 |
| 工程能力 | 类型、测试、构建、发布、文档 | 能把库发布给别人稳定使用 |
| 源码能力 | 阅读优秀库并提炼设计 | 能复述一个库的核心架构 |

## 最小心智模型

一个库至少有三层：

```text
public API  给使用者调用
core model  内部稳定模型
runtime     具体环境适配和副作用
```

例如请求库：

```text
axios.get('/users')
  -> request config 标准化
  -> interceptor/middleware 链
  -> adapter 选择 xhr/fetch/http
  -> response normalize
```

使用者只看到简单 API，但内部需要处理配置合并、拦截器、取消、错误、适配器和类型。

## 练习方式

每学一个设计点，都用这个问题自测：

1. 如果 API 发布后不能改，我现在的设计还稳吗？
2. 如果使用者组合多个插件，会不会互相影响？
3. 如果运行环境从浏览器换到 Node，会影响哪些模块？
4. 如果出现错误，使用者能不能知道错在哪里？
5. 如果下个版本要扩展能力，是否需要破坏旧 API？

## 知识点展开与对应练习

| 知识点 | 小点展开 | 对应练习 | 验收标准 |
| --- | --- | --- | --- |
| 能力地图 | 把写库拆成问题定义、API、核心模型、模块边界、扩展机制、类型、构建、测试、文档和版本治理 | 选一个你熟悉的业务函数，画出它如果抽成库需要补齐的能力地图 | 至少列出 8 个能力点，并说明每个能力点解决什么风险 |
| 问题定义 | 明确这个库服务谁、解决什么、不解决什么，避免上来就写实现 | 写一个 `mini-request` 的 goals 和 non-goals | goals 不超过 5 条，non-goals 至少 3 条，不能出现业务专有规则 |
| Public API | public API 是长期契约，内部实现可以改，外部入口要稳定 | 给 `mini-request` 设计 3 个最小 API：`createClient`、`request`、`get` | 每个 API 都写出参数、返回值、错误情况和一个调用示例 |
| Core model | 核心模型是库内部的稳定语言，例如 Request、Response、Adapter、Plugin | 为一个请求库画出核心模型关系图 | 能说清哪个模型暴露给用户，哪个只在内部使用 |
| Runtime 边界 | 浏览器、Node、测试环境的差异要通过 adapter 或 runtime 层隔离 | 设计 `fetchAdapter` 和 `mockAdapter` 的统一接口 | core 不直接引用 `fetch`，测试能用 mock adapter |
| 学习路径 | 不同目标有不同路线，不能只按目录顺序机械阅读 | 为自己选一条路线：API 设计优先、插件设计优先或发布工程优先 | 写出接下来要读的 5 篇和每篇要完成的练习 |
