# 中间件管道策略模式与适配器

中间件、管道、策略和适配器是库设计中最常用的扩展模式。它们的共同目标是把变化点从核心流程里抽出来，让库既有稳定主流程，又能替换局部能力。

## 中间件

中间件适合处理一条可串联的流程：

```typescript
type Middleware<T> = (ctx: T, next: () => Promise<void>) => Promise<void>
```

请求库示例：

```typescript
const authMiddleware: Middleware<RequestContext> = async (ctx, next) => {
  ctx.headers.set('Authorization', 'Bearer token')
  await next()
}
```

中间件适合：

- 请求拦截。
- 日志。
- 鉴权。
- 重试。
- 缓存。
- 参数标准化。

## 管道

管道适合把一个值按顺序转换：

```typescript
type Transform<T> = (value: T) => T

function pipe<T>(value: T, transforms: Transform<T>[]) {
  return transforms.reduce((current, transform) => transform(current), value)
}
```

适合：

- 配置归一化。
- AST 转换。
- 数据清洗。
- 响应格式化。

管道中的每一步最好是纯函数，便于测试和组合。

## 策略模式

策略模式适合替换算法：

```typescript
type RetryStrategy = (attempt: number, error: unknown) => number | false

const exponentialBackoff: RetryStrategy = (attempt) => {
  if (attempt > 3) return false
  return Math.pow(2, attempt) * 100
}
```

使用者可以传入不同策略，不需要库核心写死所有分支。

## 适配器

适配器适合屏蔽运行环境差异：

```typescript
type Adapter = (request: NormalizedRequest) => Promise<Response>
```

浏览器：

```typescript
const fetchAdapter: Adapter = async (request) => {
  const res = await fetch(request.url, {
    method: request.method,
    headers: request.headers,
    body: request.body
  })

  return normalizeFetchResponse(res)
}
```

Node、测试环境、mock 都可以提供不同 adapter。

## 如何取舍

| 模式 | 适合变化点 |
| --- | --- |
| 中间件 | 流程前后包裹，有 next |
| 管道 | 数据一步步转换 |
| 策略 | 替换某个决策算法 |
| 适配器 | 替换运行环境或外部系统 |
| 事件 | 通知外部发生了什么 |
| 插件 | 组合多个扩展点 |

## 自检清单

- 当前变化点是流程、算法、环境还是通知？
- 中间件是否可能忘记调用 `next`？
- 管道每一步是否可单独测试？
- 策略是否有默认实现？
- adapter 是否屏蔽了环境差异？
- 扩展点是否会破坏核心流程稳定性？

## 知识点展开与对应练习

| 知识点 | 小点展开 | 对应练习 | 验收标准 |
| --- | --- | --- | --- |
| 中间件 | 中间件用 `next` 包裹流程，适合鉴权、日志、重试、缓存 | 实现 `compose(middlewares)` | 中间件按注册顺序进入，按相反顺序退出 |
| next 约束 | 中间件可能忘记调用 `next` 或调用多次 | 给 compose 增加防重复调用保护 | 同一个 middleware 调两次 `next` 会抛出明确错误 |
| 管道 | 管道适合数据一步步转换，最好保持纯函数 | 实现 `pipe(value, transforms)` 处理 request config | 每个 transform 单独可测试，不依赖外部状态 |
| 策略模式 | 策略适合替换算法，例如 retry delay、cache key、serialize | 实现 `RetryStrategy` | 支持固定间隔和指数退避两种策略 |
| 适配器 | adapter 屏蔽运行环境差异，core 只依赖统一接口 | 实现 `fetchAdapter` 和 `mockAdapter` | 两个 adapter 都满足同一个 `Adapter` 类型 |
| 模式取舍 | 变化点不同，使用不同模式，不能都塞进 plugin | 为 logging、retry delay、Node 发送请求、数据转换选择模式 | 每个选择都能说明为什么不用其他模式 |
| 流程可视化 | 中间件和管道复杂后要能调试执行链路 | 给 pipeline 增加 debug trace | 输出每个 middleware/transform 的执行顺序和耗时 |
