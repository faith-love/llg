# 核心模型抽象与数据结构

库的核心模型决定了内部复杂度上限。很多库不是因为代码写得差而难维护，而是最开始没有抽象出稳定概念，导致后续功能都堆在临时对象和临时流程上。

## 找核心名词

设计库时先找领域名词：

```text
请求库：Client、Request、Response、Adapter、Interceptor、Error
校验库：Schema、Parser、Issue、Result、Context
状态库：Store、State、Action、Subscriber、Selector
构建插件：Plugin、Hook、Module、Transform、Context
```

这些名词会变成内部数据结构和 public API 的基础。

## 核心模型要少而稳定

不要一开始就设计很多概念。先问：

- 哪些概念是不可缺少的？
- 哪些只是实现细节？
- 哪些应该放到插件里？
- 哪些会被使用者感知？

例如请求库的核心模型可以是：

```typescript
type RequestConfig = {
  url: string
  method: 'GET' | 'POST' | 'PUT' | 'DELETE'
  headers?: Record<string, string>
  body?: unknown
  timeout?: number
}

type Response<T> = {
  status: number
  headers: Record<string, string>
  data: T
  config: RequestConfig
}
```

先稳定请求和响应，再增加重试、缓存、拦截器。

## 内部模型和外部模型

外部 API 可以友好，内部模型要统一。

```typescript
// 外部允许简写
client.get('/users')
client.request({ url: '/users', method: 'GET' })

// 内部统一归一化
type NormalizedRequest = {
  url: URL
  method: string
  headers: Headers
  body: BodyInit | null
  timeout: number
}
```

归一化能减少内部条件分支。越靠近核心，数据结构越应该稳定、完整、显式。

## 数据结构选择

| 需求 | 数据结构 |
| --- | --- |
| 按 key 快速查找 | `Map` |
| 保持插入顺序且唯一 | `Set` |
| 先进先出任务 | queue |
| 优先级调度 | priority queue |
| 父子层级 | tree |
| 依赖关系 | graph |
| 事件订阅 | map of listeners |

不要所有东西都用普通对象和数组。数据结构会直接影响复杂度和 API 表达。

## 状态机思维

复杂流程可以用状态机约束：

```text
idle -> loading -> success
idle -> loading -> error
loading -> canceled
```

状态机的好处：

- 明确合法状态。
- 避免布尔值组合爆炸。
- 便于测试。
- 便于调试和可视化。

```typescript
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading'; requestId: string }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error }
  | { status: 'canceled'; reason?: string }
```

## 模型演进

核心模型变更要谨慎。建议：

- public 类型变更必须进 changelog。
- 内部模型变更要有迁移测试。
- 先增加字段，再废弃字段，最后删除。
- 不要让插件直接依赖过多内部结构。

## 自检清单

- 这个库的 3-5 个核心概念是什么？
- 外部输入是否会先归一化成内部模型？
- 内部模型是否稳定、显式、可测试？
- 是否用了合适的数据结构？
- 是否存在多个布尔值组合导致状态混乱？
- 插件是否过度依赖内部模型？

## 知识点展开与对应练习

| 知识点 | 小点展开 | 对应练习 | 验收标准 |
| --- | --- | --- | --- |
| 核心名词 | 从领域里找稳定名词，名词会变成类型、模块和 API | 为请求库、状态库、校验库各列 5 个核心名词 | 每个名词都能解释职责，不能混入实现细节 |
| 外部模型 | 面向用户友好，允许简写和默认值 | 设计用户传入的 `RequestConfig` | 支持 `url`、`method`、`headers`、`body`、`timeout` |
| 内部模型 | 面向实现稳定，字段完整、类型统一、少分支 | 设计 `NormalizedRequest` | URL、headers、method 都被标准化，内部不再处理多种输入形态 |
| 数据结构 | Map、Set、Queue、Graph 等选择会影响复杂度 | 为 listener 管理、pending 请求、插件顺序各选一个数据结构 | 每个选择都说明查询、插入、删除复杂度 |
| 状态机 | 用联合状态替代多个布尔值，避免非法组合 | 把 `{ loading, error, data }` 改成状态联合类型 | 类型上不能同时出现 loading 和 success |
| 模型演进 | 核心模型变更要分阶段，避免插件和使用者崩溃 | 给 `Response` 增加 `duration` 字段，设计兼容发布步骤 | 先新增字段，再文档说明，不破坏旧字段 |
| 内部上下文 | 上下文传递要清晰，避免全局变量 | 设计 `RequestContext` | 包含 request、response、error、meta，但不暴露内部缓存实现 |
