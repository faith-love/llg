# 常见设计反模式与重构策略

库设计最常见的问题不是能力不够，而是边界失控。API 越加越多、配置越来越深、插件能改一切、内部状态到处共享，最后维护者不敢改，使用者不敢升级。

## 万能 options

反模式：

```typescript
createThing({
  mode: 'advanced',
  enableA: true,
  enableB: false,
  customA: {},
  internalFlag: true
})
```

问题：

- 配置语义不清。
- 组合关系复杂。
- 默认值难以解释。
- 类型越来越大。

重构：

- 拆成 core options 和 plugin options。
- 把互斥模式拆成不同 API。
- 为复杂能力提供 builder 或 preset。

## 巨型核心

核心包什么都做：

```text
core = request + cache + retry + react + logger + devtools + mock
```

后果：

- 包体大。
- tree-shaking 差。
- 修改任何能力都影响 core。
- 测试矩阵变大。

重构：

```text
core
plugin-retry
plugin-cache
adapter-fetch
react-binding
devtools
```

## 深继承

反模式：

```text
Base -> WithCache -> WithRetry -> WithLogger -> AppClient
```

问题：

- 初始化顺序难懂。
- 方法覆盖风险高。
- 组合能力不灵活。

重构：用插件、策略、组合对象。

## 隐式全局状态

```typescript
let currentClient: Client | null = null
```

全局状态会导致测试污染、多实例冲突、SSR 问题。重构为显式实例或上下文传递。

## 魔法行为

过度自动化会让调试困难：

- 自动扫描目录。
- 自动修改全局对象。
- 自动推断运行环境但无法覆盖。
- 静默吞错误。

库可以提供默认行为，但必须允许显式配置和 debug。

## 重构策略

库重构要保护使用者：

1. 先加新 API。
2. 旧 API 标记 deprecated。
3. 文档给迁移示例。
4. 提供 codemod。
5. major 版本再删除。
6. 保留兼容测试。

## 自检清单

- options 是否已经表达不清？
- core 是否包含太多可选能力？
- 是否有隐式全局状态？
- 插件是否能随意修改内部对象？
- API 是否有魔法行为但不可调试？
- 重构是否有兼容路径？

## 知识点展开与对应练习

| 知识点 | 小点展开 | 对应练习 | 验收标准 |
| --- | --- | --- | --- |
| 万能 options | options 过深过杂会让 API 难学难维护 | 拆分一个 20 字段 options | 至少拆成 core options、plugin options、advanced options |
| 巨型核心 | core 包含所有能力会导致包体大和维护困难 | 把 retry、cache、logger 从 core 拆成插件 | 主入口 API 不变，功能通过插件恢复 |
| 深继承 | 多层继承表达能力组合会造成初始化和覆盖问题 | 把 3 层继承改成组合 | 每个能力可独立测试和启用 |
| 隐式全局 | 全局 client 会导致测试污染、SSR 冲突和多实例问题 | 把全局单例改成显式 createClient | 两个 client 实例配置互不影响 |
| 魔法行为 | 自动扫描、自动注入、静默吞错会降低可调试性 | 给一个魔法 API 增加显式配置和 debug | 使用者能关闭自动行为并看到执行日志 |
| 兼容重构 | 库重构要先新增、再废弃、最后删除 | 为旧 API `initClient` 设计迁移周期 | 包含 deprecated 标注、文档、codemod、major 删除 |
| 反模式审查 | 设计审查要形成固定 checklist | 审查 `mini-request` 设计 | 至少发现 5 个潜在反模式并给出修复方案 |
