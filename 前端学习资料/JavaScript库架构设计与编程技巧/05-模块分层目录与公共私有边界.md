# 模块分层目录与公共私有边界

库的目录结构要表达边界。使用者只能依赖 public API，内部模块可以重构；如果使用者大量深层引用内部文件，库就失去了演进空间。

## 推荐结构

```text
src/
  index.ts          # public API
  core/             # 核心模型和流程
  adapters/         # 环境适配
  plugins/          # 内置插件
  utils/            # 内部工具
  errors/           # 错误类型和错误码
  types/            # 公共类型或内部类型
```

`index.ts` 是最重要的文件之一，它定义了库真正承诺的 API。

## Public 和 Internal

```typescript
// public
export { createClient } from './core/createClient'
export type { Client, ClientOptions } from './types'

// internal 不从 index 导出
// normalizeConfig、runPipeline、mergeHeaders
```

使用者不应该这样引用：

```typescript
import { normalizeConfig } from 'your-lib/dist/core/normalizeConfig'
```

这会让内部重构变成 breaking change。

## 子路径导出

如果确实需要子路径导出，要显式设计：

```json
{
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./plugins/retry": {
      "types": "./dist/plugins/retry.d.ts",
      "import": "./dist/plugins/retry.js"
    }
  }
}
```

只要写进 `exports`，就代表你承诺这个入口的兼容性。

## Core 和 Adapter

把核心逻辑和运行环境分开：

```text
core/request.ts       不依赖 fetch、XMLHttpRequest、node:http
adapters/fetch.ts     浏览器或现代运行时
adapters/node.ts      Node
```

这样库可以支持多个运行时，也更容易测试核心逻辑。

## Utils 不要膨胀

`utils` 容易变成垃圾桶。建议：

- 和领域相关的工具放回对应模块。
- 真正通用的工具才放 utils。
- utils 不依赖 core。
- public 工具函数单独设计 API，不要直接暴露内部 utils。

## 依赖方向

推荐依赖方向：

```text
index -> core -> errors/types/utils
plugins -> core/types
adapters -> core/types
core 不依赖 plugins
core 不依赖具体 adapter
```

核心层不应该知道所有插件和适配器，否则库会越来越难拆。

## 自检清单

- public API 是否只从固定入口导出？
- package exports 是否和文档一致？
- 内部文件是否可能被用户深层引用？
- core 是否和运行环境解耦？
- utils 是否已经膨胀？
- 模块依赖方向是否清晰？

## 知识点展开与对应练习

| 知识点 | 小点展开 | 对应练习 | 验收标准 |
| --- | --- | --- | --- |
| public 入口 | `index.ts` 定义库承诺的 API，不应把内部函数全部导出 | 为 `mini-request` 写 `src/index.ts` 导出清单 | 只导出 `createClient`、public 类型和官方插件 |
| internal 模块 | 内部模块可以重构，不应被使用者深层引用 | 标记 5 个内部函数并说明为什么不导出 | 每个内部函数都不出现在 README 示例中 |
| package exports | 子路径导出必须显式声明，声明后就是兼容承诺 | 为 `./plugins/retry` 和 `./adapters/fetch` 设计 exports | 每个子路径都有 types 和 import 字段 |
| core/adapter 分离 | core 不直接依赖 fetch、DOM、Node http | 把请求发送逻辑从 core 移到 adapter | core 单测不需要真实网络 |
| utils 治理 | utils 只放无领域依赖的通用函数，领域函数放回模块 | 整理 10 个 utils，重新归类 | 至少 5 个函数能归回 core、errors、adapters 或 plugins |
| 依赖方向 | core 不依赖 plugin，plugin 依赖 core 的扩展接口 | 画出模块依赖图 | 图中不能出现 `core -> plugins` 或 `core -> adapters/fetch` 的硬依赖 |
| 私有边界 | TypeScript private、闭包和不导出都可以形成边界 | 用闭包实现一个 `createRegistry()` | 外部只能 register、get、remove，不能直接改内部 Map |
