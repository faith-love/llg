# 阅读路线与工程心智模型

学 Babel 工程化前，先把工具职责分清。很多构建问题定位困难，不是因为工具难，而是因为把编译、打包、压缩、polyfill、类型检查、开发服务器混在一起了。

## 一条完整构建链路

典型前端生产构建可以拆成：

```text
源码入口
  -> 解析入口和 import
  -> 建立模块依赖图
  -> 对每个模块做转换
  -> 处理 CSS、图片、字体等资源
  -> tree-shaking 删除无用代码
  -> code splitting 生成多个 chunk
  -> 压缩和混淆
  -> 生成 source map 和 manifest
  -> 输出 dist
```

Babel 只覆盖其中一部分：

```text
对单个 JS/TS/JSX 文件做语法解析、AST 转换和代码生成
```

它通常不负责：

- 从入口递归收集所有模块。
- 决定 chunk 怎么分。
- 处理图片、字体、CSS 抽取。
- 生成 HTML。
- 开发服务器和 HMR。
- 最终资源 hash 和 manifest。

这些通常由 Webpack、Rollup、Vite 等打包工具负责。

## 工具职责表

| 工具 | 主要职责 | 常见误区 |
| --- | --- | --- |
| Babel | JS 语法转换、JSX 转换、插件化 AST 改写 | 以为 Babel 会自动打包 |
| TypeScript | 类型检查、TS 编译、声明文件生成 | 以为 Babel 处理 TS 就等于做了类型检查 |
| Webpack | 模块依赖图、loader、plugin、chunk、资源输出 | 以为 loader 和 plugin 是一回事 |
| Rollup | ESM 打包、tree-shaking、库构建 | 以为 Rollup 只适合库，不适合应用 |
| Vite | 开发服务器、预构建、生产构建编排 | 以为 Vite 开发和生产完全同一套流程 |
| esbuild/SWC | 高性能转译、压缩、预构建 | 以为它们和 Babel 插件生态完全等价 |
| Terser | 压缩、变量混淆、删除死代码 | 以为它负责语法降级 |

## 开发模式和生产模式不同

开发模式优先：

- 启动快。
- HMR 快。
- source map 好调试。
- 少做昂贵优化。

生产模式优先：

- 产物小。
- 兼容目标环境。
- 缓存友好。
- tree-shaking 和分包有效。
- source map 按安全策略输出。

Vite 开发时常用原生 ESM 和快速转译，生产构建则会进入 bundling 阶段。Webpack 开发和生产都围绕 bundle，但优化程度不同。

## 学习路线

建议按三层学：

### 第一层：Babel 单文件编译

关注：

- parser 把源码变 AST。
- plugin 遍历和改 AST。
- generator 把 AST 生成代码。
- preset 是插件组合。

### 第二层：兼容性和运行时

关注：

- 语法转换和 API polyfill 的区别。
- `@babel/preset-env` 如何根据 targets 决定插件。
- `core-js` 注入策略。
- `@babel/plugin-transform-runtime` 如何复用 helper。

### 第三层：打包器完整流程

关注：

- 入口和依赖图。
- loader/plugin。
- module graph 和 chunk graph。
- tree-shaking。
- code splitting。
- source map。
- cache。
- 输出产物分析。

## 关键判断句

遇到构建问题时先问：

```text
这个问题发生在单文件语法转换，还是发生在多模块打包？
```

如果是新语法不能解析，查 Babel/parser/loader。

如果是 API 运行时报不存在，查 polyfill。

如果是包太大，查 tree-shaking、分包、依赖。

如果是路径找不到，查模块解析和别名。

如果是类型没报错，查 TypeScript 类型检查是否真的执行。
