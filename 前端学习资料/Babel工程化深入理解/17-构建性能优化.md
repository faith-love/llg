# 构建性能优化

构建慢要先定位瓶颈，不要一上来换工具。常见瓶颈包括 Babel 转译范围过大、TypeScript 类型检查慢、依赖预构建慢、压缩慢、source map 慢。

## 先测量

要知道时间花在哪里：

- 启动时间。
- 单文件 transform 时间。
- TypeScript 类型检查时间。
- 打包时间。
- 压缩时间。
- source map 时间。
- 依赖预构建时间。

Webpack 可用 speed-measure-webpack-plugin 或内置 stats。

Vite 可看 debug 日志、依赖预构建输出和插件耗时。

## 缩小 Babel 范围

Webpack：

```javascript
{
  test: /\.[jt]sx?$/,
  include: path.resolve(__dirname, 'src'),
  use: 'babel-loader'
}
```

不要让 Babel 扫整个仓库或所有 `node_modules`。

需要转译特定依赖时，做白名单：

```javascript
include: [
  path.resolve(__dirname, 'src'),
  path.resolve(__dirname, 'node_modules/some-modern-package')
]
```

## 开启缓存

```javascript
{
  loader: 'babel-loader',
  options: {
    cacheDirectory: true
  }
}
```

Webpack 5 文件系统缓存：

```javascript
cache: {
  type: 'filesystem'
}
```

## 减少 Babel 插件

每个插件都会参与 AST 遍历或转换。插件越多，转换越慢。

优化：

- 用 `preset-env` 按 targets 自动选择。
- 删除过时 proposal 插件。
- 不在现代目标上做不必要降级。
- 不对测试、故事书、构建分别重复重转译。

## 使用更快的转译器

如果不依赖 Babel 插件生态，可以考虑：

- esbuild。
- SWC.
- Rspack 内置转译能力。

但要确认语义差异，尤其是 decorators、class fields、helper、polyfill 策略。

## 类型检查并行化

如果用 Babel 转译 TS，类型检查可以单独跑：

```bash
tsc --noEmit
```

开发时可由编辑器和单独进程处理，生产 CI 必须检查。

Webpack 项目可使用类型检查插件把检查从 loader 中移出。

## source map 策略

source map 会影响构建速度。

开发环境要可调试。

生产环境根据需要选择：

- 不生成。
- 生成但不公开。
- hidden source map。
- 上传监控平台。

不要默认所有环境都用最慢最完整 source map。

## 压缩优化

压缩通常很耗时。

可选：

- esbuild minify 更快。
- Terser 压缩更成熟但可能更慢。
- 并行压缩。
- 只在生产构建压缩。

## 依赖优化

大依赖会拖慢构建和加载。

检查：

- 是否引入整个 lodash 而不是按需函数。
- moment locale 是否过大。
- 图表库、编辑器、地图是否按需加载。
- 是否有重复版本依赖。

## 优化顺序

1. 测量。
2. 缩小 transform 范围。
3. 开缓存。
4. 减少不必要插件。
5. 调整 source map。
6. 优化压缩。
7. 分析大依赖。
8. 必要时替换转译/打包工具。
