# 模块系统、声明文件与第三方库类型

TypeScript 的模块系统既要服务类型检查，也要配合运行时构建工具。声明文件则用于描述已有 JavaScript 代码的类型。

## import 和 export

```typescript
export type User = {
  id: string
  name: string
}

export function formatUser(user: User) {
  return user.name
}
```

导入：

```typescript
import { formatUser } from './format'
import type { User } from './format'
```

类型只在编译期使用时，优先 `import type`。

## 默认导出和命名导出

命名导出更利于重构：

```typescript
export function request() {}
```

默认导出：

```typescript
export default function request() {}
```

团队选择一种风格并保持一致更重要。

## .d.ts 声明文件

声明文件只描述类型，不实现运行时代码。

```typescript
declare function analyticsTrack(event: string, payload?: unknown): void
```

用于描述全局变量：

```typescript
declare global {
  interface Window {
    __APP_VERSION__: string
  }
}
```

文件需要成为模块时，加：

```typescript
export {}
```

## 声明第三方模块

```typescript
declare module 'legacy-lib' {
  export function run(input: string): string
}
```

适合没有类型声明的老库。

## @types

很多 JS 库的类型由 DefinitelyTyped 提供：

```bash
npm install -D @types/node
```

但现代库很多已经自带类型，不需要额外安装 `@types`。

## moduleResolution

常见模块解析策略：

- `node`：传统 Node 风格。
- `node16` / `nodenext`：更贴近 Node ESM。
- `bundler`：适合 Vite、现代 bundler 项目。

前端 Vite 项目通常会选择适配 bundler 的解析方式，具体跟项目模板和 TS 版本有关。

## 路径别名

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

注意：`paths` 只告诉 TypeScript 怎么解析类型，不一定改变运行时打包。Vite、Webpack、Jest、Vitest 也要配置一致。

## 类型导出边界

公共模块建议导出稳定类型：

```typescript
export type { User, CreateUserInput }
export { createUser }
```

不要把内部临时类型暴露成公共 API，否则后续重构会被外部依赖绑住。

## 常见问题

### 找不到模块类型

```text
Cannot find module 'xxx' or its corresponding type declarations
```

排查：

1. 包是否安装。
2. 包是否自带类型。
3. 是否需要安装 `@types/xxx`。
4. `moduleResolution` 是否匹配项目。
5. 是否需要手写 `declare module`。

### 全局类型不生效

排查：

1. `.d.ts` 是否被 `tsconfig.include` 包含。
2. 文件里是否错误使用了顶层 import/export。
3. `declare global` 是否放在模块文件中。
4. 编辑器 TS Server 是否需要重启。
