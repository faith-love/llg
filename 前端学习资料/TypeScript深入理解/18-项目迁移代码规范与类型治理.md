# 项目迁移、代码规范与类型治理

TypeScript 项目长期质量取决于类型治理。迁移旧项目时尤其要控制节奏，避免一口气把所有文件改成 `.ts` 却留下满地 `any`。

## 迁移策略

推荐顺序：

1. 加入 TypeScript 和基础 tsconfig。
2. 先允许 JS 共存。
3. 从工具函数、类型稳定模块开始迁移。
4. 再迁移 API 层和状态层。
5. 最后迁移复杂组件。
6. 逐步打开严格检查。

不要从最复杂、依赖最多的页面开始。

## allowJs 和 checkJs

```json
{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": false
  }
}
```

`allowJs` 允许 JS 文件参与项目。

`checkJs` 会检查 JS 文件，迁移初期可以先不开。

## any 债务

短期可以用 `any` 推进迁移，但必须隔离：

```typescript
// TODO(ts-migration): replace any after legacy API typed
function legacyAdapter(input: any): unknown {
  return input
}
```

不要让 `any` 直接进入核心业务类型。

## unknown 优先

外部边界：

```typescript
function parse(input: string): unknown {
  return JSON.parse(input)
}
```

内部使用前做校验或转换。

## 类型文件组织

推荐：

```text
src/
  features/
    user/
      user.types.ts
      user.api.ts
      UserList.tsx
```

公共类型：

```text
src/
  shared/
    types/
      api.ts
      pagination.ts
```

不要所有类型都放到全局命名空间。

## 命名规范

建议：

- 业务实体：`User`、`Order`。
- 入参：`CreateUserInput`、`UpdateUserInput`。
- 返回值：`UserDetail`、`UserListItem`。
- Props：`UserCardProps`。
- 状态：`UserPageState`。
- 事件：`UserSelectedPayload`。

避免：

- `IData`
- `IInfo`
- `Obj`
- `anyData`
- 和后端字段不一致的随意缩写。

## 类型和运行时校验

TypeScript 不会校验运行时数据。关键边界可以配合校验库或手写守卫：

```typescript
function isUser(value: unknown): value is User {
  return (
    typeof value === 'object' &&
    value !== null &&
    'id' in value &&
    'name' in value
  )
}
```

## CI 类型检查

项目应该在 CI 里跑：

```bash
tsc --noEmit
```

前端应用可能还要跑：

```bash
eslint .
vitest run
```

不要只依赖编辑器提示。

## 类型治理指标

可以定期检查：

- `any` 数量。
- `@ts-ignore` 数量。
- `as unknown as` 数量。
- 是否开启 `strict`。
- API 层是否有统一响应类型。
- 组件 props 是否明确。
- 公共库是否生成 `.d.ts`。

## @ts-ignore 和 @ts-expect-error

优先使用：

```typescript
// @ts-expect-error: legacy SDK type is wrong, remove after sdk v2
legacyCall(wrongInput)
```

`@ts-expect-error` 如果下一次不再报错，会提示你移除它。

少用：

```typescript
// @ts-ignore
```

它会无条件忽略下一行错误，容易长期隐藏问题。
