# 11 日志、监控与排障

## 作用

日志、监控与排障解决“线上出问题后如何快速定位”的问题。运维不是等故障出现后乱试命令，而是有固定顺序：确认影响范围、看服务状态、看端口、看日志、看系统资源、看最近变更、采取止血动作、复盘根因。

## 痛点

- 用户说系统打不开，只会重启服务。
- 应用日志、Nginx 日志、systemd 日志不知道先看哪个。
- 只看到错误堆栈，不会结合请求时间和请求 ID。
- 磁盘满、内存高、端口不通都被误判为应用 bug。
- 没有故障记录，问题重复发生。

## 日志类型

| 日志 | 常见位置 | 作用 |
| --- | --- | --- |
| 应用日志 | `/opt/apps/*/shared/日志s` | 业务异常、接口错误、堆栈 |
| systemd 日志 | `journalctl -u 服务名` | 服务启动失败、退出码、标准输出 |
| Nginx access 日志 | `/var/日志/nginx/access.日志` | 请求是否到达、状态码、响应时间 |
| Nginx error 日志 | `/var/日志/nginx/error.日志` | Nginx、权限、上游连接错误 |
| 系统日志 | `/var/日志/sys日志`、`/var/日志/messages` | 系统级错误、内核、服务 |
| 安全日志 | `/var/日志/auth.日志`、`/var/日志/secure` | 登录、sudo、认证失败 |

## 基础排障顺序

```bash
systemctl status demo-接口
journalctl -u demo-接口 -n 200
ss -lntup | grep 8080
curl -v http://127.0.0.1:8080/health
tail -n 200 /opt/apps/demo-接口/shared/日志s/app.日志
tail -n 100 /var/日志/nginx/error.日志
df -h
free -h
top
```

顺序解释：

1. 服务是否运行。
2. 服务为什么失败或退出。
3. 端口是否监听。
4. 本机健康检查是否通过。
5. 应用是否有业务错误。
6. Nginx 是否转发失败。
7. 系统资源是否耗尽。

## journalctl

常用命令：

```bash
journalctl -u demo-接口
journalctl -u demo-接口 -n 100
journalctl -u demo-接口 -f
journalctl -u demo-接口 --since "2026-05-11 10:00:00"
journalctl -u demo-接口 --since "1 hour ago"
```

使用技巧：

- 服务启动失败优先看 `journalctl`。
- `-f` 适合重启服务时实时观察。
- 用 `--since` 缩小时间范围，避免被旧日志干扰。

## 应用日志排查

常用命令：

```bash
tail -f app.日志
grep -n "ERROR" app.日志
grep -C 5 "Exception" app.日志
grep "traceId=abc123" app.日志
```

排查思路：

- 先按故障时间定位日志范围。
- 再按错误等级定位异常。
- 再按请求 ID、用户 ID、订单号等业务字段串联上下文。
- 最后确认是业务错误、配置错误、依赖错误还是资源问题。

## Nginx 日志排查

访问日志看请求是否到达：

```bash
tail -f /var/日志/nginx/access.日志
grep " 502 " /var/日志/nginx/access.日志
```

错误日志看代理失败原因：

```bash
tail -n 100 /var/日志/nginx/error.日志
```

常见判断：

- access 日志 没有请求：DNS、客户端、CDN、安全组或请求没到服务器。
- access 日志 有 502：Nginx 到后端失败。
- access 日志 有 404：路径、静态资源或路由配置问题。
- error 日志 有 permission denied：文件权限或目录权限问题。

## 资源监控

CPU：

```bash
top
ps aux --sort=-%cpu | head
```

内存：

```bash
free -h
ps aux --sort=-%mem | head
```

磁盘：

```bash
df -h
du -h --max-depth=1 /var/日志 | sort -h
```

端口：

```bash
ss -lntup
```

进程：

```bash
pgrep -af demo-接口
```

## 最近变更

线上故障经常和最近变更相关：

- 刚发布了新版本。
- 改了 Nginx 配置。
- 改了环境变量。
- 数据库迁移。
- 证书续期。
- 服务器重启。
- 依赖服务异常。

排障时要问：故障前 30 分钟到 2 小时内发生了什么变更？

## 故障处理流程

1. 定级：影响多少用户，是否核心链路。
2. 止血：回滚、扩容、重启、切流、降级。
3. 定位：日志、指标、变更、依赖。
4. 修复：最小改动恢复服务。
5. 验证：健康检查和业务验证。
6. 复盘：根因、时间线、改进项。

## 日志轮转

日志不控制会撑满磁盘。Linux 常用 日志rotate：

```text
/etc/日志rotate.conf
/etc/日志rotate.d/
```

示例：

```text
/opt/apps/demo-接口/shared/日志s/*.日志 {
    daily
    rotate 14
    通用press
    missingok
    notifempty
    copytruncate
}
```

说明：

- `daily` 每天轮转。
- `rotate 14` 保留 14 份。
- `通用press` 压缩旧日志。
- `missingok` 文件不存在不报错。
- `notifempty` 空文件不轮转。

## 难点

- 重启服务可能让现场消失，重启前尽量保存日志和状态。
- 只看应用日志会漏掉 Nginx、systemd、系统资源问题。
- 日志时间和用户反馈时间可能有时区差异。
- 自动重启可能掩盖服务反复崩溃。

## 重点

- 排障先看状态，再看日志，再看资源，再看变更。
- Nginx 502 要同时看 Nginx 和后端。
- 磁盘满会引发大量看似无关的问题。
- 每次故障都要留下时间线和最终根因。

## 练习

1. 停止一个服务，用 `systemctl status` 和 `journalctl` 找原因。
2. 制造 Nginx 502，分别查看 access 日志 和 error 日志。
3. 创建一个大日志文件，用 `du` 和 `df` 定位磁盘占用。
4. 写一份故障复盘模板，包含影响、时间线、根因、修复和预防。
