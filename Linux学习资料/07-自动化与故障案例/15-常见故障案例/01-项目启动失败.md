# 01 项目启动失败

项目启动失败是部署中最常见的故障之一。排查时不要只盯着“服务没起来”，要把 systemd、启动命令、工作目录、运行用户、配置文件、环境变量、端口和应用日志串起来看。

## 作用

- 快速判断服务是没有启动、启动后退出，还是启动成功但无法访问。
- 用 `systemctl status` 和 `journalctl` 找到第一条关键错误。
- 检查 `ExecStart`、`WorkingDirectory`、配置文件和权限是否匹配。
- 用服务用户手动执行启动命令，复现 systemd 环境下的问题。
- 把启动失败沉淀成发布前检查清单。

## 常见现象

- `systemctl start demo-接口` 返回失败。
- `systemctl status demo-接口` 显示 `failed`。
- 服务启动几秒后自动退出。
- 端口没有监听。
- Nginx 返回 502。
- 日志中出现 `No such file or directory`、`Permissiondenied denied`、`Address already in use`、`failed to load 配置`。

## 先确认影响范围

先回答四个问题：

| 问题 | 判断方式 |
| --- | --- |
| 是新发布后失败，还是一直失败 | 查看最近部署记录和服务日志时间 |
| 只有一个服务失败，还是多个服务失败 | `systemctl --failed` |
| 是进程没起来，还是端口没监听 | `systemctl status` + `ss -lntup` |
| 是应用失败，还是 Nginx/网络失败 | 本机 `curl 127.0.0.1:端口` |

不要一开始就重启机器。先保留现场信息。

## 快速检查命令

```bash
systemctl status demo-接口 --no-分页r
journalctl -u demo-接口 -n 200 --no-分页r
systemctl cat demo-接口
ss -lntup | grep 8080
ls -lah /opt/apps/demo-接口/current
```

如果服务依赖配置文件：

```bash
ls -lah /opt/apps/demo-接口/shared/配置
```

如果服务有健康检查：

```bash
curl -v http://127.0.0.1:8080/health
```

## 看 systemctl status

重点字段：

```text
Loaded: loaded (/etc/systemd/system/demo-接口.服务; enabled)
Active: failed
Main PID: 1234
ExecStart=/usr/bin/Java学习资料 -jar /opt/apps/demo-接口/current/demo-接口.jar
status=203/EXEC
```

常见状态含义：

| 线索 | 可能原因 |
| --- | --- |
| `status=203/EXEC` | `ExecStart` 命令不存在、脚本无执行权限、解释器路径错误 |
| `No such file or directory` | jar、脚本、工作目录或配置文件路径错误 |
| `Permissiondenied denied` | 服务用户无执行、读取或写入权限 |
| `failed` 后很快退出 | 应用启动时报错或配置不完整 |
| `activating` 很久 | 启动卡住、依赖服务慢、健康检查阻塞 |

## 看 journalctl

查看最新日志：

```bash
journalctl -u demo-接口 -n 200 --no-分页r
```

跟随日志：

```bash
journalctl -u demo-接口 -f
```

查看某个时间段：

```bash
journalctl -u demo-接口 --since "2026-05-12 10:00" --until "2026-05-12 10:30"
```

排查时优先找第一条根因错误，而不是最后一条“服务退出”。例如：

- 配置文件不存在。
- JDBC失败。
- 端口占用。
- 目录无权限。
- 运行时版本不兼容。

## 检查 unit 文件

查看 systemd 实际加载的配置：

```bash
systemctl cat demo-接口
```

重点检查：

```ini
[Service]
用户=app
Group=app
WorkingDirectory=/opt/apps/demo-接口/current
EnvironmentFile=/opt/apps/demo-接口/shared/配置/demo-接口.env
ExecStart=/usr/bin/Java学习资料 -jar /opt/apps/demo-接口/current/demo-接口.jar
Restart=always
```

常见错误：

- `ExecStart` 路径写成旧版本目录。
- `WorkingDirectory` 指向不存在的目录。
- `EnvironmentFile` 文件不存在。
- 修改 unit 后忘记 `systemctl daemon-reload`。
- 服务名和实际操作的服务名不一致。

修改 unit 后执行：

```bash
sudo systemctl daemon-reload
sudo systemctl restart demo-接口
```

## 检查启动命令和运行时

确认命令存在：

```bash
which Java学习资料
Java学习资料 -version
which node
node -v
which Python学习资料3
Python学习资料3 --version
```

systemd 中建议写绝对路径：

```ini
ExecStart=/usr/bin/Java学习资料 -jar /opt/apps/demo-接口/current/demo-接口.jar
```

不要依赖交互式 Shell 的 `PATH`。你在终端里能执行，不代表 systemd 能执行。

## 用服务用户手动复现

先看服务用户：

```bash
systemctl cat demo-接口 | grep -E "^(用户|Group)="
```

模拟服务用户执行：

```bash
sudo -u app -H /usr/bin/Java学习资料 -jar /opt/apps/demo-接口/current/demo-接口.jar
```

如果需要工作目录：

```bash
cd /opt/apps/demo-接口/current
sudo -u app -H /usr/bin/Java学习资料 -jar demo-接口.jar
```

如果手动执行成功而 systemd 失败，重点检查：

- systemd 环境变量。
- `WorkingDirectory`。
- `EnvironmentFile`。
- systemd 安全限制项。
- 文件描述符、内存限制等资源限制。

## 检查配置和环境变量

查看环境文件：

```bash
sudo ls -lah /opt/apps/demo-接口/shared/配置/demo-接口.env
sudo sed -n '1,120p' /opt/apps/demo-接口/shared/配置/demo-接口.env
```

生产环境不要在共享输出里展示真实密码。排障时可只看变量名：

```bash
sudo cut -d= -f1 /opt/apps/demo-接口/shared/配置/demo-接口.env
```

检查 systemd 看到的环境文件：

```bash
systemctl show demo-接口 -p EnvironmentFiles
systemctl show demo-接口 -p Environment
```

注意：

- `.bashrc`、`.profile` 不会自动影响 systemd 服务。
- `EnvironmentFile` 中一般不写 `export`。
- 修改环境文件后需要重启服务，不只是 `daemon-reload`。

## 检查权限

查看路径链路：

```bash
namei -l /opt/apps/demo-接口/current/demo-接口.jar
namei -l /opt/apps/demo-接口/shared/配置/demo-接口.env
```

验证服务用户权限：

```bash
sudo -u app 测试 -r /opt/apps/demo-接口/current/demo-接口.jar && echo jar-readable
sudo -u app 测试 -r /opt/apps/demo-接口/shared/配置/demo-接口.env && echo 配置-readable
sudo -u app 测试 -w /opt/apps/demo-接口/shared/日志s && echo 日志s-writable
```

不要用：

```bash
chmod -R 777 /opt/apps/demo-接口
```

应按目录用途修复：

```bash
sudo chown -R deploy:app /opt/apps/demo-接口/current
sudo chown -R app:app /opt/apps/demo-接口/shared/日志s
sudo chmod 640 /opt/apps/demo-接口/shared/配置/demo-接口.env
```

## 检查端口和依赖

端口是否占用：

```bash
ss -lntup | grep 8080
sudo lsof -i :8080
```

依赖服务是否可访问：

```bash
nc -vz 127.0.0.1 3306
nc -vz 127.0.0.1 6379
```

如果没有 `nc`，可用：

```bash
timeout 3 bash -c '</dev/tcp/127.0.0.1/3306' && echo ok
```

JDBC失败时，要区分：

- 主机和端口不通。
- 用户密码错误。
- 数据库权限不足。
- 数据库服务未启动。
- 防火墙阻断。

## 修复流程

按错误类型处理：

| 错误 | 修复方向 |
| --- | --- |
| 路径不存在 | 修正 unit 路径或重新发布制品 |
| 命令不存在 | 安装运行时或改为绝对路径 |
| 权限不足 | 修正属主、组和目录权限 |
| 配置缺失 | 补齐 `EnvironmentFile` 或配置文件 |
| 端口占用 | 停旧服务、改端口或修复重复启动 |
| 依赖不可用 | 恢复数据库、缓存、网络或配置 |
| 应用异常 | 根据应用日志修复代码、参数或数据 |

修复后验证：

```bash
sudo systemctl daemon-reload
sudo systemctl restart demo-接口
systemctl status demo-接口 --no-分页r
ss -lntup | grep 8080
curl -fsS http://127.0.0.1:8080/health
```

## 发布前预防清单

- 制品文件存在且版本正确。
- systemd unit 中路径正确。
- 环境变量文件存在且权限正确。
- 服务用户可读配置、可写日志。
- 端口未被占用。
- 依赖服务可访问。
- `systemctl daemon-reload` 已执行。
- 本机健康检查通过。
- 回滚版本可用。

## 好用工具

| 工具 | 用途 |
| --- | --- |
| `systemctl status` | 看服务状态和退出码 |
| `journalctl` | 看 systemd 服务日志 |
| `systemctl cat` | 看实际加载的 unit |
| `ss`/`lsof` | 看端口监听和占用 |
| `namei -l` | 查路径链路权限 |
| `sudo -u` | 模拟服务用户执行 |
| `curl` | 做健康检查 |

## 练习

1. 故意把 `ExecStart` 改成不存在的 jar 路径，观察 `status=203/EXEC` 或相关错误。
2. 去掉配置文件读取权限，用 `namei -l` 和 `sudo -u app 测试 -r` 定位。
3. 让应用端口被另一个进程占用，查看启动日志和 `ss` 输出。
4. 写一份自己的“项目启动失败排查表”。
