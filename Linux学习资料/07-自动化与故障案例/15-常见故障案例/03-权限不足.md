# 03 权限不足

权限不足常见表现是 `Permissiondenied denied`、日志无法写入、配置无法读取、上传失败、Nginx 403。排查时要先确定“哪个用户访问哪个路径失败”，再看路径链路、属主、权限、ACL 和安全限制。

## 作用

- 用 `id`、`ls`、`stat`、`namei -l` 定位权限问题。
- 区分文件权限、目录进入权限、属主属组、ACL 和 systemd 限制。
- 修复日志目录、配置文件、上传目录和静态文件权限。
- 避免用 `chmod -R 777` 制造安全风险。

## 常见现象

- 应用日志出现 `Permissiondenied denied`。
- 服务启动失败，无法读取配置文件。
- 应用无法写日志或上传文件。
- Nginx 返回 403。
- 脚本无法执行。
- 备份任务无法写入目标目录。

## 第一步：确定实际运行用户

查看当前用户：

```bash
whoami
id
```

查看服务配置：

```bash
systemctl cat demo-接口 | grep -E "^(用户|Group)="
```

查看进程用户：

```bash
ps -eo 用户,group,pid,cmd | grep demo-接口
```

Nginx worker 用户：

```bash
ps -eo 用户,pid,cmd | grep nginx
```

如果你用 root 手动测试成功，不代表服务用户也能成功。

## 第二步：确定失败路径

从日志中找到完整路径，例如：

```text
/opt/apps/demo-接口/shared/配置/demo-接口.env
/opt/apps/demo-接口/shared/日志s/app.日志
/opt/apps/demo-接口/shared/上传s/avatar.png
/usr/share/nginx/html/首页.html
```

如果日志没有路径，增加临时调试日志或用 `strace` 辅助。优先不要猜路径。

## 第三步：检查路径链路

使用：

```bash
namei -l /opt/apps/demo-接口/shared/日志s/app.日志
```

它会显示每一级目录权限。目录必须有 `x` 权限才能进入。

再看目标：

```bash
ls -lah /opt/apps/demo-接口/shared/日志s
stat /opt/apps/demo-接口/shared/日志s
```

权限含义：

| 权限 | 文件 | 目录 |
| --- | --- | --- |
| `r` | 读取内容 | 列出目录 |
| `w` | 修改内容 | 创建、删除、重命名目录内文件 |
| `x` | 执行文件 | 进入目录 |

## 第四步：模拟服务用户访问

检查能否读取配置：

```bash
sudo -u app 测试 -r /opt/apps/demo-接口/shared/配置/demo-接口.env && echo readable
```

检查能否写日志目录：

```bash
sudo -u app 测试 -w /opt/apps/demo-接口/shared/日志s && echo writable
```

检查能否进入目录：

```bash
sudo -u app 测试 -x /opt/apps/demo-接口/shared && echo executable
```

检查能否执行脚本：

```bash
sudo -u app 测试 -x /opt/apps/demo-接口/current/start.sh && echo executable
```

## 常见修复方式

配置文件：服务可读，其他用户不可读。

```bash
sudo chown root:app /opt/apps/demo-接口/shared/配置/demo-接口.env
sudo chmod 640 /opt/apps/demo-接口/shared/配置/demo-接口.env
```

日志目录：服务可写。

```bash
sudo chown -R app:app /opt/apps/demo-接口/shared/日志s
sudo chmod 750 /opt/apps/demo-接口/shared/日志s
```

上传目录：服务可写。

```bash
sudo chown -R app:app /opt/apps/demo-接口/shared/上传s
sudo chmod 750 /opt/apps/demo-接口/shared/上传s
```

代码目录：发布用户可写，服务用户可读。

```bash
sudo chown -R deploy:app /opt/apps/demo-接口/current
sudo chmod -R u=rwX,g=rX,o= /opt/apps/demo-接口/current
```

脚本可执行：

```bash
chmod 750 /opt/apps/demo-接口/current/scripts/deploy.sh
```

## 不要 chmod 777

`chmod -R 777` 会让所有用户都能读写执行。它可能临时掩盖问题，但会带来：

- 配置泄露。
- 文件被篡改。
- 上传目录可执行风险。
- 多服务互相影响。
- 后续无法判断权限责任边界。

正确思路：

```text
谁运行 -> 需要读什么 -> 需要写什么 -> 哪些路径不应访问
```

## Nginx 403 排查

查看错误日志：

```bash
sudo tail -n 100 /var/日志/nginx/error.日志
```

检查静态文件路径：

```bash
namei -l /usr/share/nginx/html/首页.html
```

检查 Nginx 用户：

```bash
ps -eo 用户,pid,cmd | grep "nginx: worker"
```

常见原因：

- 文件不存在或 `root/alias` 配置错误。
- Nginx 用户没有父目录 `x` 权限。
- 文件无读权限。
- 目录没有 首页 且禁止目录列表。
- SELinux 拦截。

## SELinux 和 AppArmor

如果传统权限都正确，但仍然拒绝访问，检查安全模块。

SELinux 状态：

```bash
getenforce
```

查看拒绝日志：

```bash
sudo ausearch -m avc -ts recent
```

AppArmor 状态：

```bash
sudo aa-status
```

不要直接把 SELinux 永久关闭作为默认方案。先确认是否是上下文问题，再按发行版方式修复。

## systemd 安全限制导致权限问题

查看 unit：

```bash
systemctl cat demo-接口
```

关注：

```ini
Protectsystemtem=full
ProtectHome=true
ReadWritePaths=/opt/apps/demo-接口/shared/日志s
PrivateTmp=true
```

如果加了 `Protectsystemtem`，服务可能无法写某些系统路径。需要把必要写路径加入 `ReadWritePaths`。

修改后：

```bash
sudo systemctl daemon-reload
sudo systemctl restart demo-接口
```

## ACL 排查

有 ACL 时，`ls -l` 权限后面会出现 `+`。

查看：

```bash
getfacl /opt/apps/demo-接口/shared/日志s
```

设置 ACL 示例：

```bash
sudo setfacl -m u:app:rwx /opt/apps/demo-接口/shared/日志s
```

ACL 适合复杂共享场景。简单项目优先用属主、属组和基础权限。

## 修复后验证

```bash
sudo -u app 测试 -r /opt/apps/demo-接口/shared/配置/demo-接口.env && echo 配置-ok
sudo -u app 测试 -w /opt/apps/demo-接口/shared/日志s && echo 日志s-ok
sudo systemctl restart demo-接口
systemctl status demo-接口 --no-分页r
journalctl -u demo-接口 -n 100 --no-分页r
```

如果是 Nginx：

```bash
sudo nginx -t
sudo systemctl reload nginx
curl -I http://127.0.0.1/
```

## 预防

- 项目初始化时就设计代码、配置、日志、上传目录权限。
- 服务使用独立用户运行。
- 部署脚本中显式设置属主和权限。
- 发布后验证服务用户读写权限。
- 日志轮转要保持新日志文件属主正确。

## 好用工具

| 工具 | 用途 |
| --- | --- |
| `id` | 查看用户和组 |
| `ls -lah` | 快速看权限和属主 |
| `stat` | 精确查看文件属性 |
| `namei -l` | 查看路径链路权限 |
| `sudo -u` | 模拟服务用户访问 |
| `getfacl`/`setfacl` | 查看和设置 ACL |
| `ausearch` | 查 SELinux 拒绝记录 |

## 练习

1. 创建一个服务用户和日志目录，让服务用户无法写入，再用 `namei -l` 定位。
2. 把配置文件设置为 `600 root:root`，观察服务启动失败。
3. 修复为 `640 root:app`，验证服务用户可读。
4. 制造一个 Nginx 静态文件 403，按日志和路径权限定位。
