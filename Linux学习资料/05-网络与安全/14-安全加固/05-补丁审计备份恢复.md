# 05 补丁、审计、备份恢复

安全加固不是一次性配置。系统会持续出现漏洞，账号会变化，服务会新增，数据会增长。补丁、审计、备份恢复要形成周期性机制，否则服务器短期看似稳定，长期风险会不断累积。

## 作用

- 及时修复系统和软件漏洞。
- 发现异常登录、异常 sudo、异常服务行为。
- 通过基线扫描发现弱配置。
- 在误删、入侵、磁盘损坏、升级失败后恢复业务。
- 用恢复演练验证备份是否真的可用。

## 痛点

- 长期不升级，系统存在已公开漏洞。
- 生产环境随手全量升级，导致核心服务不兼容。
- 只做备份不做恢复演练，出事后发现备份不可用。
- 备份和生产数据放在同一台机器，机器损坏时一起丢失。
- 登录和 sudo 日志没人看，异常行为发现太晚。

## 补丁升级策略

补丁不是越快越好，也不是越慢越稳。生产环境需要分级处理。

| 类型 | 处理策略 |
| --- | --- |
| 高危安全漏洞 | 尽快评估和修复，必要时开紧急维护窗口 |
| 普通安全补丁 | 定期维护窗口统一升级 |
| 内核升级 | 注意是否需要重启，提前安排窗口 |
| 数据库大版本 | 单独评估兼容性和回滚方案 |
| 运行时版本 | 先在测试环境验证应用兼容 |

推荐流程：

1. 查看可升级包。
2. 判断是否安全补丁或高危漏洞相关。
3. 在测试环境验证。
4. 备份配置和数据。
5. 安排维护窗口。
6. 生产升级。
7. 验证服务。
8. 记录变更和回滚结果。

## 查看可升级包

Ubuntu/Debian：

```bash
sudo apt update
apt list --upgradable
```

只模拟升级：

```bash
sudo apt upgrade -s
```

查看安全更新信息：

```bash
sudo unattended-upgrades --dry-run --debug
```

CentOS/RHEL：

```bash
sudo dnf check-update
sudo dnf updateinfo list 安全
```

只升级安全补丁：

```bash
sudo dnf update --安全
```

旧系统可能使用：

```bash
sudo yum check-update
sudo yum update --安全
```

## 升级前检查清单

升级前确认：

- 当前服务版本和运行状态。
- 关键配置文件已经备份。
- 数据库已经备份。
- 有回滚包或旧版本制品。
- 有维护窗口和通知。
- 有控制台登录方式，防止 SSH 或网络异常。
- 明确升级后验证命令。

记录当前版本：

```bash
uname -a
cat /etc/os-release
nginx -v
mySQL学习资料 --version
Java学习资料 -version
```

记录服务状态：

```bash
systemctl status nginx
systemctl status demo-接口
```

## 升级后验证

基础验证：

```bash
systemctl --failed
systemctl status nginx
systemctl status demo-接口
journalctl -p err -n 100 --no-分页r
```

业务验证：

```bash
curl -I 安全HTTP://example.通用
curl -fsS http://127.0.0.1:8080/health
```

资源验证：

```bash
df -h
free -h
ss -lntup
```

如果内核升级：

```bash
needs-restarting -r
```

或检查是否提示需要重启。不同发行版工具不同，没有该命令时以发行版提示为准。

## 登录和 sudo 审计

成功登录：

```bash
last
```

失败登录：

```bash
lastb
```

当前登录：

```bash
who
w
```

Ubuntu/Debian：

```bash
sudo grep "Accepted" /var/日志/auth.日志
sudo grep "Failed password" /var/日志/auth.日志
sudo grep "sudo" /var/日志/auth.日志
```

CentOS/RHEL：

```bash
sudo grep "Accepted" /var/日志/secure
sudo grep "Failed password" /var/日志/secure
sudo grep "sudo" /var/日志/secure
```

重点关注：

- 陌生 IP 登录成功。
- root 登录成功。
- 同一 IP 大量失败登录。
- 非维护窗口 sudo。
- 普通业务用户尝试 sudo。

## auditd 审计

`auditd` 可以记录更细粒度的系统行为，例如关键文件被谁修改。

安装：

```bash
sudo apt install auditd
```

或：

```bash
sudo dnf install audit
```

启动：

```bash
sudo systemctl enable --now auditd
```

监控 sudoers：

```bash
sudo auditctl -w /etc/sudoers -p wa -k sudoers_change
sudo auditctl -w /etc/sudoers.d -p wa -k sudoers_change
```

查询：

```bash
sudo ausearch -k sudoers_change
```

持久规则通常放在：

```text
/etc/audit/rules.d/
```

注意：审计规则过多会增加日志量和系统开销，要围绕关键文件配置。

## 基线扫描

### lynis

`lynis` 是常用 Linux 安全基线扫描工具。

安装：

```bash
sudo apt install lynis
```

或：

```bash
sudo dnf install lynis
```

扫描：

```bash
sudo lynis audit system
```

重点看：

- Warnings。
- Suggestions。
- SSH 配置建议。
- 文件权限建议。
- 日志和审计建议。

不要盲目追求满分。扫描结果要结合业务可用性逐项评估。

### rkhunter 和 chkrootkit

这类工具用于检查已知 rootkit 痕迹。

```bash
sudo apt install rkhunter chkrootkit
sudo rkhunter --check
sudo chkrootkit
```

注意：

- 它们只能作为辅助检查。
- 不能证明系统一定安全。
- 有误报和漏报。
- 如果确认被入侵，通常应重建系统并从可信备份恢复。

## 备份范围

至少备份：

| 内容 | 示例 |
| --- | --- |
| 数据库 | MySQL、PostgreSQL、MongoDB |
| 上传文件 | 用户头像、附件、业务文件 |
| 配置 | Nginx、systemd、应用配置、环境变量 |
| 证书 | TLS 证书和私钥 |
| 部署脚本 | 发布脚本、回滚脚本 |
| 定时任务 | crontab、systemd timer |
| 基础设施配置 | 防火墙规则、Docker Compose、K8s YAML |

不建议只备份数据库。很多业务恢复还依赖上传文件、配置和证书。

## 备份策略

常见策略：

```text
每日增量 + 每周全量 + 保留 30 天 + 异地存储 + 加密
```

关键要求：

- 自动执行。
- 失败告警。
- 权限受控。
- 备份加密。
- 不只放在同一台服务器。
- 定期恢复演练。

简单备份目录：

```bash
sudo tar -czf /backup/demo-配置-$(date +%F).tar.gz /etc/nginx /etc/systemd/system /opt/apps/demo-接口/shared/配置
sudo chmod 600 /backup/demo-配置-$(date +%F).tar.gz
```

数据库备份示例：

```bash
mySQL学习资料dump --single-transaction -u backup -p demo > demo-$(date +%F).SQL学习资料
```

PostgreSQL：

```bash
pg_dump -Fc demo > demo-$(date +%F).dump
```

## 恢复演练

恢复演练要回答：

- 备份文件能否解压或导入。
- 数据是否完整。
- 配置是否匹配当前版本。
- 证书和密钥是否可用。
- 恢复耗时多久。
- 恢复步骤是否有人能照着执行。

演练环境：

```text
新机器或隔离测试环境
```

不要直接在生产库上测试恢复。

恢复演练记录模板：

```text
演练日期：
备份文件：
恢复环境：
恢复步骤：
验证结果：
耗时：
发现问题：
改进措施：
负责人：
```

## 入侵后的恢复原则

如果怀疑服务器被入侵：

1. 保留现场证据，避免立即清空日志。
2. 临时隔离网络或下线公网入口。
3. 导出关键日志和进程信息。
4. 轮换所有可能泄露的密钥。
5. 不要继续信任原系统。
6. 使用干净镜像重建服务器。
7. 从可信备份恢复数据。
8. 分析入侵路径并修补后再开放。

不要只删除可疑文件就继续使用。攻击者可能留下后门、计划任务、SSH key、系统服务或篡改二进制。

## 常见排障

### 升级后服务启动失败

查看：

```bash
systemctl status demo-接口
journalctl -u demo-接口 -n 200 --no-分页r
```

处理：

- 回滚应用版本。
- 回滚配置。
- 恢复旧运行时。
- 必要时从快照恢复。

### 备份任务执行了但文件不可用

检查：

```bash
ls -lh /backup
tar -tzf backup.tar.gz | head
mySQL学习资料 --force < backup.SQL学习资料
```

原因可能是：

- 备份命令失败但脚本没有退出。
- 备份时数据库正在写入，未使用一致性参数。
- 磁盘满导致备份不完整。
- 备份文件没有同步到异地。

### 日志被轮转找不到旧记录

查看：

```bash
ls -lh /var/日志/auth.日志*
zgrep "Accepted" /var/日志/auth.日志*
zgrep "sudo" /var/日志/auth.日志*
```

CentOS/RHEL：

```bash
ls -lh /var/日志/secure*
zgrep "Accepted" /var/日志/secure*
```

## 好用工具

| 工具 | 用途 | 使用建议 |
| --- | --- | --- |
| `apt`/`dnf`/`yum` | 补丁和软件升级 | 生产先测试再升级 |
| `needrestart` | 判断服务是否需重启 | Debian/Ubuntu 常用 |
| `needs-restarting` | 判断是否需重启 | RHEL 系常用 |
| `auditd` | 系统审计 | 监控关键文件变更 |
| `lynis` | 安全基线扫描 | 定期扫描并跟踪改进 |
| `rkhunter`/`chkrootkit` | rootkit 辅助检查 | 不要迷信结果 |
| `rsync` | 文件同步备份 | 适合增量同步 |
| `restic`/`borg` | 加密去重备份 | 适合长期备份 |
| `日志rotate` | 日志轮转 | 防止日志撑满磁盘 |

## 重点

- 补丁升级要有维护窗口、备份、验证和回滚。
- 登录、失败登录、sudo 行为要定期审计。
- `lynis` 可帮助发现基线问题，但需要人工判断。
- 备份必须包含数据库、上传文件、配置、证书和部署脚本。
- 没有恢复演练的备份不能算可靠备份。

## 练习

1. 查看当前系统可升级包，并区分安全补丁和普通升级。
2. 检查最近 50 条成功登录、失败登录和 sudo 记录。
3. 使用 `lynis audit system` 做一次基线扫描，记录前三个可改进项。
4. 备份一个应用的配置目录和数据库。
5. 在测试目录或测试库中做一次恢复演练，并记录耗时和问题。
