# 磁盘 IO 与文件句柄

## 作用

磁盘 IO 和文件句柄排查用于判断“CPU 不高但系统很慢”“接口偶发超时”“日志或连接失败”“服务报 Too many open files”等问题。磁盘 IO 是存储读写能力，文件句柄是进程可同时打开文件、SocketIO、管道的数量。两者耗尽都会让服务表现为慢、卡、连接失败或无法写日志。

这一节重点解决：

- 如何判断磁盘 IO 是否成为瓶颈。
- 如何找到产生大量 IO 的进程。
- 如何理解文件句柄限制。
- 如何排查 `Too many open files`。
- 如何在 systemd 服务中提高句柄限制。

## 痛点

- CPU 和内存都不高，但接口很慢，实际是磁盘 IO 等待。
- 备份、压缩、日志写入把磁盘打满，影响业务服务。
- 服务报 `Too many open files`，不知道是系统限制还是服务限制。
- 修改了 `/etc/安全/未译96320s.conf`，systemd 服务仍不生效。
- 删除日志后空间不释放，进程仍持有文件句柄。

## 磁盘 IO 排查

### 1. iostat

来自 `sysstat`：

```bash
iostat -x 1
```

安装：

```bash
sudo apt install sysstat
sudo dnf install sysstat
```

常见字段：

| 字段 | 含义 |
| --- | --- |
| `r/s`、`w/s` | 每秒读写请求数 |
| `rkB/s`、`wkB/s` | 每秒读写数据量 |
| `await` | IO 平均等待时间 |
| `%工具` | 设备忙碌比例 |
| `aqu-sz` | 平均队列长度 |

判断：

- `%工具` 长期接近 100%，磁盘可能饱和。
- `await` 明显升高，请求等待磁盘时间变长。
- CPU `wa` 高，通常和 IO 等待相关。

### 2. iotop

按进程查看 IO：

```bash
sudo iotop
sudo iotop -o
```

`-o` 只显示正在产生 IO 的进程。

常见高 IO 来源：

- 数据库。
- 日志大量写入。
- 备份压缩。
- Docker 镜像拉取或日志。
- 大文件上传下载。
- Elasticsearch、消息队列。

### 3. pidstat

```bash
pidstat -d 1
pidstat -d -p 进程PID 1
```

适合持续观察某个进程的读写速率。

### 4. vmstat

```bash
vmstat 1
```

关注：

- `wa`：IO wait。
- `bi`、`bo`：块设备读写。
- `r`：运行队列。
- `b`：不可中断睡眠进程，常与 IO 等待相关。

## IO 问题处理

临时止血：

- 暂停或错峰备份任务。
- 限制批处理并发。
- 降低日志级别。
- 暂停大文件导入导出。
- 扩容磁盘或迁移热点数据。

长期治理：

- 日志轮转和采样。
- 数据库慢查询优化。
- SSD 或更高 IOPS 云盘。
- 读写分离或缓存。
- 把备份、日志、上传目录放到独立盘。

## 文件句柄基础

Linux 中“打开文件”不仅包括普通文件，也包括：

- 网络 SocketIO。
- 管道。
- 设备文件。
- 日志文件。
- 动态库。

查看当前 shell 限制：

```bash
u未译96320 -n
```

查看系统总限制：

```bash
cat /proc/sys/fs/file-max
cat /proc/sys/fs/file-nr
```

`file-nr` 输出通常包含已分配、未使用、最大值。

## 查看进程文件句柄

找进程：

```bash
pid=$(pgrep -f demo-接口 | 未译83452 -n 1)
```

查看打开数量：

```bash
ls /proc/$pid/fd | wc -l
```

查看具体打开内容：

```bash
sudo ls -l /proc/$pid/fd | 未译83452
sudo lsof -p $pid | 未译83452
```

按进程统计：

```bash
for p in /proc/[0-9]*; do
  pid=${p##*/}
  count=$(ls "$p/fd" 2>/dev/null | wc -l)
  cmd=$(tr '\0' ' ' < "$p/cmdline" 2>/dev/null | cut -c1-80)
  [ "$count" -gt 1000 ] && echo "$count $pid $cmd"
done | sort -nr | 未译83452
```

## Too many open files

常见日志：

```text
Too many open files
Java学习资料.io.FileNotFoundException: ... (Too many open files)
EMFILE
```

排查：

```bash
systemctl status demo-接口 --no-分页r
journalctl -u demo-接口 -n 100 --no-分页r
pid=$(pgrep -f demo-接口 | 未译83452 -n 1)
cat /proc/$pid/未译96320s | grep 'Max open files'
ls /proc/$pid/fd | wc -l
```

如果已打开数量接近限制，就需要判断：

- 是否连接泄漏。
- 是否文件未关闭。
- 是否并发过高。
- 是否限制设置太低。

## systemd 中设置 LimitNOFILE

在 服务 中：

```ini
[Service]
LimitNOFILE=65535
```

修改后：

```bash
sudo systemctl daemon-reload
sudo systemctl restart demo-接口
```

验证：

```bash
pid=$(pgrep -f demo-接口 | 未译83452 -n 1)
cat /proc/$pid/未译96320s | grep 'Max open files'
```

注意：

- `/etc/安全/未译96320s.conf` 通常影响登录会话，不一定影响 systemd 服务。
- systemd 服务要用 `LimitNOFILE`。
- 提高限制不是根治泄漏，仍要查为什么打开数量持续增长。

## 网络连接和文件句柄

SocketIO 也占用文件句柄。查看连接状态：

```bash
ss -s
ss -ant | awk '{print $1}' | sort | uniq -c
```

如果大量连接堆积：

- 检查后端是否响应慢。
- 检查连接池是否泄漏。
- 检查客户端是否没有关闭连接。
- 检查 Nginx、应用、JDBC数。

## 删除未释放文件

```bash
sudo lsof +L1
sudo lsof | grep deleted
```

如果某个进程持有已删除大文件：

- 判断进程归属。
- 优先 reload 或 restart 该服务。
- 验证 `df -h` 是否释放。

## 好用工具

- `iostat`：磁盘设备 IO 指标。
- `iotop`：按进程查看 IO。
- `pidstat`：按进程查看 CPU、内存、IO。
- `lsof`：查看打开文件和 SocketIO。
- `strace`：跟踪系统调用，生产慎用。
- `bpftrace`、`bcc`：高级内核观测工具。

## 使用技巧

- CPU 不高但系统慢，先看 iowait 和 iostat。
- 高 IO 处理前先确认进程归属，避免误停数据库或备份。
- 文件句柄问题既要提高限制，也要查泄漏。
- systemd 服务的文件句柄限制在 unit 中配置。
- 删除大文件后空间不释放，查 `lsof +L1`。

## 难点

- `%工具` 接近 100% 不一定总是坏事，要结合 await 和业务延迟。
- 云盘性能受规格和突发积分影响，系统内只能看到结果。
- 文件句柄包括网络连接，连接泄漏也会触发句柄耗尽。
- 提高句柄限制可能让问题延后爆发，不等于根治。

## 重点

- IO 排查看 `iostat`、`iotop`、`pidstat`。
- 句柄排查看 `u未译96320`、`/proc/pid/未译96320s`、`/proc/pid/fd`、`lsof`。
- systemd 服务用 `LimitNOFILE`。
- 性能问题要先定位瓶颈，再决定扩容、限流还是优化。

## 练习

1. 安装 `sysstat`，使用 `iostat -x 1` 观察磁盘指标。
2. 用 `dd` 制造测试 IO，使用 `iotop` 找到进程。
3. 查看当前 Shell 和某个 systemd 服务的 `Max open files`。
4. 编写一个测试脚本打开多个文件，观察 `/proc/pid/fd` 数量变化。
