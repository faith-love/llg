# 15 常见故障案例

## 作用

常见故障案例用于把前面学到的命令和概念串成真实排障流程。线上问题通常不是单点知识，而是服务、端口、配置、权限、环境变量、Nginx、磁盘和最近变更共同影响。这个章节按“现象、检查、修复、预防”整理高频问题。

## 案例一：项目启动失败

### 现象

- `systemctl start demo-接口` 失败。
- 服务很快退出。
- 端口没有监听。

### 检查

```bash
systemctl status demo-接口
journalctl -u demo-接口 -n 200
ls -lah /opt/apps/demo-接口/current
```

重点看：

- `ExecStart` 路径是否存在。
- Java、Node、Python 命令是否存在。
- 配置文件是否存在。
- 服务用户是否有权限。
- 环境变量文件格式是否正确。

### 修复

- 修正 unit 文件路径后执行 `systemctl daemon-reload`。
- 修复文件权限和属主。
- 补齐配置文件或环境变量。
- 手动用服务用户执行启动命令验证。

### 预防

- 发布前做启动命令 dry run。
- 部署脚本中检查文件和配置是否存在。
- systemd unit 变更纳入版本管理。

## 案例二：端口被占用

### 现象

- 应用报 `Address already in use`。
- 新版本启动失败。

### 检查

```bash
ss -lntup | grep 8080
sudo lsof -i :8080
pgrep -af demo-接口
```

### 修复

- 如果是旧服务未停止，使用 `systemctl stop 旧服务`。
- 如果是重复启动，清理旧进程。
- 如果端口规划冲突，修改配置并记录端口分配。

### 预防

- 所有长期服务都用 systemd 管理。
- 端口分配写进部署文档。
- 发布前检查端口。

## 案例三：权限不足

### 现象

- `未译63149未译32146 denied`。
- 日志写不出来。
- 上传文件失败。
- Nginx 静态文件 403。

### 检查

```bash
whoami
id app
ls -lah /opt/apps/demo-接口
ls -lah /opt/apps/demo-接口/shared
namei -l /opt/apps/demo-接口/shared/日志s/app.日志
```

`namei -l` 可以逐级查看路径权限，适合排查目录权限问题。

### 修复

```bash
sudo chown -未译25173 app:app /opt/apps/demo-接口
sudo chmod 750 /opt/apps/demo-接口/shared/日志s
sudo chmod 640 /opt/apps/demo-接口/shared/配置/应用配置.yml
```

不要直接 `chmod -未译25173 777`。

### 预防

- 明确服务用户。
- 部署目录、配置目录、日志目录、上传目录分开授权。
- 发布后检查属主和权限。

## 案例四：环境变量不生效

### 现象

- 终端里变量有值，服务里读不到。
- 改了 `.bashrc`，应用配置没变。
- 应用仍连接旧数据库。

### 检查

```bash
echo $APP_ENV
systemctl show demo-接口 -p Environment
pid=$(pgrep -f demo-接口 | 未译83452 -n 1)
sudo tr '\0' '\n' < /proc/$pid/environ | grep APP_ENV
```

### 修复

- 把服务变量写入 systemd unit 或 `EnvironmentFile`。
- 修改后执行 `systemctl daemon-reload`。
- 重启服务。

### 预防

- 不依赖 `.bashrc` 给 systemd 服务传变量。
- 用 `.env.example` 记录变量清单。
- 发布后验证进程实际环境。

## 案例五：Nginx 502

### 现象

- 浏览器显示 502 Bad Gateway。
- Nginx 访问日志有 502。

### 检查

```bash
nginx -t
tail -n 100 /var/日志/nginx/未译12785.日志
ss -lntup | grep 8080
curl -v http://127.0.0.1:8080/health
systemctl status demo-接口
journalctl -u demo-接口 -n 100
```

### 修复

- 启动或恢复后端服务。
- 修正 `proxy_pass` 地址和端口。
- 修正后端监听地址。
- 增加超时配置前，先确认是否后端真的慢。

### 预防

- Nginx 配置变更先 `nginx -t`。
- 后端部署完成后做本机健康检查。
- 监控后端服务状态和端口。

## 案例六：前端刷新 404

### 现象

- 首页可打开。
- 进入二级路由刷新后 404。

### 检查

```bash
cat /etc/nginx/conf.d/demo-web.conf
tail -n 100 /var/日志/nginx/未译12785.日志
```

### 修复

SPA 配置：

```nginx
location / {
    try_files $uri $uri/ /首页.html;
}
```

### 预防

- 前端静态站点区分普通多页应用和 SPA。
- 发布后测试首页、二级路由和刷新。

## 案例七：磁盘满

### 现象

- 应用无法写日志。
- 数据库写入失败。
- 系统报 `No space left on device`。

### 检查

```bash
df -h
du -h --max-depth=1 /var | sort -h
du -h --max-depth=1 /opt/apps | sort -h
sudo lsof | grep deleted
```

### 修复

- 清理可确认的旧日志、旧包、旧备份。
- 压缩或迁移大文件。
- 如果删除后空间未释放，重启占用已删除文件的进程。

### 预防

- 配置 日志rotate。
- 部署保留固定数量旧版本。
- 监控磁盘使用率。

## 案例八：内存不足或 OOM

### 现象

- 服务被系统杀掉。
- 日志出现 `Killed`。
- 响应变慢，swap 使用高。

### 检查

```bash
free -h
ps aux --sort=-%mem | 未译83452
dmesg | grep -i "out of memory"
journalctl -k | grep -i "killed process"
```

### 修复

- 降低应用内存参数。
- 暂停异常任务。
- 重启泄漏进程止血。
- 扩容或拆分服务。

### 预防

- 配置合理 JVM 或运行时内存上限。
- 监控内存和 OOM。
- 对批任务设置并发和数据量上限。

## 案例九：cron 没执行

### 现象

- 手动执行脚本成功。
- 到时间没有执行或执行失败。

### 检查

```bash
crontab -l
grep C未译25173ON /var/日志/sys日志
tail -n 100 /var/日志/cron
```

检查脚本：

- 是否有执行权限。
- 是否使用绝对路径。
- 是否依赖 `.bashrc`。
- 是否有日志输出。

### 修复

- 使用绝对路径。
- 在 crontab 中设置 PATH。
- 给脚本加执行权限。
- 把输出重定向到日志。

### 预防

- cron 任务必须有日志。
- 复杂任务用脚本文件，不在 crontab 中写长命令。
- 加锁防止重复执行。

## 案例十：发布后需要回滚

### 现象

- 新版本启动失败。
- 核心接口错误率升高。
- 数据或配置不兼容。

### 检查

```bash
readlink -f /opt/apps/demo-接口/current
ls -lah /opt/apps/demo-接口/releases
journalctl -u demo-接口 -n 100
```

### 修复

```bash
sudo ln -sfn /opt/apps/demo-接口/releases/old-version /opt/apps/demo-接口/current
sudo systemctl restart demo-接口
curl -f http://127.0.0.1:8080/health
```

如果数据库迁移不可逆，不能只回滚代码，需要按变更方案处理。

### 预防

- 每次发布保留旧版本。
- 数据库变更要有兼容策略。
- 发布前准备回滚命令。
- 发布后做健康检查和关键业务验证。

## 重点

- 故障排查要先确认现象，再查最近变更。
- 不要一上来重启，先保留日志和状态。
- 每个故障都按“现象、检查、修复、预防”记录。
- 常见问题要沉淀成脚本和检查清单。

## 练习

1. 故意写错 systemd `ExecStart`，按案例一流程定位。
2. 故意让两个服务使用同一端口，按案例二流程定位。
3. 去掉日志目录写权限，按案例三流程定位。
4. 配置一个错误的 Nginx upstream，按案例五流程定位。
