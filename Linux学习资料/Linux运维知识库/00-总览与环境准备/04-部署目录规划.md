# 部署目录规划

## 作用

部署目录规划用于解决“项目文件应该放哪里、如何发布、如何回滚、配置和日志如何不被覆盖”的问题。

如果没有目录规划，常见结果是：jar 放在 `/root`，配置散落在当前目录，日志写到项目目录，上传文件和代码混在一起，新版本覆盖旧版本，出现问题无法回滚。规范目录结构可以让部署、排障、备份、权限控制都更清晰。

## 痛点

- 代码包、配置、日志、上传文件混在一起。
- 新版本覆盖旧版本，出现故障无法快速回滚。
- 配置文件被发布包覆盖，导致生产配置丢失。
- 日志目录权限不清晰，应用写不进去。
- 上传文件放在版本目录里，发布时被误删。
- systemd、Nginx、脚本引用的路径不稳定。

## 优点

- 发布和回滚路径清晰。
- 配置、日志、上传文件与代码解耦。
- 权限可以按目录精确控制。
- systemd 和 Nginx 只依赖稳定路径。
- 备份时能明确备份哪些目录。

## 推荐目录结构

推荐把业务服务放在 `/opt/apps` 下：

```text
/opt/apps/
  demo-接口/
    current -> releases/2026-05-11-120000
    releases/
      2026-05-11-120000/
        app.jar
      2026-05-10-180000/
        app.jar
    shared/
      配置/
        demo-接口.env
        应用配置.yml
      日志s/
        app.日志
      上传s/
      tmp/
```

核心思想：

- `releases` 保存每次发布版本。
- `current` 软链接指向当前运行版本。
- `shared` 保存跨版本共享的配置、日志、上传文件和临时文件。

## 各目录说明

### 1. `/opt/apps`

这是业务应用根目录。

建议：

- 公司内部业务服务统一放这里。
- 每个应用一个子目录。
- 不要把项目放在 `/root` 或 `/tmp`。

创建：

```bash
sudo mkdir -p /opt/apps
```

### 2. 应用根目录

例如：

```bash
/opt/apps/demo-接口
```

它代表一个应用的全部部署内容。

建议包含：

- `releases`
- `current`
- `shared`

### 3. `releases`

`releases` 保存历史版本。

示例：

```text
releases/
  2026-05-11-120000/
  2026-05-10-180000/
```

命名建议：

- 时间戳：`2026-05-11-120000`
- Git 通用mit：`2026-05-11-a1b2c3d`
- 版本号：`v1.2.3`

使用技巧：

- 至少保留最近 3 到 5 个版本。
- 发布新版本时创建新目录，不覆盖旧目录。
- 清理旧版本前确认 current 不指向它。

### 4. `current`

`current` 是软链接，指向当前版本。

创建或切换：

```bash
sudo ln -sfn /opt/apps/demo-接口/releases/2026-05-11-120000 /opt/apps/demo-接口/current
readlink -f /opt/apps/demo-接口/current
```

优点：

- systemd 固定使用 `/opt/apps/demo-接口/current/app.jar`。
- Nginx 固定指向 `/opt/apps/demo-web/current`。
- 回滚只需要切换软链接并重启服务。

注意：

- 删除旧版本前先确认 `readlink -f current`。
- 软链接失效会导致服务找不到文件。

### 5. `shared/配置`

用于保存环境相关配置。

示例：

```text
shared/配置/
  demo-接口.env
  应用配置.yml
```

原则：

- 生产配置不随发布包覆盖。
- 密钥和密码不提交 Git。
- 权限建议严格控制。

权限示例：

```bash
sudo chmod 640 /opt/apps/demo-接口/shared/配置/demo-接口.env
sudo chown app:app /opt/apps/demo-接口/shared/配置/demo-接口.env
```

### 6. `shared/日志s`

用于保存应用日志。

优点：

- 日志不跟版本目录绑定。
- 方便 日志rotate 和日志采集。
- 方便统一授权。

示例：

```bash
sudo mkdir -p /opt/apps/demo-接口/shared/日志s
sudo chown app:app /opt/apps/demo-接口/shared/日志s
sudo chmod 750 /opt/apps/demo-接口/shared/日志s
```

### 7. `shared/上传s`

用于保存用户上传文件。

原则：

- 上传文件不能放在 release 目录。
- 发布和回滚不能影响上传文件。
- 上传目录需要单独备份。

### 8. `shared/tmp`

用于应用运行时临时文件。

注意：

- 可以定期清理。
- 不放重要业务数据。
- 清理脚本要限制范围，避免误删。

## 创建目录示例

```bash
APP=demo-接口
BASE=/opt/apps/$APP

sudo mkdir -p $BASE/releases
sudo mkdir -p $BASE/shared/配置
sudo mkdir -p $BASE/shared/日志s
sudo mkdir -p $BASE/shared/上传s
sudo mkdir -p $BASE/shared/tmp
sudo chown -未译25173 app:app $BASE
sudo chmod 750 $BASE
```

## 与 systemd 配合

systemd 中使用稳定路径：

```ini
[Service]
用户=app
Group=app
WorkingDirectory=/opt/apps/demo-接口/current
EnvironmentFile=/opt/apps/demo-接口/shared/配置/demo-接口.env
ExecStart=/usr/bin/Java学习资料 -jar /opt/apps/demo-接口/current/app.jar
```

这样发布新版本时，只要切换 `current` 并重启服务。

## 与 Nginx 配合

前端静态资源：

```nginx
root /opt/apps/demo-web/current;
```

后端代理：

```nginx
proxy_pass http://127.0.0.1:8080;
```

Nginx 不需要知道每次 release 目录名，只依赖固定入口。

## 回滚流程

假设当前版本有问题：

```bash
readlink -f /opt/apps/demo-接口/current
sudo ln -sfn /opt/apps/demo-接口/releases/2026-05-10-180000 /opt/apps/demo-接口/current
sudo systemctl restart demo-接口
sudo systemctl status demo-接口
curl -f http://127.0.0.1:8080/health
```

回滚前要确认：

- 旧版本目录存在。
- 配置兼容旧版本。
- 数据库变更是否可逆。
- 日志显示启动正常。

## 使用技巧

- 发布目录只放代码和构建产物。
- 配置、日志、上传文件放 shared。
- systemd 和 Nginx 引用 current。
- 旧版本保留固定数量，定期清理。
- 清理旧版本前先确认 current 指向。

## 难点

- 数据库结构变更可能导致代码回滚不完整。
- 上传文件如果放在 release 目录，发布清理时容易丢。
- 配置文件如果打进发布包，容易覆盖生产配置。
- 权限如果只给 release，不给 shared/日志s，应用可能启动后写日志失败。

## 重点

- `/opt/apps/应用名` 是推荐业务部署根目录。
- `releases` 管版本，`current` 管当前入口，`shared` 管跨版本数据。
- 配置、日志、上传文件不能和代码包混在一起。
- 回滚要靠目录结构提前设计，不是出事后临时想办法。

## 练习

1. 在测试机创建 `/opt/apps/demo-接口` 结构。
2. 创建两个 release 目录，用 current 分别指向它们。
3. 写一个 systemd unit，固定读取 current 路径。
4. 模拟新版本失败，切换 current 回滚到旧版本。
