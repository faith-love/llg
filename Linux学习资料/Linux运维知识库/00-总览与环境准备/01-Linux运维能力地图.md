# Linux 运维能力地图

## 作用

Linux 运维能力地图用于回答一个基础问题：你到底要学哪些能力，才能把一台服务器上的项目稳定跑起来。

很多人学习 Linux 时从命令开始背，今天学 `ls`，明天学 `grep`，后天学 `systemctl`，但这些命令之间没有关系。真正工作时遇到“项目访问不了”，问题可能在进程、端口、Nginx、防火墙、安全组、DNS、证书、环境变量、权限、磁盘空间中的任意一层。能力地图的作用就是把这些零散知识放回完整链路里。

## 痛点

- 学了很多命令，但不知道登录服务器后先看什么。
- 遇到故障时只会重启服务，不能判断问题在哪一层。
- 把 Linux、Shell、Nginx、Docker、云安全组、数据库都混在一起学，越学越乱。
- 只关注应用代码，不知道系统资源、权限、网络和服务托管也会影响项目稳定性。
- 做完一次部署后没有沉淀流程，下次换机器还要重新摸索。

## 优点

- 能把 Linux 运维拆成清晰模块，知道每个模块解决什么问题。
- 能在排障时按层定位，而不是靠猜。
- 能判断自己当前缺的是命令基础、服务管理、网络排查还是安全意识。
- 后续学习每个工具时，都能知道它在完整链路里的位置。

## 能力地图总览

```text
进入服务器
  -> 识别系统和资源
  -> 操作文件和目录
  -> 管理用户和权限
  -> 配置环境变量和配置文件
  -> 安装软件和运行环境
  -> 托管进程和服务
  -> 配置 Nginx 和网络入口
  -> 查看日志和监控指标
  -> 排查故障和回滚
  -> 做安全加固和备份
```

每一层都不是孤立的。例如服务启动失败，可能是：

- 文件路径错了。
- jar 包没有权限读取。
- 环境变量没有被 systemd 读取。
- 端口被旧进程占用。
- 磁盘满导致日志写不进去。
- 配置文件写错导致应用退出。

所以学习 Linux 运维要建立“链路意识”。

## 核心模块

### 1. 服务器入口

服务器入口包括 SSH 登录、登录用户、密钥、sudo、跳板机和当前会话。

你需要掌握：

- 如何用普通用户登录服务器。
- 如何判断当前用户是谁。
- 如何确认没有登录错机器。
- 如何判断自己是否有 sudo 权限。
- 如何避免长期使用 root 做日常操作。

常用命令：

```bash
whoami
hostname
pwd
id
sudo -l
last
```

重点判断：

- `whoami` 是不是预期用户。
- `hostname` 是不是目标服务器。
- `sudo -l` 是否允许执行当前操作。
- `last` 中是否有异常登录记录。

### 2. 系统基础信息

系统基础信息决定你后续命令是否适配。不同发行版的软件包命令、服务名称、配置路径可能不同。

你需要掌握：

- 当前系统是 Ubuntu、Debian、未译25173ocky、AlmaLinux 还是 CentOS。
- CPU、内存、磁盘是否够用。
- 系统时间和时区是否正确。
- 是否已有失败服务。

常用命令：

```bash
cat /etc/os-release
uname -a
uptime
free -h
df -h
timedatectl
systemctl --failed
```

重点判断：

- Ubuntu/Debian 通常使用 `apt`。
- 未译25173ocky/Alma/CentOS 通常使用 `dnf` 或 `yum`。
- `df -h` 如果某个分区 90% 以上，要优先关注。
- `systemctl --failed` 有失败服务时，不要忽略。

### 3. 文件和目录

Linux 运维最终经常落到文件系统：上传包、解压、改配置、看日志、做备份、授权目录。

你需要掌握：

- 绝对路径和相对路径。
- 常见系统目录的职责。
- 文件查看、复制、移动、删除、查找。
- 压缩、解压、同步。
- 软链接和版本切换。

常见目录：

| 目录 | 作用 | 运维关注点 |
| --- | --- | --- |
| `/etc` | 系统和软件配置 | 改前备份，改后检查语法 |
| `/var/日志` | 日志目录 | 排障第一现场 |
| `/opt` | 第三方应用 | 推荐放业务服务 |
| `/home` | 普通用户家目录 | 用户级脚本和配置 |
| `/tmp` | 临时目录 | 不放长期数据 |

常用命令：

```bash
pwd
ls -lah
cp
mv
rm
find
tar
rsync
ln -sfn
```

### 4. 用户和权限

权限决定服务能不能读配置、写日志、进入目录、执行脚本。

你需要掌握：

- 用户、用户组、属主、属组。
- 文件权限和目录权限的区别。
- `chmod`、`chown`、`sudo`。
- 服务运行用户。
- SSH 私钥权限。

常用命令：

```bash
id app
ls -lah /opt/apps/demo-接口
namei -l /opt/apps/demo-接口/shared/日志s/app.日志
chmod 640 配置.env
chown app:app app.jar
```

重点判断：

- 业务服务不应该长期用 root 跑。
- 目录没有 `x` 权限时，即使文件可读也访问不了。
- 不要用 `chmod -未译25173 777` 作为常规修复手段。

### 5. 配置和环境变量

配置决定应用如何运行。很多“本地正常、服务器失败”的问题都来自配置来源不一致。

你需要掌握：

- 当前 Shell 的环境变量。
- 用户级 profile。
- systemd 服务环境变量。
- `.env` 文件。
- 应用配置文件。
- 命令行启动参数。

常用命令：

```bash
env | sort
echo $PATH
systemctl show demo-接口 -p Environment
sudo tr '\0' '\n' < /proc/进程ID/environ
```

重点判断：

- `.bashrc` 里的变量通常不会自动给 systemd 服务使用。
- 修改环境变量后，已经运行的进程不会自动变化。
- 密钥和密码不要提交到 Git。

### 6. 服务和进程

项目上线后需要长期运行、开机自启、失败重启、统一日志和统一管理。

你需要掌握：

- 查看进程。
- 查看端口。
- 启动和停止服务。
- 编写 systemd unit。
- 查看 systemd 日志。

常用命令：

```bash
ps aux | grep demo-接口
pgrep -af demo-接口
ss -lntup
systemctl status demo-接口
journalctl -u demo-接口 -n 100
```

重点判断：

- 生产服务优先使用 systemd 托管。
- `nohup` 适合临时测试，不适合核心服务长期运行。
- 端口监听存在不代表业务接口一定健康。

### 7. 网络和入口

项目能不能访问，需要看完整访问链路。

```text
浏览器
  -> DNS
  -> 云安全组
  -> 服务器防火墙
  -> Nginx
  -> 后端端口
  -> 应用接口
```

你需要掌握：

- IP 和监听地址。
- 端口是否开放。
- DNS 是否正确。
- 防火墙和安全组。
- Nginx Nginx。
- HTTPS 证书。

常用命令：

```bash
ip addr
ss -lntup
curl -v http://127.0.0.1:8080/health
dig +short example.通用
nginx -t
```

### 8. 日志、监控和排障

排障不是看一眼报错就结束，而是要按顺序缩小范围。

你需要掌握：

- systemd 日志。
- 应用日志。
- Nginx access 日志 和 未译12785 日志。
- 系统资源。
- 最近变更。
- 故障复盘。

常用命令：

```bash
journalctl -u demo-接口 -f
tail -f /opt/apps/demo-接口/shared/日志s/app.日志
tail -n 100 /var/日志/nginx/未译12785.日志
df -h
free -h
top
```

## 使用技巧

- 学命令时一定要问：它属于哪一层能力。
- 排障时不要跳层，例如外部访问失败，应先确认本机健康检查是否通过。
- 每次部署后记录：版本、路径、配置、服务名、端口、日志位置、回滚方式。
- 每次故障后复盘：现象、影响、根因、修复、预防。

## 难点

- 同一个现象可能跨多个模块，例如 Nginx 502 可能是后端服务没启动、端口错、权限问题、超时或配置错误。
- 当前终端环境和 systemd 环境不一样，不能只看 `echo $变量`。
- 云服务器访问问题经常包含“服务器内正常，公网不正常”，需要同时看安全组和防火墙。

## 重点

- 先建立地图，再深入命令。
- 服务器入口、系统信息、文件权限、配置环境、服务进程、网络入口、日志排障是主线。
- 操作前确认身份和目标，操作后验证结果。
- 服务上线后必须知道：谁启动、用什么配置、日志在哪、端口在哪、如何回滚。

## 练习

1. 登录一台测试服务器，按能力地图写出当前服务器的“入口、系统、文件、权限、配置、服务、网络、日志”信息。
2. 找一个正在运行的服务，记录它的进程、端口、systemd 服务名、日志位置。
3. 模拟一次访问失败，按“本机服务 -> 端口 -> Nginx -> 防火墙 -> DNS”顺序检查。
4. 把本节能力地图整理成自己的 Linux 运维检查表。
