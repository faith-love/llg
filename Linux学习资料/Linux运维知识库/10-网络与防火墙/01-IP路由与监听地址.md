# IP、路由与监听地址

## 作用

IP、路由与监听地址用于判断“请求能不能到达这台机器、能不能到达目标进程”。服务启动成功只是第一步，如果程序只监听 `127.0.0.1`，公网客户端就无法直接访问；如果路由不对，服务器可能无法访问外部依赖；如果监听在错误网卡，内网调用也会失败。

这一节重点解决：

- 如何查看服务器有哪些 IP。
- 如何判断默认路由和出口网卡。
- 如何理解 `127.0.0.1`、`0.0.0.0`、内网 IP、公网 IP。
- 如何查看服务实际监听地址。
- 如何根据监听地址判断访问范围。

## 痛点

- 本机 `curl 127.0.0.1:8080` 正常，其他机器访问失败。
- 服务监听在 `127.0.0.1`，却期望公网直接访问。
- 服务器有多张网卡，服务监听错了 IP。
- 云服务器只有内网 IP 出现在系统里，公网 IP 由云平台 NAT 映射，初学者误判。
- Nginx 代理后端正常，但直接访问后端端口失败，以为服务异常。

## 查看 IP

### 1. ip addr

```bash
ip addr
ip -br addr
```

`ip -br addr` 更适合快速查看：

```text
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0             UP             10.0.0.12/24
```

重点看：

- 网卡是否 `UP`。
- 是否有内网 IP。
- 是否有公网 IP。
- 是否有多个网卡。

### 2. hostname -I

```bash
hostname -I
```

它会输出本机 IP 列表，适合快速查看，但不如 `ip addr` 详细。

### 3. 公网 IP

云服务器系统里不一定能看到公网 IP，因为公网 IP 可能在云平台做 NAT。

查看公网出口：

```bash
curl -4 if配置.me
curl -4 ipinfo.io/ip
```

注意：

- 这看到的是出公网 IP，不一定等于入站公网 IP。
- 有负载均衡、NAT 网关、代理时，结果可能不是当前实例的公网 IP。
- 内网服务器可能无法访问这些公网服务。

## 查看路由

### 1. 默认路由

```bash
ip route
```

示例：

```text
default via 10.0.0.1 dev eth0
10.0.0.0/24 dev eth0 proto kernel scope link 源码 10.0.0.12
```

含义：

- `default`：默认出口。
- `via 10.0.0.1`：网关。
- `dev eth0`：通过哪块网卡出去。
- `源码 10.0.0.12`：源 IP。

### 2. 判断访问某个目标走哪条路由

```bash
ip route get 8.8.8.8
ip route get 10.0.1.20
```

这比只看路由表更直接。排查“服务器访问某个内网服务失败”时非常有用。

## 监听地址

### 1. 查看监听端口

```bash
ss -lntup
sudo ss -lntup | grep ':8080'
sudo lsof -iTCP:8080 -sTCP:LISTEN
```

示例：

```text
LISTEN 0 128 127.0.0.1:8080 0.0.0.0:* 用户s:(("Java学习资料",pid=1234,fd=12))
LISTEN 0 128 0.0.0.0:80    0.0.0.0:* 用户s:(("nginx",pid=5678,fd=6))
```

### 2. 地址含义

| 监听地址 | 含义 | 访问范围 |
| --- | --- | --- |
| `127.0.0.1:8080` | 只监听本机回环地址 | 只有本机能访问 |
| `0.0.0.0:8080` | 监听所有 IPv4 网卡 | 本机、内网、公网入口都有机会访问 |
| `10.0.0.12:8080` | 只监听指定内网 IP | 同内网或可路由网络可访问 |
| `[::]:8080` | 监听 IPv6 | 取决于系统和配置，可能影响 IPv4 |

### 3. 后端服务监听建议

如果后端只给 Nginx 代理：

```text
后端监听 127.0.0.1:8080
Nginx 监听 0.0.0.0:80/443
```

这样更安全，公网不能直接访问后端端口。

如果后端需要被其他内网机器访问：

```text
后端监听 10.0.0.12:8080 或 0.0.0.0:8080
```

同时要配置本机防火墙和云安全组，只允许必要来源访问。

## 典型访问链路

### 1. 本机访问

```text
当前服务器 -> 127.0.0.1:8080 -> 应用进程
```

验证：

```bash
curl -v http://127.0.0.1:8080/health
```

### 2. 内网访问

```text
另一台内网机器 -> 10.0.0.12:8080 -> 应用进程
```

要求：

- 服务监听内网 IP 或 `0.0.0.0`。
- 本机防火墙放行来源。
- 安全组或内网 ACL 放行。
- 路由可达。

### 3. 公网经 Nginx 访问

```text
浏览器 -> 公网 IP:443 -> Nginx -> 127.0.0.1:8080
```

这种是生产常见模式。后端不暴露公网，Nginx 作为唯一入口。

## 排查流程

### 场景 1：本机可访问，外部不可访问

```bash
curl -v http://127.0.0.1:8080/health
sudo ss -lntup | grep ':8080'
ip addr
sudo ufw status verbose 2>/dev/null || true
sudo firewall-cmd --list-all 2>/dev/null || true
```

判断：

- 如果监听 `127.0.0.1`，外部不能直接访问是正常现象。
- 如果监听 `0.0.0.0`，继续查防火墙和安全组。
- 如果外部通过域名访问，继续查 DNS 和 Nginx。

### 场景 2：内网访问失败

在服务端：

```bash
sudo ss -lntup | grep ':8080'
ip addr
ip route
```

在客户端：

```bash
nc -vz 10.0.0.12 8080
curl -v http://10.0.0.12:8080/health
ip route get 10.0.0.12
```

重点判断：

- 客户端能不能路由到服务端内网 IP。
- 服务端是否监听内网地址。
- 中间是否有安全组、ACL、防火墙。

### 场景 3：服务器访问外部接口失败

```bash
ip route
ip route get 目标IP
curl -v 安全HTTP://目标域名
dig +short 目标域名
```

如果 DNS 解析正常但连接超时，查出口路由、防火墙、代理、云平台 NAT。

## 好用工具

- `iproute2`：提供 `ip addr`、`ip route`，现代 Linux 网络基础工具。
- `ss`：查看监听端口和连接状态。
- `lsof`：查看端口对应进程。
- `mtr`：结合 ping 和 traceroute，观察网络路径质量。
- `traceroute` / `tracepath`：查看路由路径。
- `tcpdump`：抓包确认请求是否到达网卡。

安装示例：

```bash
sudo apt install iproute2 lsof mtr traceroute tcpdump
sudo dnf install iproute lsof mtr traceroute tcpdump
```

## 使用技巧

- 先看监听地址，再谈防火墙；服务只监听 `127.0.0.1` 时公网不可能直连。
- 后端服务优先只监听本机，由 Nginx 对外暴露。
- 多网卡服务器要用 `ip route get 目标IP` 判断实际出口。
- 云服务器公网 IP 不一定出现在 `ip addr` 里，要结合云控制台判断。
- 外部访问失败要从本机、内网、公网逐层验证。

## 难点

- `0.0.0.0` 是监听所有 IPv4 地址，不是一个真实可访问 IP。
- `ping` 通不代表 TCP 端口通，TCP 端口通也不代表 HTTP 接口正常。
- 云平台安全组和 Linux 本机防火墙是两层控制。
- IPv6 监听 `[::]` 的行为受系统配置影响，排查时不要忽略。

## 重点

- 监听地址决定服务能被谁直接访问。
- 路由决定请求从哪块网卡出去。
- 后端服务是否公网直连，是架构和安全决策，不是只改监听地址。
- 网络排查从近到远：进程、端口、本机、内网、公网、域名。

## 练习

1. 启动一个只监听 `127.0.0.1:8080` 的测试服务，分别从本机和其他机器访问。
2. 改成监听 `0.0.0.0:8080`，观察 `ss -lntup` 输出变化。
3. 使用 `ip route get 8.8.8.8` 判断默认出口网卡。
4. 使用 `lsof` 找出占用 80 或 8080 端口的进程。
