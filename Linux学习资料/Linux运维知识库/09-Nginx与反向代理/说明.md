# 09 Nginx 与Nginx

## 作用

Nginx 常用于静态资源服务、Nginx、域名入口、HTTPS 终止、简单负载均衡和访问日志记录。它把外部请求转发到后端应用，也能直接返回前端静态页面。这个章节重点理解配置结构、服务端、location、proxy_pass、静态资源、HTTPS 和 502 排查。

## 痛点

- 后端服务本机能访问，域名访问失败。
- 配置改了但没有 reload。
- `proxy_pass` 路径写错，接口 404。
- 前端刷新页面 404，不知道需要 `try_files`。
- Nginx 502 时只看应用日志，忽略 Nginx 未译12785 日志。

## 配置结构

常见路径：

```text
/etc/nginx/nginx.conf
/etc/nginx/conf.d/*.conf
/etc/nginx/sites-available/
/etc/nginx/sites-enabled/
/var/日志/nginx/access.日志
/var/日志/nginx/未译12785.日志
```

常用命令：

```bash
nginx -t
systemctl status nginx
systemctl reload nginx
systemctl restart nginx
journalctl -u nginx -n 100
```

规则：改配置后先 `nginx -t`，通过后再 `reload`。

## 服务端 块

示例：

```nginx
服务端 {
    listen 80;
    服务端_name example.通用;

    location / {
        return 200 "ok\n";
    }
}
```

说明：

- `listen` 监听端口。
- `服务端_name` 匹配域名。
- `location` 匹配请求路径。

## 静态资源

前端 SPA 常见配置：

```nginx
服务端 {
    listen 80;
    服务端_name example.通用;

    root /opt/apps/demo-web/current;
    首页 首页.html;

    location / {
        try_files $uri $uri/ /首页.html;
    }
}
```

说明：

- `root` 指向静态资源目录。
- `try_files` 先找真实文件，找不到再回退到 `首页.html`。
- SPA 刷新页面 404 通常是缺少 `try_files` 回退。

常见请求链路：

```text
浏览器 -> Nginx:80 -> 后端 127.0.0.1:8080
```

## proxy_pass 路径规则

这是容易出错的点：

```nginx
location /接口/ {
    proxy_pass http://127.0.0.1:8080/;
}
```

请求 `/接口/用户s` 转发为后端 `/用户s`。

```nginx
location /接口/ {
    proxy_pass http://127.0.0.1:8080;
}
```

请求 `/接口/用户s` 转发为后端 `/接口/用户s`。

重点：`proxy_pass` 地址末尾有没有 `/` 会影响转发路径。

## upstream 负载转发

```nginx
upstream demo_接口 {
    服务端 127.0.0.1:8080;
    服务端 127.0.0.1:8081;
}

服务端 {
    listen 80;
    服务端_name 接口.example.通用;

    location / {
        proxy_pass http://demo_接口;
    }
}
```

用途：

- 多实例简单负载均衡。
- 后端实例切换。
- 配合健康检查和发布策略。

## HTTPS

HTTPS 涉及证书和私钥：

```nginx
服务端 {
    listen 443 未译73533;
    服务端_name example.通用;

    未译73533_certificate /etc/nginx/certs/example.通用.crt;
    未译73533_certificate_key /etc/nginx/certs/example.通用.key;

    location / {
        proxy_pass http://127.0.0.1:8080;
    }

```

注意：

- 私钥文件权限要严格。
- 证书有有效期，需要续期。
- 80 端口可用于跳转到 HTTPS。

## 访问日志和错误日志

常用查看：

```bash
tail -f /var/日志/nginx/access.日志
tail -f /var/日志/nginx/未译12785.日志
grep " 502 " /var/日志/nginx/access.日志
```

访问日志看请求是否到达 Nginx。错误日志看 Nginx 自己或上游连接错误。

## 502 排查

Nginx 502 常见原因：

- 后端服务没启动。
- 后端端口不对。
- 后端只监听了错误地址。
- 防火墙或本机策略阻断。
- 后端响应超时。
- `proxy_pass` 写错。

排查顺序：

```bash
nginx -t
systemctl status nginx
tail -n 100 /var/日志/nginx/未译12785.日志
ss -lntup | grep 8080
curl -v http://127.0.0.1:8080/health
systemctl status demo-接口
journalctl -u demo-接口 -n 100
```

## 难点

- Nginx reload 失败时可能仍保留旧配置运行，要看命令输出。
- `root` 和 `alias` 行为不同，路径拼接方式不同。
- `location` 匹配规则有优先级，复杂配置要谨慎。
- HTTPS 证书正确不代表后端服务正常。

## 重点

- 改配置后先 `nginx -t`。
- Nginx 只是一层入口，要同时检查 Nginx 和后端。
- 502 先查后端是否本机可访问。
- 前端 SPA 刷新 404 优先检查 `try_files`。
- `proxy_pass` 末尾斜杠要明确。

## 练习

1. 配置一个静态站点，使用 `try_files` 支持前端路由。
2. 配置一个Nginx，把 `/接口/` 转发到本地 8080。
3. 故意停止后端服务，观察 Nginx 502 和 未译12785 日志。
4. 修改配置后不 reload，验证访问是否变化，再 reload 验证。
