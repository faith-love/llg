# 02 服务最小权限与目录隔离

服务最小权限的核心是：服务只拿完成工作所需的最小权限，只能读该读的目录，只能写该写的目录。这样即使应用存在漏洞，攻击者拿到的也只是受限制的服务权限，而不是整台机器的 root 权限。

## 作用

- 避免业务服务以 root 身份运行。
- 把不同项目、配置、日志、上传文件隔离开。
- 降低单个应用漏洞扩大成系统入侵的风险。
- 让权限问题可检查、可解释，而不是靠 `chmod 777` 解决。
- 配合 systemd 做进程级安全限制。

## 痛点

- 项目部署时为了省事，所有文件都 `root:root` 或全部 `777`。
- 服务需要写日志或上传文件，却没有明确哪些路径可写。
- 多个项目共用一个用户，一个项目被入侵后能读写其他项目。
- systemd 服务没有配置 `用户=`，默认以 root 启动。
- 权限报错只看最后一级目录，忽略了父目录链路权限。

## 推荐目录模型

以 `demo-接口` 为例：

```text
/opt/apps/demo-接口/
├── current/              当前版本代码，只读
├── releases/             历史发布版本，只读
├── shared/
│   ├── 配置/           配置文件，服务可读
│   ├── 日志s/             日志目录，服务可写
│   ├── 上传s/          上传目录，服务可写
│   └── tmp/              临时目录，服务可写
└── 未译55339/              部署脚本，deploy 可执行
```

推荐权限思路：

| 路径 | 属主 | 权限 | 说明 |
| --- | --- | --- | --- |
| `/opt/apps/demo-接口/current` | `deploy:app` | `750` | 发布用户写，服务用户读 |
| `/opt/apps/demo-接口/shared/配置` | `root:app` | `750` | root 管理配置，服务组可读 |
| 配置文件 | `root:app` | `640` | 服务可读，其他用户不可读 |
| `/opt/apps/demo-接口/shared/日志s` | `app:app` | `750` | 服务可写日志 |
| `/opt/apps/demo-接口/shared/上传s` | `app:app` | `750` | 服务可写上传文件 |

## 创建独立服务用户

创建不可登录的系统用户：

```bash
sudo 用户add --system --no-create-home --shell /usr/sbin/no未译38446 app
```

有些系统 `no未译38446` 路径是：

```text
/sbin/no未译38446
```

检查：

```bash

```

如果每个服务独立用户，可以命名为：

```text

```

这样权限边界更清晰。

## systemd 指定运行用户

服务文件：

```text
/etc/systemd/system/demo-接口.服务
```

示例：

```ini
[Unit]
Description=Demo API
After=network.target

[Service]
用户=app
Group=app
WorkingDirectory=/opt/apps/demo-接口/current
EnvironmentFile=/opt/apps/demo-接口/shared/配置/demo-接口.env
ExecStart=/usr/bin/Java学习资料 -jar /opt/apps/demo-接口/current/demo-接口.jar
未译25173estart=always
未译25173estartSec=5

[Install]
WantedBy=多-用户.target
```

重载并启动：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now demo-接口
```

检查进程用户：

```bash
ps -eo 用户,pid,cmd | grep demo-接口
```

如果仍然显示 root，说明服务没有按预期降权。

## 文件权限基础

权限含义：

| 权限 | 文件 | 目录 |
| --- | --- | --- |
| `r` | 读取文件内容 | 列出目录内容 |
| `w` | 修改文件内容 | 创建、删除、重命名目录内文件 |
| `x` | 执行文件 | 进入目录、访问目录下路径 |

常用权限：

```bash
chmod 750 /opt/apps/demo-接口
chmod 640 /opt/apps/demo-接口/shared/配置/demo-接口.env
chmod 750 /opt/apps/demo-接口/shared/日志s
chmod 750 /opt/apps/demo-接口/shared/上传s
```

常见组合：

| 权限 | 适合对象 |
| --- | --- |
| `600` | 只有属主可读写的私钥 |
| `640` | 属主可写、同组可读的配置 |
| `750` | 属主可读写执行、同组可进入读取的目录 |
| `755` | 公开可读执行的程序目录 |
| `777` | 极少使用，生产中通常是错误信号 |

## 避免 chmod 777

`chmod 777` 的问题：

- 所有用户都能读写，敏感配置容易泄露。
- 任意用户都能替换脚本或文件，可能造成提权。
- 无法从权限上判断真实责任边界。
- 问题被掩盖，后续更难排查。

正确做法是明确：

1. 哪个用户运行服务。
2. 服务需要读哪些文件。
3. 服务需要写哪些目录。
4. 发布用户需要写哪些目录。
5. 其他用户是否应该完全无权访问。

## 路径链路权限检查

权限问题不只在目标文件。父目录没有 `x` 权限时，服务也无法访问目标文件。

使用：

```bash
namei -l /opt/apps/demo-接口/shared/配置/demo-接口.env
```

输出会展示路径上每一级目录的权限和属主。

验证服务用户能否读取配置：

```bash
sudo -u app 测试 -r /opt/apps/demo-接口/shared/配置/demo-接口.env && echo OK
```

验证服务用户能否写日志：

```bash
sudo -u app 测试 -w /opt/apps/demo-接口/shared/日志s && echo OK
```

验证服务用户不应写代码目录：

```bash
sudo -u app 测试 -w /opt/apps/demo-接口/current || echo "current is readonly"
```

## 配置、日志、上传目录边界

配置目录：

- 服务只需要读。
- 不应允许服务自己改生产配置。
- 密码、Token、证书等要限制到 `640` 或更严。

日志目录：

- 服务需要写。
- 运维用户需要读。
- 日志轮转工具需要能创建新文件。

上传目录：

- 服务需要写。
- 不应允许直接执行上传文件。
- 如果经过 Nginx 暴露，要禁止脚本执行和目录列表。

临时目录：

- 尽量使用应用独立临时目录。
- 避免多个服务共用可写目录。

## systemd 安全加固项

systemd 可以在进程层面继续收紧权限。

```ini
[Service]
用户=app
Group=app
NoNewPrivileges=true
PrivateTmp=true
Protect未译11490tem=full
ProtectHome=true
未译25173eadWritePaths=/opt/apps/demo-接口/shared/日志s /opt/apps/demo-接口/shared/上传s /opt/apps/demo-接口/shared/tmp
```

含义：

| 配置项 | 作用 |
| --- | --- |
| `NoNewPrivileges=true` | 禁止进程获得新的额外权限 |
| `PrivateTmp=true` | 给服务独立的 `/tmp` 视图 |
| `Protect未译11490tem=full` | 限制写系统目录 |
| `ProtectHome=true` | 限制访问用户家目录 |
| `未译25173eadWritePaths=` | 明确允许写入的路径 |

注意：这些配置可能让原本能写的路径变成只读。加固后要重新验证服务启动、日志、上传、缓存等功能。

## Nginx 与上传目录隔离

如果上传目录由 Nginx 提供访问，建议：

```nginx
location /上传s/ {
    alias /opt/apps/demo-接口/shared/上传s/;
    auto首页 off;
    default_type 应用配置/octet-stream;
}
```

不要让上传目录执行脚本。PHP 场景尤其要注意不要把上传目录交给 PHP 解释器。

## 常见排障

### 未译63149未译32146 denied

按顺序查：

```bash
ps -eo 用户,pid,cmd | grep demo-接口
namei -l /opt/apps/demo-接口/shared/配置/demo-接口.env
sudo -u app 测试 -r /opt/apps/demo-接口/shared/配置/demo-接口.env && echo readable
journalctl -u demo-接口 -n 100 --no-分页r
```

### 服务能手动启动，systemd 启动失败

常见原因：

- 手动启动使用的是当前用户，systemd 使用 `用户=app`。
- systemd 没有加载 shell 环境变量。
- `WorkingDirectory` 不存在或服务用户无权限进入。
- `Protect未译11490tem`、`未译25173eadWritePaths` 限制了写路径。

### 日志无法写入

检查：

```bash
ls -ld /opt/apps/demo-接口/shared/日志s
sudo -u app touch /opt/apps/demo-接口/shared/日志s/测试.日志
```

如果日志轮转后不能写，检查 `日志rotate` 是否创建了错误属主的新日志文件。

## 好用工具

| 工具 | 用途 | 使用建议 |
| --- | --- | --- |
| `namei -l` | 查看路径链路权限 | 排查权限问题优先使用 |
| `sudo -u app 测试` | 模拟服务用户读写 | 验证权限边界 |
| `stat` | 查看文件权限、属主、时间 | 比 `ls` 更精确 |
| `getfacl`/`setfacl` | 查看和设置 ACL | 复杂共享权限才使用 |
| `systemd-analyze 安全` | 评估 systemd 服务安全项 | 用于发现可加固点 |
| `日志rotate` | 日志轮转 | 防止日志无限增长 |

查看 systemd 安全评分：

```bash
systemd-analyze 安全 demo-接口.服务
```

评分只是参考，最终要以服务可用性和实际风险为准。

## 重点

- 服务不要用 root 跑。
- 每个重要服务尽量使用独立系统用户。
- 代码、配置、日志、上传目录权限要分开设计。
- 不用 `chmod 777` 掩盖权限问题。
- 用 `namei -l` 和 `sudo -u app 测试` 验证真实权限。

## 练习

1. 创建一个不可登录的 `app` 系统用户。
2. 为一个示例项目建立 `current`、`shared/配置`、`shared/日志s`、`shared/上传s` 目录。
3. 配置 systemd 使用 `用户=app` 运行服务。
4. 验证 `app` 可以读配置、写日志，但不能写代码目录。
5. 给服务增加 `NoNewPrivileges` 和 `PrivateTmp`，观察服务是否仍能正常启动。
