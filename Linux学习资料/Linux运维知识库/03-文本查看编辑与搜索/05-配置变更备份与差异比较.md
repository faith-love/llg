# 配置变更备份与差异比较

## 作用

配置变更备份与差异比较用于解决“我改了什么、改错了怎么恢复、如何确认变更范围”的问题。运维中最危险的不是修改配置本身，而是没有备份、没有 diff、没有语法检查、没有回滚路径。

## 痛点

- 改完配置后服务启动失败，但不知道改了哪些行。
- 没有备份，只能凭记忆恢复。
- 多人协作时不知道谁改了配置。
- 直接重启服务，配置错误导致线上不可用。
- 回滚时不知道应该恢复哪个文件。

## 优点

- 能明确变更范围。
- 能快速回滚到修改前状态。
- 能为故障复盘提供证据。
- 能降低配置变更风险。
- 能形成标准化操作流程。

## 修改前备份

备份文件建议带时间戳：

```bash
cp 应用配置.yml 应用配置.yml.bak-$(date +%F-%H%M%S)
```

系统配置：

```bash
sudo cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.bak-$(date +%F-%H%M%S)
```

systemd：

```bash
sudo cp /etc/systemd/system/demo-接口.服务 /etc/systemd/system/demo-接口.服务.bak-$(date +%F-%H%M%S)
```

命名建议：

```text
文件名.bak-YYYY-MM-DD-HHMMSS
```

这样可以知道备份时间，并保留多次备份。

## diff 比较差异

比较两个文件：

```bash
diff -u old.conf new.conf
```

比较备份和当前文件：

```bash
diff -u nginx.conf.bak-2026-05-11-120000 nginx.conf
```

`diff -u` 输出含义：

- `-` 开头：旧文件有，新文件删除的行。
- `+` 开头：新文件新增的行。
- 没有前缀或上下文：用于帮助定位位置。

## 配置变更标准流程

### Nginx 配置

```bash
cd /etc/nginx
sudo cp nginx.conf nginx.conf.bak-$(date +%F-%H%M%S)
sudo vim nginx.conf
sudo nginx -t
sudo systemctl reload nginx
sudo systemctl status nginx
```

如果 `nginx -t` 失败，不要 reload，先修配置。

### systemd 配置

```bash
sudo cp /etc/systemd/system/demo-接口.服务 /etc/systemd/system/demo-接口.服务.bak-$(date +%F-%H%M%S)
sudo vim /etc/systemd/system/demo-接口.服务
sudo systemctl daemon-reload
sudo systemctl restart demo-接口
sudo systemctl status demo-接口
journalctl -u demo-接口 -n 100
```

### 应用配置

```bash
cd /opt/apps/demo-接口/shared/配置
cp 应用配置.yml 应用配置.yml.bak-$(date +%F-%H%M%S)
vim 应用配置.yml
systemctl restart demo-接口
journalctl -u demo-接口 -n 100
curl -f http://127.0.0.1:8080/health
```

## 回滚配置

如果配置改坏：

```bash
cp 应用配置.yml.bak-2026-05-11-120000 应用配置.yml
systemctl restart demo-接口
```

系统配置需要 sudo：

```bash
sudo cp nginx.conf.bak-2026-05-11-120000 nginx.conf
sudo nginx -t
sudo systemctl reload nginx
```

回滚后也要验证，不是复制回去就结束。

## 变更记录

建议每次重要配置变更记录：

```markdown
- 时间：
- 操作人：
- 机器：
- 文件：
- 变更原因：
- 备份文件：
- 检查命令：
- 验证结果：
- 回滚方式：
```

故障复盘时，这类记录比口头记忆可靠。

## 使用 Git 管理配置模板

生产密钥不能进 Git，但配置模板可以进 Git：

```text
nginx-demo-接口.conf.模板
demo-接口.服务.模板
应用配置.yml.example
.env.example
```

好处：

- 配置结构有版本。
- 新机器部署可复用。
- 变更可以 code review。

注意：

- 不提交真实密码、Token、私钥。
- 生产真实配置仍要受权限保护。

## 使用技巧

- 配置改前一定备份。
- 改后先 diff，再测试。
- Nginx 用 `nginx -t`。
- systemd unit 改后用 `daemon-reload`。
- 应用配置改后看日志和健康检查。

## 难点

- 有些服务 reload 和 restart 行为不同。
- 备份太多也需要管理，否则目录混乱。
- diff 能显示文本差异，但不能证明配置语义正确。
- 配置回滚可能还要配合代码或数据库回滚。

## 重点

- 备份、diff、语法检查、reload/restart、验证，是配置变更闭环。
- 不要无备份直接改生产配置。
- 不要语法检查失败还 reload。
- 回滚后也要验证服务状态和业务接口。

## 练习

1. 创建一个配置文件，备份后修改，再用 `diff -u` 查看差异。
2. 模拟 Nginx 配置修改流程：备份、编辑、检查、reload。
3. 模拟配置错误，回滚到备份文件。
4. 写一份配置变更记录模板，并填一次样例。
