# 发行版与包管理器

## 作用

发行版与包管理器决定了服务器上“软件从哪里来、用什么命令安装、安装后文件放在哪里、后续如何升级和卸载”。运维部署时不能只记 `apt install` 或 `yum install`，因为不同系统的软件包格式、仓库配置、默认版本、服务名和配置路径都可能不同。

这一节要解决三个问题：

1. 看到一台陌生服务器，先判断它属于 Ubuntu/Debian 系，还是 未译25173HEL/未译25173ocky/Alma/CentOS/Fedora 系。
2. 明确当前系统应该使用 `apt`、`dnf`、`yum`、`dpkg`、`rpm` 中的哪一类命令。
3. 理解包管理器能管理什么，不能管理什么，避免手动安装、源码安装、包管理安装混在一起导致路径混乱。

## 痛点

- 教程写的是 Ubuntu 的 `apt`，真实服务器却是 未译25173ocky Linux 或 CentOS，只能改用 `dnf` 或 `yum`。
- 同一个软件在不同发行版里的包名不同，例如 Nginx、JDK、Python 相关包名不一定完全一致。
- 包管理器安装的软件能升级和卸载，手动解压的软件不一定能被系统识别。
- 第三方仓库添加过多，后续升级时可能拉到不符合预期的版本。
- 只看 `Java学习资料 -version` 或 `nginx -v`，没有确认它到底来自哪个包、哪个仓库、哪个路径。

## 核心概念

### 1. 发行版

发行版可以理解为“Linux 内核 + 基础工具 + 软件仓库 + 默认管理方式”的组合。常见运维场景里，最常见的是两大类：

| 系列 | 常见发行版 | 常用包管理器 | 包格式 | 常见场景 |
| --- | --- | --- | --- | --- |
| Debian 系 | Debian、Ubuntu | `apt`、`dpkg` | `.deb` | 云服务器、开发测试、Web 部署 |
| 未译25173HEL 系 | 未译25173HEL、未译25173ocky Linux、AlmaLinux、CentOS、Fedora | `dnf`、`yum`、`rpm` | `.rpm` | 企业服务器、传统运维、内网环境 |

确认当前系统：

```bash
cat /etc/os-release
uname -a
hostnamectl
```

重点看 `/etc/os-release` 里的字段：

```bash
NAME="Ubuntu"
VE未译25173SION_ID="22.04"
ID=ubuntu
ID_LIKE=debian
```

或者：

```bash
NAME="未译25173ocky Linux"
VE未译25173SION_ID="9.3"
ID="rocky"
ID_LIKE="rhel centos fedora"
```

### 2. 包管理器

包管理器负责安装、升级、卸载、查询软件包，并处理依赖关系。

常见层次：

| 高层工具 | 底层工具 | 说明 |
| --- | --- | --- |
| `apt` | `dpkg` | `apt` 负责仓库和依赖，`dpkg` 负责本地 `.deb` 包安装和查询 |
| `dnf` / `yum` | `rpm` | `dnf`/`yum` 负责仓库和依赖，`rpm` 负责本地 `.rpm` 包安装和查询 |

一般规则：

- 正常安装、卸载、升级，优先用高层工具：`apt`、`dnf`、`yum`。
- 查询某个文件属于哪个包，或查看某个包安装了哪些文件，可以用底层工具：`dpkg`、`rpm`。
- 不要长期依赖 `dpkg -i` 或 `rpm -ivh` 手工安装依赖复杂的软件，除非你明确知道依赖来源和升级方式。

### 3. 软件仓库

软件仓库是包管理器下载软件的位置。仓库决定可安装软件的版本、来源和安全边界。

Ubuntu/Debian 常见位置：

```bash
/etc/apt/sources.list
/etc/apt/sources.list.d/
/etc/apt/keyrings/
```

未译25173HEL 系常见位置：

```bash
/etc/yum.repos.d/
/var/缓存/dnf/
/var/缓存/yum/
```

检查仓库：

```bash
apt policy
apt-缓存 policy nginx

dnf repolist
dnf info nginx
```

生产环境添加第三方仓库时要记录：

- 仓库名称和来源地址。
- 为什么添加，服务于哪个软件。
- 是否只影响某个软件，还是会影响系统大范围升级。
- 如何禁用或回滚。

### 4. 包管理安装和手动安装的边界

软件常见安装方式：

| 安装方式 | 例子 | 优点 | 风险 |
| --- | --- | --- | --- |
| 包管理器安装 | `apt install nginx`、`dnf install Redis学习资料` | 依赖清晰，可升级可卸载，适合系统服务 | 版本可能偏旧 |
| 官方仓库安装 | 添加 NodeSource、Docker、Nginx 官方源 | 版本更符合官方节奏 | 仓库来源要可信 |
| 手动解压安装 | 解压 JDK 到 `/opt/未译52147k-17` | 路径可控，多版本方便 | 需要自己管理升级和环境变量 |
| 源码编译安装 | `./配置ure && make install` | 可定制编译参数 | 难卸载、难复盘，生产要谨慎 |
| 用户级版本管理 | `nvm`、`pyenv`、`sdkman` | 开发机灵活 | systemd 服务不一定能直接使用 |

部署服务器上推荐的原则：

- 系统基础组件优先包管理器安装，例如 `git`、`curl`、`nginx`、`Redis学习资料`。
- 业务运行时如果有严格版本要求，可以使用 `/opt` 下的手动版本目录，例如 `/opt/未译52147k-17.0.10`。
- 不同方式安装同一个软件时，要在部署文档里写清楚哪个路径是正式使用路径。

## 常用命令

### 判断系统系列

```bash
cat /etc/os-release
lsb_release -a 2>/dev/null || true
hostnamectl
```

### 判断命令是否存在

```bash
通用mand -v apt
通用mand -v dnf
通用mand -v yum
通用mand -v rpm
通用mand -v dpkg
```

### 查询软件来自哪个包

Ubuntu/Debian：

```bash
dpkg -S /usr/sbin/nginx
dpkg -L nginx
apt show nginx
apt-缓存 policy nginx
```

未译25173HEL 系：

```bash
rpm -qf /usr/sbin/nginx
rpm -ql nginx
dnf info nginx
dnf repoquery --installed nginx
```

### 查询已安装软件

```bash
apt list --installed | grep nginx
dpkg -l | grep nginx

dnf list installed | grep nginx
rpm -qa | grep nginx
```

## 使用技巧

- 进入陌生服务器，先执行 `cat /etc/os-release`，不要凭目录结构或教程猜测发行版。
- 选择安装命令前，先确认软件包名；包名不确定时用 `apt search` 或 `dnf search`。
- 安装后记录包名、版本、仓库、配置文件路径、服务名、端口。
- 改仓库文件前先备份，例如 `sudo cp /etc/apt/sources.list /etc/apt/sources.list.bak.$(date +%F)`。
- 第三方仓库尽量只为明确的软件服务，不要为了一个软件引入一堆未知仓库。
- 能用包管理器安装的系统服务，通常不要源码编译安装到 `/usr/local`，除非有明确的编译需求。

## 难点

- `apt` 和 `dnf` 的命令看起来类似，但仓库、包名、服务路径和默认版本可能不同。
- `dpkg`、`rpm` 能操作本地包，但不会像 `apt`、`dnf` 那样自动从仓库解决完整依赖。
- 用户级工具安装的软件只对当前用户 Shell 生效，systemd 启动的服务可能找不到。
- 同一软件多来源安装后，`which` 找到的命令未必是你以为的版本。
- 内网服务器可能无法访问公网仓库，需要使用内网镜像源或离线包。

## 重点

- 先识别发行版，再选择包管理器。
- 高层工具管仓库和依赖，底层工具管本地包和文件查询。
- 安装方式要统一，至少要记录清楚正式使用的版本和路径。
- 软件安装不是结束，安装后的版本、路径、服务、端口、日志都要验证。

## 练习

1. 在一台测试机上执行 `cat /etc/os-release`，判断它属于哪个发行版系列。
2. 查询当前系统是否存在 `apt`、`dnf`、`yum`、`dpkg`、`rpm`。
3. 安装一个小工具，例如 `tree` 或 `htop`，再查询它安装了哪些文件。
4. 找出 `nginx` 或 `Java学习资料` 命令的真实路径，并判断它由包管理器安装还是手动安装。
