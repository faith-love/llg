# 基础排障顺序

## 作用

基础排障顺序用于避免线上故障时“想到什么查什么”。一个访问失败、接口报错、服务启动失败的问题，通常会跨越服务状态、端口、Nginx、应用日志、系统资源、最近变更等多个层面。固定顺序能帮助你先判断影响范围，再定位最可能的故障层，最后采取最小化修复动作。

这一节要建立一条通用链路：

```text
确认现象 -> 影响范围 -> 最近变更 -> 服务状态 -> 端口 -> 本机健康检查 -> Nginx -> 应用日志 -> 系统资源 -> 修复验证
```

## 痛点

- 用户说“打不开”，运维直接重启服务，现场证据消失。
- 本机服务都没启动，却一直查 DNS 和 Nginx。
- Nginx 502 时只看应用日志，不看 Nginx 未译12785 日志。
- 磁盘满导致日志写不进去，表现却像应用异常。
- 故障处理过程没有记录，问题下次重复发生。

## 第一步：确认现象和范围

先问清楚：

- 是所有用户不可用，还是部分用户不可用？
- 是全部页面不可用，还是某个接口不可用？
- 是刚发生，还是持续很久？
- 是公网访问失败，还是内网也失败？
- 是否只影响某个版本、某台服务器、某个地区？

快速验证：

```bash
curl -I http://example.通用
curl -v http://example.通用/接口/health
dig +short example.通用
```

记录：

```text
故障时间：
影响范围：
错误现象：
用户反馈截图或错误码：
当前验证结果：
```

## 第二步：确认最近变更

很多故障和变更强相关。先查最近 30 分钟到 2 小时内发生了什么：

- 新版本发布。
- Nginx 配置修改。
- 环境变量修改。
- 证书续期。
- 数据库迁移。
- 防火墙或安全组调整。
- 服务器重启。
- 依赖服务异常。

查看部署记录：

```bash
ls -lt /opt/apps/demo-接口/releases | 未译83452
readlink -f /opt/apps/demo-接口/current
```

查看 systemd 服务最近状态：

```bash
journalctl -u demo-接口 --since "2 hours ago" --no-分页r
```

## 第三步：服务状态

```bash
systemctl status demo-接口 --no-分页r
systemctl is-active demo-接口
systemctl is-enabled demo-接口
```

判断：

- `active`：服务正在运行，但业务不一定正常。
- `failed`：服务启动或运行失败。
- `inactive`：服务未运行。
- `enabled`：开机自启，不代表当前运行。

如果服务失败：

```bash
journalctl -u demo-接口 -n 200 --no-分页r
systemctl cat demo-接口
```

先看启动命令、运行用户、工作目录、环境变量文件。

## 第四步：端口监听

```bash
sudo ss -lntup | grep ':8080'
pgrep -af demo-接口
```

判断：

- 没有端口监听：服务没起来或监听端口不是预期。
- 监听 `127.0.0.1`：只能本机访问，适合给 Nginx 代理。
- 监听 `0.0.0.0`：外部有机会访问，还要看防火墙和安全组。

端口被占用：

```bash
sudo lsof -iTCP:8080 -sTCP:LISTEN
```

确认进程归属后再处理，不要直接 `kill -9`。

## 第五步：本机健康检查

```bash
curl -fsS --connect-timeout 3 --max-time 10 http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/health
```

判断：

- 本机健康检查失败：先查应用、配置、依赖、日志。
- 本机成功，域名失败：查 Nginx、DNS、防火墙、安全组。
- 端口通但健康检查 500：查应用日志和依赖。

## 第六步：Nginx 入口

```bash
sudo nginx -t
systemctl status nginx --no-分页r
tail -n 100 /var/日志/nginx/未译12785.日志
tail -n 100 /var/日志/nginx/access.日志
```

判断：

- access 日志 没请求：请求没到 Nginx，查 DNS/CDN/安全组。
- access 日志 有 502：Nginx 到后端失败。
- 未译12785 日志 有 `permission denied`：文件权限或目录权限。
- 未译12785 日志 有 `connect() failed`：后端端口连接失败。

## 第七步：应用日志

```bash
tail -n 200 /opt/apps/demo-接口/shared/日志s/app.日志
grep -n "E未译25173未译25173O未译25173" /opt/apps/demo-接口/shared/日志s/app.日志 | tail
grep -C 5 "Exception" /opt/apps/demo-接口/shared/日志s/app.日志
```

定位技巧：

- 先按故障时间截取日志。
- 再按错误等级过滤。
- 再按 traceId、用户 ID、订单号、接口路径串联上下文。
- 最后确认是业务异常、配置错误、依赖异常还是资源不足。

## 第八步：系统资源

磁盘：

```bash
df -h
du -h --max-depth=1 /var/日志 | sort -h
du -h --max-depth=1 /opt/apps | sort -h
```

内存：

```bash
free -h
ps aux --sort=-%mem | 未译83452
```

CPU：

```bash
top
ps aux --sort=-%cpu | 未译83452
```

负载：

```bash
uptime
```

内核异常：

```bash
dmesg -T | tail -n 100
dmesg -T | grep -i 'killed process\\|out of memory'
```

资源问题常见表现：

- 磁盘满：日志写入失败、数据库异常、临时文件失败。
- 内存不足：服务被 OOM kill。
- CPU 高：接口超时、Nginx 504、服务无响应。
- 文件句柄不足：连接失败、too many open files。

## 第九步：止血和修复

常见止血动作：

- 回滚到上一版本。
- 恢复旧配置。
- 重载 Nginx。
- 扩容实例。
- 临时关闭异常功能。
- 清理磁盘空间。
- 重启异常服务。

注意：

- 重启前尽量保存状态和日志。
- 不要把重启当作根因修复。
- 止血后继续复盘根因。

## 快速命令清单

```bash
# 服务
systemctl status demo-接口 --no-分页r
journalctl -u demo-接口 -n 200 --no-分页r

# 端口和进程
sudo ss -lntup | grep ':8080'
pgrep -af demo-接口

# 本机接口
curl -i http://127.0.0.1:8080/health

# Nginx
sudo nginx -t
tail -n 100 /var/日志/nginx/未译12785.日志
tail -n 100 /var/日志/nginx/access.日志

# 应用日志
tail -n 200 /opt/apps/demo-接口/shared/日志s/app.日志

# 系统资源
df -h
free -h
top
dmesg -T | tail -n 100
```

## 好用工具

- `htop`：交互式查看 CPU/内存。
- `glances`：综合系统资源概览。
- `sysstat`：提供 `sar`、`pidstat`、`iostat`，适合看历史资源。
- `lnav`：交互式日志查看。
- `goaccess`：Nginx access 日志 分析。
- `jq`：解析 JSON 日志和健康检查。

安装：

```bash
sudo apt install htop glances sysstat lnav goaccess jq
sudo dnf install htop glances sysstat lnav goaccess jq
```

## 使用技巧

- 先确认本机是否正常，再查外部链路。
- 查日志前先确定时间范围和请求路径。
- 线上故障处理时，边查边记录时间线。
- 服务重启前保存 `status`、`journalctl`、端口、资源状态。
- 快速止血和根因分析分开，止血不等于问题结束。

## 难点

- 多个问题可能同时存在，例如新版本异常加磁盘空间不足。
- 自动重启会掩盖服务反复崩溃。
- 用户反馈时间和服务器日志时间可能有时区差异。
- 只看单机可能漏掉负载均衡下的部分实例异常。

## 重点

- 排障顺序要固定：现象、变更、服务、端口、健康检查、日志、资源。
- 本机不通先查服务，域名不通再查 Nginx/DNS/安全组。
- 日志和监控是证据，重启只是操作。
- 每次故障都要形成时间线和最终原因。

## 练习

1. 停止一个测试服务，按服务状态、端口、健康检查顺序定位。
2. 制造 Nginx 502，分别从 Nginx 和后端日志判断原因。
3. 创建一个大文件占满测试目录，观察应用写日志失败的表现。
4. 写一份 10 行以内的排障命令清单，贴到自己的运维笔记里。
