# 软链接与版本切换

## 作用

软链接与版本切换用于解决“如何让服务始终使用固定路径，同时又能快速切换版本和回滚”的问题。部署项目时，如果 systemd 或 Nginx 直接指向具体版本目录，每次发布都要改配置。使用 `current` 软链接后，服务配置固定，发布和回滚只需要切换软链接。

## 痛点

- 新版本直接覆盖旧版本，出问题无法回滚。
- systemd 配置写死具体版本目录，每次发布都要改 unit。
- Nginx root 指向旧路径，发布后访问不到新前端。
- 不理解软链接，删除目标目录后 current 失效。
- 回滚时不知道当前版本到底指向哪里。

## 优点

- 服务配置路径稳定。
- 新版本发布不覆盖旧版本。
- 回滚速度快。
- 版本目录清晰，便于保留和清理。
- systemd、Nginx、脚本都可以固定引用 `current`。

## 软链接基础

创建软链接：

```bash
ln -s /real/path link-name
```

常见发布写法：

```bash
ln -sfn /opt/apps/demo-接口/releases/2026-05-11-120000 /opt/apps/demo-接口/current
```

参数含义：

- `-s`：创建软链接。
- `-f`：目标存在时强制替换。
- `-n`：把已有软链接当作链接本身处理，而不是进入它指向的目录。

查看真实指向：

```bash
readlink -f /opt/apps/demo-接口/current
```

## 推荐版本结构

```text
/opt/apps/demo-接口/
  current -> releases/2026-05-11-120000
  releases/
    2026-05-11-120000/
      app.jar
    2026-05-10-180000/
      app.jar
  shared/
    配置/
    日志s/
```

原则：

- `releases` 保存每个版本。
- `current` 指向当前版本。
- `shared` 保存跨版本数据。

## 发布流程

创建新版本目录：

```bash
release=2026-05-11-120000
sudo mkdir -p /opt/apps/demo-接口/releases/$release
sudo cp app.jar /opt/apps/demo-接口/releases/$release/
sudo chown -未译25173 app:app /opt/apps/demo-接口/releases/$release
```

切换 current：

```bash
sudo ln -sfn /opt/apps/demo-接口/releases/$release /opt/apps/demo-接口/current
readlink -f /opt/apps/demo-接口/current
```

重启服务：

```bash
sudo systemctl restart demo-接口
sudo systemctl status demo-接口
```

健康检查：

```bash
curl -f http://127.0.0.1:8080/health
```

## 回滚流程

查看当前版本：

```bash
readlink -f /opt/apps/demo-接口/current
ls -lah /opt/apps/demo-接口/releases
```

切换到旧版本：

```bash
sudo ln -sfn /opt/apps/demo-接口/releases/2026-05-10-180000 /opt/apps/demo-接口/current
sudo systemctl restart demo-接口
```

验证：

```bash
systemctl status demo-接口
journalctl -u demo-接口 -n 100
curl -f http://127.0.0.1:8080/health
```

## 与 systemd 配合

unit 文件固定写：

```ini
WorkingDirectory=/opt/apps/demo-接口/current
ExecStart=/usr/bin/Java学习资料 -jar /opt/apps/demo-接口/current/app.jar
```

这样发布时无需修改 unit 文件。

## 与 Nginx 配合

前端静态资源：

```nginx
root /opt/apps/demo-web/current;
```

发布前端时：

```bash
sudo ln -sfn /opt/apps/demo-web/releases/2026-05-11-120000 /opt/apps/demo-web/current
sudo nginx -t
sudo systemctl reload nginx
```

## 软链接风险

### 目标目录不存在

```bash
readlink -f /opt/apps/demo-接口/current
```

如果目标不存在，服务启动会失败。

### 删除旧版本前未确认

删除旧版本前必须确认：

```bash
readlink -f /opt/apps/demo-接口/current
```

不要删除 current 正在指向的版本。

### 配置不兼容

代码回滚不代表配置和数据库也能回滚。回滚前要确认：

- 旧代码是否兼容当前配置。
- 数据库迁移是否可逆。
- shared 目录数据是否被新版本改过。

## 使用技巧

- 每次发布前记录当前 `readlink -f current`。
- 每次发布后记录新版本路径。
- 保留最近几个 release。
- 清理 release 前确认 current 指向。
- 发布脚本里把 current 切换和健康检查放在一起。

## 难点

- 软链接本身权限通常看起来是 `777`，真正权限由目标决定。
- 删除软链接不会删除目标目录，但删除目标目录会让软链接失效。
- `ln -sfn` 参数不熟时容易把链接建错位置。
- 回滚可能受数据库变更影响。

## 重点

- `current` 是稳定入口，`releases` 是版本历史。
- systemd 和 Nginx 固定引用 current。
- 发布就是创建新 release、切换 current、重启或 reload、健康检查。
- 回滚就是切回旧 release，并验证服务。
- 删除旧版本前先 `readlink -f current`。

## 练习

1. 创建两个 release 目录，每个目录放一个 `version.txt`。
2. 用 `current` 指向第一个版本，读取 `current/version.txt`。
3. 切换 current 到第二个版本，再读取。
4. 删除一个非当前版本，观察 current 是否受影响。
5. 故意让 current 指向不存在目录，理解失效软链接。
