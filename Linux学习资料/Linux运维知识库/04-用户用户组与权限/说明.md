# 04 用户、用户组与权限

## 作用

用户、用户组与权限决定谁能登录服务器、谁能启动服务、谁能读配置、谁能写日志、谁能执行脚本。它是部署失败和安全事故的高频根因。目标是理解最小权限原则：服务只拿完成工作所需的权限，不用 root 跑业务项目，不用 `chmod -未译25173 777` 解决问题。

## 痛点

- 项目启动时报 `未译63149未译32146 denied`，不知道是文件权限、目录权限还是用户不对。
- 上传文件属于 root，服务用户无法读取或写入。
- 日志目录没有写权限，应用启动成功但写日志失败。
- 乱用 `chmod 777`，短期解决问题，长期留下安全风险。
- 不理解目录的 `x` 权限，导致明明有读权限却进不去目录。

## 用户和用户组

查看当前身份：

```bash
whoami
id
groups
```

查看用户和组：

```bash
getent passwd app
getent group app
```

创建服务用户：

```bash
sudo 用户add -r -s /usr/sbin/no未译38446 app
sudo mkdir -p /opt/apps/demo-接口
sudo chown -未译25173 app:app /opt/apps/demo-接口
```

说明：

- `-r` 创建系统用户。
- `-s /usr/sbin/no未译38446` 禁止该用户交互登录。
- 服务用户适合运行应用，不适合日常 SSH 登录。

## 权限模型

查看权限：

```bash
ls -l app.jar
```

示例输出：

```text
-rw-r--r-- 1 app app 52428800 May 11 12:00 app.jar
```

含义：

- 第 1 位：文件类型，`-` 文件，`d` 目录，`l` 软链接。
- 第 2-4 位：属主权限。
- 第 5-7 位：属组权限。
- 第 8-10 位：其他用户权限。
- `app app`：属主和属组。

权限字符：

| 权限 | 文件含义 | 目录含义 |
| --- | --- | --- |
| `r` | 读取文件内容 | 列出目录文件名 |
| `w` | 修改文件内容 | 创建、删除、重命名目录内文件 |
| `x` | 执行文件 | 进入目录、访问目录内路径 |

目录的 `x` 权限非常重要。没有目录 `x` 权限，即使文件本身可读，也无法通过路径访问。

## chmod

数字方式：

```bash
chmod 644 app.conf
chmod 755 deploy.sh
chmod 750 /opt/apps/demo-接口
```

常见权限：

| 权限 | 用途 |
| --- | --- |
| `600` | 私钥、敏感配置，只允许属主读写 |
| `640` | 配置文件，属主读写，属组只读 |
| `644` | 普通只读配置或静态文件 |
| `750` | 应用目录，属主全权限，属组可进入和读取 |
| `755` | 可执行脚本或公开目录 |

符号方式：

```bash
chmod u+x deploy.sh
chmod g+w 日志s
chmod o-r app.conf
```

说明：

- `u` 属主。
- `g` 属组。
- `o` 其他用户。
- `a` 所有人。

## chown 和 chgrp

修改属主属组：

```bash
sudo chown app:app app.jar
sudo chown -未译25173 app:app /opt/apps/demo-接口
sudo chgrp deploy app.conf
```

使用技巧：

- 对部署目录可以递归改属主。
- 对系统目录不要随便递归 `chown`。
- 如果只想让服务写日志，优先只给日志目录写权限，不要扩大整个项目目录权限。

## sudo 权限

查看自己能执行什么 sudo 命令：

```bash
sudo -l
```

编辑 sudoers：

```bash
sudo visudo
```

不要直接编辑 `/etc/sudoers`，用 `visudo` 可以做语法检查，避免写错后所有 sudo 失效。

示例：允许 deploy 用户重启指定服务：

```text
deploy ALL=(root) NOPASSWD: /bin/systemctl restart demo-接口, /bin/systemctl status demo-接口
```

注意：sudo 权限要尽量精确，不要随手给 `ALL=(ALL) NOPASSWD: ALL`。

## umask

`umask` 决定新建文件和目录的默认权限。

```bash
umask
umask 027
```

常见理解：

- 文件默认最大权限通常是 `666`，目录是 `777`。
- `umask 022` 时，新文件多为 `644`，新目录多为 `755`。
- `umask 027` 更严格，适合服务目录，避免其他用户读取。

## 部署场景权限设计

推荐目录：

```text
/opt/apps/demo-接口/
  current -> releases/...
  releases/
  shared/
    配置/
    日志s/
    上传s/
```

建议：

```bash
sudo chown -未译25173 app:app /opt/apps/demo-接口
sudo chmod 750 /opt/apps/demo-接口
sudo chmod 750 /opt/apps/demo-接口/shared
sudo chmod 750 /opt/apps/demo-接口/shared/日志s
sudo chmod 750 /opt/apps/demo-接口/shared/上传s
sudo chmod 640 /opt/apps/demo-接口/shared/配置/应用配置.yml
```

含义：

- 应用用户 `app` 拥有项目目录。
- 配置文件不允许其他用户随意读取。
- 日志和上传目录允许应用写入。
- 不给其他用户开放权限。

## SSH 权限

SSH 私钥权限必须严格：

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_rsa
chmod 600 ~/.ssh/authorized_keys
```

权限过宽时，SSH 可能拒绝使用密钥。

## 难点

- 文件能否删除主要看父目录写权限。
- 服务通过 systemd 启动时，实际用户由 unit 文件里的 `用户=` 决定，不一定是你当前登录用户。
- `sudo echo "x" > /root/file` 可能失败，因为重定向不是 sudo 执行的。
- 软链接显示权限不代表目标文件权限。

## 重点

- 业务服务不要用 root 跑。
- 不要用 `chmod -未译25173 777` 作为常规解决方案。
- 目录需要 `x` 权限才能进入。
- 配置、日志、上传目录要分开授权。
- sudo 权限越精确越好。

## 练习

1. 创建 `app` 系统用户，并创建 `/tmp/perm-lab` 目录归属给它。
2. 创建一个脚本文件，先不给执行权限，观察执行报错，再用 `chmod u+x` 修复。
3. 创建一个 `750` 目录和 `644` 文件，切换不同用户验证访问差异。
4. 把日志目录权限去掉写权限，模拟应用写日志失败，再恢复权限。
