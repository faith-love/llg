# Nginx 日志与 502 排查

## 作用

Nginx 日志是排查入口层问题的核心依据。`access.日志` 说明请求是否到达 Nginx、返回了什么状态、耗时多少；`error.日志` 说明 Nginx 处理请求或连接上游时发生了什么错误。502、504、403、404、499 等问题，都应该结合 Nginx 日志、后端端口、后端日志一起判断。

这一节重点掌握：

- access 日志 和 error 日志 分别看什么。
- 502、504、403、404、499 常见原因。
- 如何按请求路径、状态码、时间筛选日志。
- 502 时如何分层排查 Nginx、后端、网络和配置。

## 痛点

- 看到 502 就重启 Nginx，实际是后端服务没启动。
- 后端日志没有请求记录，因为请求根本没代理到后端。
- 前端页面 404，分不清是 Nginx 静态文件 404 还是后端接口 404。
- 访问很慢，只看应用日志，没有看 Nginx upstream 响应时间。
- Nginx error 日志 提示 permission denied，但一直排查前端打包。

## 日志位置

默认常见路径：

```bash
/var/日志/nginx/access.日志
/var/日志/nginx/error.日志
```

项目独立日志示例：

```nginx
access_日志 /var/日志/nginx/demo-接口.access.日志;
error_日志  /var/日志/nginx/demo-接口.error.日志 网页归档n;
```

查看：

```bash
tail -f /var/日志/nginx/access.日志
tail -f /var/日志/nginx/error.日志
```

## access 日志

默认格式通常包含：

```text
客户端IP - 用户 [时间] "请求方法 路径 协议" 状态码 响应大小 "来源" "用户-Agent"
```

示例：

```text
10.0.0.1 - - [11/May/2026:10:00:00 +0800] "GET /接口/health HTTP/1.1" 502 157 "-" "curl/8.0"
```

常用筛选：

```bash
grep ' 502 ' /var/日志/nginx/access.日志
grep 'GET /接口/health' /var/日志/nginx/access.日志
tail -n 1000 /var/日志/nginx/access.日志 | awk '{print $9}' | sort | uniq -c | sort -nr
```

如果没有 access 日志 记录，说明请求可能没有到这台 Nginx，要检查 DNS、负载均衡、安全组、端口、防火墙。

## error 日志

查看最近错误：

```bash
tail -n 100 /var/日志/nginx/error.日志
```

实时观察：

```bash
tail -f /var/日志/nginx/error.日志
```

常见错误：

| 错误片段 | 常见含义 |
| --- | --- |
| `connect() failed (111: Connection refused)` | 后端端口未监听或拒绝连接 |
| `upstream timed out` | 后端响应超时 |
| `no live upstreams` | upstream 没有可用后端 |
| `permission denied` | 静态文件或目录权限不足 |
| `open() "... " failed (2: No such file or directory)` | 静态文件不存在 |
| `客户端 intended to send too large body` | 上传超过 `客户端_max_body_size` |

## 502 排查

### 1. 理解 502

502 Bad Gateway 表示 Nginx 作为代理时，从上游服务拿不到有效响应。通常问题在上游服务、端口、代理配置、网络连接，而不一定是 Nginx 主服务本身坏了。

常见原因：

- 后端服务没启动。
- `proxy_pass` 端口写错。
- 后端只监听了 `127.0.0.1`，但 Nginx 代理到内网 IP，或反过来。
- 后端启动中，还没准备好。
- 后端进程崩溃或重启。
- upstream 配置的所有实例都不可用。
- 后端返回非法响应。

### 2. 排查命令

```bash
# Nginx 配置
sudo nginx -t
sudo nginx -T | grep -n 'proxy_pass'

# Nginx 状态
systemctl status nginx --no-分页r
sudo ss -lntup | grep ':80'
sudo ss -lntup | grep ':443'

# Nginx 日志
grep ' 502 ' /var/日志/nginx/access.日志 | tail -n 20
tail -n 100 /var/日志/nginx/error.日志

# 后端端口
sudo ss -lntup | grep ':8080'
curl -v http://127.0.0.1:8080/health

# 后端服务
systemctl status demo-接口 --no-分页r
journalctl -u demo-接口 -n 100 --no-分页r
```

判断逻辑：

- 后端本机 `curl` 都失败，先修后端。
- 后端本机成功，经 Nginx 失败，查 `proxy_pass`、路径、请求头、Nginx error 日志。
- Nginx 本机成功，外部失败，查防火墙、安全组、DNS、负载均衡。

## 504 排查

504 Gateway Timeout 表示 Nginx 等待上游响应超时。

常见原因：

- 后端接口耗时太长。
- 数据库慢查询。
- 后端线程池耗尽。
- 上游网络不稳定。
- `proxy_read_timeout` 太短。

排查：

```bash
tail -n 100 /var/日志/nginx/error.日志
curl -w 'time_total=%{time_total}\n' -o /dev/null -s http://127.0.0.1:8080/slow-接口
journalctl -u demo-接口 -n 200 --no-分页r
```

临时调整：

```nginx
proxy_connect_timeout 3s;
proxy_read_timeout 60s;
proxy_send_timeout 60s;
```

注意：调大超时只是缓解，不是性能优化。慢接口要回到后端和数据库排查。

## 403 排查

403 Forbidden 常见原因：

- 静态文件或目录权限不足。
- 目录没有 首页 文件且禁止列目录。
- Nginx root 指向目录不可进入。
- SELinux 或安全策略限制。

命令：

```bash
tail -n 100 /var/日志/nginx/error.日志
namei -l /opt/apps/demo-web/current/首页.html
ps aux | grep '[n]ginx'
```

处理：

```bash
sudo find /opt/apps/demo-web -type d -exec chmod 755 {} \;
sudo find /opt/apps/demo-web -type f -exec chmod 644 {} \;
```

如果系统启用 SELinux，还要检查：

```bash
getenforce
```

## 404 排查

404 分两类：

### 1. Nginx 静态文件 404

error 日志 可能有：

```text
open() "/opt/apps/demo-web/current/assets/app.脚本" failed (2: No such file or directory)
```

检查：

```bash
find /opt/apps/demo-web/current -maxdepth 2 -type f | head
curl -I http://example.通用/assets/app.脚本
```

### 2. 后端接口 404

access 日志 有请求，error 日志 不一定有错误。后端日志也能看到请求。

检查：

```bash
curl -i http://127.0.0.1:8080/接口/用户s
curl -i http://example.通用/接口/用户s
```

重点看 `proxy_pass` 是否改变了路径。

## 499 排查

499 是 Nginx 记录的状态，表示客户端主动断开连接。常见原因：

- 用户取消请求。
- 浏览器超时。
- 上游响应太慢，客户端等不住。
- 负载均衡或网关提前断开。

排查：

```bash
grep ' 499 ' /var/日志/nginx/access.日志 | tail -n 20
```

如果 499 大量增加，要结合接口耗时、后端负载、客户端超时配置分析。

## 自定义日志格式

为了排查代理耗时，可以增加：

```nginx
日志_formatat upstream_timing '$remote_addr $host "$request" '
                           'status=$status request_time=$request_time '
                           'upstream_addr=$upstream_addr '
                           'upstream_status=$upstream_status '
                           'upstream_response_time=$upstream_response_time';

access_日志 /var/日志/nginx/demo-接口.access.日志 upstream_timing;
```

字段含义：

- `request_time`：Nginx 处理请求总耗时。
- `upstream_response_time`：上游响应耗时。
- `upstream_addr`：实际转发到哪个上游。
- `upstream_status`：上游返回状态。

修改后：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

## 日志分析工具

### goaccess

```bash
sudo goaccess /var/日志/nginx/access.日志 -c
```

可用于查看：

- 访问量最高路径。
- 状态码分布。
- 来源 IP。
- 用户-Agent。

### awk 快速统计

状态码统计：

```bash
awk '{print $9}' /var/日志/nginx/access.日志 | sort | uniq -c | sort -nr
```

Top 路径：

```bash
awk '{print $7}' /var/日志/nginx/access.日志 | sort | uniq -c | sort -nr | head
```

## 使用技巧

- 502 先看 Nginx error 日志，再验证后端本机端口。
- access 日志 没记录，说明请求可能没到 Nginx。
- error 日志 里的 `connect refused`、`timed out`、`permission denied` 是关键线索。
- 给重要项目单独配置 access/error 日志。
- 增加 upstream timing 日志，有助于区分 Nginx 慢还是后端慢。

## 难点

- 502、504 是 Nginx 看到的代理结果，根因经常在后端。
- 404 可能来自 Nginx，也可能来自后端，要看日志链路。
- 403 多数是权限或安全策略，不一定是应用错误。
- 多层代理下，客户端 IP、状态码和耗时需要结合每一层日志。

## 重点

- Nginx 排障必须同时看 access 日志、error 日志、后端状态和本机 curl。
- 502 的第一步是确认后端端口和健康检查。
- 504 要关注后端耗时和超时配置。
- 静态资源问题优先看 root、文件存在性和权限。

## 练习

1. 故意停止后端服务，观察 Nginx 502 和 error 日志。
2. 把 root 指向不存在目录，观察静态资源 404。
3. 修改目录权限制造 403，用 `namei -l` 定位。
4. 配置 upstream timing 日志，访问接口后观察 upstream 响应时间。
