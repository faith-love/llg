# 配置优先级与生效验证

## 作用

配置优先级与生效验证用于解决“最终生效的配置到底是哪一个”的问题。一个应用的配置可能来自默认值、配置文件、环境变量、启动参数、profile、Docker参数、配置中心。如果不验证最终值，很容易误以为配置已修改，实际进程仍在使用旧值。

## 痛点

- 改了配置文件，但命令行参数覆盖了它。
- 改了环境变量，但进程没有重启。
- 改了 `.bashrc`，systemd 服务不受影响。
- 多个配置文件同时存在，不知道应用加载哪个。
- 排障时只看文件内容，不看进程实际环境。

## 优点

- 能判断配置来源。
- 能确认最终生效值。
- 能减少“改了但没生效”的问题。
- 能为部署和回滚提供证据。

## 常见配置来源

| 来源 | 示例 | 特点 |
| --- | --- | --- |
| 默认值 | 代码内默认端口 | 不外部配置时使用 |
| 配置文件 | `应用配置.yml` | 项目常用 |
| 环境变量 | `SERVER_PORT=8080` | 适合环境差异 |
| 命令行参数 | `--服务端.port=8081` | 优先级常较高 |
| systemd | `EnvironmentFile=` | 长期服务常用 |
| Docker | `environment:`、`.env` | Docker场景 |
| 配置中心 | Nacos、Consul 等 | 分布式配置 |

不同框架优先级不同，必须看对应框架文档。这里重点是建立验证思路。

## 常见优先级思路

通常越接近启动命令的配置，优先级越高：

```text
默认值
  < 配置文件
  < 环境变量
  < 命令行参数
```

例如 Spring Boot 中：

```bash
Java学习资料 -jar app.jar --服务端.port=8081
```

命令行参数往往会覆盖配置文件中的端口。

## 生效验证层次

### 1. 看文件

```bash
cat /opt/apps/demo-接口/shared/配置/应用配置.yml
cat /opt/apps/demo-接口/shared/配置/demo-接口.env
```

这只能说明文件内容，不代表进程已读取。

### 2. 看 systemd 配置

```bash
systemctl cat demo-接口
systemctl show demo-接口 -p Environment
```

确认 unit 和 EnvironmentFile 指向是否正确。

### 3. 看进程环境

```bash
pid=$(pgrep -f demo-接口 | head -n 1)
sudo tr '\0' '\n' < /proc/$pid/environ | grep APP_ENV
```

确认进程实际环境变量。

### 4. 看进程启动参数

```bash
ps -ef | grep demo-接口
```

确认是否有 `--服务端.port=...`、`--spring.profiles.active=...` 等参数。

### 5. 看应用自检接口或日志

```bash
journalctl -u demo-接口 -n 100
curl -f http://127.0.0.1:8080/health
```

部分应用启动日志会打印 profile、端口、配置文件路径。

## 修改配置后的流程

推荐流程：

1. 备份旧配置。
2. 修改配置文件或 env 文件。
3. 如果改了 unit，执行 `daemon-reload`。
4. 重启服务。
5. 查看服务状态。
6. 查看进程环境和启动参数。
7. 调用健康检查。
8. 记录变更。

示例：

```bash
cp demo-接口.env demo-接口.env.bak-$(date +%F-%H%M%S)
vim demo-接口.env
sudo systemctl restart demo-接口
sudo systemctl status demo-接口
pid=$(pgrep -f demo-接口 | head -n 1)
sudo tr '\0' '\n' < /proc/$pid/environ | grep APP_ENV
curl -f http://127.0.0.1:8080/health
```

## 常见问题

### 改了 env 文件没生效

原因：

- 服务未重启。
- unit 没有引用该 EnvironmentFile。
- EnvironmentFile 路径写错。
- 文件权限导致服务读不到。

检查：

```bash
systemctl cat demo-接口
ls -lah /opt/apps/demo-接口/shared/配置/demo-接口.env
sudo -u app cat /opt/apps/demo-接口/shared/配置/demo-接口.env
```

### 改了端口但仍监听旧端口

检查：

```bash
ps -ef | grep demo-接口
ss -lntup | grep Java学习资料
grep -R "服务端.port" /opt/apps/demo-接口/shared/配置
```

可能是命令行参数覆盖配置文件。

### 当前终端变量和服务变量不一致

这是正常的。检查服务环境：

```bash
systemctl show demo-接口 -p Environment
```

不要只看：

```bash
echo $APP_ENV
```

## 使用技巧

- 配置变更必须有验证步骤。
- 看配置文件只是第一步，最终要看进程和服务行为。
- 命令行参数通常优先级高，要重点检查 `ps -ef`。
- systemd unit 修改后要 `daemon-reload`。
- 配置和代码回滚要考虑兼容性。

## 难点

- 不同框架配置优先级不同。
- 环境变量、启动参数、配置文件可能互相覆盖。
- 进程环境包含敏感信息，查看时要谨慎。
- Docker场景还有 Docker Compose、镜像默认值、Kubernetes Secret/ConfigMap 等来源。

## 重点

- 改配置不等于生效。
- 生效验证看文件、unit、进程环境、启动参数、日志和接口。
- 修改 unit 后 `daemon-reload`。
- 修改服务变量后重启服务。
- 记录最终生效值和验证命令。

## 练习

1. 写一个 env 文件，通过 systemd 读取，然后用 `/proc/$pid/environ` 验证。
2. 同时设置配置文件端口和命令行端口，观察哪个生效。
3. 修改 env 文件但不重启服务，验证进程变量是否变化。
4. 写一份配置变更记录，包括文件、变量、重启命令和验证结果。
