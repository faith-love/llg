# 网络连接与性能排查顺序

## 作用

网络连接与性能排查用于判断服务慢、连接失败、502/504、连接数堆积等问题是否来自连接状态、网络延迟、后端响应、资源瓶颈或上游依赖。`ss` 可以观察连接状态，`curl` 可以测接口耗时，系统资源命令可以判断瓶颈类型。性能排查最重要的是按顺序缩小范围，而不是一次性乱看所有指标。

这一节重点解决：

- 如何查看当前连接状态。
- `ESTAB`、`TIME-WAIT`、`CLOSE-WAIT` 等状态代表什么。
- 如何判断连接堆积。
- 如何把 CPU、内存、磁盘、IO、网络放在同一条排查链路里。
- 如何建立性能问题排查顺序。

## 痛点

- 接口慢时只查 CPU，忽略连接池和上游超时。
- 大量 `CLOSE-WAIT` 出现，但不知道是应用没有关闭连接。
- 看到 `TIME-WAIT` 很多就急着改内核参数，实际是正常短连接流量。
- Nginx 504 被误判为 Nginx 问题，根因是后端慢查询。
- 指标很多，但不知道先判断哪一个瓶颈。

## 网络连接状态

查看汇总：

```bash
ss -s
```

查看 TCP 连接：

```bash
ss -ant
```

按状态统计：

```bash
ss -ant | awk 'NR>1 {print $1}' | sort | uniq -c | sort -nr
```

查看某个端口：

```bash
ss -ant sport = :8080
ss -ant dport = :3306
```

查看进程：

```bash
sudo ss -antp | grep ':8080'
```

## 常见连接状态

| 状态 | 含义 | 排查方向 |
| --- | --- | --- |
| `LISTEN` | 端口正在监听 | 服务是否启动 |
| `ESTAB` | 连接已建立 | 当前活跃连接 |
| `TIME-WAIT` | 主动关闭后等待 | 短连接多时常见 |
| `CLOSE-WAIT` | 对端关闭，本端未关闭 | 应用可能未正确关闭连接 |
| `SYN-SENT` | 正在发起连接 | 目标不可达或慢 |
| `SYN-RECV` | 收到连接请求未完成 | 可能连接洪峰或握手问题 |
| `FIN-WAIT` | 正在关闭连接 | 连接关闭过程 |

### TIME-WAIT

适量 `TIME-WAIT` 正常。大量出现时先判断：

- 是否短连接非常多。
- HTTP keepalive 是否合理。
- 客户端是否频繁新建连接。
- 是否是压测或爬虫。

不要一上来改内核参数。先看业务连接模式和 Nginx/应用连接复用。

### CLOSE-WAIT

大量 `CLOSE-WAIT` 更值得警惕，通常表示对端已经关闭连接，但本端应用没有关闭 socket。

排查：

```bash
sudo ss -antp | grep CLOSE-WAIT | head
```

方向：

- 应用代码连接泄漏。
- HTTP 客户端未关闭响应体。
- 数据库或 Redis 客户端连接未释放。

## 接口耗时分解

使用 curl：

```bash
curl -o /dev/null -s -w 'code=%{http_code} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} start=%{time_starttransfer} total=%{time_total}\n' https://example.com/api/health
```

字段：

- `time_namelookup`：DNS 耗时。
- `time_connect`：TCP 连接耗时。
- `time_appconnect`：TLS 握手耗时。
- `time_starttransfer`：首字节时间，常反映后端处理时间。
- `time_total`：总耗时。

判断：

- DNS 慢：查 DNS、解析器、网络。
- connect 慢：查网络、端口、防火墙、负载均衡。
- TLS 慢：查证书、握手、网络。
- starttransfer 慢：多半是后端慢或上游依赖慢。

## Nginx upstream 耗时

建议日志格式：

```nginx
log_format upstream_timing '$remote_addr "$request" '
                           'status=$status request_time=$request_time '
                           'upstream_addr=$upstream_addr '
                           'upstream_status=$upstream_status '
                           'upstream_response_time=$upstream_response_time';
```

作用：

- `request_time` 高、`upstream_response_time` 高：后端慢。
- `request_time` 高、upstream 低：可能客户端慢、响应体大、网络慢。
- `upstream_addr` 可以定位哪台后端慢。

## 性能排查总顺序

### 1. 先确认现象

```bash
curl -w 'code=%{http_code} total=%{time_total}\n' -o /dev/null -s http://example.com/api/health
```

明确：

- 是慢，还是失败。
- 是所有接口，还是某个接口。
- 是所有用户，还是部分用户。
- 是持续慢，还是峰值慢。

### 2. 看入口日志

```bash
tail -n 100 /var/log/nginx/access.log
tail -n 100 /var/log/nginx/error.log
```

判断：

- 请求是否到达。
- 状态码是否异常。
- 是否 502/504。
- upstream 响应是否慢。

### 3. 看后端健康

```bash
curl -w 'code=%{http_code} total=%{time_total}\n' -o /dev/null -s http://127.0.0.1:8080/health
systemctl status demo-api --no-pager
journalctl -u demo-api -n 100 --no-pager
```

如果本机后端也慢，继续看系统资源和应用日志。

### 4. 看 CPU 和 load

```bash
uptime
top
ps aux --sort=-%cpu | head
```

判断：

- CPU 是否打满。
- load 是否高于核心数。
- 是否有异常高 CPU 进程。

### 5. 看内存和 OOM

```bash
free -h
ps aux --sort=-%mem | head
dmesg -T | grep -i 'killed process\\|out of memory'
```

判断：

- available 是否不足。
- Swap 是否大量使用。
- 是否发生 OOM。

### 6. 看磁盘空间和 IO

```bash
df -h
iostat -x 1
sudo iotop -o
```

判断：

- 磁盘是否满。
- IO wait 是否高。
- 哪个进程在大量读写。

### 7. 看连接和句柄

```bash
ss -s
ss -ant | awk 'NR>1 {print $1}' | sort | uniq -c | sort -nr
pid=$(pgrep -f demo-api | head -n 1)
cat /proc/$pid/limits | grep 'Max open files'
ls /proc/$pid/fd | wc -l
```

判断：

- 是否连接堆积。
- 是否大量 `CLOSE-WAIT`。
- 文件句柄是否接近上限。

### 8. 看应用和依赖

```bash
tail -n 200 /opt/apps/demo-api/shared/logs/app.log
grep -n "ERROR\\|timeout\\|Exception" /opt/apps/demo-api/shared/logs/app.log | tail
```

继续查：

- 数据库慢查询。
- Redis 超时。
- 外部接口超时。
- 线程池和连接池耗尽。
- GC 或运行时问题。

## 常见场景判断

### CPU 高、接口慢

方向：

- 高 CPU 业务逻辑。
- 死循环。
- 批任务。
- 压缩、加密、JSON 处理。
- GC。

命令：

```bash
ps aux --sort=-%cpu | head
pidstat -t -p PID 1
```

### Load 高、CPU 不高

方向：

- IO wait。
- 磁盘慢。
- 不可中断任务。

命令：

```bash
top
iostat -x 1
vmstat 1
```

### 502/504 增加

方向：

- 后端没启动。
- 后端端口不可达。
- 后端处理慢。
- 连接池耗尽。

命令：

```bash
tail -n 100 /var/log/nginx/error.log
curl -v http://127.0.0.1:8080/health
journalctl -u demo-api -n 100 --no-pager
```

### CLOSE-WAIT 很多

方向：

- 应用未关闭连接。
- HTTP 客户端响应体未关闭。
- 数据库或 Redis 客户端泄漏。

命令：

```bash
sudo ss -antp | grep CLOSE-WAIT | head
```

## 好用工具

- `ss`：连接状态。
- `curl -w`：HTTP 耗时分解。
- `mtr`：网络路径质量。
- `sar`：历史 CPU、内存、网络、IO 指标。
- `pidstat`：进程级资源。
- `iostat`：磁盘 IO。
- `glances`：综合资源。
- `netdata`：轻量实时监控面板。

## 使用技巧

- 性能问题先分类：慢、失败、超时、连接数高、资源高。
- 入口日志和后端本机 curl 能快速判断问题在哪一层。
- `TIME-WAIT` 不一定是问题，`CLOSE-WAIT` 更要警惕。
- 指标要和时间线、发布、流量、批任务关联。
- 不要只改内核参数，先确认应用连接模式和瓶颈。

## 难点

- 慢请求可能由数据库、缓存、外部接口、日志写入共同造成。
- 单机指标正常，不代表负载均衡后所有实例都正常。
- 短时间尖峰和持续瓶颈处理方式不同。
- 连接池耗尽可能表现为后端慢、502、线程阻塞等多种现象。

## 重点

- 性能排查要先定位瓶颈类型，再采取动作。
- `curl -w`、Nginx upstream 日志、系统资源指标要结合看。
- 网络连接状态可以暴露连接泄漏和堆积。
- 最终结论必须能解释用户现象和日志指标。

## 练习

1. 使用 `ss -s` 和 `ss -ant` 统计当前 TCP 连接状态。
2. 使用 `curl -w` 分析一个 HTTPS 网站的 DNS、连接、TLS 和响应耗时。
3. 配置 Nginx upstream timing 日志，并观察后端响应时间。
4. 按本节顺序写一份“接口变慢”的排查记录。
