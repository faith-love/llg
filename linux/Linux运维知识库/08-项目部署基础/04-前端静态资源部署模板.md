# 前端静态资源部署模板

## 作用

前端静态资源部署，是把 Vue、React、Angular 等项目构建出的 `dist/` 或 `build/` 目录发布到服务器，并通过 Nginx 提供访问。它和后端服务部署不同，静态资源通常不需要 systemd 托管业务进程，但非常依赖构建产物、Nginx root、路由 fallback、缓存策略、接口代理和权限设置。

这一节重点解决：

- 构建产物如何上传到版本目录。
- Nginx 如何指向 `current`。
- SPA 刷新 404 如何处理。
- 静态资源缓存如何配置。
- 发布后如何验证页面、资源、接口代理。

## 痛点

- 只上传了部分 `dist` 文件，页面白屏或资源 404。
- Nginx `root` 指错目录，访问到旧版本。
- Vue/React 的 history 路由刷新后 404。
- 静态资源缓存过强，用户仍然访问旧 JS。
- 前端页面打开正常，但 API 代理失败。
- 发布直接覆盖目录，回滚只能重新上传旧包。

## 部署前检查

### 1. 确认构建产物

常见构建命令：

```bash
npm ci
npm run build
```

pnpm：

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm build
```

常见产物目录：

```text
dist/
build/
```

检查产物：

```bash
ls -lh dist
find dist -maxdepth 2 -type f | head
test -f dist/index.html
```

### 2. 确认部署类型

前端项目要确认：

- 是 SPA 还是多页面。
- 是否使用 history 路由。
- 是否部署在域名根路径 `/`，还是子路径 `/admin/`。
- API 是同域反代，还是独立域名。
- 是否需要 gzip 或 brotli。
- 是否需要缓存策略。

### 3. 确认 Nginx 用户

不同系统 Nginx 运行用户可能不同：

```bash
ps aux | grep '[n]ginx'
grep -n '^user' /etc/nginx/nginx.conf
```

常见用户：

- `www-data`：Ubuntu/Debian 常见。
- `nginx`：RHEL 系或官方 Nginx 常见。

静态文件至少要让 Nginx 用户可读，让目录链路可进入。

## 目录结构

推荐：

```text
/opt/apps/demo-web/
  current -> releases/2026-05-11-120000
  releases/
    2026-05-11-120000/
      index.html
      assets/
  shared/
    logs/
```

初始化：

```bash
sudo mkdir -p /opt/apps/demo-web/{releases,shared/logs}
sudo chown -R app:app /opt/apps/demo-web
sudo chmod 755 /opt/apps /opt/apps/demo-web
```

如果 Nginx 用户不是 `app`，静态资源目录通常需要其他用户可读和目录可执行：

```bash
sudo find /opt/apps/demo-web -type d -exec chmod 755 {} \;
sudo find /opt/apps/demo-web -type f -exec chmod 644 {} \;
```

## 上传发布

使用 rsync 上传：

```bash
release=$(date +%F-%H%M%S)
base=/opt/apps/demo-web

sudo mkdir -p $base/releases/$release
sudo rsync -av --delete /tmp/dist/ $base/releases/$release/
sudo chown -R app:app $base/releases/$release
sudo find $base/releases/$release -type d -exec chmod 755 {} \;
sudo find $base/releases/$release -type f -exec chmod 644 {} \;
sudo ln -sfn $base/releases/$release $base/current
```

注意：

- `dist/` 后面的斜杠表示同步目录内容。
- `--delete` 会删除目标中源目录不存在的文件，只能用于新 release 目录，不能随便对共享目录使用。
- 每次发布新 release，不直接覆盖 current 指向目录。

验证：

```bash
readlink -f /opt/apps/demo-web/current
test -f /opt/apps/demo-web/current/index.html
find /opt/apps/demo-web/current -maxdepth 2 -type f | head
```

## Nginx 基础配置

示例：部署在根路径 `/`

```nginx
server {
    listen 80;
    server_name example.com;

    root /opt/apps/demo-web/current;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8080/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

检查：

```bash
sudo nginx -t
sudo systemctl reload nginx
curl -I http://example.com
```

## SPA 路由

Vue Router、React Router 使用 history 模式时，浏览器刷新 `/users/1` 会请求服务器上的 `/users/1` 文件。如果 Nginx 不 fallback 到 `index.html`，会 404。

关键配置：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

如果部署在子路径 `/admin/`：

```nginx
location /admin/ {
    alias /opt/apps/demo-web/current/;
    try_files $uri $uri/ /admin/index.html;
}
```

子路径部署要同时确认前端构建配置中的 base/publicPath，例如 Vite 的 `base`、Vue CLI 的 `publicPath`。

## 静态资源缓存

现代前端构建通常会生成带 hash 的资源：

```text
assets/index-a1b2c3d4.js
assets/index-e5f6g7h8.css
```

可以对带 hash 的静态资源设置长缓存：

```nginx
location /assets/ {
    root /opt/apps/demo-web/current;
    expires 30d;
    add_header Cache-Control "public, immutable";
}
```

对 `index.html` 不建议长缓存：

```nginx
location = /index.html {
    root /opt/apps/demo-web/current;
    add_header Cache-Control "no-cache";
}
```

原因：

- `index.html` 决定当前引用哪个 JS/CSS。
- 如果 `index.html` 被强缓存，用户可能长期访问旧版本入口。
- 带 hash 的 JS/CSS 可以长缓存，因为文件名变化代表内容变化。

## gzip 压缩

基础配置可放到 `http` 段：

```nginx
gzip on;
gzip_types text/plain text/css application/javascript application/json image/svg+xml;
gzip_min_length 1024;
```

检查响应头：

```bash
curl -H 'Accept-Encoding: gzip' -I http://example.com/assets/index.js
```

## 发布后验证

本机验证：

```bash
curl -I http://127.0.0.1
curl -s http://127.0.0.1 | head
```

域名验证：

```bash
curl -I http://example.com
curl -I http://example.com/assets/文件名.js
```

SPA 路由验证：

```bash
curl -I http://example.com/users/1
```

API 代理验证：

```bash
curl -I http://example.com/api/health
```

日志：

```bash
tail -n 100 /var/log/nginx/access.log
tail -n 100 /var/log/nginx/error.log
```

## 回滚

查看版本：

```bash
readlink -f /opt/apps/demo-web/current
ls -lt /opt/apps/demo-web/releases
```

切换旧版本：

```bash
old=/opt/apps/demo-web/releases/2026-05-10-180000
sudo test -f $old/index.html
sudo ln -sfn $old /opt/apps/demo-web/current
sudo nginx -t
sudo systemctl reload nginx
```

验证：

```bash
curl -I http://example.com
```

## 好用工具

- `rsync`：同步构建产物。
- `nginx -t`：检查配置语法。
- `curl -I`：检查响应状态和缓存头。
- `find`：检查资源文件是否上传完整。
- `tree`：查看 dist 结构。
- `brotli`、`gzip`：静态资源压缩。

## 使用技巧

- 在 CI 构建前端，服务器只接收构建产物，不在生产服务器临时构建。
- `root` 指向 `current`，发布和回滚都只切软链接。
- SPA 使用 `try_files $uri $uri/ /index.html`。
- `index.html` 不长缓存，带 hash 的静态资源可以长缓存。
- 每次改 Nginx 配置先 `nginx -t`，再 reload。

## 难点

- 子路径部署需要 Nginx 配置和前端构建 base 同时正确。
- API 代理路径是否保留 `/api/`，取决于 `proxy_pass` 末尾是否带 `/`。
- 目录权限不够时，Nginx 会 403，而不是前端构建问题。
- 浏览器缓存可能掩盖发布结果，验证时要看响应头和资源文件名。

## 重点

- 前端部署核心是 dist、Nginx root、try_files、缓存、API 代理。
- 静态资源也要有 releases/current 结构，方便回滚。
- 发布后要验证首页、静态资源、SPA 路由、API 代理和 Nginx 日志。
- 不要把构建环境问题和运行环境问题混在一起。

## 练习

1. 部署一个简单 `dist` 目录，用 Nginx 指向 `current`。
2. 配置 SPA fallback，验证刷新二级路由不会 404。
3. 为 `/assets/` 增加长缓存，为 `index.html` 设置 `no-cache`。
4. 创建两个静态版本，用 current 软链接完成一次回滚。
