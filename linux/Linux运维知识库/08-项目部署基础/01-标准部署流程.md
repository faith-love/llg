# 标准部署流程

## 作用

标准部署流程解决的是“如何把构建产物稳定、可验证、可回滚地运行在服务器上”。部署不是把文件上传到服务器后执行一条启动命令，而是一条完整链路：服务器检查、环境准备、用户和目录规划、产物上传、配置拆分、权限设置、服务托管、反向代理、健康检查、日志观察、版本记录和回滚准备。

一套标准流程的价值在于：

- 每次发布步骤一致，减少临时操作。
- 新人接手时能根据清单复现部署。
- 出问题时知道从哪里验证和回滚。
- 服务重启、服务器重启后仍能自动恢复。
- 配置、日志、上传文件不会被新版本覆盖。

## 痛点

- 手工启动服务后，SSH 断开或服务器重启，服务就停止。
- 新包直接覆盖旧包，出现问题时无法切回上一版。
- 配置文件和代码包混在一起，每次发布都可能覆盖生产配置。
- 服务用 root 启动，权限过大，安全风险高。
- 部署完成只看进程存在，没有检查端口、接口、日志和外部访问。
- 出现故障后无法复盘，因为没有记录版本号、发布命令、操作者和时间。

## 部署前确认

### 1. 明确部署对象

部署前先回答：

- 部署的是后端 API、前端静态资源、Node 服务、Python 服务，还是定时任务？
- 产物是什么：`jar`、`dist/`、`tar.gz`、源码目录、二进制文件？
- 服务端口是多少？
- 是否需要 Nginx 反向代理？
- 是否需要数据库、Redis、消息队列等外部依赖？
- 是否有健康检查地址？

建议记录成表：

```text
项目名：
服务名：
产物类型：
部署路径：
运行用户：
监听端口：
健康检查：
配置文件：
日志路径：
回滚方式：
```

### 2. 服务器基线检查

```bash
cat /etc/os-release
hostname
ip addr
df -h
free -h
uptime
date
timedatectl
```

重点确认：

- 系统发行版和版本。
- CPU、内存、磁盘是否满足项目要求。
- 磁盘空间是否足够存放多个 release。
- 时间和时区是否正确。
- 服务器 IP 和主机名是否是目标环境。

### 3. 运行环境检查

Java：

```bash
java -version
which java
readlink -f "$(command -v java)"
```

Node：

```bash
node -v
npm -v
which node
```

Python：

```bash
python3 --version
pip3 --version
```

Nginx：

```bash
nginx -v
nginx -t
systemctl status nginx --no-pager
```

重点不是“有输出”，而是版本和路径是否符合项目要求。

## 标准部署步骤

### 1. 创建服务用户

业务服务不建议直接用 root 运行。可以创建专用用户：

```bash
sudo useradd -r -s /usr/sbin/nologin app
id app
```

说明：

- `-r` 创建系统用户。
- `-s /usr/sbin/nologin` 禁止普通登录。
- 服务通过 systemd 指定 `User=app` 运行。

如果系统没有 `/usr/sbin/nologin`，可以确认实际路径：

```bash
command -v nologin
```

### 2. 规划目录

推荐目录：

```text
/opt/apps/项目名/
  current -> releases/当前版本
  releases/
  shared/
    config/
    logs/
    uploads/
    tmp/
```

创建：

```bash
sudo mkdir -p /opt/apps/demo-api/{releases,shared/config,shared/logs,shared/uploads,shared/tmp}
sudo chown -R app:app /opt/apps/demo-api
sudo chmod 750 /opt/apps/demo-api
```

目录含义：

- `releases`：每次发布一个新版本目录。
- `current`：软链接，指向当前正在运行版本。
- `shared/config`：生产配置和环境变量。
- `shared/logs`：应用日志。
- `shared/uploads`：用户上传文件。
- `shared/tmp`：临时文件。

### 3. 上传构建产物

常用方式：

```bash
scp app.jar user@server:/tmp/
rsync -avz dist/ user@server:/tmp/dist/
```

更推荐使用 `rsync`，因为它支持增量同步、保留目录结构、显示变更。

校验产物：

```bash
sha256sum app.jar
ls -lh app.jar
```

如果产物来自 CI，建议记录：

- Git commit。
- 构建编号。
- 构建时间。
- 产物校验值。

### 4. 创建 release

```bash
release=$(date +%F-%H%M%S)
sudo mkdir -p /opt/apps/demo-api/releases/$release
sudo cp /tmp/app.jar /opt/apps/demo-api/releases/$release/
sudo chown -R app:app /opt/apps/demo-api/releases/$release
sudo ln -sfn /opt/apps/demo-api/releases/$release /opt/apps/demo-api/current
```

验证：

```bash
readlink -f /opt/apps/demo-api/current
ls -lh /opt/apps/demo-api/current
```

### 5. 准备配置文件

示例环境文件：

```bash
sudo install -o app -g app -m 640 /dev/null /opt/apps/demo-api/shared/config/demo-api.env
sudo vim /opt/apps/demo-api/shared/config/demo-api.env
```

内容示例：

```bash
APP_ENV=prod
SERVER_PORT=8080
JAVA_OPTS=-Xms512m -Xmx512m
```

配置原则：

- 配置不放进 release 目录，避免发布时覆盖。
- 密钥文件权限要收紧。
- systemd 使用 `EnvironmentFile` 读取变量。
- 配置变更要记录，不要只保留在某个人终端历史里。

### 6. 设置权限

```bash
sudo chown -R app:app /opt/apps/demo-api
sudo find /opt/apps/demo-api -type d -exec chmod 750 {} \;
sudo find /opt/apps/demo-api -type f -exec chmod 640 {} \;
```

如果脚本需要执行权限：

```bash
sudo chmod 750 /opt/apps/demo-api/current/bin/start.sh
```

验证服务用户权限：

```bash
sudo -u app test -r /opt/apps/demo-api/current/app.jar
sudo -u app test -r /opt/apps/demo-api/shared/config/demo-api.env
sudo -u app test -w /opt/apps/demo-api/shared/logs
```

### 7. 创建 systemd 服务

示例：

```ini
[Unit]
Description=Demo API Service
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=app
Group=app
WorkingDirectory=/opt/apps/demo-api/current
EnvironmentFile=/opt/apps/demo-api/shared/config/demo-api.env
ExecStart=/bin/bash -lc 'exec /usr/bin/java $JAVA_OPTS -jar /opt/apps/demo-api/current/app.jar'
Restart=on-failure
RestartSec=5
SuccessExitStatus=143

[Install]
WantedBy=multi-user.target
```

保存到：

```bash
/etc/systemd/system/demo-api.service
```

生效：

```bash
sudo systemd-analyze verify /etc/systemd/system/demo-api.service
sudo systemctl daemon-reload
sudo systemctl enable --now demo-api
```

### 8. 启动后验证

```bash
systemctl status demo-api --no-pager
journalctl -u demo-api -n 100 --no-pager
sudo ss -lntup | grep ':8080'
curl -f http://127.0.0.1:8080/health
```

如果通过 Nginx 暴露：

```bash
sudo nginx -t
sudo systemctl reload nginx
curl -I http://example.com
```

验证维度：

- 服务 active。
- 端口监听。
- 本机健康检查成功。
- Nginx 转发成功。
- 日志没有启动错误。
- 外部访问路径正常。

### 9. 记录发布信息

建议在服务器保留发布记录：

```bash
sudo install -o app -g app -m 640 /dev/null /opt/apps/demo-api/shared/deploy.log
```

记录内容：

```text
时间：
项目：
版本目录：
Git commit：
产物校验：
操作者：
变更内容：
健康检查结果：
回滚版本：
```

也可以通过 CI/CD 系统记录，但服务器本地保留一份简要记录很有价值。

## 好用工具

- `rsync`：高效同步文件和目录。
- `scp`：简单上传单个文件。
- `sha256sum`：校验产物完整性。
- `tar`：打包和解压 release。
- `systemctl`：服务托管和状态管理。
- `journalctl`：查看启动和运行日志。
- `curl`：接口和健康检查验证。
- `jq`：格式化 JSON 健康检查结果。

安装示例：

```bash
sudo apt install rsync curl jq
sudo dnf install rsync curl jq
```

## 使用技巧

- 发布前先确认主机和环境，避免把测试包发到生产。
- 每次发布创建新 release，不直接覆盖 current 目录内容。
- 配置、日志、上传文件放 shared，不随版本替换。
- systemd 服务使用绝对路径和专用用户。
- 健康检查失败时不要继续配置外部流量，先在本机修复。
- 部署记录要包含版本和回滚点。

## 难点

- 服务启动成功不代表业务可用，依赖数据库、Redis、外部接口也可能失败。
- 本机健康检查成功不代表外部可访问，还要看 Nginx、防火墙、安全组、DNS。
- 数据库结构变更可能让应用回滚不再简单。
- systemd 环境和手工 Shell 环境不同，运行时路径和环境变量要显式配置。

## 重点

- 部署流程要形成闭环：准备、发布、启动、验证、记录、回滚。
- `releases/current/shared` 是降低覆盖风险和回滚成本的基础结构。
- 生产服务优先 systemd 托管，不依赖 `nohup`。
- 每次发布都必须能回答：当前版本是什么、如何验证、失败如何回滚。

## 练习

1. 用一个简单 HTTP 服务模拟部署，完整执行目录创建、release 创建、current 切换、systemd 启动。
2. 写一份部署记录，包含版本、时间、操作者、健康检查和回滚版本。
3. 故意让服务端口配置错误，按标准流程定位问题。
4. 创建两个 release，用软链接切换并观察服务重启后的版本变化。
