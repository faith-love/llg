# 健康检查与回滚

## 作用

健康检查与回滚是部署闭环的最后一段。发布完成后，不能只看命令执行成功或进程存在，而要确认服务真正可用；一旦新版本不可用，要能在明确风险的前提下快速回到上一版。

健康检查回答：“新版本是否可以接流量？”

回滚回答：“新版本不可用时，如何恢复到已知可用状态？”

## 痛点

- 服务 `active`，但接口 500，发布仍被认为成功。
- 端口监听正常，但 Nginx 代理配置错误，外部访问失败。
- 本机健康检查成功，但安全组或防火墙导致外部访问失败。
- 代码回滚了，但数据库结构已经迁移，旧版本无法运行。
- 找不到上一版 release，或者旧版本配置已经被覆盖。

## 健康检查层次

### 1. 服务状态

```bash
systemctl status demo-api --no-pager
systemctl is-active demo-api
systemctl is-enabled demo-api
```

判断：

- `is-active` 输出 `active` 才表示服务正在运行。
- `is-enabled` 只表示是否开机自启，不代表当前运行。
- `status` 中的最近日志要一起看。

### 2. 进程和端口

```bash
pgrep -af demo-api
sudo ss -lntup | grep ':8080'
```

确认：

- 进程命令是否是当前项目。
- 端口是否是预期端口。
- 监听地址是 `127.0.0.1` 还是 `0.0.0.0`。

### 3. 本机接口

```bash
curl -f http://127.0.0.1:8080/health
curl -i http://127.0.0.1:8080/health
```

`curl -f` 在 HTTP 4xx/5xx 时返回失败，适合脚本判断。

带超时：

```bash
curl -fsS --connect-timeout 3 --max-time 10 http://127.0.0.1:8080/health
```

### 4. Nginx 或网关访问

```bash
curl -I http://api.example.com
curl -fsS http://api.example.com/health
```

如果是前端：

```bash
curl -I http://example.com
curl -I http://example.com/assets/文件名.js
curl -I http://example.com/任意前端路由
```

### 5. 日志检查

systemd 日志：

```bash
journalctl -u demo-api -n 200 --no-pager
journalctl -u demo-api -p err --since "10 minutes ago" --no-pager
```

Nginx 日志：

```bash
tail -n 100 /var/log/nginx/error.log
tail -n 100 /var/log/nginx/access.log
```

应用文件日志：

```bash
tail -n 100 /opt/apps/demo-api/shared/logs/app.log
```

注意：没有错误日志不等于业务正常。仍要看接口返回、关键功能和依赖连接。

### 6. 依赖检查

根据项目检查：

- 数据库连接。
- Redis 连接。
- 消息队列连接。
- 文件存储或对象存储。
- 第三方接口。
- 定时任务是否启动。

健康检查接口如果只返回进程存活，不检查依赖，就不能代表完整业务健康。

## 健康检查脚本模板

示例：`/opt/apps/demo-api/shared/check-health.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail

service=demo-api
port=8080
url="http://127.0.0.1:${port}/health"

systemctl is-active --quiet "$service"
sudo ss -lntup | grep -q ":${port}"
curl -fsS --connect-timeout 3 --max-time 10 "$url" >/dev/null

echo "OK: $service is healthy"
```

权限：

```bash
sudo chown app:app /opt/apps/demo-api/shared/check-health.sh
sudo chmod 750 /opt/apps/demo-api/shared/check-health.sh
```

如果脚本中使用 `sudo ss`，需要考虑执行用户权限。也可以只使用 `curl` 和 `systemctl is-active`。

## 发布后观察窗口

发布刚完成时建议观察：

```bash
journalctl -u demo-api -f
```

另一个终端持续请求：

```bash
watch -n 2 'curl -fsS http://127.0.0.1:8080/health && echo'
```

观察内容：

- 服务是否反复重启。
- 错误日志是否增加。
- 内存是否持续上涨。
- 接口响应是否稳定。
- Nginx 是否出现 502、504。

## 回滚类型

### 1. 应用代码回滚

最常见，切换 `current` 到旧 release：

```bash
old=/opt/apps/demo-api/releases/2026-05-10-180000
sudo test -d $old
sudo ln -sfn $old /opt/apps/demo-api/current
sudo systemctl restart demo-api
```

适合：

- 新代码启动失败。
- 新代码接口异常。
- 前端资源异常。

前提：

- 旧 release 完整存在。
- 配置兼容旧代码。
- 数据库变更不阻止旧代码运行。

### 2. 配置回滚

如果问题来自配置变更：

```bash
sudo cp /opt/apps/demo-api/shared/config/demo-api.env.bak /opt/apps/demo-api/shared/config/demo-api.env
sudo systemctl restart demo-api
```

配置变更前要备份：

```bash
sudo cp /opt/apps/demo-api/shared/config/demo-api.env /opt/apps/demo-api/shared/config/demo-api.env.bak.$(date +%F-%H%M%S)
```

### 3. Nginx 配置回滚

改前备份：

```bash
sudo cp /etc/nginx/conf.d/demo.conf /etc/nginx/conf.d/demo.conf.bak.$(date +%F-%H%M%S)
```

回滚：

```bash
sudo cp /etc/nginx/conf.d/demo.conf.bak.时间 /etc/nginx/conf.d/demo.conf
sudo nginx -t
sudo systemctl reload nginx
```

### 4. 数据库回滚

数据库回滚最复杂，不能简单照搬代码回滚。

部署前要确认：

- 是否有数据库迁移。
- 迁移是否向后兼容。
- 是否有备份。
- 是否能执行反向迁移。
- 回滚是否会丢数据。

推荐策略：

- 优先做向后兼容变更。
- 分阶段发布：先加字段，再用字段，最后清理旧字段。
- 高风险变更先备份和演练。

## 回滚流程

### 1. 决策

触发回滚的条件：

- 健康检查失败。
- 错误率明显升高。
- 关键接口不可用。
- 服务反复重启。
- Nginx 大量 502/504。
- 资源异常影响业务。

先判断是否能快速修配置。如果不能在很短时间内确认修复，优先回滚到上一稳定版本。

### 2. 执行

```bash
service=demo-api
base=/opt/apps/demo-api
old=$base/releases/2026-05-10-180000

sudo test -d "$old"
sudo ln -sfn "$old" "$base/current"
sudo systemctl restart "$service"
```

### 3. 验证

```bash
readlink -f /opt/apps/demo-api/current
systemctl status demo-api --no-pager
journalctl -u demo-api -n 100 --no-pager
curl -fsS http://127.0.0.1:8080/health
curl -I http://api.example.com
```

### 4. 记录

记录：

```text
回滚时间：
触发原因：
新版本：
回滚版本：
执行人：
验证结果：
后续处理：
```

## 前端回滚

前端静态资源回滚通常不需要重启业务服务：

```bash
old=/opt/apps/demo-web/releases/2026-05-10-180000
sudo test -f $old/index.html
sudo ln -sfn $old /opt/apps/demo-web/current
sudo nginx -t
sudo systemctl reload nginx
```

验证：

```bash
curl -I http://example.com
curl -I http://example.com/assets/文件名.js
```

注意缓存：

- 如果 `index.html` 被缓存，用户可能仍访问旧入口。
- 回滚后可检查响应头 `Cache-Control`。

## 好用工具

- `curl -f`：脚本化健康检查。
- `watch`：持续观察健康检查。
- `jq`：解析 JSON 健康响应。
- `journalctl`：观察服务日志。
- `ss`：验证端口监听。
- `readlink -f`：确认 current 指向。
- `ab`、`wrk`：简单压测和冒烟流量验证，生产谨慎使用。

示例：

```bash
watch -n 2 'curl -fsS http://127.0.0.1:8080/health | jq .'
```

## 使用技巧

- 健康检查至少覆盖服务状态、端口、本机接口、代理访问和日志。
- 回滚命令发布前就要准备好，不要故障发生后才找旧版本。
- 每次发布保留最近几个 release。
- 配置和数据库变更要单独评估回滚能力。
- 健康检查失败时不要继续扩大流量。

## 难点

- 健康接口如果只检查进程存活，不能代表数据库等依赖健康。
- 代码回滚简单，数据回滚困难。
- 缓存、CDN、浏览器缓存可能让前端回滚看起来不生效。
- systemd 服务 active 不能证明业务接口可用。
- 多台服务器回滚要保证版本一致。

## 重点

- 发布必须有健康检查，健康检查必须有明确失败标准。
- 回滚依赖 releases/current/shared 结构和部署记录。
- 数据库变更要提前设计兼容和回滚策略。
- 回滚后仍要完整验证，不是切回旧目录就结束。

## 练习

1. 写一个健康检查脚本，检查 systemd 状态、端口和 HTTP 接口。
2. 创建两个 release，模拟新版本健康检查失败后回滚。
3. 修改 Nginx 配置制造 502，查看日志并回滚配置。
4. 设计一份发布检查表，包含发布前、发布后和回滚条件。
