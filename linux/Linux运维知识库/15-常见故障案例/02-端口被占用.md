# 02 端口被占用

端口被占用通常表现为应用启动时报 `Address already in use`。排查时重点不是“杀掉占用进程”，而是判断这个进程是谁、为什么占用、能不能停、是否存在重复启动或端口规划冲突。

## 作用

- 快速定位哪个进程占用了目标端口。
- 区分旧版本未停止、重复启动、配置冲突和端口规划错误。
- 避免误杀生产进程。
- 建立端口分配和发布前检查习惯。

## 常见现象

- 应用日志出现 `Address already in use`。
- Spring Boot 报 `Port 8080 was already in use`。
- Node.js 报 `EADDRINUSE`。
- Nginx 启动失败，提示 `bind() to 0.0.0.0:80 failed`。
- 新版本服务启动失败，旧版本仍在运行。

## 先判断端口类型

| 类型 | 示例 | 排查重点 |
| --- | --- | --- |
| Web 入口端口 | 80、443 | 是否 Nginx/Apache 已占用 |
| 应用内部端口 | 8080、3000 | 是否旧应用未停止或重复启动 |
| 数据库端口 | 3306、5432 | 是否启动了多个数据库实例 |
| 缓存端口 | 6379 | 是否 Docker 映射冲突 |
| 临时端口 | 高位端口 | 是否程序错误固定使用 |

## 查看端口占用

使用 `ss`：

```bash
sudo ss -lntup | grep ':8080'
```

使用 `lsof`：

```bash
sudo lsof -i :8080
```

查看进程详情：

```bash
ps -fp PID
```

查看完整命令：

```bash
tr '\0' ' ' < /proc/PID/cmdline
```

查看进程属于哪个服务：

```bash
systemctl status PID
```

有些系统不支持 `systemctl status PID`，可用：

```bash
cat /proc/PID/cgroup
```

## 判断是否旧服务未停止

查看同类进程：

```bash
pgrep -af demo-api
```

查看 systemd 服务：

```bash
systemctl status demo-api --no-pager
systemctl status demo-api-old --no-pager
```

如果旧服务仍在运行：

```bash
sudo systemctl stop demo-api-old
```

再验证端口：

```bash
sudo ss -lntup | grep ':8080'
```

不要直接 `kill -9`。优先使用 systemd 停止服务，让它有机会释放资源、写完日志和执行退出逻辑。

## 判断是否重复启动

重复启动常见于：

- 手动运行了一次 jar，又用 systemd 启动一次。
- 部署脚本中后台启动，systemd 也启动。
- Docker 容器和宿主机服务都使用同一端口。
- 旧进程没有退出，新进程继续启动。

检查：

```bash
pgrep -af "java.*demo-api"
systemctl status demo-api --no-pager
docker ps --format "table {{.Names}}\t{{.Ports}}"
```

处理：

- 长期服务统一交给 systemd 或容器编排管理。
- 部署脚本不要再 `nohup java -jar ... &`。
- 清理重复的启动入口。

## 判断是否端口规划冲突

如果两个不同服务都配置了同一端口，不应靠抢占解决。

建立端口表：

| 服务 | 环境 | 监听地址 | 端口 | 暴露范围 |
| --- | --- | --- | --- | --- |
| nginx | prod | `0.0.0.0` | 80/443 | 公网 |
| demo-api | prod | `127.0.0.1` | 8080 | 本机 |
| admin-api | prod | `127.0.0.1` | 8081 | 本机 |
| mysql | prod | `127.0.0.1` | 3306 | 本机或内网 |

修改应用端口后，要同步：

- 应用配置。
- systemd 环境文件。
- Nginx `proxy_pass`。
- 健康检查脚本。
- 防火墙或安全组。
- 监控配置。

## Nginx 端口占用

检查配置：

```bash
sudo nginx -t
sudo ss -lntup | grep -E ':80|:443'
```

常见原因：

- Apache 已占用 80。
- 另一个 Nginx 实例已运行。
- Docker 容器映射了 80/443。
- 多个配置监听同一端口不是问题，冲突通常来自不同进程抢同一个地址端口。

查看占用：

```bash
sudo lsof -i :80
sudo lsof -i :443
```

## Docker 端口冲突

查看容器端口：

```bash
docker ps --format "table {{.Names}}\t{{.Ports}}"
```

常见冲突：

```yaml
ports:
  - "8080:8080"
```

如果宿主机已有服务监听 8080，容器启动会失败。

更安全的内部服务绑定：

```yaml
ports:
  - "127.0.0.1:8080:8080"
```

如果只给同一 Docker 网络内部访问，优先不暴露 `ports`。

## 何时可以杀进程

可以考虑杀进程的情况：

- 明确是手动启动的重复进程。
- 进程不属于 systemd 管理。
- 已确认不是当前生产流量进程。
- 已保存必要日志和现场信息。

优雅停止：

```bash
kill PID
```

等待后仍不退出：

```bash
kill -TERM PID
```

最后手段：

```bash
kill -9 PID
```

`kill -9` 不给程序清理机会，可能造成临时文件、锁、连接和数据写入异常。生产环境要谨慎。

## 修复流程

1. 用 `ss` 或 `lsof` 找到占用进程。
2. 用 `ps`、`systemctl`、`docker ps` 判断进程来源。
3. 如果是旧服务，使用 systemd 或容器命令停止。
4. 如果是重复启动，清理多余启动方式。
5. 如果是规划冲突，修改端口并同步 Nginx、健康检查和监控。
6. 重启目标服务。
7. 验证端口和业务。

验证：

```bash
sudo systemctl restart demo-api
sudo ss -lntup | grep ':8080'
curl -fsS http://127.0.0.1:8080/health
```

## 预防

- 每个项目维护端口清单。
- 发布前检查目标端口是否空闲。
- 长期服务统一使用 systemd、Docker Compose 或 Kubernetes 管理。
- 不在部署脚本里留下多个启动入口。
- 应用内部端口默认监听 `127.0.0.1`，由 Nginx 对外暴露 80/443。

发布前检查：

```bash
sudo ss -lntup | grep ':8080' && echo "port used" || echo "port free"
```

## 好用工具

| 工具 | 用途 |
| --- | --- |
| `ss` | 查看监听端口和进程 |
| `lsof` | 查看端口打开者 |
| `pgrep -af` | 按命令行查进程 |
| `ps -fp` | 查看进程详情 |
| `systemctl status` | 判断进程是否属于服务 |
| `docker ps` | 查看容器端口映射 |
| `fuser` | 查找并可结束占用端口的进程 |

`fuser` 示例：

```bash
sudo fuser -v 8080/tcp
```

## 练习

1. 启动两个简单 HTTP 服务，让它们监听同一端口，观察报错。
2. 用 `ss`、`lsof`、`pgrep` 分别定位占用进程。
3. 把一个服务端口从 8080 改到 8081，并同步 Nginx 反代配置。
4. 写一张项目端口规划表。
