# 05 Nginx 502 与前端刷新 404

Nginx 502 和前端刷新 404 是部署 Web 项目时的高频问题。502 通常是 Nginx 找不到或连不上后端；前端刷新 404 通常是 SPA 路由没有回退到 `index.html`。

## 作用

- 用 Nginx 日志、后端健康检查和端口检查定位 502。
- 区分 Nginx 配置错误、后端未启动、端口不通和超时。
- 用 `try_files` 修复 Vue/React 等 SPA 刷新 404。
- 建立前后端部署后的验证清单。

## 一、Nginx 502

### 常见现象

- 浏览器显示 `502 Bad Gateway`。
- Nginx access.log 状态码是 502。
- 后端应用日志没有收到请求。
- 发布后首页能打开，但接口全部失败。

### 502 的常见原因

| 原因 | 典型线索 |
| --- | --- |
| 后端服务没启动 | `connect() failed (111: Connection refused)` |
| `proxy_pass` 端口错误 | Nginx 连到错误端口 |
| 后端只监听内网或其他地址 | 本机 curl 不通 |
| 后端处理太慢 | `upstream timed out` |
| 后端提前断开 | `upstream prematurely closed connection` |
| socket 权限问题 | Unix socket permission denied |

## 502 排查顺序

先看 Nginx 配置语法：

```bash
sudo nginx -t
```

看错误日志：

```bash
sudo tail -n 100 /var/log/nginx/error.log
```

看访问日志：

```bash
sudo tail -n 100 /var/log/nginx/access.log
```

看后端端口：

```bash
ss -lntup | grep 8080
```

本机直连后端：

```bash
curl -v http://127.0.0.1:8080/health
```

看后端服务：

```bash
systemctl status demo-api --no-pager
journalctl -u demo-api -n 100 --no-pager
```

## 读懂 error.log

### Connection refused

```text
connect() failed (111: Connection refused) while connecting to upstream
```

含义：Nginx 连接的 IP/端口没有服务监听。

检查：

```bash
ss -lntup | grep 8080
systemctl status demo-api
```

修复：

- 启动后端服务。
- 修正 `proxy_pass` 端口。
- 确认后端监听 `127.0.0.1` 或 Nginx 可访问的地址。

### Upstream timed out

```text
upstream timed out while reading response header from upstream
```

含义：Nginx 连上了后端，但后端响应太慢。

检查：

```bash
journalctl -u demo-api -n 200 --no-pager
top
free -h
curl -w "%{time_total}\n" -o /dev/null -s http://127.0.0.1:8080/health
```

修复优先级：

1. 查后端为什么慢。
2. 查数据库、缓存、外部接口。
3. 必要时临时增加超时。

不要一看到 timeout 就只加 Nginx 超时时间。

### Prematurely closed connection

```text
upstream prematurely closed connection while reading response header
```

含义：后端连接中途断开，可能是应用崩溃、进程重启、OOM 或异常退出。

检查：

```bash
journalctl -u demo-api -n 200 --no-pager
journalctl -k | grep -i "killed process"
```

## 正确的反向代理配置

示例：

```nginx
server {
    listen 80;
    server_name example.com;

    location /api/ {
        proxy_pass http://127.0.0.1:8080/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

注意 `proxy_pass` 尾部斜杠会影响路径拼接：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080/;
}
```

`/api/users` 转发到后端 `/users`。

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
```

`/api/users` 转发到后端 `/api/users`。

## 二、前端刷新 404

### 常见现象

- 首页 `/` 可以打开。
- 点击进入 `/user/list` 可以打开。
- 在 `/user/list` 刷新后 Nginx 返回 404。
- 直接访问二级路由返回 404。

### 根因

Vue Router、React Router 的 history 模式是前端路由。用户刷新 `/user/list` 时，浏览器会向服务器请求 `/user/list`。如果服务器上没有这个真实文件，就会 404。

服务器需要把未知前端路径回退到：

```text
index.html
```

再由前端路由接管。

## SPA Nginx 配置

标准写法：

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/demo-web;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8080/;
    }
}
```

配置后：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

验证：

```bash
curl -I http://example.com/
curl -I http://example.com/user/list
```

都应返回 200 或符合预期的入口页面响应。

## 前端静态资源 404

如果页面打开但 JS/CSS 404，检查：

- `root` 是否指向构建产物目录。
- 构建产物是否包含 `index.html`、`assets/`。
- 前端 `base` 或 `publicPath` 是否正确。
- 项目是否部署在子路径，例如 `/admin/`。

检查文件：

```bash
ls -lah /var/www/demo-web
ls -lah /var/www/demo-web/assets
```

如果部署到 `/admin/`：

```nginx
location /admin/ {
    alias /var/www/admin-web/;
    try_files $uri $uri/ /admin/index.html;
}
```

子路径部署要同时配置前端构建 base。

## 修改 Nginx 的安全流程

1. 备份配置。
2. 修改配置。
3. 执行 `nginx -t`。
4. reload，不直接 restart。
5. 验证首页、接口、二级路由刷新。

命令：

```bash
sudo cp /etc/nginx/conf.d/demo.conf /etc/nginx/conf.d/demo.conf.bak.$(date +%F-%H%M%S)
sudo nginx -t
sudo systemctl reload nginx
```

## 发布后验证清单

- `curl -I http://域名/` 返回正常。
- 二级路由刷新正常。
- 静态资源 JS/CSS 状态码正常。
- `/api/health` 或后端健康接口正常。
- Nginx error.log 没有新增错误。
- 后端服务日志没有异常。

## 练习

1. 把 `proxy_pass` 端口写错，观察 Nginx 502 日志。
2. 停止后端服务，再访问接口，确认 `Connection refused`。
3. 部署一个 history 模式前端，先不配置 `try_files`，复现刷新 404。
4. 加上 `try_files $uri $uri/ /index.html;` 后重新验证。
