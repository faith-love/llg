# 故障处理与复盘模板

## 作用

故障处理不是“把服务恢复就结束”，而是一套从发现、定级、止血、定位、修复、验证到复盘的闭环。好的故障处理能缩短恢复时间，好的复盘能减少同类问题再次发生。复盘不是追责，而是把系统、流程、监控、发布、文档里的薄弱点找出来。

这一节提供可直接复用的故障处理流程和复盘模板。

## 痛点

- 故障发生时没人知道谁负责、先做什么。
- 一边处理一边丢失关键现场，最终无法确认根因。
- 为了快速恢复做了重启，但没有记录重启前状态。
- 复盘只写“已修复”，没有时间线、根因和改进项。
- 同类问题重复出现，因为没有把改进落实到监控、脚本、流程或代码。

## 故障处理流程

### 1. 定级

先判断影响程度：

| 级别 | 影响 | 示例 |
| --- | --- | --- |
| P0 | 核心业务全不可用 | 全站不可访问、支付完全失败 |
| P1 | 核心链路部分不可用 | 部分用户无法下单、API 大量 5xx |
| P2 | 非核心功能异常 | 后台某功能失败、少量接口报错 |
| P3 | 轻微问题 | 日志告警、单个任务失败、体验问题 |

定级要回答：

- 影响多少用户。
- 是否影响核心业务。
- 是否持续扩大。
- 是否有明确止血手段。

### 2. 分工

至少明确：

- 指挥人：控制节奏和决策。
- 操作人：执行命令、回滚、变更。
- 记录人：记录时间线、证据、决策。
- 沟通人：同步业务、客服、管理或用户。

小团队可以一人多岗，但角色要清楚。

### 3. 止血

止血优先于彻底定位。常见动作：

- 回滚代码版本。
- 回滚配置。
- 切换流量。
- 重启异常实例。
- 扩容或摘除异常节点。
- 限流、降级、关闭异常功能。
- 清理磁盘空间。

注意：

- 重启前尽量保存 `systemctl status`、`journalctl`、端口、资源状态。
- 止血动作要尽量小，避免扩大影响。
- 止血成功后继续定位根因。

### 4. 定位

按证据链定位：

```text
用户现象 -> 入口日志 -> 后端日志 -> 系统资源 -> 最近变更 -> 根因假设 -> 验证
```

常用命令：

```bash
systemctl status demo-api --no-pager
journalctl -u demo-api -n 200 --no-pager
sudo ss -lntup | grep ':8080'
curl -i http://127.0.0.1:8080/health
tail -n 100 /var/log/nginx/error.log
df -h
free -h
dmesg -T | tail -n 100
```

### 5. 修复

修复要遵循：

- 优先最小改动。
- 有备份和回滚方式。
- 修改后有明确验证命令。
- 不在故障中做无关优化。

示例：

```bash
sudo nginx -t
sudo systemctl reload nginx
curl -I http://example.com
```

### 6. 验证

验证不能只看服务 active：

```bash
systemctl is-active demo-api
sudo ss -lntup | grep ':8080'
curl -fsS http://127.0.0.1:8080/health
curl -I http://example.com
tail -n 50 /var/log/nginx/error.log
```

还要确认：

- 错误率下降。
- 关键业务路径恢复。
- 日志不再出现新错误。
- 监控告警恢复。
- 用户侧或业务侧确认恢复。

## 复盘写法

### 直接原因和根本原因

示例：

```text
直接原因：Nginx proxy_pass 端口配置为 8081，但后端实际监听 8080，导致请求 502。
根本原因：发布前没有 Nginx 配置自动校验和回归访问链路检查；配置变更没有代码审查。
```

不要只写：

```text
Nginx 配错了。
```

### 时间线

时间线要包含事实，不写猜测。

较好：

```text
10:12 执行 sudo systemctl reload nginx，nginx -t 通过。
10:13 access log 开始出现大量 502。
10:18 回滚 /etc/nginx/conf.d/demo.conf 到上一版本。
```

较差：

```text
上午 Nginx 有点问题，后来好了。
```

### 改进项

改进项要可执行：

```text
增加发布脚本：reload Nginx 前自动 curl /health。
增加告警：5 分钟内 502 比例超过 2% 告警。
增加文档：proxy_pass 斜杠规则加入 Nginx 配置规范。
```

不要写空泛描述：

```text
以后注意。
```

## 常见止血策略

### 1. 回滚版本

```bash
sudo ln -sfn /opt/apps/demo-api/releases/旧版本 /opt/apps/demo-api/current
sudo systemctl restart demo-api
curl -f http://127.0.0.1:8080/health
```

### 2. 回滚 Nginx 配置

```bash
sudo cp /etc/nginx/conf.d/demo.conf.bak /etc/nginx/conf.d/demo.conf
sudo nginx -t
sudo systemctl reload nginx
```

### 3. 摘除异常实例

如果前面有负载均衡：

- 标记实例不可用。
- 等流量下降。
- 再排查单机问题。

### 4. 清理磁盘

先找大目录：

```bash
df -h
sudo du -h --max-depth=1 /var | sort -h
sudo du -h --max-depth=1 /opt/apps | sort -h
```

不要盲删。优先清理可确认的旧日志、旧 release、临时文件。

## 监控和告警改进

故障后要检查是否需要补：

- 服务存活告警。
- HTTP 5xx 比例告警。
- Nginx 502/504 告警。
- 磁盘使用率告警。
- 内存和 OOM 告警。
- 证书到期告警。
- 定时任务失败告警。
- 关键业务指标告警。

常见工具：

- Prometheus + node_exporter：系统指标。
- Grafana：可视化面板。
- Alertmanager：告警路由。
- Loki 或 ELK/OpenSearch：日志聚合。
- Uptime Kuma：简单站点可用性监控。

## 使用技巧

- 故障时优先恢复服务，恢复后再深入根因。
- 操作前后都记录时间和验证结果。
- 截图、日志片段、命令输出要保存。
- 复盘只接受可验证事实，不用模糊描述。
- 每个改进项要有负责人和截止时间。

## 难点

- 故障中容易过早下结论，导致误操作。
- 多个变更叠加时，根因不一定是最近那一个。
- 重启可能恢复服务，但也会抹掉关键现场。
- 没有监控基线时，很难判断“恢复到正常水平”。

## 重点

- 故障处理闭环是：定级、止血、定位、修复、验证、复盘。
- 复盘目标是减少复发，不是追责。
- 时间线、根因、改进项是复盘核心。
- 改进项必须可执行、可验收、有人负责。

## 练习

1. 用一次模拟 502 故障填写完整故障记录模板。
2. 把“重启解决”改写成包含直接原因和根本原因的复盘描述。
3. 为磁盘满故障设计 3 个监控告警和 3 个预防动作。
4. 设计一次服务回滚演练清单。
