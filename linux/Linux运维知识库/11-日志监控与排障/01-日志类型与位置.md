# 日志类型与位置

## 作用

日志是线上排障的第一手证据。一次故障通常不会只体现在一个文件里：服务启动失败可能在 `journalctl`，请求是否到达可能在 Nginx access log，代理失败原因可能在 Nginx error log，业务异常在应用日志，登录和 sudo 行为在安全日志，磁盘、内核、OOM 等系统问题在系统日志。

这一节要解决：

- 常见日志在哪里。
- 每类日志适合回答什么问题。
- 排障时先看哪类日志。
- 如何避免只盯应用日志而漏掉系统和入口层问题。

## 痛点

- 用户反馈访问失败，只会重启服务，不知道先看哪份日志。
- 应用日志没有报错，但 Nginx error log 已经提示后端连接失败。
- 服务启动失败，应用日志还没生成，真正错误在 `journalctl`。
- 磁盘满导致服务异常，却一直排查业务代码。
- SSH 暴力破解、sudo 操作、安全异常没有被关注。

## 日志分类

| 日志类型 | 常见位置或命令 | 主要用途 |
| --- | --- | --- |
| 应用日志 | `/opt/apps/*/shared/logs/` | 业务异常、接口错误、堆栈、请求 ID |
| systemd 日志 | `journalctl -u 服务名` | 启动失败、退出码、标准输出、服务重启 |
| Nginx access log | `/var/log/nginx/access.log` | 请求是否到达、状态码、耗时、来源 |
| Nginx error log | `/var/log/nginx/error.log` | 代理失败、权限错误、静态文件错误 |
| 系统日志 | `/var/log/syslog`、`/var/log/messages` | 系统服务、内核、硬件、网络 |
| 安全日志 | `/var/log/auth.log`、`/var/log/secure` | 登录、sudo、SSH、认证失败 |
| 内核日志 | `dmesg`、`journalctl -k` | OOM、磁盘、驱动、内核错误 |
| 定时任务日志 | `/var/log/cron`、`journalctl -u cron` | cron 执行情况 |

## 应用日志

推荐部署目录：

```text
/opt/apps/demo-api/shared/logs/
  app.log
  error.log
  access.log
```

常用查看：

```bash
tail -f /opt/apps/demo-api/shared/logs/app.log
tail -n 200 /opt/apps/demo-api/shared/logs/app.log
grep -n "ERROR" /opt/apps/demo-api/shared/logs/app.log
grep -C 5 "Exception" /opt/apps/demo-api/shared/logs/app.log
```

应用日志适合回答：

- 某个接口为什么失败。
- 数据库、Redis、外部接口是否报错。
- 某个用户、订单、请求 ID 的完整上下文。
- 业务异常是参数问题、依赖问题还是代码异常。

建议日志中包含：

- 时间。
- 日志级别。
- 服务名。
- traceId/requestId。
- 用户或业务关键字段。
- 错误堆栈。

## systemd 日志

服务由 systemd 托管时，启动和退出信息通常在 journal 中：

```bash
journalctl -u demo-api -n 100 --no-pager
journalctl -u demo-api -f
journalctl -u demo-api --since "1 hour ago" --no-pager
```

systemd 日志适合回答：

- 服务为什么启动失败。
- `ExecStart` 是否找不到命令。
- 服务退出码是多少。
- 是否被 systemd 自动重启。
- 标准输出和标准错误是否有异常。

如果服务启动后很快退出，优先看：

```bash
systemctl status demo-api --no-pager
journalctl -u demo-api -n 200 --no-pager
```

## Nginx access log

常见位置：

```bash
/var/log/nginx/access.log
```

查看：

```bash
tail -f /var/log/nginx/access.log
grep ' 502 ' /var/log/nginx/access.log
grep 'GET /api/health' /var/log/nginx/access.log
```

access log 适合回答：

- 请求是否到达 Nginx。
- 返回状态码是多少。
- 请求路径是什么。
- 客户端 IP 是什么。
- 是否有大量 404、502、499、504。

如果 access log 没有对应请求，说明请求可能没到这台 Nginx，要查 DNS、CDN、负载均衡、安全组或客户端。

## Nginx error log

常见位置：

```bash
/var/log/nginx/error.log
```

查看：

```bash
tail -n 100 /var/log/nginx/error.log
tail -f /var/log/nginx/error.log
```

error log 适合回答：

- Nginx 是否连接不到后端。
- 静态文件是否不存在。
- 目录或文件权限是否不足。
- 上传文件是否超过限制。
- upstream 是否超时。

常见错误片段：

| 错误 | 方向 |
| --- | --- |
| `connect() failed (111: Connection refused)` | 后端端口没监听 |
| `upstream timed out` | 后端响应超时 |
| `permission denied` | 文件或目录权限 |
| `No such file or directory` | 静态文件路径错误 |
| `client intended to send too large body` | 上传大小限制 |

## 系统日志

Ubuntu/Debian：

```bash
/var/log/syslog
```

RHEL/Rocky/Alma/CentOS：

```bash
/var/log/messages
```

查看：

```bash
sudo tail -n 200 /var/log/syslog
sudo tail -n 200 /var/log/messages
journalctl -p warning --since "1 hour ago" --no-pager
```

系统日志适合回答：

- 系统服务是否异常。
- 网络、磁盘、内核是否报错。
- 是否出现 OOM、磁盘错误、文件系统错误。
- cron、rsyslog、systemd-journald 是否异常。

## 安全日志

Ubuntu/Debian：

```bash
/var/log/auth.log
```

RHEL 系：

```bash
/var/log/secure
```

查看 SSH 登录：

```bash
sudo grep 'sshd' /var/log/auth.log | tail
sudo grep 'sshd' /var/log/secure | tail
```

查看 sudo：

```bash
sudo grep 'sudo' /var/log/auth.log | tail
sudo grep 'sudo' /var/log/secure | tail
```

安全日志适合回答：

- 谁登录过服务器。
- 是否有 SSH 暴力破解。
- 谁执行过 sudo。
- 是否出现认证失败。

## 内核和 OOM 日志

查看内核日志：

```bash
dmesg -T | tail -n 100
journalctl -k -n 100 --no-pager
```

查 OOM：

```bash
dmesg -T | grep -i 'killed process\\|out of memory'
journalctl -k --since "1 hour ago" | grep -i 'killed process\\|out of memory'
```

如果应用突然消失，日志里没有正常退出信息，要怀疑：

- OOM killer 杀进程。
- 宿主机重启。
- 容器限制触发。
- 磁盘或文件系统异常。

## 好用工具

- `lnav`：交互式查看多份日志，支持高亮和时间排序。
- `multitail`：同时 tail 多个日志文件。
- `goaccess`：分析 Nginx access log。
- `journalctl`：查看 systemd 和系统日志。
- `grep`、`awk`、`sed`：日志过滤和统计。
- `jq`：解析 JSON 格式日志。

安装示例：

```bash
sudo apt install lnav multitail goaccess jq
sudo dnf install lnav multitail goaccess jq
```

## 使用技巧

- 先按故障时间范围缩小日志，不要从头翻。
- 请求类问题同时看 Nginx access log、error log 和应用日志。
- 启动类问题优先看 `systemctl status` 和 `journalctl`。
- 资源类问题结合 `df`、`free`、`top`、`dmesg`。
- 安全类问题看 auth/secure，并结合 SSH 配置和防火墙。

## 难点

- 不同发行版日志路径不同。
- 应用日志时间、系统时间、用户反馈时间可能存在时区差异。
- 重启服务可能清掉部分现场状态，重启前尽量先保存日志和状态。
- 日志量大时，要靠时间、traceId、状态码、服务名过滤。

## 重点

- 不同日志回答不同问题，不能只看应用日志。
- 启动失败看 journal，访问失败看 Nginx 和应用日志，系统异常看 syslog/messages/dmesg。
- 日志排查要结合时间线、请求链路和最近变更。
- 重要服务要规划日志路径、轮转和检索方式。

## 练习

1. 找出当前系统的应用日志、Nginx 日志、系统日志和安全日志位置。
2. 用 `journalctl -u` 查看一个服务最近 100 行日志。
3. 用 `grep` 从 Nginx access log 中统计 404 或 502。
4. 安装 `lnav`，同时查看 Nginx access log 和 error log。
