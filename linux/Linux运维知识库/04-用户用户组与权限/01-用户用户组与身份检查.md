# 用户用户组与身份检查

## 作用

用户、用户组与身份检查用于回答“我是谁、我属于哪些组、目标用户是否存在、服务到底以哪个用户运行”的问题。权限排查不能一上来就 `chmod 777`，第一步应该先确认身份和归属。

在 Linux 中，权限判断离不开用户和用户组。文件有属主和属组，进程也有运行用户。应用能不能读配置、写日志、进入目录，最终都要回到“哪个用户在访问哪个路径”。

## 痛点

- 当前登录用户和服务运行用户不是同一个，却只检查当前用户权限。
- 上传文件属于 root，应用用户无法读取。
- 不知道某个用户是否存在。
- 不知道某个用户属于哪些组。
- systemd unit 里 `User=` 配置错误，导致服务启动失败。

## 优点

- 能明确权限问题的主体是谁。
- 能区分登录用户、部署用户、服务用户。
- 能快速判断账号和用户组是否存在。
- 能避免盲目扩大权限。

## 常见用户类型

| 类型 | 示例 | 用途 |
| --- | --- | --- |
| root 用户 | `root` | 系统最高权限，谨慎使用 |
| 登录用户 | `deploy`、`admin` | SSH 登录、执行部署 |
| 服务用户 | `app`、`nginx`、`mysql` | 运行服务进程 |
| 系统用户 | `www-data`、`redis` | 软件安装时创建 |

推荐：

- 日常 SSH 登录用普通用户。
- 部署用 `deploy` 或个人账号。
- 业务应用用独立服务用户，例如 `app`。
- 不用 root 长期跑业务服务。

## 当前身份检查

查看当前用户：

```bash
whoami
```

查看用户 ID 和组：

```bash
id
```

查看所属组：

```bash
groups
```

示例输出：

```text
uid=1001(deploy) gid=1001(deploy) groups=1001(deploy),27(sudo)
```

含义：

- `uid`：用户 ID。
- `gid`：主组 ID。
- `groups`：附加组。
- 如果在 `sudo` 组里，通常可以使用 sudo。

## 查看指定用户

查看用户是否存在：

```bash
getent passwd app
```

查看组是否存在：

```bash
getent group app
```

为什么用 `getent`：

- 它会走系统名称服务，不只看 `/etc/passwd`。
- 在接入 LDAP、NIS 等场景时更通用。

## 创建服务用户

创建不能登录的系统用户：

```bash
sudo useradd -r -s /usr/sbin/nologin app
```

说明：

- `-r`：系统用户。
- `-s /usr/sbin/nologin`：禁止交互登录。
- `app`：用户名称。

确认：

```bash
getent passwd app
id app
```

注意：不同发行版 `nologin` 路径可能是：

```text
/usr/sbin/nologin
/sbin/nologin
```

可用下面命令确认：

```bash
command -v nologin
```

## 服务运行用户

systemd unit 中常见：

```ini
[Service]
User=app
Group=app
```

查看服务配置：

```bash
systemctl cat demo-api
```

查看进程真实用户：

```bash
ps -eo user,pid,cmd | grep demo-api
```

判断：

- unit 里写 `User=app`，进程应该由 `app` 运行。
- 如果进程是 root，要确认是否符合预期。
- 如果没有 `User=`，服务可能以 root 运行。

## 常见排查场景

### 应用无法读取 jar

```bash
id app
ls -lah /opt/apps/demo-api/current/app.jar
namei -l /opt/apps/demo-api/current/app.jar
```

判断：

- 文件属主是否是 `app`。
- 父目录是否允许 `app` 进入。
- current 软链接目标是否可访问。

### 应用无法写日志

```bash
id app
ls -ld /opt/apps/demo-api/shared/logs
sudo -u app touch /opt/apps/demo-api/shared/logs/test-write
```

如果 `sudo -u app touch` 失败，说明服务用户没有写权限。

### 部署用户无法 sudo

```bash
whoami
groups
sudo -l
```

判断：

- 是否在 sudo 组。
- sudoers 是否允许执行目标命令。

## 使用技巧

- 排权限问题先确认“哪个用户在操作”。
- 对服务问题，检查 systemd 的 `User=`，不是只看当前登录用户。
- 用 `sudo -u app 命令` 模拟服务用户访问。
- 用户不存在时不要直接改权限，先创建合适服务用户。

## 难点

- 当前登录用户和服务运行用户经常不同。
- 文件属主正确不代表目录链路可访问。
- root 能访问不代表服务用户能访问。
- systemd 没写 `User=` 时，服务可能以 root 运行。

## 重点

- `whoami` 看当前用户。
- `id` 看 UID、GID 和附加组。
- `getent passwd 用户` 看用户是否存在。
- `systemctl cat 服务` 看服务运行用户。
- `sudo -u app 命令` 可模拟服务用户执行。

## 练习

1. 创建一个 `app` 系统用户，并用 `id app` 验证。
2. 创建一个目录，只允许 `app` 访问，用普通用户尝试访问。
3. 写一个简单 systemd 服务，分别配置和不配置 `User=app`，观察进程用户。
4. 用 `sudo -u app touch 文件` 验证服务用户写权限。
