# 服务检查、日志清理与备份脚本

## 作用

服务检查、日志清理和备份是运维自动化中最常见的三类脚本。它们看起来简单，但都涉及风险：健康检查如果只会重启会掩盖根因；日志清理如果范围不严会误删；备份如果不验证恢复，故障时可能不可用。

这一节提供三类脚本的关键设计思路和可复用模板：

- 服务健康检查脚本。
- 日志清理脚本。
- 备份脚本。
- 恢复验证和保留策略。

## 痛点

- 健康检查失败就无限重启，服务反复抖动。
- 日志清理命令写得太宽，误删重要文件。
- 备份脚本每天都显示成功，但从未恢复验证。
- 备份文件没有校验值，传输损坏也不知道。
- 自动化脚本没有日志，失败后无法追踪。

## 服务检查脚本

### 1. 检查目标

健康检查至少包含：

- systemd 服务状态。
- 端口监听。
- HTTP 健康接口。
- 最近错误日志。

简单模板：

```bash
#!/usr/bin/env bash
set -euo pipefail

SERVICE="demo-api"
PORT="8080"
URL="http://127.0.0.1:${PORT}/health"
LOG_FILE="/var/log/check-${SERVICE}.log"

log() {
  echo "[$(date '+%F %T')] $*" | tee -a "$LOG_FILE"
}

fail() {
  log "FAIL: $*"
  exit 1
}

systemctl is-active --quiet "$SERVICE" || fail "service inactive: $SERVICE"
ss -lnt "( sport = :${PORT} )" | grep -q ":${PORT}" || fail "port not listening: $PORT"
curl -fsS --connect-timeout 3 --max-time 10 "$URL" >/dev/null || fail "health check failed: $URL"

log "OK: $SERVICE healthy"
```

### 2. 是否自动重启

可以自动重启，但要谨慎：

```bash
if ! curl -fsS --connect-timeout 3 --max-time 10 "$URL" >/dev/null; then
  log "health failed, restart $SERVICE"
  systemctl restart "$SERVICE"
  sleep 5
  curl -fsS --connect-timeout 3 --max-time 10 "$URL" >/dev/null || fail "restart did not recover"
fi
```

注意：

- 自动重启是止血，不是根因修复。
- 频繁重启必须告警。
- 重启前最好记录 `systemctl status` 和最近日志。
- 对数据库、消息队列等有状态服务，不要轻易自动重启。

### 3. cron 配置

```text
*/5 * * * * flock -n /var/lock/check-demo-api.lock /opt/scripts/check-demo-api.sh >> /var/log/check-demo-api.cron.log 2>&1
```

## 日志清理脚本

更推荐使用 logrotate。只有特殊场景才写清理脚本。

### 1. 先预览

```bash
find /opt/apps/demo-api/shared/logs -type f -name "*.log.*" -mtime +14 -print
```

确认无误后再删除：

```bash
find /opt/apps/demo-api/shared/logs -type f -name "*.log.*" -mtime +14 -delete
```

禁止写法：

```bash
find / -name "*.log" -delete
rm -rf "$LOG_DIR"/*
```

### 2. 安全模板

```bash
#!/usr/bin/env bash
set -euo pipefail

LOG_DIR="/opt/apps/demo-api/shared/logs"
RETENTION_DAYS="14"
RUN_DELETE="${1:-dry-run}"

log() {
  echo "[$(date '+%F %T')] $*"
}

[[ -d "$LOG_DIR" ]] || { log "log dir not found: $LOG_DIR"; exit 1; }
[[ "$LOG_DIR" == /opt/apps/demo-api/shared/logs ]] || { log "unsafe LOG_DIR: $LOG_DIR"; exit 1; }

log "scan files older than ${RETENTION_DAYS} days"

if [[ "$RUN_DELETE" == "delete" ]]; then
  find "$LOG_DIR" -type f -name "*.log.*" -mtime +"$RETENTION_DAYS" -print -delete
else
  find "$LOG_DIR" -type f -name "*.log.*" -mtime +"$RETENTION_DAYS" -print
fi
```

执行：

```bash
/opt/scripts/clean-demo-log.sh
/opt/scripts/clean-demo-log.sh delete
```

设计要点：

- 默认 dry-run。
- 限定目录。
- 限定文件名模式。
- 删除前打印文件。
- 不清理当前正在写的 `app.log`。

### 3. 删除后空间不释放

如果删除日志后 `df -h` 不变：

```bash
sudo lsof +L1
```

说明文件可能仍被进程打开，需要 reload 或 restart 对应服务。

## 备份脚本

### 1. 备份要素

备份脚本至少包含：

- 备份对象。
- 备份路径。
- 时间戳。
- 临时文件。
- 校验值。
- 保留周期。
- 成功和失败日志。
- 恢复验证方法。

只会备份不会恢复，不能算完整备份方案。

### 2. 文件目录备份模板

```bash
#!/usr/bin/env bash
set -euo pipefail

SRC_DIR="/opt/apps/demo-api/shared/uploads"
BACKUP_DIR="/backup/demo-api/uploads"
RETENTION_DAYS="14"
TS="$(date '+%F-%H%M%S')"
TMP_FILE="${BACKUP_DIR}/uploads-${TS}.tar.gz.tmp"
FINAL_FILE="${BACKUP_DIR}/uploads-${TS}.tar.gz"
LOG_FILE="/var/log/backup-demo-api.log"

log() {
  echo "[$(date '+%F %T')] $*" | tee -a "$LOG_FILE"
}

die() {
  log "ERROR: $*"
  exit 1
}

[[ -d "$SRC_DIR" ]] || die "source dir not found: $SRC_DIR"
mkdir -p "$BACKUP_DIR"

log "backup start: $SRC_DIR"
tar -czf "$TMP_FILE" -C "$(dirname "$SRC_DIR")" "$(basename "$SRC_DIR")"
sha256sum "$TMP_FILE" > "${TMP_FILE}.sha256"
mv "$TMP_FILE" "$FINAL_FILE"
mv "${TMP_FILE}.sha256" "${FINAL_FILE}.sha256"

log "backup created: $FINAL_FILE"

find "$BACKUP_DIR" -type f -name "uploads-*.tar.gz" -mtime +"$RETENTION_DAYS" -print -delete
find "$BACKUP_DIR" -type f -name "uploads-*.tar.gz.sha256" -mtime +"$RETENTION_DAYS" -print -delete

log "backup done"
```

### 3. 数据库备份提示

MySQL 示例：

```bash
mysqldump --single-transaction --routines --triggers -h 127.0.0.1 -u backup_user -p database_name > backup.sql
```

PostgreSQL 示例：

```bash
pg_dump -h 127.0.0.1 -U backup_user -F c -f backup.dump database_name
```

注意：

- 密码不要直接明文写在脚本里。
- 使用专用低权限备份账号。
- 大库备份要评估锁、IO、耗时和恢复时间。
- 云数据库优先使用云平台快照和备份能力，同时保留恢复演练。

## 恢复验证

备份完成后要定期验证。

文件备份验证：

```bash
sha256sum -c uploads-2026-05-11-020000.tar.gz.sha256
tar -tzf uploads-2026-05-11-020000.tar.gz | head
```

恢复演练：

```bash
mkdir -p /tmp/restore-test
tar -xzf uploads-2026-05-11-020000.tar.gz -C /tmp/restore-test
find /tmp/restore-test -maxdepth 2 -type f | head
```

数据库恢复演练要在测试库进行，不要直接覆盖生产。

## 保留策略

示例：

```text
小时备份：保留 24 份
每日备份：保留 14 天
每周备份：保留 8 周
每月备份：保留 12 个月
```

具体取决于：

- 数据重要性。
- 磁盘成本。
- 合规要求。
- 恢复时间目标 RTO。
- 恢复点目标 RPO。

## 告警

关键任务失败要告警。简单方式：

- 发送邮件。
- 企业微信/飞书/钉钉 webhook。
- 写入监控系统。
- systemd timer 结合 `OnFailure=`。

脚本至少要有非 0 退出码，这样上层调度系统才能识别失败。

## 好用工具

- `rsync`：增量同步。
- `tar`：目录打包。
- `sha256sum`：校验备份完整性。
- `rclone`：同步到对象存储或云盘。
- `restic`：加密、去重、快照式备份工具。
- `borgbackup`：去重压缩备份工具。
- `logrotate`：日志轮转，替代大多数日志清理脚本。

## 使用技巧

- 健康检查脚本不要只看进程，要看端口和接口。
- 日志清理默认 dry-run，确认后再 delete。
- 备份先写临时文件，完成后再改最终文件名。
- 备份要有校验值和恢复演练。
- 定时任务用 `flock` 防重复执行。

## 难点

- 自动重启可能掩盖根因，必须配合告警和日志。
- 删除脚本风险很高，范围必须严格限制。
- 备份成功不等于可恢复。
- 大文件备份会占用 IO 和网络，可能影响业务。
- 密钥和数据库密码不能随便明文写在脚本中。

## 重点

- 自动化脚本要可观测、可失败、可追踪。
- 日志清理优先 logrotate，脚本清理必须限定范围。
- 备份必须包含恢复验证。
- 健康检查、清理、备份都要有日志、锁和保留策略。

## 练习

1. 写一个服务健康检查脚本，检查 systemd、端口和 HTTP 接口。
2. 写一个默认 dry-run 的日志清理脚本，再用参数开启删除。
3. 写一个目录备份脚本，生成 tar.gz 和 sha256 校验文件。
4. 从备份文件恢复到 `/tmp/restore-test`，验证文件完整性。
