# 04 密钥配置与日志脱敏

密钥、Token、数据库密码、证书私钥和生产配置一旦泄露，攻击者可能绕过系统登录，直接访问数据库、云资源、第三方接口或用户数据。配置安全的重点是“不该出现的地方永远不要出现”，日志脱敏的重点是“排障需要信息，但不需要完整秘密”。

## 作用

- 防止敏感配置进入 Git、日志、截图和共享文档。
- 限制生产配置文件的读取范围。
- 建立密钥轮换和泄露应急流程。
- 避免备份文件成为新的泄露源。
- 让开发、测试、生产环境配置边界清晰。

## 痛点

- `.env` 文件为了方便被提交到仓库。
- 应用启动时把完整配置打印到日志。
- 报错堆栈里带出数据库连接串、Authorization Header、Cookie。
- 证书私钥权限过宽，普通用户也能读取。
- Git 历史里出现过密钥，但只删除当前文件，没有轮换密钥。

## 常见敏感信息

| 类型 | 示例 | 风险 |
| --- | --- | --- |
| 数据库密码 | `DB_PASSWORD` | 数据库被直连 |
| API Token | `GITHUB_TOKEN`、短信接口密钥 | 第三方资源被滥用 |
| 私钥 | `id_rsa`、`*.key` | 服务器或证书被冒用 |
| JWT Secret | `JWT_SECRET` | 伪造登录态 |
| Cookie | `Set-Cookie`、`sessionid` | 账号会话被盗用 |
| Authorization | `Bearer xxx` | 接口被冒用 |
| 云访问密钥 | `AccessKeyId`、`SecretAccessKey` | 云资源被接管 |
| 个人信息 | 手机号、身份证、邮箱 | 合规和隐私风险 |

## 配置文件存放原则

推荐：

```text
代码仓库：只放配置模板
服务器：放真实生产配置
密钥系统：集中管理高价值密钥
CI/CD：通过安全变量注入
```

仓库中可以放：

```text
.env.example
application.example.yml
config.template.json
```

仓库中不应放：

```text
.env
application-prod.yml
id_rsa
*.pem
*.key
数据库备份
生产证书包
```

`.gitignore` 示例：

```gitignore
.env
.env.*
!.env.example
*.key
*.pem
*.p12
*.jks
application-prod.yml
backup/
```

注意：`.gitignore` 只能阻止未来新增文件，不能删除已经进入 Git 历史的秘密。

## 文件权限建议

私钥：

```bash
chmod 600 ~/.ssh/id_ed25519
```

生产环境变量：

```bash
sudo chown root:app /opt/apps/demo-api/shared/config/demo-api.env
sudo chmod 640 /opt/apps/demo-api/shared/config/demo-api.env
```

证书私钥：

```bash
sudo chown root:root /etc/ssl/private/example.com.key
sudo chmod 600 /etc/ssl/private/example.com.key
```

检查：

```bash
ls -l /opt/apps/demo-api/shared/config/demo-api.env
stat /opt/apps/demo-api/shared/config/demo-api.env
```

原则：

- 服务用户只读它必须读取的配置。
- 普通用户不应读取生产配置。
- 私钥通常只允许属主读写。
- 配置备份与原配置同等敏感。

## 环境变量安全

环境变量比写死在代码里好，但不是绝对安全。很多情况下，环境变量可能被进程列表、调试信息、崩溃报告或管理面板间接暴露。

systemd 使用环境文件：

```ini
[Service]
EnvironmentFile=/opt/apps/demo-api/shared/config/demo-api.env
ExecStart=/usr/bin/java -jar /opt/apps/demo-api/current/demo-api.jar
```

环境文件示例：

```bash
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=demo
DB_PASSWORD=change_me
JWT_SECRET=change_me
```

注意：

- 不要在 `ExecStart=` 中直接写密码。
- 不要把完整环境变量输出到日志。
- CI/CD 平台里使用 masked/protected variables。
- 本地开发使用 `.env.example` 说明字段，不保存真实生产值。

## 日志脱敏

日志应该帮助排障，但不能暴露完整秘密。

必须脱敏字段：

```text
password
passwd
pwd
token
access_token
refresh_token
authorization
cookie
set-cookie
secret
private_key
id_card
phone
email
银行卡号
身份证号
```

脱敏方式：

| 数据 | 建议输出 |
| --- | --- |
| 密码 | `******` |
| Token | 前 4 后 4，中间隐藏 |
| 手机号 | `138****5678` |
| 身份证 | `110101********1234` |
| 邮箱 | `d***@example.com` |
| Cookie | 只输出是否存在，不输出值 |

示例：

```text
Authorization: Bearer abcd****wxyz
phone=138****5678
password=******
```

不要记录：

- 完整请求头。
- 完整 Cookie。
- 完整数据库连接串。
- 完整 `.env` 内容。
- 用户上传的敏感文件正文。

## 应用日志常见风险点

排查以下位置：

- 请求日志中是否打印 Header。
- 异常日志是否带完整请求参数。
- ORM 或数据库日志是否打印连接串。
- 启动日志是否打印全部配置项。
- 调试模式是否在生产开启。
- 网关或 Nginx 是否记录敏感 Query String。

Nginx 避免记录完整敏感参数的一种思路是减少 query 依赖，或自定义 log_format 时不要记录 `$request`，改成更受控的字段。

## Git 泄露处理流程

如果密钥已经提交到 Git：

1. 立即判断密钥影响范围。
2. 立刻轮换密钥、密码或证书。
3. 下线旧密钥。
4. 检查访问日志，确认是否被使用。
5. 清理仓库当前文件。
6. 必要时清理 Git 历史。
7. 增加扫描和提交前检查。

重点：清理 Git 历史不是替代轮换。只要密钥进入过远程仓库、CI 日志、代码评审系统或他人本地仓库，就应视为泄露。

## 密钥扫描工具

### gitleaks

扫描仓库：

```bash
gitleaks detect --source . --verbose
```

作为提交前检查或 CI 步骤使用。

### trufflehog

扫描 Git 历史：

```bash
trufflehog git file://. --only-verified
```

适合发现历史提交中的密钥。

### git-secrets

安装后添加规则：

```bash
git secrets --install
git secrets --register-aws
git secrets --scan
```

适合阻止常见云密钥进入提交。

## 加密配置工具

### sops

`sops` 可加密 YAML、JSON、ENV 等配置，并结合 KMS、GPG 或 age 使用。

常见方式：

```bash
sops -e prod.env > prod.enc.env
sops -d prod.enc.env
```

### age

`age` 是轻量加密工具，适合加密备份或配置片段。

```bash
age-keygen -o key.txt
age -r age1... secrets.env > secrets.env.age
age -d -i key.txt secrets.env.age > secrets.env
```

注意：加密后的文件可以进入仓库，但解密密钥不能进入仓库。

## 备份和共享也要脱敏

敏感文件不仅存在于线上配置，也可能出现在：

- 数据库备份。
- 日志压缩包。
- 故障排查截图。
- 工单附件。
- 即时通讯消息。
- 导出的配置包。
- 本地临时目录。

共享前检查：

```bash
grep -RniE "password|token|authorization|secret|private_key" ./logs
```

压缩包也要按敏感文件处理：

```bash
chmod 600 backup.tar.gz
```

必要时加密：

```bash
age -r age1... backup.tar.gz > backup.tar.gz.age
```

## 常见排障

### 应用读取不到环境变量

检查：

```bash
systemctl cat demo-api
sudo systemctl show demo-api -p EnvironmentFiles
journalctl -u demo-api -n 100 --no-pager
```

常见原因：

- `EnvironmentFile` 路径写错。
- 文件权限导致服务用户无法读取。
- systemd 修改后没有 `daemon-reload`。
- 环境文件中有不符合 systemd 格式的内容。

### 修改配置后没有生效

处理：

```bash
sudo systemctl daemon-reload
sudo systemctl restart demo-api
systemctl status demo-api
```

如果应用内部有配置缓存，还要按应用框架要求刷新。

### 日志中出现完整 Token

处理：

1. 立即停止继续打印。
2. 轮换已经泄露的 Token。
3. 限制日志文件访问权限。
4. 清理或加密历史日志。
5. 增加脱敏测试或日志过滤器。

## 好用工具

| 工具 | 用途 | 使用建议 |
| --- | --- | --- |
| `gitleaks` | 扫描 Git 密钥泄露 | CI 和本地都可用 |
| `trufflehog` | 深度扫描历史密钥 | 处理历史仓库时使用 |
| `git-secrets` | 提交前拦截常见密钥 | 特别适合云密钥 |
| `sops` | 加密结构化配置 | 团队配置管理 |
| `age` | 文件加密 | 备份和密钥文件加密 |
| `chmod`/`chown` | 控制配置权限 | 生产配置必须设置 |
| `grep`/`ripgrep` | 搜索敏感字段 | 排查日志和仓库 |

## 重点

- 密钥不进 Git、不进日志、不进截图。
- `.env.example` 可以提交，真实 `.env` 不提交。
- 文件权限至少做到服务可读、其他无权。
- Git 泄露后必须轮换密钥。
- 日志脱敏要在应用、网关和排障流程中同时落实。

## 练习

1. 为一个项目创建 `.env.example` 和真实 `.env`，并配置 `.gitignore`。
2. 将真实 `.env` 权限设置为 `640`，属组设置为服务用户组。
3. 用 `gitleaks` 扫描当前仓库。
4. 检查最近一份应用日志，找出可能需要脱敏的字段。
5. 用 `age` 加密一个配置备份文件。
