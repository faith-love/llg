# 镜像分层缓存与构建上下文

Docker 构建慢、镜像大、缓存总失效，通常不是 Docker 本身慢，而是 Dockerfile 顺序和构建上下文没有控制好。

## 构建上下文是什么

执行：

```bash
docker build -t app:1.0.0 .
```

最后的 `.` 表示当前目录会作为构建上下文发送给 Docker daemon。Dockerfile 中的 `COPY`、`ADD` 只能访问构建上下文内的文件。

如果目录里有 `.git`、`node_modules`、`target`、日志和测试数据，构建上下文会变大，构建也会变慢。

## .dockerignore 示例

```text
.git
.idea
node_modules
target
dist
logs
*.log
.env
```

原则：

- 不发送源码历史。
- 不发送本地构建缓存。
- 不发送密钥和环境变量文件。
- 不发送运行日志。

## 缓存失效规则

Docker 会从上到下执行 Dockerfile。某一层缓存失效后，后续层通常都要重新执行。

错误顺序：

```dockerfile
COPY . .
RUN npm ci
RUN npm run build
```

只要任意源码变化，`npm ci` 就会重新执行。

更好的顺序：

```dockerfile
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
```

依赖描述文件不变时，安装依赖可以复用缓存。

## 查看镜像层

```bash
docker history 镜像名
```

重点看：

- 哪一层体积最大。
- 是否把无关目录复制进镜像。
- 是否有敏感信息出现在构建命令里。

## 优化清单

- 用 `.dockerignore` 控制上下文。
- 把变化少的依赖安装步骤放前面。
- 把变化多的源码复制放后面。
- 使用多阶段构建。
- 构建后清理包管理器缓存。
- 不在同一层先复制大文件再删除。
