# 镜像容器仓库关系

Docker 的核心对象可以用一句话理解：仓库保存镜像，镜像创建容器，容器运行应用。

## 基本关系

```text
Dockerfile -> build -> Image -> run -> Container
                         |
                         tag / push / pull
                         |
                       Registry
```

## Image 和 Container

| 对象 | 是否可运行 | 是否可变 | 典型动作 |
| --- | --- | --- | --- |
| Image | 不能直接运行，必须创建容器 | 只读 | `pull`、`build`、`tag`、`push` |
| Container | 可以运行 | 有可写层 | `run`、`start`、`stop`、`exec`、`logs` |

一个镜像可以创建多个容器。删除容器不会删除镜像，删除镜像也需要先确认没有容器依赖它。

## Tag 和 Digest

标签示例：

```text
nginx:stable
redis:7
mysql:8
registry.example.com/demo/app:1.4.2
```

标签是可读名称，但标签可能被重新指向。Digest 是镜像内容的哈希，更适合精确锁定镜像内容。

生产建议：

- 部署配置里使用明确版本标签。
- 关键生产系统可以记录 digest，方便追溯。
- 不把 `latest` 当成唯一生产版本。

## Registry、Repository、Image 的区别

| 名称 | 示例 | 说明 |
| --- | --- | --- |
| Registry | `registry.example.com` | 镜像仓库服务地址 |
| Repository | `demo/app` | 某一类镜像的仓库路径 |
| Tag | `1.4.2` | 具体版本标签 |
| Full image name | `registry.example.com/demo/app:1.4.2` | 完整镜像名 |

## 常见误区

- 把容器当镜像备份。容器只是运行实例，不是标准交付物。
- 只记容器名不记镜像标签。排障和回滚时必须知道容器来自哪个镜像。
- 本地构建后没打仓库标签，导致无法推送。
- 生产直接拉 `latest`，重建后不知道实际运行内容是否变化。
